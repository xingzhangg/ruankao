# 21 · 软件工程：结构化开发方法与数据流图 DFD

## 定位

需求问清楚之后，怎么画成一张谁看都是同一个意思的图，再从这张图走到模块结构。全程用"公司内部报销系统"：员工提单、主管审批、超 5000 元走二级、审完打款到银行。写成一段话交给开发会在四处不够用，第二～五节各补一处：①用什么符号画（DFD）、②图太大怎么拆（分层与平衡）、③图上的名字什么意思（数据字典与小说明）、④怎么从数据流走到模块调用（结构化设计）。第一节先交代结构化方法与 SA 产物，第六节 WebApp 不在这条链上。全课无计算。

---

## 一、结构化方法与 SA 的产物

**原话｜** 结构化分析与设计方法是一种**面向数据流**的传统软件开发方法，它以数据流为中心构建软件的分析模型和设计模型。——不问"有哪些对象"，只问"数据从哪来、被谁加工、到哪去"。

| 组成 | 管什么 |
|---|---|
| **结构化分析 SA**（Structured Analysis） | 把业务画清楚 |
| **结构化设计 SD** | 把它切成模块 |
| **结构化程序设计 SPD** | 模块内部只用顺序、选择、循环三种结构写代码 |

**原话｜** SA 的分析结果由四部分组成：**一套分层的数据流图、一本数据词典、一组小说明（也称加工逻辑说明）、补充材料**。分层 DFD 补①②，数据词典和小说明补③，补充材料是零碎附件；④归 SD。"数据词典"与"数据字典"是同一样东西的两种写法。

**易混对 SA 产物 vs SD 产物**
- 判据｜画"数据怎么流"、说明数据和加工的是分析产物；画"模块谁调谁"的是设计产物。
- 例子｜分层 DFD、数据字典、小说明属于 SA；**结构图**（第五节）是设计阶段的产物，不在 SA 结果里。

## 二、数据流图 DFD：四种符号 + 三种画错

**原话｜** 数据流图（Data Flow Diagram，DFD）描述数据在系统中如何被传送或变换，以及如何对数据流进行变换的功能或子功能，用于对功能建模。图上只允许出现四种东西，谁画都一样。

| 元素 | 原话 / 判据 | 画法 | 报销系统里 |
|---|---|---|---|
| **外部实体**（外部主体） | "存在于软件系统之外的人员或组织"，是系统所需数据的**发源地（源）**和所产生数据的**归宿地（宿）**；另一个系统（银行网银接口、信用卡管理系统）也算。判据：**系统管不管得着它** | 方框 | 员工、主管、银行的网银接口 |
| **加工**（处理） | 描述输入数据流到输出数据流之间的变换；名字是动词 | 圆角矩形 或 圆 | 登记报销单、审批、打款 |
| **数据存储**（文件） | 存储数据，每个文件有名字；**流向文件＝写，流出文件＝读** | 双横线，或右边开口的矩形 | 报销单表、审批记录表 |
| **数据流** | 由一组固定成分的数据组成，表示数据的流向；通常用名词命名 | 带名字的箭头 | 报销单、付款指令 |

**三条硬规则**（画图、判图全靠它们）：

1. **数据流必须经过加工**——箭头两端至少一端是加工，所以外部实体↔外部实体、外部实体↔数据存储、数据存储↔数据存储一律不许直接连线；
2. **加工不能是黑洞、奇迹或灰洞**（下表）；
3. **父图与子图必须平衡**（第三节）。

| 画错 | 原话 | 判法 | "会员应用"DFD 片段 |
|---|---|---|---|
| **黑洞** | 加工有输入但是没有输出 | 数箭头：有没有出 | 3.1.2 创建新的会员账号：进 会员应用、现有账号、雇员状态，无输出 |
| **奇迹** | 加工有输出但是没有输入 | 数箭头：有没有进 | 3.1.3 冻结会员账号：无输入，出 冻结账号通知、回写会员账号 |
| **灰洞** | 加工中输入不足以产生输出 | 读业务：够不够 | 3.1.1 生成雇员银行结算表：只进"雇员地址"，出"银行结算表"——账号、金额、结算周期无来源 |

黑洞、奇迹数箭头即可；灰洞一进一出形式上没毛病，必须读懂业务才看得出。原图第三处批注正是"账目数据从哪里来"：

![会员应用 DFD 的三处画错：3.1.2 没有输出、3.1.3 没有输入、3.1.1 账目数据无来源](images/fig_d13_s011.jpg)

**DFD 画不出"状态"。** 报销单草稿→待审→已审→已打款，事件是"提交""驳回""打款成功"——这要用**状态转换图（STD）**：画**状态**（须标出**初态**和**终态**）和触发跳转的**事件**。下图画学员：注册状态下"没有交费"转回自己，"开通课程[已交费]"到学习，"已学完指定教材"到测试，"合格"到终态，"测试不合格"退回学习：

![状态转换图 STD 示例：注册 → 学习 → 测试](images/fig_d11_s038.jpg)

| 建模对象 | 用哪张图 |
|---|---|
| 功能模型 | **DFD** |
| 行为模型 | **STD** |
| 数据模型 | **E-R 图**（实体及其联系，数据库板块细讲） |

## 三、分层 DFD 与父图子图平衡

**顶层图**（上下文数据流图）**只含一个加工，表示整个系统**，描述系统的输入输出及与外部实体的数据交互，一般不画数据存储。报销系统顶层图（纯文本里 `[ ]` 代表方框＝外部实体，`( )` 代表圆角框＝加工，别弄反）：

```
 [员工 E1] ──报销单────▶ (            ) ──审批结果──▶ [员工 E1]
 [主管 E2] ──审批意见──▶ (  报销系统  ) ──审批请求──▶ [主管 E2]
 [银行 E3] ──付款回执──▶ (            ) ──付款指令──▶ [银行 E3]
```

三个外部实体、一个加工、六条数据流、零个数据存储。

**0 层图**拆成 P1 登记报销单、P2 审批、P3 打款，**数据存储从这一层开始出现**：D1 报销单表、D2 审批记录表。共 13 条数据流：

- 一端连外部实体的 6 条：E1→P1 报销单、E2→P2 审批意见、E3→P3 付款回执；P2→E1 审批结果、P2→E2 审批请求、P3→E3 付款指令。
- 只在加工与存储间的 7 条：P1→D1 新报销单、D1→P2 待审报销单、P2→D2 审批记录、P2→D1 审批后状态、D1→P3 已批准报销单、D2→P3 审批记录、P3→D1 付款状态。

**1 层图**把 P2 拆成 2.1 校验金额、2.2 判定审批级别、2.3 记录审批意见——**子图的加工编号继承父图编号**。（P 只是本讲义的行文记号，图上加工写 1、2、3 和 2.1、2.2。）上一层叫**父图**，下一层叫**子图**。

**原话｜** 父图与子图的平衡原则：**子图的输入输出数据流，同父图相应加工的输入输出数据流必须一致**。顶层图 6 条对外箭头，0 层图一端连外部实体的也必须是这 6 条、名字一一对上。道理：拆开只是把一个盒子换成几个小盒子，和外界的口子不该多也不该少——多一条说明子图偷偷跟外面通信，少一条说明父图承诺的事没人干。

**放宽口径：** 父图的一条数据流可以对应子图里的几条，只要这几条的数据项合起来正好是父图那一条，仍算平衡。**判平衡看数据项合起来对不对得上，不是数箭头。**

**易混对 条数对得上 vs 数据项对得上**
- 判据｜比较子图对外流和父图对应加工的进出流，按数据项合并后是否一致。
- 例子｜考务处理系统（下图）：(c) 加工 1 的 1 层图拆成 1.1 检查报名表、1.2 编准考证号、1.3 登记考生，对外进"报名单"，出"不合格报名单、准考证、考生名单"外加写入考生名册，与父图逐条同名；(d) 加工 2 的 1 层图拆成 2.1 检验成绩单、2.2 审定合格者、2.3 制作通知单、2.4 分类统计、2.5 难度分析，出流四条（错误成绩清单、考生通知单、难度分析表、分类统计表），父图加工 2 只有三条（错误成绩清单、考生通知单、统计分析表）——"统计分析表"被拆成"难度分析表＋分类统计表"，数据项合起来一致，**仍然平衡**。

![分层数据流图：（a）顶层图（b）0 层图（c）加工 1 的 1 层图（d）加工 2 的 1 层图](images/fig_d13_s012.jpg)

该图 (a) 顶层：一个加工、三个外部实体（考生、考试中心、阅卷站）、零个数据存储；(b) 0 层：两个加工（1 报名登记表、2 统计成绩），数据存储"考生名册"这一层才出现。

分层三判据：顶层图**一个加工**；数据存储**从 0 层起**出现；平衡存在于**父图与子图之间**。

## 四、数据字典与小说明

**原话｜** 数据流图描述了系统的分解，但没有对图中各成分进行说明。**数据字典（Data Dictionary，DD）就是为数据流图中的每个数据流、文件、加工，以及组成数据流或文件的数据项做出说明。** 图是骨架，字典是图例。

**原话｜** 数据字典有以下 **4 类条目：数据流、数据项、数据存储和基本加工**。数据项＝不可再分的最小数据单位（单号、金额）；基本加工＝不再往下拆的最底层加工。

**易混对 字典条目 vs DFD 图形元素**
- 判据｜外部实体是 DFD 的图形元素，**不是**字典条目；数据流、数据存储、（基本）加工两边都有，数据项只在字典里。
- 例子｜"外部实体、数据流、数据项、基本加工"四者中不属于字典条目的是**外部实体**。

另一套教材口径列 6 项：**数据元素、数据结构、数据流、数据存储、加工逻辑、外部实体**——把数据项叫"数据元素"，另加数据结构和外部实体。两套都不是笔误，是两本教材各自的分法。用词是"数据项、基本加工"时按 4 类，外部实体不是条目；整套换成"数据元素、数据结构、加工逻辑"时按 6 项那套。

| 符号 | 含义 | 举例 |
|---|---|---|
| **=** | 被定义为 | 报销单 = 单号 + 金额 |
| **+** | 与 | x=a+b，x 由 a 和 b 组成 |
| **[…\|…]** | 或 | x=[a\|b]，x 由 a 或 b 组成 |
| **{…}** | 重复 | x={a}，x 由 **0 个或多个** a 组成（不是"至少 1 个"） |
| **( )** | 可选 | x=(a)，a 可有可无 |
| **m{…}n** | 限定次数的重复 | x=2{a}5，a 至少 2 次、至多 5 次 |

前四个是重点，后两个认得即可。报销系统条目：

```
报销单 = 单号 + 员工工号 + 报销日期 + {费用明细} + 合计金额 + [发票照片|电子发票号]
费用明细 = 费用类型 + 金额 + 发生日期
```

一张报销单挂 0 到多条费用明细；发票照片和电子发票号二选一。

**小说明：** 加工逻辑也称"小说明"，写这个基本加工把输入变成输出的规则。**常用描述方法 3 种：结构化语言、判定表、判定树**。P2 审批三种写法：

```
结构化语言：  if (合计金额 > 5000) 转二级审批;
              else 转直属主管审批;

判定表：      条件：合计金额>5000 |  是   否
              动作：转二级审批    |  √
                    转直属主管    |       √

判定树：      合计金额 ─┬─ >5000 ─→ 转二级审批
                        └─ ≤5000 ─→ 转直属主管审批
```

| 写法 | 是什么 | 适合 |
|---|---|---|
| 结构化语言 | 带缩进的伪代码，中文照写 | — |
| 判定表 | 条件取值组合列成表，每列写该走的动作 | 条件多、组合密，不易漏组合 |
| 判定树 | 同一件事的树形画法，从左往右按条件分叉，叶子是动作 | 条件有明显层次，更直观 |

**小说明只写"输入变成输出的规则"，不写"用什么数据结构、什么算法实现"**——那是详细设计阶段的事，需求分析阶段还轮不到。

## 五、结构化设计 SD：从数据流图走到模块结构

**原话｜** 结构化设计（Structured Design，SD）方法是一种面向数据流的设计方法，它可以与 SA 方法衔接。基本思想是将系统设计成由相对独立、功能单一的模块组成的结构。

SD 用**结构图（Structure Chart）描述软件系统的体系结构**：由哪些模块组成、模块间的调用关系——画"谁调用谁"，不是 DFD 的"数据往哪流"。**结构图（模块结构图）由模块、调用、数据、控制和转接五种基本符号组成**：模块是方框；调用是箭头；数据和控制是挂在调用箭头旁的小箭头，表示传的是数据还是控制信息；转接是图画不下时的续接标记。

| SD 四项任务 | 原话 | 报销系统里 |
|---|---|---|
| **体系结构设计** | 定义软件的主要结构元素及其关系 | 提单、审批、打款、报表四大块及层次 |
| **数据设计** | 基于实体联系图确定软件涉及的文件系统的结构及数据库的表结构 | 报销单表、审批记录表建几张、什么字段 |
| **接口设计** | 描述用户界面，软件和其他硬件设备、其他软件系统及使用人员的外部接口，以及各种构件之间的内部接口 | 提单页面、与银行的对接接口 |
| **过程设计** | 确定软件各个组成部分内的算法及内部数据结构，并选定某种过程的表达形式来描述各种算法 | 审批状态机内部怎么写 |

**易混对 数据设计 vs 接口设计的依据**
- 判据｜**数据设计基于 E-R 图，接口设计依据数据流图**。接口就是"谁和谁之间过数据"，DFD 画的正是数据在系统内外怎么流。
- 例子｜定报销单表字段 → 看 E-R 图；定与银行的对接接口 → 看 DFD 上报销系统与银行之间的付款指令、付款回执。

**DFD → 结构图的两条路线**（认名即可）：

| 类型 | DFD 形态 | 结构图顶层 |
|---|---|---|
| **变换型** | 一条流水线：取数据→加工→送数据 | 输入、变换、输出三个分支 |
| **事务型** | 一个中心接到请求后按类型分发给互不相干的几条支路 | 接收模块＋调度模块，调度再分发 |

判别看中心加工是在"变"还是在"分"；真实系统常是混合的，先按事务型切分支，再对每条分支做变换分析。

## 六、WebApp 分析与设计（认名即可）

**WebApp** 是基于 web 的系统和应用（浏览器里跑的那类）。**大多数 WebApp 采用敏捷开发过程模型进行开发**——不先写厚文档，一两周交付一个能用的版本再改。

| 六特性 | 关键词 |
|---|---|
| 网络密集性 | 驻留在网络上，服务不同客户群体 |
| 并发性 | 大量用户可能同时访问 |
| 无法预知的负载量 | 用户数每天可能有数量级变化（周一 100 人，周四可能 10000 人） |
| 性能 | 等太久用户就走了 |
| 可用性 | 热门 WebApp 用户通常要求 **24/7/365 全天候**访问 |
| 数据驱动 | 主要用超媒体（文字里嵌图片、音视频和跳转链接）提供文本图片音频视频，常访问外部数据库 |

| 五种需求模型 | 内容 |
|---|---|
| 内容模型 | WebApp 提供的全部内容（文字、图形、图像、音频、视频） |
| 交互模型 | 用户与 WebApp 采用哪种交互方式，由用例、顺序图、状态图、用户界面原型等构成 |
| 功能模型 | 用于内容的操作及其他处理功能 |
| 导航模型 | 所有导航策略，考虑每类用户如何从一个元素导航到另一个 |
| 配置模型 | WebApp 所在的环境和基础设施，复杂时可用 **UML 部署图**（哪个程序装在哪台机器上） |

| 四块设计 | 内容 |
|---|---|
| 架构设计 | 以什么方式管理用户交互、操作内部处理任务、实现导航及展示内容；**MVC（模型-视图-控制器）是 WebApp 基础结构模型之一**，把功能及信息内容分离 |
| 构件设计 | 构件是一包定义良好的聚合功能（为最终用户处理内容或提供计算），同时包括**内容设计元素和功能设计元素**：构件级内容设计关注内容对象及包装后展示给用户的方式；构件级功能设计把 WebApp 作为一系列构件交付，与信息体系结构并行开发以保证一致性 |
| 内容设计 | 着重内容对象的表现和导航的组织，采用**线性、网格、层次、网络**四种结构及其组合——与网络拓扑的总线/星型/环型是两码事 |
| 导航设计 | 定义导航路径，使用户能访问内容和功能 |

## 速记

- SA 面向数据流，产物四件：分层 DFD ＋ 数据词典 ＋ 小说明 ＋ 补充材料；**结构图是设计的产物，不是分析的**
- DFD 四元素：外部实体方框、加工圆或圆角框、数据存储双横线或右开口框、数据流箭头；数据流必过加工，实体、存储两两不能直连；进存储写、出存储读
- 三种画错：只进不出黑洞、只出不进奇迹、进得不够灰洞；DFD 功能模型、STD 行为模型（标初态终态）、E-R 数据模型
- 分层：顶层一个加工一般不画存储，存储从 0 层起，子图编号带父级前缀；平衡在父图与子图之间，**父图一条可对子图几条，看数据项合不合得上**
- 数据字典 4 类条目：数据流、数据项、数据存储、基本加工——**外部实体不是条目**；`=` 定义、`+` 与、`[a|b]` 或、`{a}` 重复 0 到多次
