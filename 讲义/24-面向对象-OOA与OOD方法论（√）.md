# 24 · 面向对象：OOA 与 OOD 方法论

## 定位

用面向对象做一个系统，工序怎么排。全程用内部报销系统（讲义 15–17 那套）：类从哪来（名词识别法）→ 类挑出来后按什么顺序做完分析（OOA 五个活动）→ 设计在分析之上补什么（与技术相关的部分，三件套长成五件套）→ 做出来按什么层次测（面向对象特有的四层）。重点在分界线：一件事归分析还是设计、一句描述属于哪一层。全课无计算。

---

## 一、类从哪来：名词识别法

**问题域**＝系统要解决的那摊业务本身（有哪些角色、单据、规则），与用什么语言、数据库无关。

**原话｜** 面向对象的分析：是为了确定问题域，理解问题。

**名词识别法**（名词分析法）：需求文本里的名词和名词短语当候选类，动词当候选操作。道理：业务里"是个东西、有自己的状态、能指着说'这一张'"的，中文里以名词出现；"做一件事"以动词出现。

需求："员工填写报销单，选择报销类型并填入金额，上传发票后提交；部门经理在待办列表里审批，金额超过 5000 元的还要走财务总监二级审批；财务发起打款，打款状态由银行接口回传。"

候选名词：员工、报销单、报销类型、金额、发票、部门经理、待办列表、财务总监、财务、打款、银行接口。圈完不是答案，还要过三道筛：

| 筛 | 判据 | 处理 | 报销系统里 |
|---|---|---|---|
| ① 只是别人身上的一个值 | 删掉它主体还在，删掉主体它就没意义 | 降级成**属性** | 金额、报销类型（报销金额这类数值不做类） |
| ② 在系统边界之外 | 只交换数据、不管理它的状态 | 剔除，或只当**参与者**（站在系统外跟系统打交道的人或外部系统） | 银行接口；"公司""财务部"这类场所名词 |
| ③ 别名或动作 | 只是视图／动词名词化 | 合并或剔除 | 待办列表（视图）；打款（真正实体是打款单） |

筛完剩：员工、报销单、发票、审批人（部门经理、财务总监职责相同级别不同，归一类）、打款单。再**补**文本里没作为名词出现的类：审批记录（审批走了几步、谁批、何时批）。所以这一步是**又减又加**。

**易混对 参与者 vs 类**（不互斥）
- 判据｜系统要不要保存并维护它的状态：要，就是类（可以同时是参与者）；不要，只当参与者。
- 例子｜员工在系统外使用系统（参与者），系统又管他的工号、部门、报销额度（也是类）；银行接口的内部状态不归我们管，只当参与者。商场系统里的顾客、收银员，只要系统记他们的信息，就都是类。

**易混对 OOA 的起点 vs 五活动的第一条**
- 判据｜问 OOA 的起点／第一步 → **确定问题域**（定义第一句，先圈范围）；问活动清单第一条 → **认定对象**。
- 例子｜圈定报销这件事涉及哪些角色、单据、规则 → 确定问题域（起点）；在圈定的范围里定下员工、报销单等类 → 认定对象（五活动第一条）。

## 二、OOA 的五个活动

**原话｜** 包含五个活动：**认定对象、组织对象、描述对象间的相互作用、确定对象的操作、定义对象的内部信息**。

| 活动 | 干什么 | 报销系统里 |
|---|---|---|
| 认定对象 | 在应用领域中按自然存在的实体认定对象（需求里的名词） | 员工、报销单、发票、审批人、审批记录、打款单 |
| 组织对象 | 理清类之间是哪类关系（符号归讲义 25–27） | 部门经理、财务总监都是审批人（一般与特殊）；报销单挂若干发票（整体与部分） |
| 描述对象间的相互作用 | 谁找谁办事、按什么次序 | 提交后通知审批人；审批通过后通知打款单 |
| 确定对象的操作 | 交互落成每个类对外的方法 | 报销单：提交、撤回；审批记录：追加一条 |
| 定义对象的内部信息 | 补属性与数据结构 | 报销单：金额、类型、状态、提交时间 |

顺序的道理：先有谁 → 谁跟谁什么关系 → 怎么打交道 → 各自对外提供什么能力 → 内部装什么数据。先定属性，交互一变就得推倒重来。是**五个**，不是四个。

**另一套切法：面向对象需求建模**，分两条并行线：

- **建立用例模型**：识别参与者 → 合并需求获得用例 → 细化用例描述 → 调整用例模型。**用例**＝用户拿系统完成的一件完整的事（如"员工提交报销单"）。用例描述八项：用例名称、简要说明、事件流、非功能需求、前置条件、后置条件、扩展点、优先级。调整时理顺包含、扩展、泛化三种关系（画法归讲义 25）。
- **建立分析模型**：定义概念类 → 识别类之间的关系 → 为类添加职责 → 建立交互图（交互图＝一次调用里对象之间谁先找谁、按什么次序来往的图）。

两套用词对应：定义概念类＝认定对象；识别类之间的关系＝组织对象；为类添加职责＝确定对象的操作；建立交互图＝描述对象间的相互作用。

## 三、设计在分析之上补什么：OOD

**原话｜** 面向对象的设计：是设计分析模型和实现相应源代码，设计问题域的解决方案，与技术相关。OOD 同样应遵循抽象、信息隐蔽、功能独立、模块化等设计准则。

- "**同样**"：这四条准则结构化设计里也有，不是面向对象独有（抽象＝只留关键特征；信息隐蔽＝内部实现不外露；功能独立＝一个模块只干一件事、少耦合；模块化＝拆成可分别开发的块）。
- "**与技术相关**"是分水岭：**OOA 只描述问题，OOD 才开始解决问题**。

**原话｜** 分析模型主要由**顶层架构图、用例与用例图、领域概念模型**构成；设计模型则包含以**包图表示的软件体系结构图、以交互图表示的用例实现图、完整精确的类图、针对复杂对象的状态图和用以描述流程化处理过程的活动图**等。（下称三件套、五件套）

| 同一件事 | 分析模型（三件套） | 设计模型（五件套） |
|---|---|---|
| 整体形状 | 顶层架构图：粗到只有几个大块 | 以包图表示的软件体系结构图：类按模块分组，哪个包依赖哪个包定死 |
| 用户能做的事 | 用例与用例图：谁能拿系统做哪几件事 | 以交互图表示的用例实现图：这件事由哪几个对象按什么次序协作完成 |
| 类 | 领域概念模型：只有业务概念，有类名和大致属性，无方法签名、字段类型 | 完整精确的类图：属性类型、方法签名、可见性齐全 |
| 状态与流程 | 不画 | 状态图（复杂对象如报销单从草稿到已打款怎么变）、活动图（一段流程怎么走） |

各图画法归讲义 25–27。

**OOD 四步**：设计用例实现方案 → 设计技术支撑设施 → 设计用户界面 → 精化设计模型。

| 步骤 | 报销系统里 |
|---|---|
| 设计用例实现方案 | 把"员工提交报销单"排成一串对象协作 |
| 设计技术支撑设施 | 日志、事务、权限、持久化等每个用例都用的公共底座 |
| 设计用户界面 | 提单页几个字段、审批页怎么排 |
| 精化设计模型 | 把前三样落回类图，补全属性类型和方法签名 |

用词：另见印成"设计技术支撑**实施**／技术支撑**方案**……**细化**设计模型"的，与"设施""精化"是同一件事，以「设施／精化」为准。

**易混对 OOA vs OOD**
- 判据｜只谈业务里有哪些东西、什么关系、谁找谁办事 → OOA；出现界面、数据库、框架、线程、接口规格 → OOD。
- 例子｜"报销单挂若干张发票"→ OOA；"报销单持久化到 MySQL、审批用异步线程通知"→ OOD。

**易混对 面向对象 vs 结构化的阶段衔接**
- 判据｜分析、设计是否用同一套概念：面向对象共用"类"，阶段间**平滑过渡、无缝**，设计是在同一批类上补细节；结构化分析交数据流图、设计交模块结构图，中间要人工转换，容易走样、丢信息。
- 例子｜领域概念模型里的"报销单"类，到设计模型里还是"报销单"，只是补了类型和签名；DFD 里的"审批"加工要重新映射成结构图里的模块。

## 四、面向对象测试的四个层次

传统"函数 → 模块 → 系统"分级套不上：函数长在类里，类会被继承、被子类替换一部分行为（继承、多态归讲义 23）。例：父类"审批人"的"审批()"已测通过，子类"财务总监"继承且未重写它，仍要在子类里再测——"审批()"调用了"校验额度()"，而子类重写了"校验额度()"，同一段代码在子类里行为已变。

**原话｜**
（1）**算法层**。测试**类中定义的每个方法**，基本上相当于传统软件测试中的单元测试。
（2）**类层**。测试封装在**同一个类中的所有方法与属性之间的相互作用**。在面向对象软件中类是基本模块，因此可以认为这是面向对象测试中所特有的模块测试。
（3）**模板层**。测试**一组协同工作的类之间的相互作用**，大体上相当于传统软件测试中的集成测试，但是也有面向对象软件的特点（例如，对象之间通过发送消息相互作用）。
（4）**系统层**。把**各个子系统组装成完整的面向对象软件系统**，在组装过程中同时进行测试。

| 层 | 关键词 | 传统对应 | 报销系统里 |
|---|---|---|---|
| 算法层 | 类中定义的每个方法 | 单元测试 | 单测"报销单.计算应报金额()" |
| 类层 | 同一个类中方法与属性的相互作用 | **无**（面向对象特有的模块测试，"类是基本模块"） | 报销单的状态属性与提交()、撤回()、审批通过()配合，先撤回再提交会不会搞乱状态 |
| 模板层 | 一组协同工作的类 | 集成测试 | 报销单、审批记录、审批人一起走完一次二级审批 |
| 系统层 | 子系统组装 | 系统测试 | 报销子系统、打款子系统、单点登录组装后整体跑 |

**易混对 算法层 vs 类层**
- 判据｜只测单个方法 → 算法层；测一个类里多个方法与属性配合 → 类层。
- 例子｜"测试类中定义的每个方法"→ 算法层；把状态属性也带进来，看"撤回()后再提交()"状态对不对 → 类层。

名字别被带偏：**模板层**与 C++／Java 的模板（泛型）无关，测的是一组类协作；**算法层**的"算法"指一个方法内部的逻辑，不是排序查找。

用例怎么挑（黑盒、白盒）、覆盖到什么程度、验收测试，是所有软件通用的，归讲义 17。

## 速记

- OOA：**确定问题域、理解问题**，与技术无关，起点是确定问题域；OOD：设计问题域的**解决方案**，**与技术相关**。出现界面／数据库／框架／线程／接口规格就是 OOD
- OOA 五活动：**认定对象 → 组织对象 → 描述对象间的相互作用 → 确定对象的操作 → 定义对象的内部信息**
- 用例模型四步：识别参与者 → 合并需求获得用例 → 细化用例描述 → 调整用例模型；分析模型四步：定义概念类 → 识别类之间的关系 → 为类添加职责 → 建立交互图
- 名词识别法：名词做类、动词做操作；三筛（属性值、边界外、别名与动作），再补文本没写的类；系统要维护其状态的参与者也是类
- 分析模型三件套：**顶层架构图＋用例与用例图＋领域概念模型**；设计模型五件套：**包图（体系结构）、交互图（用例实现）、完整精确的类图、状态图、活动图**
- OOD 四步：设计用例实现方案 → 设计技术支撑**设施** → 设计用户界面 → **精化**设计模型；遵循抽象、信息隐蔽、功能独立、模块化
- OO 测试四层：**算法层（每个方法）→ 类层（同一类中方法与属性的相互作用）→ 模板层（一组协同工作的类）→ 系统层（子系统组装）**，对应单元、（无，OO 特有模块测试）、集成、系统
- 面向对象阶段间平滑过渡、无缝：分析设计共用同一套类的概念
