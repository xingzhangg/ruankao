## 开讲：报销系统要推倒重来，这回用面向对象

还是讲义 15–17 那套内部报销系统。老板说旧的太难改，重做一版，你决定用面向对象。

最朴素的做法：打开需求文档，想到哪个类写哪个类——先建个 `Bill`，再建个 `User`，边写边加。这个第一反应会在四个地方翻车：

- ① 类是"想"出来的。为什么是 `Bill` 和 `User`，不是"报销单"和"员工"？换个人做就是另一套，谁也说不清谁对；
- ② 类列出来就没下文了。它们之间什么关系、谁找谁办事、每个类该提供哪些能力、里面装什么数据，没有先后，全靠边写边补；
- ③ 就算业务上的类都齐了，界面长什么样、数据存哪、要不要开线程，一个字没定——这一堆离能跑的系统还差一截；
- ④ 写完怎么测。传统那套"函数 → 模块 → 系统"套不上：类算模块吗？父类的方法测过了，子类还要不要再测一遍？

下面四节，一条一条补。

### 一、类是从哪来的：名词识别法

先把一个词说死。**问题域**指的是系统要解决的那摊业务本身——报销这件事里有哪些角色、哪些单据、什么规则，跟你用 Java 还是 Go、用 MySQL 还是 Oracle 一点关系没有。培训资料给面向对象分析（OOA）下的定义只有一句：**面向对象的分析：是为了确定问题域，理解问题。**

看一段报销系统的需求：

> "员工填写报销单，选择报销类型并填入金额，上传发票后提交；部门经理在待办列表里审批，金额超过 5000 元的还要走财务总监二级审批；财务发起打款，打款状态由银行接口回传。"

**先别往下看，自己圈一遍**：这段话里，哪些名词应该做成类？把你圈的写下来，再对下面。

多数人第一遍圈出来的是：员工、报销单、报销类型、金额、发票、部门经理、待办列表、财务总监、财务、打款、银行接口。这个直觉对了一半——**从名词下手**是对的，这就是**名词识别法**（也叫名词分析法）：把需求文本里的名词和名词短语挑出来当候选类，把动词挑出来当候选操作。

道理很直白，业务里"是个东西、有自己的状态、能指着说'这一张''那一个'"的，在中文里就是以名词出现的；"做一件事"则以动词出现。

错的那一半在于**圈完就当答案**。候选名词还要过三道筛：

1. **它只是别人身上的一个值吗？** "金额""报销类型"是报销单上的一个字段，删掉它报销单还在，删掉报销单它就没有意义了——**降级成属性**。把"报销金额"这种数值当成一个类，是这类题最常见的错法。
2. **它在系统边界之外吗？** "银行接口"是外部系统，我们只跟它交换数据、不管理它的状态；"公司""财务部"这种场所名词同理——**剔除，或者只把它当参与者**（参与者＝站在系统外面跟系统打交道的人或外部系统，比如员工、银行接口）。
3. **它是同一个东西的别名，或者根本是个动作？** "待办列表"只是审批人看到的一个视图，不是独立的业务实体；"打款"是动词名词化，真正的实体是"打款单"——**合并或剔除**。

筛完剩下：员工、报销单、发票、审批人（部门经理和财务总监职责相同、级别不同，归一类）、打款单。还差一类：审批走了几步、谁批的、什么时候批的，总得有个地方存——"审批记录"。这个词在需求文本里根本没作为名词出现过。所以这一步是**又减又加**：只照抄名词会漏，只做减法也会漏。

### 二、挑出一串类之后按什么顺序做：OOA 的五个活动

培训资料把 OOA 拆成五步，原文照录：**包含五个活动：认定对象、组织对象、描述对象间的相互作用、确定对象的操作、定义对象的内部信息**。挨个落到报销系统上：

**认定对象**就是上一节干的事——把问题域里的类定下来：员工、报销单、发票、审批人、审批记录、打款单；考试里这一步的标准说法是"在应用领域中按自然存在的实体认定对象"，认的就是需求文本里的名词。**组织对象**是理清这些类彼此什么关系："部门经理和财务总监都是审批人"属于一般与特殊（父与子），"一张报销单挂着若干张发票"属于整体与部分。这一步只判断是哪一类关系，至于关系有几种、各画成什么符号，归讲义 25–27。**描述对象间的相互作用**是排谁找谁办事、按什么次序：报销单一提交就要通知审批人有单待批，审批通过后再通知打款单可以打款。**确定对象的操作**把上一步的交互落成每个类对外提供的方法：报销单要有"提交""撤回"，审批记录要有"追加一条"。**定义对象的内部信息**最后补上每个类内部的属性与数据结构：报销单里有金额、类型、状态、提交时间。

顺序不用背，顺着推就出来了：先知道**有谁**，才谈得上**谁跟谁什么关系**；有了关系才排得出**怎么打交道**；交互定了才知道**每个类要对外提供什么能力**；能力定了最后才补**各自内部装什么数据**。反过来先定属性，交互一变属性就得推倒重来。

**注意是五个活动不是四个。** 排序题常只列前四项让你排，但"以下不属于面向对象分析活动的是"这种反问会用到第五项，五个都要有印象。

同一件事，培训资料还配了一张"面向对象需求建模"图，用的是另一套切法，把 OOA 分成并行的两条线：

**建立用例模型**四步——识别参与者 → 合并需求获得用例 → 细化用例描述 → 调整用例模型。**用例**就是用户拿系统能完成的一件完整的事，比如"员工提交报销单"。细化用例描述要写足八项：用例名称、简要说明、事件流、非功能需求、前置条件、后置条件、扩展点、优先级。调整用例模型时理顺用例之间的包含、扩展、泛化三种关系（怎么画归讲义 25）。

**建立分析模型**四步——定义概念类 → 识别类之间的关系 → 为类添加职责 → 建立交互图（分析模型就是分析做完之后交出去的那一摞图和说明，具体是哪几份下一节列全；交互图就是画一次调用里对象之间谁先找谁、按什么次序来往的图）。**这四步和上面五个活动是同一件事的两种切法**：定义概念类＝认定对象，识别类之间的关系＝组织对象，为类添加职责＝确定对象的操作，建立交互图＝描述对象间的相互作用。考试两套用词都可能出现在选项里，按题面给的词对号入座就行。

### 三、分析交出去之后，设计补什么

培训资料给 OOD 下的定义，原文照录：**面向对象的设计：是设计分析模型和实现相应源代码，设计问题域的解决方案，与技术相关。OOD 同样应遵循抽象、信息隐蔽、功能独立、模块化等设计准则。** 后半句里的"同样"两个字是关键——这四条准则不是面向对象独有的（抽象＝只留关键特征、忽略枝节；信息隐蔽＝内部实现别让外面看见；功能独立＝一个模块只干一件事、少跟别人纠缠；模块化＝拆成可以分别开发的块），结构化设计里也是这四条，换成面向对象照样适用。

前半句里"**与技术相关**"四个字，就是 OOA 与 OOD 的分水岭：**OOA 只描述问题，OOD 才开始解决问题**。

这条界线最直观的体现，是两个阶段各交什么东西，培训资料原文：**分析模型**主要由**顶层架构图、用例与用例图、领域概念模型**构成；**设计模型**则包含以**包图表示的软件体系结构图、以交互图表示的用例实现图、完整精确的类图、针对复杂对象的状态图和用以描述流程化处理过程的活动图**等。前者三件、后者五件，下文就叫三件套、五件套。

里面的图名先各用一句话说清：顶层架构图＝粗到只有几个大块的整体形状图；用例图＝画"谁能拿系统做哪几件事"的图；领域概念模型＝只有业务概念的类图，有类名、有大致属性，但没有方法签名、没有字段类型；包图＝把类按模块分组、画组与组之间依赖的图；交互图＝画一次调用过程里对象之间来往次序的图；类图＝画类及类之间关系的图；状态图＝画一个对象从"草稿"到"已打款"怎么变的图；活动图＝画一段流程怎么走的图。它们各自怎么画、什么符号，归讲义 25–27。

两个模型摆在一起对着看，就知道设计比分析多出来的到底是什么：

| 同一件事 | 分析模型给的 | 设计模型给的 |
|---|---|---|
| 系统的整体形状 | 顶层架构图，粗到只有几个大块 | 以包图表示的软件体系结构图，哪个包依赖哪个包都定死 |
| 用户能做的事 | 用例与用例图，只说"员工能提交报销单" | 以交互图表示的用例实现图，提交这件事由哪几个对象按什么次序协作完成 |
| 类 | 领域概念模型，只有业务概念 | 完整精确的类图，属性类型、方法签名、可见性齐全 |
| 复杂对象的状态与流程 | 不画 | 针对复杂对象的状态图、描述流程化处理过程的活动图 |

从分析模型走到设计模型，中间要干的活也是四步（培训资料原图）：**设计用例实现方案 → 设计技术支撑实施 → 设计用户界面 → 细化设计模型**。

落到报销系统：设计用例实现方案是把"员工提交报销单"这个用例排成一串对象协作；设计技术支撑实施是搭日志、事务、权限、持久化这些每个用例都要踩的公共底座；设计用户界面是定提单页几个字段、审批页怎么排；细化设计模型是把前三样落回类图，补全属性类型和方法签名。

**用词提醒**：同一套活动，教材与题库常印成"设计技术支撑**设施**……**精化**设计模型"（信息系统项目管理师 2017 上第 25 题的卷面就是这个印法），与原图的"实施""细化"是同一件事的不同抄法，选项里两种写法都可能出现，按意思对，别卡在字上。

**分界怎么判**（考试最常拿来互换设错的一对）：题干只谈业务里有哪些东西、什么关系、谁找谁办事 → OOA；一出现界面、数据库、框架、线程、接口规格 → OOD。

也正因为分析和设计两头用的是同一套"类"的概念，面向对象方法的阶段之间才是**平滑过渡、没有断层**的：设计不是把分析的成果翻译成另一种模型，而是在同一批类上继续补细节。结构化那边不是这样——分析交数据流图，设计交模块结构图，中间要靠人脑硬翻一道，翻的时候就会走样、会丢信息。

### 四、做出来怎么测：面向对象特有的四个层次

**先猜一下**：父类"审批人"的"审批()"方法已经测过并且通过了，子类"财务总监"继承了它、也没有重写它，这个方法还用不用在子类里再测一遍？

**要测。** 因为"审批()"里可能调用了另一个方法"校验额度()"，而"财务总监"把"校验额度()"重写了——同一段代码，在子类里跑出来的行为已经变了。这正是传统那套"函数 → 模块 → 系统"分级在面向对象上套不住的原因：最小的可测单位不再是一个孤立的函数，函数长在类里，类还会被继承、被子类替换掉一部分行为（继承和多态本身归讲义 23，这里只用它们造成的后果）。

于是培训资料按面向对象自己的结构重分了四层，原文照录：

（1）**算法层**。测试**类中定义的每个方法**，基本上相当于传统软件测试中的单元测试。
（2）**类层**。测试封装在**同一个类中的所有方法与属性之间的相互作用**。在面向对象软件中类是基本模块，因此可以认为这是面向对象测试中所特有的模块测试。
（3）**模板层**。测试**一组协同工作的类之间的相互作用**，大体上相当于传统软件测试中的集成测试，但是也有面向对象软件的特点（例如，对象之间通过发送消息相互作用）。
（4）**系统层**。把**各个子系统组装成完整的面向对象软件系统**，在组装过程中同时进行测试。

对着报销系统看一遍就不会记混：算法层是单测"报销单.计算应报金额()"这一个方法算得对不对；类层是看"报销单"的状态属性和提交()、撤回()、审批通过()几个方法配合起来对不对——先撤回再提交会不会把状态搞乱；模板层是让报销单、审批记录、审批人三个类一起走完一次二级审批；系统层是把报销子系统、打款子系统、单点登录组装起来整体跑。

**四层与传统四级的对应只有三处对得上，第四处正是考点**：算法层≈单元测试（测一个最小可独立编译的单元），模板层≈集成测试（测拼起来之后接口对不对），系统层≈系统测试（测整机满不满足需求，这三级的做法归讲义 17）；**类层没有传统对应物**，它是面向对象特有的"模块测试"——因为在面向对象里，"模块"这个词指的是类，不是函数。原文那句"在面向对象软件中类是基本模块，因此可以认为这是面向对象测试中所特有的模块测试"说的就是这件事。

至于用例怎么挑（黑盒、白盒）、覆盖到什么程度算够、什么时候做验收测试，那是所有软件通用的，归讲义 17；本节只管"分几层、每层测的是什么"。

**收口**：开头四条短板，四节一一回应——① 类凭什么是这几个（名词识别法：名词做类、动词做操作，再筛掉属性值、边界外、别名与动作，最后补上文本没写的类）→ ② 挑完之后按什么顺序做完（五个活动，或者用例模型四步＋分析模型四步的另一套切法）→ ③ 业务类离能跑的系统差什么（OOD 四步补上与技术相关的部分，分析模型三件套变成设计模型五件套）→ ④ 做出来怎么测（算法／类／模板／系统四层）。做题时先认出题干问的是这条链上的哪一环，再对定义，比背表快。

## 考试怎么考

**考点① 从需求文本里认对象。** 直接考的样子是"按自然存在的实体认定对象，即将自然存在的（ ）作为一个对象"，答**名词**（2022 下考过；干扰项放"动词""关系""问题"，动词对应的是操作不是对象）。变形考法是给一段需求让你挑哪几个词该做类，错法固定两类：把"金额""条码"这种长在别人身上的字段当成类，把"结账""打款"这种动作当成类。

**考点② 活动归属与顺序。** 问顺序，按"有谁 → 什么关系 → 怎么打交道 → 提供什么能力 → 内部装什么"推，别背；问"不属于面向对象分析的活动是"，错项通常从别的阶段抓一个塞进来（面向对象程序设计、确定接口规格、设计用户界面都是设计或实现阶段的活儿）；问"面向对象分析的第一步"，答**确定问题域**——因为 OOA 的定义就是"为了确定问题域，理解问题"，认定对象是拆开来的第一个活动，两问不冲突，看题干问的是"目的的起点"还是"活动清单的第一条"。

**考点③ 两个模型的构成，以及 OOA 与 OOD 的分界。** 培训资料在本课范围内收的那道真题一题挖三个空：分析模型缺的那一空填**领域概念模型**（干扰项爱放"数据流模型""功能分解图"，那是结构化的东西）；设计模型里"表示软件体系结构图"的那一空填**包图**（干扰项爱放"组件图""模型视图控制器"）；"描述复杂对象的"那一空填**状态图**（干扰项爱放"序列图""协作图"，那两个是交互图，已经被用例实现图占掉了）。记法：**分析三件套＝顶层架构图＋用例与用例图＋领域概念模型**，设计五件套＝**包图、交互图、类图、状态图、活动图**各管一摊。分界一句话过筛：只谈业务里有什么、什么关系 → 分析；出现界面、数据库、框架、线程、接口规格 → 设计。常见错法是把"确定接口规格""设计人机交互"当成分析活动，或者反过来说"OOD 与具体技术无关"——原文明明写着 OOD"与技术相关"。另有一个送分点：面向对象方法阶段之间"平滑过渡、无缝衔接"的原因是分析设计共用同一套概念，选项若写成"因为使用了统一的建模工具""因为省略了设计阶段"，一律排除。

**考点④ 测试层次。** 抓关键词对定义：出现"每个方法"→算法层；"同一个类中方法与属性之间的相互作用"→类层；"一组协同工作的类"→模板层；"子系统组装"→系统层。**这里有一道必须知情的分歧题**：2023 上第 39 题问的正是"测试类中定义的每个方法属于（ ）层"，信管网题库的参考答案标 **B（类）**，而培训资料与教材的原句白纸黑字是"算法层。测试类中定义的每个方法"，按定义应选 **A（算法）**。软考上午题从不公布标准答案，两边都拿不出官方依据。**考场口径：见到这句措辞就填 A（算法层）**——上午题的命题依据是教程，这句题干几乎是教程原句直接搬用，而题库那一边给不出与之相反的教材出处。但要有数：这一分本来就不牢靠，别在它上面反复权衡；真正稳的是上面那四条判据，换年份换措辞照样能答。

### 参考答案

1. **B　C　D**。第一空用排除法：数据流模型、功能分解图是结构化方法的产物，功能需求模型不是模型三件套里的词，只剩领域概念模型。第二空软件体系结构图讲的是"包与包之间怎么依赖"，用包图；组件图画的是构件，模型视图控制器是架构模式不是图。第三空"描述复杂对象的"是状态图的岗位，序列图和协作图都属于交互图，已被"用例实现图"那一空占了。
2. **A**。按教材与培训资料原句"算法层。测试类中定义的每个方法"作答。**此题答案有分歧**，信管网题库标 B（类层），考点④已给出取舍与理由；四条判据里"每个方法"归算法层，"同一个类中方法与属性之间的相互作用"才归类层，两句在原文里各有归属。
3. **C**。业务里"是个东西、能指着说这一张那一个"的，在中文里都以名词出现，所以认定对象就是从名词下手。A 的"问题"是要解决的事不是实体，B 的"关系"要等对象定下来才谈得上，D 的"动词"对应的是操作不是对象。
4. **C**。五个活动是认定对象、组织对象、描述对象间的相互作用、确定对象的操作、定义对象的内部信息；A 是前两个合写，B、D 各对应一个，只有"面向对象程序设计"属于实现阶段，不在分析里。
5. **C**。OOA 的定义就是"为了确定问题域，理解问题"，所以起点是把问题域圈出来。定义服务（操作）排在很后面，定义类和对象要先有问题域才谈得上，附加的系统约束属于设计要考虑的事。
6. **B**。前一句是类层的定义原文，后一句是模板层的定义原文。这两句和第 2 题的"每个方法"是三条互不重叠的判据。
7. **A**。B 全是动词，应作为候选操作；C 的"条码"是商品的属性、"总价"是小票或结算过程的一个数值，都该降级为属性；D 的"结账"是动作，"收银台"是场所、落在系统边界之外。
8. **C**。界面和持久化方案都与具体技术相关，是设计阶段才定的；A 是认定对象、B 是组织对象、D 是描述对象间的相互作用，三个都在分析里。
9. **A**。先有参与者才谈得上参与者要做什么事，所以识别参与者在最前；用例先归并出来才有得细化，细化完再回头调整整个模型。D 是建立分析模型那条线的四步，不是用例模型的。
10. 名词：会员、积分、礼品、系统。**候选类是会员、礼品**；**"积分"降级为会员的属性**，它本质上只是一个数值，离开会员没有意义；**"系统"是边界本身，剔除**。文本里没写、但必须补上的类是**兑换记录**——不然谁在什么时候换了什么，没地方存。动词"兑换""扣减"是候选操作。
11. **③ → ④ → ② → ①**，对应认定对象 → 组织对象 → 确定对象的操作 → 定义对象的内部信息。（本题的四件事里没有"描述对象间的相互作用"，完整顺序中它排在④和②之间。）
12. **对**。选存储方案与具体技术相关，正是 OOD 的活；放到 OOA 去做才是错的——OOA 只建立问题域模型，不碰实现细节。

## 速记

- OOA 定义：为了**确定问题域、理解问题**，与技术无关；OOD 定义：设计问题域的**解决方案**，**与技术相关**。分界＝一出现界面／数据库／框架／线程／接口规格就是 OOD
- OOA 五活动：**认定对象 → 组织对象 → 描述对象间的相互作用 → 确定对象的操作 → 定义对象的内部信息**（有谁 → 什么关系 → 怎么打交道 → 提供什么能力 → 内部装什么），是五个不是四个
- 另一套切法：用例模型四步＝识别参与者 → 合并需求获得用例 → 细化用例描述 → 调整用例模型；分析模型四步＝定义概念类 → 识别类之间的关系 → 为类添加职责 → 建立交互图
- 名词识别法：名词做类、动词做操作；三筛——属性值、边界外、别名与动作；再补文本没写的类
- 分析模型三件套：**顶层架构图＋用例与用例图＋领域概念模型**；设计模型五件套：**包图（体系结构）、交互图（用例实现）、完整精确的类图、状态图、活动图**
- OOD 四步：设计用例实现方案 → 设计技术支撑实施 → 设计用户界面 → 细化设计模型（另一种印法：技术支撑设施／精化设计模型）；遵循抽象、信息隐蔽、功能独立、模块化
- OO 测试四层：**算法层（每个方法）→ 类层（同一类中方法与属性的相互作用）→ 模板层（一组协同工作的类）→ 系统层（子系统组装）**；对应单元、（无）、集成、系统——**类层是面向对象特有的模块测试**
- 面向对象阶段间"平滑过渡、无缝"的理由：分析设计共用同一套类的概念，不用换模型
