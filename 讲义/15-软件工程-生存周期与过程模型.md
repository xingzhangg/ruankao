## 定位

**这一课回答**：软件的一辈子分几个阶段；按什么节奏走完这些阶段（过程模型：瀑布、原型、增量、螺旋、V、喷泉等）；用什么思路做分析和设计（开发方法：结构化、面向对象、原型化、敏捷、RUP）。

## 开讲：接了一个项目，从立项到下线该怎么走

假设你接了个活：给公司做一套内部报销系统。老板只说了一句"把现在的 Excel 流程搬到线上"。这一课的名词都在回答这个项目的三个问题：**它的一辈子分几步？这几步按什么节奏走？分析和设计用什么思路？**

### 一、先把一辈子切成阶段：生存周期

六十年代的软件项目普遍超支、延期、改不动，史称软件危机。病根是一群人边想边写，没人说得清现在该干什么、产出什么、谁来验收。软件工程给出的第一剂药就是**分阶段**，每个阶段有明确的产出物，做完评审再进下一阶段。Boehm 提出、教材转述的七条基本原理是：用分阶段的生命周期计划严格管理、坚持阶段评审、实行严格的产品控制（报销政策改了要走变更审批，不能想改就改）、采用现代程序设计技术、结果应能清楚地审查、开发小组人员少而精、承认不断改进软件工程实践的必要性。考试偶尔点名，认得即可。软件工程的三要素是**方法、工具、过程**，"过程"就是第二节要讲的节奏。

七个阶段用报销系统对照着看。教材有两套口径，软件生存周期七阶段和信息系统五阶段，考试都会用，对齐在一张表里：

| 软件生存周期（七阶段） | 信息系统口径（五阶段） | 回答什么 | 报销系统里是什么 | 产出 |
|---|---|---|---|---|
| 可行性分析与项目开发计划 | 系统规划 | 值不值得做，花多少钱多久 | 评估搬线上能省多少人力 | 可行性研究报告、系统设计任务书 |
| 需求分析 | 系统分析（逻辑设计） | **做什么** | 谁能提单、谁审批、超额怎么办 | 软件需求规格说明书；信息系统口径叫系统说明书 |
| 概要设计 | 系统设计（物理设计）之总体设计 | **怎么做**：分几个模块、模块间接口 | 提单模块、审批模块、报表模块 | 概要设计说明书 |
| 详细设计 | 系统设计之详细设计 | 每个模块内部的算法和数据结构 | 审批流转的状态机怎么写 | 详细设计说明书 |
| 编码 | 系统实施 | 翻译成代码 | 把状态机写成代码 | 源程序 |
| 测试 | 系统实施 | **找错**，不是证明没错 | 拿去年 200 张真单跑一遍 | 测试报告；信息系统口径还有实施进展报告、系统测试分析报告 |
| 维护 | 系统运行和维护 | 上线后修错、适配、增强 | 每年报销政策一变就要改 | |

信息系统口径先把一辈子粗分成**立项、开发、运维、消亡**四大阶段，再细分成表里的五个。几个词先说清。系统规划做的是对组织现状的**初步调查**；系统分析做的是对现行系统的**详细调查**，产出**逻辑模型**，也就是"报销单经过谁、按什么规则流转"，不管用什么数据库，所以又叫逻辑设计阶段。教材说它是整个建设的关键，也是信息系统建设与一般工程项目的重要区别所在，因为这一步定错，后面设计和代码全白做。系统设计阶段把逻辑模型落成**物理模型**，即落到 MySQL 表和接口上的技术方案，所以又叫物理设计阶段。系统实施阶段的任务是设备购置安装调试、程序编写调试、人员培训、数据文件转换、系统调试与转换，特点是多项任务同时展开，要精心安排。两套口径的分水岭是同一条：**分析回答"做什么"，设计回答"怎么做"**。维护是持续最久、花钱最多的阶段：开发花半年，系统用十年就改十年。

还有一处考试口径要记：培训资料收了一道题，问"系统分析阶段结束后得到的工作产品"，答案是**系统方案建议书**。它不是系统说明书的别名，而是另一套方法（Whitten 的 FAST）里分析阶段结束时向管理层提交的候选方案建议；做题用阶段归属排除，其余选项都不属于分析阶段。同一道题问"系统测试完成后的工作产品"答**操作手册**，因为其他选项（验收测试计划、测试标准、系统测试计划）都是测试前就该定好的。

### 二、按什么节奏走：过程模型

阶段定了，报销系统你打算怎么走？最自然的想法：先把需求谈清，设计好，写完，测完，上线，一步不回头。这就是**瀑布模型**。它靠**文档驱动**：下一阶段的人只看上一阶段的文档干活，不问人。培训资料把它写成四条：从上一项活动接受成果作为输入、完成本项活动、把成果作为输出传给下一项、对成果评审通过才往下走，否则退回前面。这样做是为了尽量减少阶段间的反复，用较小的费用开发；教材的阶段划分里编码含单元测试。它适合**需求明确、稳定**的项目。

先想一下，瀑布走报销系统会栽在哪？四个地方：

- ① 老板一开始就说不清要什么，"搬到线上"三个字签不了需求文档；
- ② 老板到最后才第一次看见系统，说"这不是我要的"；
- ③ 报销政策中途改了，整条线返工；
- ④ 测试用例等到代码写完才开始想，来不及。

后面每一个模型，都是在补其中一条。

**原型化模型补①。** 老板说不清，那就先花三天造一个能点的原型给他看，他一点就知道自己要什么了。原型必须实际可行、有最终系统的基本特征（不然看不出问题），又要构造方便快速造价低（不然扔不起）。它对需求是动态响应、逐步纳入的。用报销系统看原型的两种分法。按是否实现功能分：三个页面能点跳转但不存数据，叫**水平原型**（行为原型，只做导航）；只把"提单"这一条线从页面做通到数据库，叫**垂直原型**（结构化原型，实现部分功能）。按最终结果分：拖拽工具画的原型用完扔掉重写，叫**抛弃式**；用正式框架搭的原型直接长成产品，叫**演化式**。

**增量模型补②，也补原型的一个不足：原型只能看不能用。** 报销系统先上线"提单 + 审批"两个核心模块，员工真的开始用；下个月再加"报表"，再下个月加"打款对接"。每次交一部分，**优先级最高的服务最先交付**，而且**每个增量都是可独立运行的作品**，这是它和原型的本质区别。缺点：不是从整体规划各模块，**不利于模块划分**。报销系统里的表现是，报表模块要从审批记录取数，可审批表当初没留那个字段，模块边界和接口没从整体定过，得回头改已经上线的部分。难点就在怎么把需求切成增量。

**螺旋模型补③，同时管住原型和增量都不管的一件事：风险。** 报销系统太小，用不上它，换成把公司的 ERP 整个换掉：每转一圈先问"这一圈最可能翻车的是什么"，比如老数据迁不出来，先做实验验证再投钱。它把原型的迭代和瀑布的系统化结合起来，开发是一系列增量发布，每圈四件事：**制订计划、风险分析、实施工程（就是写和测）、客户评估**。它**强调风险分析，特别适用于庞大复杂、高风险的系统**；代价是每圈都要做风险分析，依赖有经验的人，成本高，小项目不划算。

**V 模型补④。** 先说清四种测试：**单元测试**测一个函数或模块，**集成测试**测模块拼起来接口对不对，**系统测试**测整个系统是否满足需求，**验收测试**由用户按自己的业务确认能不能用。V 模型不改瀑布的节奏，只把测试分成四级，和左边的开发阶段一一对应：**单元测试针对编码，集成测试针对详细设计，系统测试针对概要设计，验收测试针对用户需求**。好处是各级测试的计划和用例可以在对应阶段就准备：报销系统写"谁能审批"这条需求时就定验收用例，定三个模块时就定系统测试用例。注意它补的只是测试**准备**太晚，测试的**执行**仍在最后，"测试介入晚"仍是它公认的短板，本质还是线性的，同样用于需求明确、变更不频繁的项目。另一套常见说法讲的是测试**依据哪份文档**：单元测试依据详细设计说明书、集成测试依据概要设计说明书、系统测试依据需求规格说明书，讲义 17 展开；题目问"针对哪个阶段"用前者，问"依据什么文档"用后者。

收口：四条短板对四个模型。选型题就是从题干读出这个项目最怕哪一条：怕需求定不下来选原型，怕看不到东西选增量，怕变化和风险选螺旋，怕测试没准备选 V，需求本来就定了选瀑布。

另外三个模型不在这条链上，认得即可。**喷泉模型**是面向对象专用的，教材原话是"以用户需求为动力，以对象作为驱动"（面向对象第三节细讲，先记一句：分析、设计、编码全程用"对象"这一套概念）。因为表示法不换，各阶段可以边写边细化、互相交叠，所以说它迭代、**无间隙**，像喷泉的水落回再涌上。**基于构件的开发模型 CBSD**：审批流不自己写，买一个现成的工作流引擎拼上去，这种预先包装好、可以拿来拼装的软件单元叫构件，自研或商品化都行；特点是复用性强，构件库供其他系统复用。**形式化方法模型**：把"超过 5000 元必须二级审批"写成数学规则，再证明代码满足它，建立在严格数学基础上，主要活动是生成形式化的数学规格说明，航天核电才用。

### 三、再往上一层：开发方法

过程模型说的是节奏，**开发方法**说的是分析和设计用什么思路。两者是正交的：同样走瀑布，设计阶段可以画数据流图、把系统拆成模块，这是结构化；也可以画类图、找对象，这是面向对象。节奏没变，思路变了。敏捷和 RUP 是"节奏 + 思路"打包的完整方法论，所以两边都沾，培训资料把它们放在开发方法里。

**结构化方法**看报销系统怎么做：把"报销"拆成提单、审批、打款三块，每块再往下拆，拆到一个函数能写完为止，这叫**自顶向下、逐步求精、模块化**；分析时盯的是单子怎么流（画数据流图，讲义 21），不盯单子长什么样，所以后来报销单要加附件字段时改得很痛，这就是它**很少考虑数据结构**的意思。它由结构化分析 SA、结构化设计 SD、结构化程序设计 SP 组成，因为严格按生存周期一个阶段一个阶段走，又叫生命周期法。四个特点：开发目标清晰化（用户第一）、开发工作阶段化（每阶段审查）、开发文档规范化、设计方法结构化（分析设计自顶向下分解，实现时自底向上一块块拼）。三个不足：**开发周期长**（要走完全部阶段用户才能用）、**难以适应需求变化**、**很少考虑数据结构**。常用工具：数据流图、数据字典、结构化语言、判定表、判定树。

**面向对象方法**换一个视角：报销单、员工、审批人各是一个对象，自己带着数据和动作，系统是这些对象互相发消息组合起来的。分析阶段先找**用例**，即用户能做的一件事，比如"员工提交报销单"，再从用例里找对象画类图。它的特点，每条都有原因：**复用性更好**，因为"审批人"这个类可以原样搬到采购系统去，关键是建立统一的用例模型和分析模型；分析、设计、实现三个阶段之间**没有缝隙**，因为从头到尾用的都是"对象/类"这一套概念，分析画的类到设计还是那些类只是补细，前一阶段没做细后一阶段可以补；普遍适用于各类系统。不足按原文三条：必须依靠一定的面向对象技术支持；**在大型项目的开发上具有一定的局限性**；**不能涉足系统分析以前的环节**，因为它只回答"有哪些对象"，答不了"这个系统值不值得做"。第二条和考题"结构化比面向对象更适合大规模复杂项目"判错并不矛盾：那道题比的是相对谁，面向对象比结构化更能对付复杂系统；这一条说的是它自身在大型项目上也不够，所以大型系统常常**先用结构化方法自顶向下整体划分，再自底向上用面向对象开发**，两者相互依存。讲义 23、24 展开。

**原型化方法**和第二节的原型化模型要分开：模型说的是整个项目以"造原型、改、再造"为主循环；方法说的是需求分析这一步用"造个东西给你点"代替"写文档问你"，任何节奏里都能用，报销系统走瀑布，需求分析那一格照样可以用原型化方法。它以用户为中心，优点是周期短、成本和风险低、用户容易理解和接受。不足：**对开发环境要求高**，得有能快速搭页面的工具；**对管理水平要求高**，不管住会无限改下去。流程五步：确定用户基本需求、设计系统初始原型、试用和评价原型、不满意就修改完善再试用、满意后整理原型并提供文档。它**不是完整的方法论体系**，只回答"需求怎么问清"，不回答怎么设计怎么写，所以必须和其他方法结合使用。适合**需求不明确、分析层面难度大而技术层面难度不大**的系统，报销系统正是这种。

**敏捷开发**针对的是瀑布和 RUP 共同的毛病：文档和计划先行，太重。敏捷以人为核心、迭代、循序渐进，强调团队与业务专家紧密协作、面对面沟通胜过文档、频繁交付、拥抱变化。报销系统用敏捷：第一周先上能提单的版本，老板用一周提意见，第二周改，如此往复。敏捷宣言四句：**个体和交互胜过过程和工具；可以工作的软件胜过面面俱到的文档；客户合作胜过合同谈判；响应变化胜过遵循计划**。敏捷是一个家族，考试让你从描述认出是哪一个：

| 方法 | 它最在意什么 | 认它的关键词 |
|---|---|---|
| 极限编程 XP | 代码质量和反馈速度 | 四个价值观**沟通、简明、反馈、勇气**；**测试先行**（先写测试再写代码）；初期不写很多文档；实践有结对编程、小型发布、持续集成、现场客户（用户坐在团队里随时问）等 |
| 并列争球法 Scrum | 管理节奏 | **30 天一次迭代叫"冲刺"**（实际 1–4 周都有，认"固定长度迭代"即可），按需求优先级实现，多个**自组织**小组并行递增；三角色是产品负责人、Scrum Master、开发团队 |
| 自适应开发 ASD | 组织的适应性 | 不给具体实践，从组织和管理层面讲开发为什么要**适应** |
| 水晶方法 Crystal | 团队规模决定流程轻重 | **每个不同的项目需要一套不同的策略、约定和方法论** |
| 特性驱动开发 FDD | 中小项目快速出活 | 针对**中小型项目**、模型驱动的快速迭代，适合需求经常变动 |

培训资料还把**结对编程**单列：一人写、一人在旁审查代码，共同对代码负责。它本质是 XP 的一项实践，考题问"XP 的价值观"时它是干扰项。

**统一过程 RUP** 是给面向对象配的完整流程：面向对象方法只说了找对象画类图，没说整个项目怎么安排，RUP 补上这一块，它是在开发组织中**分派任务和责任的纪律化方法**，目标是在可预见的日程和预算内交付高质量产品。三个显著特点：**用例驱动**，拿"员工提交报销单"这类用例来排任务、验收；**以体系结构为中心**，先把骨架搭起来；**迭代和增量**。四个阶段，每阶段结束有技术评审和一个里程碑，里程碑是阶段末的检查点，名字就是这一段要达到的目标：

| 阶段 | 报销系统里干什么 | 里程碑 |
|---|---|---|
| 初始 Inception | 定范围、算值不值得做 | 生命周期目标 |
| 细化 Elaboration | 搭骨架跑通：分几层、用什么框架、模块怎么通信，这就是**建立体系结构基线**；这一阶段的目标还有分析问题域、编制项目计划、淘汰最高风险的元素 | 生命周期体系结构 |
| 构建 Construction | 往骨架上挂功能、集成、测试 | 初始运作能力 |
| 交付 Transition | 移交用户、beta 测试、培训 | 产品发布 |

它是一个**通用过程框架**，可用于各种领域、组织和规模的项目。"体系结构基线在细化阶段建立"是本考点出题率最高的一句。

能力成熟度模型 CMM/CMMI 在培训资料里和本章放在一起，本讲义体系放在讲义 20。先记一句：CMM 五级是"初始、可重复、已定义、已管理、优化"，CMMI 阶段式五级是"初始、已管理、已定义、定量管理、优化"，没有"可重复级"，两套名字的差别是常考点，讲义 20 再分。

## 考试怎么考

**考点① 给场景选模型。** 先问题干里的项目最怕哪一条晚，再对名字：

| 题干说 | 最怕什么 | 选 |
|---|---|---|
| 功能有清晰定义、需求明确稳定、交付时间严格 | 什么都不怕，按部就班 | 瀑布 |
| 用户说不清需求、先做雏形试用 | 需求定不下来 | 原型 |
| 核心功能先交付、分批追加 | 看不到能用的东西 | 增量 |
| 规模庞大、风险高、每阶段先评估风险 | 变化和风险晚爆 | 螺旋 |
| 开发与测试对称、测试尽早准备 | 测试设计太晚 | V 模型 |
| 面向对象、阶段无明显界限、迭代无缝 | | 喷泉 |
| 用例驱动、以体系结构为中心、迭代增量 | | RUP |
| 固定长度冲刺、自组织小组、按优先级 | | Scrum |

容易混的一对是原型和螺旋：螺旋里也有原型思想，只有出现"风险分析、风险驱动"才选螺旋，题干不提风险就选原型。

**考点② "以下叙述不正确的是"。** 四个选项三个抄定义、一个反着写。错项只有三种造法：把弱点反写成优点（"螺旋成本低适合小项目"）、把适用场景写反（"原型适用于需求明确的项目"）、张冠李戴（把"风险驱动"安到增量头上，把"无缝迭代"安到 V 模型头上）。认出造法就不用逐字比对。

**考点③ 阶段归属与产出物。** "编写需求规格说明书"是需求分析；"划分模块、定接口"是概要设计，"模块内部算法"是详细设计，这一对最常互换设错；"系统分析阶段结束的产品"答系统方案建议书，"系统测试完成后的产品"答操作手册（第一节末尾说过原因）；"成本最高的阶段"是维护，不是编码。

**考点④ RUP。** 三特点里混入的假选项常是"以文档为中心""瀑布式推进"；四阶段口诀"初细构交"，里程碑按"目标、架构、初始运作、发布"对上，架构基线在细化阶段。

**考点⑤ 开发方法的叙述判断。** 结构化方法"比面向对象更适合大规模特别复杂的项目"是错的；结构化"很少考虑数据结构""自顶向下逐层分解"是对的；原型法"是一种完整的方法论"是错的；敏捷家族按上面那张表认名字，XP 的四个价值观是封闭清单，结对编程、持续集成是实践不是价值观；Scrum 只有三个角色，没有"项目经理"。

10.【模拟】某银行核心系统改造规模庞大、风险很高，要求每个阶段开始前先评估风险再决定是否继续投入。最适合的模型？

### 参考答案

1. **A**。"功能清晰"就是需求明确，瀑布的关键词。
2. **D**。螺旋恰恰适合大型高风险项目，D 把适用场景写反了。B 对，因为每圈有风险分析和客户评估，测多测少随风险调整；C 对，维护就是再转一圈。
3. **C**。结构化面向数据流、自顶向下，A、B、D 都对；更适合大型复杂项目的是面向对象方法。
4. **C**。固定长度冲刺、自组织小组是 Scrum 的标志；ASD 强调适应性，XP 强调四价值观和测试先行。
5. **B、D**。用阶段归属排除：系统设计规格说明属设计阶段，程序规格说明属详细设计或编码，单元测试数据属测试阶段，只剩系统方案建议书落在分析阶段。第二空同样排除：验收测试计划、测试标准、系统测试计划都是测试前就该定的，"完成后的工作产品"只能是操作手册。
6. **B**。"无法给出明确需求 + 构造雏形试用"是原型的定义原文，题干不提风险，不选螺旋。
7. **B**。体系结构基线四个字锁定细化阶段。
8. **C**。四价值观是沟通、简单性、反馈、勇气。
9. **B**。产品负责人管"做什么、先做什么"，Scrum Master 管流程，团队管"怎么做"，Scrum 没有项目经理。
10. **螺旋模型**。11. **敏捷（Scrum）**，冲刺 Sprint。12. ①需求分析 ②概要设计 ③详细设计。

## 速记

- 七阶段：可行性 → 需求 → 概要设计 → 详细设计 → 编码 → 测试 → 维护；分析定"做什么"（逻辑模型），设计定"怎么做"（物理模型）；维护最久最贵
- 瀑布四短板对四模型：需求说不清用原型、看不到东西用增量、怕变化和风险用螺旋、测试设计晚用 V；风险驱动等于螺旋，无缝迭代等于喷泉
- 螺旋四象限：制订计划 → 风险分析 → 实施工程 → 客户评估
- V 模型：单元针对编码、集成针对详细设计、系统针对概要设计、验收针对用户需求；问"依据哪份文档"则是单元依据详细设计说明书、集成依据概要设计说明书、系统依据需求规格说明书
- 增量每块可独立运行，原型只是演示；原型分抛弃式/演化式、水平/垂直
- 结构化：自顶向下逐步求精模块化；周期长、难适应变化、少考虑数据结构。面向对象：复用好、阶段无缝、更适合复杂系统；不能涉足分析之前
- 敏捷宣言四句；XP 沟通简明反馈勇气、测试先行；Scrum 固定冲刺三角色；水晶每项目一套方法；FDD 中小型；ASD 适应性
- RUP：用例驱动、以体系结构为中心、迭代增量；初细构交；细化定架构基线
