# 16 · 软件工程：系统分析与设计基础

## 定位

一句"把报销的 Excel 搬到线上"，怎么变成一份签了字的需求文档，再怎么定下系统形状、切成模块，切得好不好用什么尺子量。全程用"公司内部报销系统"一个例子。一至五节管"话"（需求：分层、问全、理顺、写死、守住），六至十节管"块"（设计：看清流程、定形状、切模块、量内聚耦合、做界面），中间隔着分析与设计的交界线。第九节内聚与耦合最重。只有采样样本量一处要动笔算。

---

## 一、需求的层次与分类

| 层次 | 谁说的 | 是什么（原话） | 报销系统里 |
|---|---|---|---|
| **业务需求** | 项目投资人、客户、市场营销部门或产品策划部门 | 企业或客户对系统**高层次的目标要求**；由它确定项目视图和范围 | "每月省两个财务人力" |
| **用户需求** | 具体使用的人（访谈、问卷整理场景） | **用户的具体目标，或用户要求系统必须能完成的任务**，即用户**能使用系统来做什么** | "一次导出本月已审批单子" |
| **系统需求** | 分析人员写给开发 | 从**系统的角度**说明软件的需求 | 见下表 |

| 系统需求三类 | 原话 | 报销系统里 |
|---|---|---|
| **功能需求**（行为需求） | **规定了开发人员必须在系统中实现的软件功能** | 金额超 5000 元自动转二级审批 |
| **非功能需求** | **系统必须具备的属性或品质**，分软件质量属性（可维护性、可靠性、效率等）和其他非功能需求 | 导出接口响应不超过 3 秒 |
| **设计约束**（限制条件、补充规约） | **对系统的一些约束说明**，如必须采用国有自主知识产权的数据库、必须运行在 UNIX 下 | 必须接公司现有单点登录 |

**易混对 用户需求 vs 功能需求**
- 判据｜这句话细到能直接写出一条测试用例吗？能 → 功能需求；还停在"用户想干成什么事" → 用户需求。说不出具体动作的目标 → 业务需求。
- 例子｜"我要能一次导出本月已审批的单子"是用户需求；"导出时按审批日期筛选当月、状态为已审批的单据生成 xlsx"是功能需求。

**QFD（质量功能部署）**：**一种将用户要求转化成软件需求的技术**，目的是最大限度提升用户满意度。按"实现了会有什么反应"分三类：

| 类 | 特征 | 例子 |
|---|---|---|
| **常规需求** | 用户认为**系统应该做到的功能或性能**，实现越多越满意 | 能提单、能审批 |
| **期望需求** | 用户**想当然认为系统应具备**、但**并不能正确描述**；做不到就不满意 | 当然能查去年的单子 |
| **意外需求**（兴奋需求） | **用户要求范围外的功能或性能**，实现了更高兴，不实现不影响购买决策 | 提单自动 OCR 识别发票金额 |

原话｜**软件需求**是用户对系统在功能、行为、性能、设计约束等方面的期望，是**用户解决问题或达到目标所需的条件或能力**，是系统或系统部件要满足合同、标准、规范或其他正式规定文档所需具有的条件或能力，以及反映这些条件或能力的文档说明。

需求工程以**需求基线**为界分两大过程——基线前叫开发（把需求做出来），基线后叫管理（守住、追踪）：

```
需求开发 ──→ 需求获取 → 需求分析 → 需求定义（SRS）→ 需求验证
                                                      ↓
                                              【需求基线】
                                                      ↓
需求管理 ──→ 变更控制 → 版本控制 → 需求跟踪 → 需求状态跟踪
```

用户签字认下的那一版需求才是基线，之后要改必须走变更流程。

## 二、需求获取

原话｜**需求获取是一个确定和理解不同的项目干系人的需求和约束的过程**。干系人＝与系统有利害关系的所有人（员工、主管、财务、运维），只问老板必然漏。

| 方法 | 特征 | 软肋 |
|---|---|---|
| **用户访谈** | 1 对 1-3，有代表性的用户；分结构化和非结构化 | **灵活性好、应用范围宽，但信息量大、记录困难、需要足够的领域知识** |
| **问卷调查** | 用户多、无法一一访谈 | 问不出没想到的东西 |
| **采样** | 从种群中**系统地选出有代表性的样本集**；基于数理统计，能减少数据收集偏差 | 样本选偏就全偏 |
| **情节串联板** | 一系列图片，**通过图片讲故事** | 只能表达流程，说不清规则 |
| **联合需求计划 JRP** | 关键用户代表、系统分析师、开发团队代表**通过有组织的会议**讨论需求 | 组织成本高 |
| **需求记录技术** | 任务卡片、场景说明、用户故事、Volere 白卡 | 只是记录形式，不负责问 |

**采样样本量（计算）**：样本数量 = 0.25 ×（可信度因子 / 错误率）²
1. 可信度因子 1.96、错误率 10%：0.25 × (1.96/0.10)² = 0.25 × 384.16 = **96.04**
2. 错误率收紧到 5%：0.25 × (1.96/0.05)² = **384.16**

错误率在分母且被平方，所以错误率减半，样本量涨四倍。

## 三、需求分析

原话｜**需求分析就是分析人员把杂乱无章的用户要求和期望转化为用户需求**：把获取来的原话理成彼此不打架、没有缺口的规范条目。

好需求八性：**无二义性、完整性、一致性、可测试性、确定性、可跟踪性、正确性、必要性**。"报销单要能改"同时违反无二义性（谁改）和可测试性（怎么验收）。

需求分析七项任务：① **绘制系统上下文范围关系图**（先钉死系统边界，圈外是员工、主管、财务、银行）；② **创建用户界面原型**；③ **分析需求的可行性**；④ **确定需求的优先级**；⑤ **为需求建立模型**；⑥ **创建数据字典**；⑦ **使用 QFD**。

**结构化需求分析**：**自顶向下，逐步分解，面向数据**（先把"报销"当一个大加工，再拆成提单、审批、打款；盯数据怎么流）。三大模型加一本字典（画法见 21 与 49）：

| 要回答的问题 | 用什么 | 要点 | 报销系统里 |
|---|---|---|---|
| 数据怎么传送、变换（功能） | **功能模型＝数据流图 DFD** | 原话：**描述数据在系统中如何被传送或变换，以及如何对数据流进行变换的功能或子功能，用于对功能建模**。四种元素：**数据流**（箭头）、**加工**（圆或圆角框）、**数据存储**（双横线，或右边开口的矩形）、**外部实体**（方框，**存在于软件系统外的人员或组织**）。可分层，**顶层只含一个加工表示整个系统** | 员工、主管、银行是外部实体；报销单是数据流；报销单库是数据存储 |
| 处于什么状态、什么事件让它跳转（行为） | **行为模型＝状态转换图 STD** | 标出**初态和终态** | 草稿→待审→已审→已打款，事件"提交""驳回""打款成功" |
| 存哪些东西、几对几（数据） | **数据模型＝E-R 图** | **实体**和**联系** | 员工、报销单、审批记录；一个员工提多张单 |
| 每条数据由什么组成 | **数据字典** | 原话：**为数据流图中的每个数据流、文件、加工，以及组成数据流或文件的数据项做出说明** | 字典写清"报销单"由哪些字段组成 |

## 四、需求定义与需求验证

**需求定义的产物是软件需求规格说明书 SRS**。原话｜**编制该文档的目的是使项目干系人与开发团队对系统的初始规定有一个共同的理解，使之成为整个开发工作的基础**；**对于任何规模和性质的软件项目都不应该缺少**。（有的资料印成"SAS"，是讹字，按 SRS 认。）

| 定义方法 | 前提 / 特点 |
|---|---|
| **严格定义**（预先定义） | 三条假设：**所有需求都能够被预先定义**；开发人员与用户之间能准确清晰地交流；图形（或文字）可以充分体现最终系统 |
| **原型方法** | **迭代的循环型开发方式**；承认**并非所有需求都能在开发前被准确说明**、干系人间存在交流困难，**原型提供了克服该困难的手段**。需要可供用户参与的系统模型、合适的开发环境；**反复是完全需要和值得提倡的，需求一旦确定，就应遵从严格的方法** |

**需求验证**（需求确认）：**目的是与用户一起确认需求无误**，对 SRS 评审和测试。两步：**需求评审**（正式、非正式）和**需求测试**（设计概念测试用例——用假想业务场景"跑"文档，不跑代码）。

原话｜**验证通过后请用户签字确认，作为验收标准之一，此时这个需求规格说明书就是需求基线，不可以再随意更新，如果需要更改必须走需求变更流程。**

需求开发四阶段是获取、分析、定义、验证；形成基线、跟踪变更、控制版本都属于需求管理。

## 五、需求管理

管四件事：**变更控制**（怎么改）、**版本控制**（每版 SRS 编号存档，说得清用哪版、上版改了什么）、**需求状态跟踪**（改到哪一步）、**需求跟踪**（能否追回去）。

**需求属性**：状态、优先级、稳定性、来源、负责人等（稳定性也是需求属性）。

**需求状态**：被建议 →（通过评审）→ 被批准 →（设计完成/编码完成/通过单元测试）→ 被实现 →（通过集成测试）→ **被验证** →（通过用户验收）→ 被交付；没通过评审 → **被拒绝**；被批准或被实现之后取消 → **被丢弃**。

**变更控制**
- 变更原因四条：外部环境的变化、需求和设计做得不够完整、新技术的出现、公司机构重组造成业务流程变化。
- 原话｜**变更控制委员会 CCB（配置控制委员会），其任务是对建议的配置项变更做出评价、审批，以及监督已经批准变更的实施**。
- 流程七步：变更请求 → PM 和团队评估影响 → 将评估结果通知干系人（客户）→ CCB 审批 →（同意）执行变更 → 记录变更实施情况 → 分发新文档；不同意则取消。**评估影响在 CCB 审批之前**——先算清代价再送审。教材另一写法的前两步：**问题分析和变更描述 → 变更分析和成本计算**，次序同样不能对调。
- 七种带风险的做法：**无足够用户参与、忽略了用户分类、用户需求的不断增加（需求蔓延，最常见）、模棱两可的需求、不必要的特性、过于精简的 SRS、不准确的估算**。

**需求跟踪**：双向、两层——用户原始需求 ↔ 软件需求 ↔ 下游工作产品（设计、代码、测试用例）。**正向跟踪：用户原始需求是否都实现了；反向跟踪：软件实现的是否都是用户要求的**。

需求跟踪矩阵（行＝原始需求，列＝用例）：

| | UC-1 提单 | UC-2 一级审批 | UC-3 二级审批 | UC-4 导出 | UC-5 短信通知 |
|---|---|---|---|---|---|
| FR-1 员工能提单 | ✓ | | | | |
| FR-2 超 5000 走二级 | | ✓ | ✓ | | |
| FR-3 能查历史单据 | | | | | |
| FR-4 财务能导出 | | | | ✓ | |

原话｜**若某行都没有对号，表明原始需求未实现，正向跟踪发现问题；若某列都没有对号，表明有多余功能用例，软件实现了多余功能，反向跟踪发现问题。** FR-3 空行＝没做查历史；UC-5 空列＝开发自己加的短信通知。**空行漏做，空列多做。**

---

**分析与设计的交界**：分析阶段交出去的是一份文档，不是技术方案。四步：

1. 理解现实环境，**获得当前系统的"物理模型"**（财务现在怎么用 Excel、纸单子怎么传）；
2. **抽象出当前系统的"逻辑模型"**（扔掉 Excel、纸、跑腿，只留谁提、谁审、按什么规则）；
3. 分析优化，**建立目标系统的"逻辑模型"**；
4. 具体化（物理化），**建立目标系统的物理模型**（MySQL 表、Java 服务、页面）——即后五节的设计。

原话｜**系统开发的目的是把现有系统的物理模型转化为目标系统的物理模型，而系统分析阶段的结果是得到目标系统的逻辑模型。逻辑模型反映了系统的功能和性质，而物理模型反映的是系统的某一种具体实现方案。**

## 六、处理流程设计

线下流程原样搬上线，慢还是那么慢，所以先画出流程、看明白再决定改不改。注意两层：**业务流程建模**画企业业务流程（单子在部门间怎么传），**流程表示工具**画程序内部流程（顺序、选择、循环）。

**流程表示工具**

| 工具 | 是什么 | 长处 | 短处 / 要点 |
|---|---|---|---|
| **程序流程图 PFD** | 用图框表示各种操作 | **独立于任何一种程序设计语言**，直观清晰、易于学习 | **任何复杂的程序流程图都应该由顺序、选择和循环结构组合或嵌套而成** |
| **IPO 图** | 描述**每个模块的输入、输出和数据加工** | 一眼看清模块吃什么、吐什么 | 只到模块级，不画整体控制流；仍属流程设计工具 |
| **N-S 图** | 盒图，嵌套方框 | **容易表示嵌套和层次关系，并具有强烈的结构化特征** | **问题很复杂时 N-S 图可能很大，因此不适合复杂程序的设计** |
| **问题分析图 PAD** | 支持**结构化程序设计**的图形工具（不是原型化方法） | 清晰的逻辑结构、标准化的图形，**引导设计人员使用结构化程序设计方法，从而提高程序的质量** | — |

**易混对 BPM vs BPR**
- 判据｜要不要推倒重来：**BPR** 是**对业务流程进行根本性的再思考和彻底性的再设计**；**BPM 并不要求对所有的流程进行再造**，而是**根据现有流程的具体情况，对流程进行规范化的设计**。
- 例子｜把报销审批的三个章原样搬到线上、只规范节点和时限 → BPM 的规范流程层面；取消纸单和逐级盖章、改成超限自动路由 → BPR。

| 概念 | 原话 |
|---|---|
| **BPM 业务流程管理** | **以规范化的构造端到端的卓越业务流程为中心，以持续的提高组织业务绩效为目的的系统化方法**；三个层面：**规范流程、优化流程、再造流程** |
| **BPR 业务流程重组** | 根本性再思考、彻底性再设计，获得可以用成本、质量、服务和速度等衡量的显著性成就；三原则：**以流程为中心、团队管理（以人为本）、以客户为导向** |

**业务流程建模方法**，其余认名即可：**标杆瞄准**（以行业标杆企业为目标结合本企业分析建模）、**IDEF**（一系列建模、分析和仿真方法的统称）、**DEMO**（组织动态本质建模法）、**Petri 网**（库所—变迁—令牌，数学化图形模型，适合仿真并发流程，如两个审批人并行审）、**BPEL、BPML、BPMN、XPDL**（把流程写成机器可读格式交流程引擎，BPMN 是给人看的图形标记法）、**基于服务的 BPM**（基于 Web 服务思想建模）。

IDEF 编号（0–14 外加 1X）：**IDEF0 业务流程（功能）建模、IDEF1X 数据建模（如 ER 模型）、IDEF2 仿真建模设计、IDEF4 面向对象设计、IDEF8 用户界面建模、IDEF12 组织结构建模**；记"0 功能、1X 数据、4 对象、8 界面"。

## 七、软件体系结构风格

风格只管两样：**构件**（可独立换掉的处理单元：过滤器、服务、类）和**连接件**（构件间怎么搭话：管道、过程调用、广播事件、共享数据区）。**一种风格＝一套固定搭法：构件长什么样、连接件用哪种、彼此守什么约束。** 按"构件怎么连"分五大类，判类看连接件：

| 大类 | 连接特征 | 具体风格 | 报销系统里 |
|---|---|---|---|
| **数据流** | 数据一路往前流，构件只做变换，不关心下游是谁 | **批处理序列**（整批做完一步再交下一步）、**管道-过滤器**（边读边吐） | 月末结账：读单据→剔作废→按部门汇总→生成凭证→导出 |
| **调用/返回** | 谁调谁明确，调完等返回 | **主程序-子程序**、**面向对象**、**层次结构**（每层只用下一层） | 提单调审批、审批调打款 |
| **独立构件** | 互不点名，只发/收事件 | **进程通信**（显式发消息）、**事件驱动系统**（**隐式调用**，发布方不知谁在听） | 单据变状态就广播，短信、报表、审计各自订阅 |
| **虚拟机** | 造一台读得懂规则的"机器"再喂规则 | **解释器**、**基于规则的系统** | 审批规则写成规则表交规则引擎解释执行 |
| **仓库** | 中间一个大数据区，构件围着它读写 | **数据库系统**、**超文本系统**、**黑板系统** | 报销单库居中，财务、风控、报表各自加分析 |

**易混对 黑板 vs 数据库（同属仓库）**
- 判据｜下一步谁动手由什么决定：黑板由**板上当前状态**决定，数据库由**调用顺序**决定。黑板用于**没有确定算法、只能让多个知识源轮流试探**的场合（语音识别、信号处理、专家系统）。
- 例子｜几个识别模块轮流往公共区写候选音节、词、句，谁接手看当前结果 → 黑板；财务、报表按业务调用去读写报销单库 → 数据库。

**管道-过滤器**：过滤器高内聚低耦合、可任意重接（支持复用）、各段可并行；**不适合交互式应用**。

**易混对 C/S vs B/S**
- 判据｜客户端要不要专门装程序：要 → C/S；只要浏览器 → B/S。
- 例子｜财务装一个专用对账客户端直连数据库 → C/S；员工用浏览器打开报销页 → B/S。

| 形态 | 优点 | 代价 |
|---|---|---|
| **C/S** | 用本机算力、界面快、交互强 | **每台机器都要装要升级**、跨平台差、客户端直连数据库有安全隐患 |
| **B/S** | **零安装、升级只改服务器、跨平台** | 交互与展现弱、吃网络、服务器压力大 |
| **三层架构** | **表示层 / 功能层（业务逻辑层）/ 数据层**，分别部署升级，规则一改只动中间层 | — |

**B/S 本质上是三层结构的一种实现**：浏览器＝表示层，Web 服务器＝功能层，数据库＝数据层。

## 八、系统设计

原话｜**系统设计的主要目的是为系统制定蓝图，在各种技术和实施方法中权衡利弊，精心选择，合理地使用各种资源，最终勾画出新系统的详细设计方法**。方法有**结构化设计方法、面向对象设计方法**（后者归面向对象板块）。

**易混对 概要设计 vs 详细设计**
- 判据｜**模块之间的接口在概要设计定，模块内部的算法和数据结构在详细设计定。**
- 例子｜"分提单、审批、报表、打款四个模块，提单调审批"→ 概要；"审批状态机怎么写、报销单表建几个索引"→ 详细。

| 阶段 | 原话 |
|---|---|
| **概要设计**（系统总体结构设计） | **将系统的功能需求分配给软件模块，确定每个模块的功能和调用关系，形成软件的模块结构图，即系统结构图** |
| **详细设计** | **模块内详细算法设计、模块内数据结构设计、数据库的物理设计、其他设计（代码、输入/输出格式、用户界面）**，编写详细设计说明书、评审 |

**系统设计基本原理**四条：**抽象化；自顶而下，逐步求精；信息隐蔽**（内部数据和实现不外露，只留接口）**；模块独立（高内聚，低耦合）**。

**系统设计原则**（也叫启发式设计原则、启发式规则）六条：
1. **保持模块的大小适中**——切太碎接口数量暴涨。
2. **尽可能减少调用的深度**。
3. **多扇入，少扇出**——**扇出**＝直接调用的下级模块数，**扇入**＝调用它的上级模块数。扇出太大 → 加一层中间控制模块把下级分组；**扇出太小 → 把下级模块再往下分解**；**扇入大＝被复用多，是好事**。
4. **单入口，单出口**。
5. **模块的作用域应该在模块之内**——标准表述是"**模块的作用范围（作用域）应该在其控制范围（控制域）之内**"。**控制范围**＝模块本身加全部直接和间接下级；**作用范围**＝模块内某个判定影响到的全部模块。例：判断"是否超 5000"写在提单模块，却影响不归提单管的打款模块，作用范围超出控制范围，改法是把判断上移到共同上级。
6. **功能应该是可预测的**——同样输入得同样输出。

**子系统结构设计要考虑的问题**（四条，块里再怎么切）：每个子系统如何划分成多个模块；如何确定子系统之间、模块之间传送的数据及调用关系；如何评价并改进模块结构的质量；如何从数据流图导出模块结构图。**不含"采用何种数据结构和核心算法"**（那是详细设计）。

**模块四要素**：**输入和输出、处理功能**（把输入转换成输出的工作）是**外部特性**；**内部数据**（仅供本模块引用）、**程序代码**是**内部特性**。模块**可以组合、分解和更换**，**系统中任何一个处理功能都可以看成一个模块**；按功能具体化程度分**逻辑模块和物理模块**（概要设计里还没落到代码的"审批"框是逻辑模块，详细设计写成 `ApprovalService` 类是物理模块）。

**模块结构图**四条规矩：模块内部凝聚性要强、模块间联系要少；**只能有上下级调用，不能有同级横向联系**；**整个系统呈树状结构，不允许网状结构或交叉调用**（禁的是同级互调，公用模块被多个上级调用即扇入大不算违反）；所有模块严格分类编码并建立归档文件。**模块结构图主要关心模块的外部属性**（上下级、同级间的数据传递和调用关系），不关心内部。

其余认名即可：
- **子系统划分原则**（六条，横着切成几大块）：子系统相对独立；子系统间数据依赖尽量小；划分结果数据冗余较小；考虑今后管理发展需要；便于分阶段实现；考虑各类资源充分利用。
- **系统结构设计原则**（八条，切法好不好）：分解-协调；自顶向下；信息隐蔽、抽象；一致性；明确性；**模块间耦合尽可能小、内聚度尽可能高**；扇入扇出系数合理；模块规模适当。

## 九、内聚与耦合

**衡量模块独立程度的标准有两个：耦合性和内聚性。** 耦合看模块**之间**靠什么通信，越能绕过接口越糟（给报销单加个字段，审批、报表、打款全要改）；内聚看模块**内部**的东西凭什么待在一起，越接近同一个功能越好（`ReimbUtils` 里塞着格式化日期、发邮件、算个税）。目标：**高内聚、低耦合**。低耦合不是不许说话（提单必须调审批），而是改说话方式：传结构体改传必要的值、传开关改拆成两个方法，就是往低档挪。

### 耦合：七档，从最松（最好）到最紧（最差）

| 档 | 原话｜关键字 | 报销系统里 | 改动怎么波及 |
|---|---|---|---|
| 1 **无直接耦合** | **两个模块之间没有直接的关系，它们分别从属于不同模块的控制与调用，不传递任何信息**｜无直接关系 | `main` 分别调提单和月度报表，两者互不认识 | 不波及 |
| 2 **数据耦合** | **有调用关系，传递的是简单的数据值，相当于高级语言中的值传递**｜传数据值 | `校验金额(amount, limit)` | 只有这两个数含义变了才波及 |
| 3 **标记耦合** | **传递的是数据结构**｜传数据结构 | `校验金额(报销单 r)`，对方只用 `r.金额` | 报销单加字段，校验模块也要重编译 |
| 4 **控制耦合** | **传递的是控制变量，被调用模块通过该控制变量的值有选择的执行模块内的某一功能**｜控制变量选功能 | `导出(报销单 r, int mode)`，mode=1 导 Excel、2 导 PDF | 对方加一条分支，所有调用方都要改 |
| 5 **外部耦合** | **模块间通过软件之外的环境联合（如 I/O 将模块耦合到特定的设备、格式、通信协议上）**；另一常见表述：**一组模块都访问同一全局简单变量，而不是同一全局数据结构，且不通过参数表传递**｜软件外部环境 | 打印与归档模块按同一固定报文格式写同一台票据打印机 | 换打印机、改报文格式，两个一起改 |
| 6 **公共耦合** | **通过一个公共数据环境相互作用的那些模块的耦合**｜公共数据结构 | 五个模块直接读写全局"报销政策"结构体 | 谁改字段含义全体遭殃，还查不出是谁 |
| 7 **内容耦合** | **一个模块直接使用另一个模块的内部数据，或通过非正常入口转入另一个模块内部**｜模块内部关联 | 审批模块直接改提单模块私有变量 `_state`，或跳进提单模块中段 | **最恶劣，任何情况下都要消灭** |

**易混对 数据耦合 vs 标记耦合**
- 判据｜只看传过去的是什么，不看对方用了多少：传简单值 → 数据；传结构体 → 标记。
- 例子｜`校验金额(报销单 r)` 即使只用 `r.金额` 也是标记耦合；改成 `校验金额(r.金额, limit)` 就是数据耦合。

**易混对 外部耦合 vs 公共耦合**
- 判据｜共享的是不是一份数据结构：设备、格式、通信协议或全局**简单变量** → 外部；公共数据环境、全局**数据结构**、共享内存区、公共文件 → 公共。
- 例子｜几个模块共用全局变量 `int 当前月份` → 外部耦合；共用全局结构体"报销政策" → 公共耦合。

**多种耦合并存取最紧那一档**：`导出(报销单 r, int mode)` 同时有标记（r）和控制（mode），判控制耦合。

### 内聚：七档，从最差到最好

| 档 | 原话｜关键字 | 报销系统里 |
|---|---|---|
| 1 **偶然内聚** | **一个模块内的各处理元素之间没有任何联系**｜无直接关系 | `ReimbUtils`：格式化日期 + 发邮件 + 算个税 |
| 2 **逻辑内聚** | **执行若干个逻辑上相似的功能，通过参数确定该模块完成哪一个功能**｜逻辑相似、参数决定 | `处理单据(int 类型)`：1 新建、2 修改、3 作废 |
| 3 **时间内聚** | **把需要同时执行的动作组合在一起形成的模块**｜同时执行 | `系统启动()`：读配置、连库、预热缓存、开日志 |
| 4 **过程内聚** | **完成多个任务，这些任务必须按指定的过程执行**｜指定过程顺序 | `月末结账()`：锁定上月单据→生成凭证→通知财务，各步各自去库里读数 |
| 5 **通信内聚** | **所有处理元素都在同一个数据结构上操作，或者各处理使用相同的输入数据或者产生相同的输出数据**｜相同数据结构、相同输入输出 | 对同一张报销单表既统计本月总额又导出明细，两件事互不用对方结果 |
| 6 **顺序内聚** | **各处理元素都密切相关于同一功能且必须顺序执行，前一个功能元素的输出就是下一个功能元素的输入**｜输出即输入 | `生成月报()`：查出本月单据列表，直接作为汇总的输入 |
| 7 **功能内聚** | **最强的内聚，模块内的所有元素共同作用完成一个功能，缺一不可**｜缺一不可 | `计算个税(收入)` |

**易混对 时间内聚 vs 过程内聚**
- 判据｜次序能不能乱：能乱 → 时间（只因同一时刻）；不能乱 → 过程。
- 例子｜`系统启动()` 里先开日志还是先连库都能启动 → 时间；结账必须先锁单据再生成凭证 → 过程。

**易混对 过程 / 通信 / 顺序内聚**
- 判据｜过程＝**动作**按次序、数据不接力；顺序＝**数据**接力（前者输出即后者输入）；通信＝操作**同一份数据**、动作互不相干。
- 例子｜结账三步各自读库 → 过程；月报第一步返回值就是第二步入参 → 顺序；统计与导出都读同一张表、谁也不用谁的结果 → 通信。

**易混对 顺序内聚 vs 功能内聚**
- 判据｜拆不拆得开：几个功能元素接力、拆开各自成立 → 顺序；一件事、拆开不成立 → 功能。
- 例子｜"查单据列表 + 汇总成报表"拆开各能单用 → 顺序；`计算个税` 拆开哪半都不成立 → 功能。

**控制耦合的另一头往往是逻辑内聚模块**：要靠标志参数挑功能，说明被调模块把若干相似功能捆在了一起（`导出(r, mode)`：调用方与它是控制耦合，它自己是逻辑内聚）。

## 十、人机界面设计

三大黄金原则：

| 原则 | 立场 | 细则（加粗为原话要点） | 报销系统里 |
|---|---|---|---|
| **1. 置于用户控制之下** | 用户做主 | **以不强迫用户进入不必要的或不希望的动作的方式来定义交互方式**；提供灵活的交互；**允许用户交互可以被中断和撤销**；当技能级别增加时可以使交互流水化并允许定制交互；使用户隔离内部技术细节；设计应允许用户和屏幕上的对象直接交互 | 审批到一半能存草稿退出 |
| **2. 减少用户的记忆负担** | 要记的越少越好 | **减少对短期记忆的要求**；**建立有意义的缺省**；定义直觉性的捷径；**界面的视觉布局应该基于真实世界的隐喻**；以不断进展的方式揭示信息 | 默认填好申请人和当天日期，页面画成报销单的样子 |
| **3. 保持界面的一致性** | 别乱变 | 允许用户将当前任务放入有意义的语境；**在应用系列内保持一致性**；**如过去的交互模型已建立起了用户期望，除非有迫不得已的理由，不要改变它** | 所有页面"提交"都在右下角 |

归类看关键词：中断 / 撤销 / 定制 → 用户控制；缺省值 / 捷径 / 真实世界隐喻 → 减少记忆负担；应用系列内统一 → 一致性。"强迫用户""不允许撤销""每个模块自成一套风格"都违反原则。

## 速记

- 需求三层：业务（组织目标）→ 用户（能用系统做什么）→ 系统（功能／非功能／设计约束）；QFD：常规、期望、意外
- 以**需求基线**为界：开发＝获取→分析→定义(SRS)→验证；管理＝变更控制、版本控制、需求跟踪、需求状态跟踪；跟踪矩阵**空行漏做（正向）、空列多做（反向）**
- 获取六法：访谈（灵活但记录难）、问卷、采样（数理统计减偏差，量 = 0.25×(可信度因子/错误率)²）、情节串联板、JRP（有组织的群体会议）、需求记录技术
- 结构化分析：DFD 功能、STD 行为、E-R 数据 + 数据字典；分析得**逻辑模型**、设计得**物理模型**；BPR 根本性、以流程为中心，BPM 不要求全部再造
- 体系结构五类：数据流（批处理、管道-过滤器）｜调用返回（主程序-子程序、面向对象、层次）｜独立构件（进程通信、事件驱动＝隐式调用）｜虚拟机（解释器、基于规则）｜仓库（数据库、超文本、黑板）；C/S 装客户端、B/S 只要浏览器＝三层的一种实现
- 概要设计定模块与接口、产出模块结构图；详细设计定算法、数据结构、数据库物理设计；扇入大＝复用高、扇出大加中间层、作用范围 ⊆ 控制范围
- 耦合低→高：**无 数 标 控 外 公 内**；传值＝数据、传结构＝标记、传开关＝控制、绑设备格式协议或共享全局简单变量＝外部、共享公共数据环境＝公共、伸手改内部或非正常入口＝内容；并存取最紧
- 内聚低→高：**偶 逻 时 过 通 顺 功**；时间＝次序可乱、过程＝动作按次序、顺序＝数据接力、通信＝同一份数据、功能＝拆开不成立
