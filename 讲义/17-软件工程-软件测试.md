## 第 1 层 · 理解

### 一句话

> 输入空间是无限的，你的时间是有限的——软件测试整章都在回答同一个问题：**这有限的几十条用例，到底该往哪儿放，才最容易砸中 bug？**

### 痛点：你写完代码那一刻的真实处境

一个函数收一个 32 位整数参数。把所有输入都跑一遍？**40 多亿种取值**，穷举在工程上根本不可行。于是你只能挑几个值来测，接着就撞上一连串没底的问题：

- 挑 30 和挑 31 有区别吗？——**没有**，它们大概率走同一段代码、命中同一类错误，白挑一个。
- 那挑什么才有区别？——你隐约知道 `<` 写成 `<=`、循环多跑一次这类错**都在边界上**，可说不清该取哪几个数。
- 我写了 5 个用例全过了，能说"这段代码没问题"吗？——**不能**。这就是那句年年考的结论：**测试只能证明程序有错，不能证明程序无错**。
- 那到底写几个才算够？拍脑袋写 5 个和写 50 个，**没有任何量化标准**。

拍脑袋挑用例的结果是：**测了一堆等价的输入，真正的 bug 一个没碰到**。这一章就是把"拍脑袋"换成一套有依据的规则。

### 一条主线

```
输入空间无限，用例数量有限 —— 穷举不可行
   ↓ 所以核心问题只有一个：【挑哪些输入最值钱】
   ↓ 挑法按"设计用例时看不看代码"分成两条路
┌──────────────────────────────┬──────────────────────────────┐
│ 不看代码，只对着需求挑        │ 打开代码，对着逻辑结构挑      │
│ = 黑盒测试（功能测试）        │ = 白盒测试（结构测试）        │
│ 依据：需求规格说明            │ 依据：源代码 / 流程图         │
└──────────────────────────────┴──────────────────────────────┘
        ↓                                   ↓
黑盒问：输入域怎么切最省？          白盒问：我的用例把代码【趟到什么程度】了？
  等价类划分 —— 同类只挑一个代表        ↓ 这个"程度"必须能分级，于是有了
  边界值分析 —— 错误爱藏在边界上        【覆盖标准】，颗粒度由粗到细排成阶梯：
  判定表     —— 多条件组合别漏           语句 < 判定 < 条件 < 判定/条件
                                          < 条件组合 < 路径
        （三种方法互补，常配合使用）       ↓ 最强的是路径覆盖，可路径数会爆炸
                                          ↓ 那"基本路径"到底有几条？要几个用例？
                                        【McCabe 环路复杂度 V(G)】给出数字：
                                          V(G)=E−N+2 = 判定节点数+1 = 区域数
   ↓
用例挑法解决了，还剩两个问题：【什么时候测】和【拿什么判对错】
   ↓ V 模型：每个测试阶段，都用"当初写下的那份文档"当判卷标准
     单元测试 ← 详细设计 ｜ 集成测试 ← 概要设计 ｜ 确认测试 ← 需求规格说明书
     系统测试 ← 真实软硬件环境整体跑
   ↓ 可模块还没配齐，怎么先跑起来？→ 缺上层补【驱动模块】、缺下层补【桩模块】
   ↓ 最后交给谁测？→ α（开发方场地）→ β（用户自己环境）
   ↓ 代码改了怎么办？→ 回归测试：重跑原有用例，防"修一个、坏一片"
```

## 第 2 层 · 考点：考试怎么问

### 考点① 白盒六级覆盖标准的强弱与辨析【最高频】

**题目长相**
- "白盒测试中，下列覆盖标准**最强**（或**最弱**）的是（ ）"
- "关于覆盖标准的叙述，**错误**的是（ ）"
- 给一段带 `&&` / `||` 的判定 + 一组用例，问"该用例组满足哪种覆盖"

**怎么解**——先背这条**考试口径**的强弱链，再对照每级的一句话要求：

> **语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖**

| 覆盖标准 | 一句话要求 |
|---|---|
| 语句覆盖 | 每条**语句**至少执行一次（最弱） |
| 判定覆盖（分支覆盖） | 每个**判定整体**取真、取假各至少一次 |
| 条件覆盖 | 每个**简单条件**各取真、假至少一次 |
| 判定/条件覆盖 | 判定覆盖 **+** 条件覆盖同时满足 |
| 条件组合覆盖 | 每个判定内**条件的所有取值组合**都出现（n 个条件 → 2ⁿ 组） |
| 路径覆盖 | 程序**所有可执行路径**都走一遍（最强，也最贵） |

**记忆抓手（理解了就不用背顺序）**：从左到右，检查的**颗粒度越来越细**——先只管"每行代码跑过没"，再管"分支两头走过没"，再拆到"每个小条件真假各来过没"，最后管到"条件组合、完整路径全走没"。

**陷阱**
- ⚠️ **"满足条件覆盖就一定满足判定覆盖"→ 错**（经典考点）。每个条件都取过真假，判定整体却可能一次都没取过真/假。反例见第 3 层算例 2 与练习 1。这也说明上面那条强弱链是**考试口径的经验排序**，并非严格的数学包含关系（**条件覆盖不包含判定覆盖**）——考场按口径答，理解上要知道这个例外。
- ⚠️ **"条件组合覆盖 = 路径覆盖"→ 错**。条件组合覆盖蕴含它前面的所有标准，但**不蕴含路径覆盖**；程序里多个判定串联时，路径数按判定组合翻倍，条件组合覆盖管不到。
- ⚠️ 问"最弱"时别惯性选路径覆盖——**最弱是语句覆盖**。

### 考点② McCabe 环路复杂度计算【固定考法，阶段B】

**题目长相**
- "某程序的流程图中有 **E 条边、N 个节点**，其 McCabe 环路复杂度为（ ）"
- 给一段代码或一张流程图，问 V(G) / 问"基本路径测试至少需要几个测试用例"

**怎么解**——三条算法，**答案必然一致，考场可互相验算**：

| 算法 | 公式 | 什么时候用 |
|---|---|---|
| 公式法 | **V(G) = E − N + 2**（E=边数，N=节点数） | 题目直接给边数、节点数 |
| **判定节点法** | **V(G) = 判定节点数 + 1** | **只给代码不给图时首选**，最快 |
| 区域法 | V(G) = 流程图把平面分成的**区域数**（闭合区域数 + 1 个外部区域） | 图已经画好，用来验算 |

V(G) 的含义要记牢：它等于**线性无关的基本路径条数**，也就是**基本路径测试法要求的最少用例数**；工程上还用它衡量模块逻辑复杂度（经验值：**V(G) > 10 的模块难测难维护**）。

**陷阱**
- ⚠️ **公式记错**：是 `E − N + 2`，不是 `N − E + 2`。用"边比点多，多的部分再加 2"帮记；也可用判定节点法当场反验。
- ⚠️ **判定节点数错**：判定节点 = **引出两条分支的节点**。若判定是 `x>0 && y>0` 这种复合条件，且题目按"**每个简单条件算一个判定**"来画图，则按**图上实际分叉数**数，不能只算一个 if。
- ⚠️ 漏边：数边时循环的**回边**（如 `⑤→①`）和判定的**假分支**最容易漏，漏一条边答案就少 1。

### 考点③ 各测试阶段的依据文档【固定送分】

**题目长相**："**集成测试**的主要依据是（ ）"、"单元测试应依据（ ）进行"。

**怎么解**——V 模型思想：每个测试阶段，用"**当初写下的那份对应文档**"当判卷标准。

| 阶段 | 测什么 | **依据（考点本身）** |
|---|---|---|
| 单元测试 | 单个模块/函数内部逻辑 | **详细设计**说明书 |
| 集成测试 | 模块拼装后的接口、调用关系 | **概要设计**说明书 |
| 确认测试（验收测试） | 软件功能是否满足用户需求 | **需求规格说明书** |
| 系统测试 | 软件放进真实软硬件/网络环境整体运行（性能、压力、安全、可靠性等） | 系统需求 / 整体环境 |
| 回归测试 | 修改（改错或升级）之后重跑原有用例 | **原有测试用例集**（目的是确认修改没引入新错误） |

**理解记法**：测试阶段的范围从小到大（模块 → 接口 → 需求 → 整机），依据文档正好把开发文档"**倒着往回对**"——详细设计 → 概要设计 → 需求规格说明书。

**配套考点：让"半成品"先跑起来的两个临时模块**

单元测试时，被测模块**自己不会启动**（上层调用者可能还没写），它**要调的下层模块**也可能还没写完。于是要临时补两段代码：

| 临时模块 | 补的是哪一头 | 干什么 |
|---|---|---|
| **驱动模块 driver** | 补**上层调用者** | 模拟"谁来调我"：送入测试数据、启动被测模块、收结果 |
| **桩模块 stub**（存根模块） | 补**下层被调者** | 模拟"我要调的人"：直接返回一个假结果 |

集成测试的**组装策略**正好按这条线分：

- **一次性组装**（非增量式，俗称大爆炸）：所有模块一起接上再测——省事，但出错难定位
- **增量式·自顶向下**：先接上层、后接下层。下层还没接上 → **要写桩模块**
- **增量式·自底向上**：先接下层、后接上层。上层还没接上 → **要写驱动模块**

**陷阱**
- ⚠️ **桩模块 ↔ 驱动模块最容易对调**。一句话定位：**自顶向下缺"下面"，补桩（stub）；自底向上缺"上面"，补驱动（driver）**。
- ⚠️ **单元 ↔ 集成的依据最容易对调**。抓住语义：集成测试查的是**模块之间的接口与调用结构**，而这正是**概要设计**定义的内容；模块**内部**逻辑才是详细设计的事。
- ⚠️ 别选"源程序代码"作为集成测试的依据——代码是被测对象，不是判卷标准。

### 考点④ 黑盒三大方法的识别与应用

**题目长相**："输入框要求 1~100 的整数，按**边界值分析**法，下列用例组最恰当的是（ ）"、"下列适合用（ ）方法设计用例"。

**怎么解**——三种方法各回答一个不同的问题：

**1）等价类划分 —— 同类输入挑一个代表**

输入"年龄 1~120 合法"，测 30 和测 31 大概率走同一段代码、命中同一类错误，没必要都测。把输入域划成若干等价类，**每类挑一个代表值**：
- **有效等价类**：合法输入（如年龄 1~120）
- **无效等价类**：非法输入（如 ≤0、>120、非数字）——**必须也设计用例**，验证程序能正确拒绝

例：输入"1~120 的整数年龄" → 划 3 类：有效 [1,120]（取 30）、无效 <1（取 0）、无效 >120（取 150），**3 个用例覆盖三类**。

**2）边界值分析 —— 错误爱藏在边界上**

程序员最常写错的是 `<` 写成 `<=`、循环多跑/少跑一次——这些错都在**边界**上暴露。所以在等价类的**边界及紧邻两侧**取值：对 [1,120]，取 **0、1、2 和 119、120、121**。边界值分析是等价类划分的**补充**，两者常配合使用。

**3）判定表 —— 多条件组合决定多个动作**

业务规则形如"VIP 且满 300 → 8 折；VIP 且不满 300 → 9 折；非 VIP 且满 300 → 95 折；否则不打折"——多条件组合决定多个动作，单靠等价类容易**漏组合**。判定表把**条件的所有组合**列成表，**每列（每条规则）设计一个用例**：

| 规则 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 条件：是VIP | 是 | 是 | 否 | 否 |
| 条件：满300 | 是 | 否 | 是 | 否 |
| 动作：折扣 | 8折 | 9折 | 95折 | 不打折 |

n 个独立条件 → **2ⁿ 列组合**，逐列出用例，保证组合不漏。

**陷阱**
- ⚠️ 边界值题的错误选项通常是这三种：**全取内部值**（如 50/60/70，一个边界都没碰）、**只取有效侧**（如 1/50/100，缺无效侧的 0 和 101）、**取的不是紧邻值**（如 −1、102，跳开了真正的边界邻居）。
- ⚠️ 等价类划分只写有效类、**漏掉无效等价类**是常见错误叙述。

### 考点⑤ 方法归属：黑盒还是白盒

**题目长相**："下列属于**白盒测试**方法的是（ ）"、"关于黑盒/白盒测试的叙述，错误的是（ ）"。

**怎么解**——判据只有一句：**设计用例时看不看代码**。

| | 黑盒测试（功能测试） | 白盒测试（结构测试） |
|---|---|---|
| 视角 | 把程序当黑盒子，只看输入→输出是否符合规格 | 打开盒子，按代码内部逻辑结构设计用例 |
| 依据 | 需求规格说明 | 程序源代码 / 流程图 |
| 常用方法 | **等价类划分、边界值分析、判定表、错误推测、因果图** | **覆盖标准（语句/判定/条件/…/路径）、基本路径测试** |

> **另一条正交的分类别混**：按"**运不运行程序**"分——**动态测试**要真跑程序（黑盒、白盒**都属于动态测试**）；**静态测试**不运行程序，只人工/工具审查代码与文档，手段是**桌前检查、代码审查、代码走查**。所以"黑盒 vs 白盒"和"静态 vs 动态"是两把不同的尺子。

**陷阱**
- ⚠️ **把"静态测试"当成白盒测试的一种**——白盒要跑程序，是动态测试；静态测试压根不运行程序。
- ⚠️ **把"因果图""错误推测"错认成白盒**——它们都不看代码，是**黑盒**方法。
- ⚠️ **把"基本路径测试"错认成黑盒**——它要数流程图的节点和边，必须看代码，是**白盒**。

### 考点⑥ α / β / 系统测试 / 回归测试辨析

**题目长相**："关于 α、β 测试，正确的是（ ）"、"修复缺陷后重新执行以前通过的用例，属于（ ）测试"。

**怎么解**
- **α 测试**：用户在**开发方场所**、开发人员指导的**受控环境**下试用
- **β 测试**：用户在**自己的实际使用环境**下试用，开发方不在场，由用户反馈问题
- 二者**主体都是用户**，均属确认/验收测试范畴，**区别只在场地**
- **系统测试**：把软件放进真实软硬件/网络环境**整体**运行（性能、压力、安全、可靠性等）
- **回归测试**：修改代码（改错或升级）之后**重跑原有用例**，确认没有引入新错误

**记法**：α 在前——先在"**家里**"（开发方）测，再放到"**野外**"（用户环境）做 β。

**陷阱**
- ⚠️ 错误选项一律在**主体**上做文章：凡是写成"**由开发人员进行**"的 α/β 选项都错——两者主体都是**用户**，变的只是场地。

### 考点⑦ 关于软件测试的基本命题

**题目长相**："关于软件测试的叙述，**错误**的是（ ）"。

**怎么解**——两句定论：
1. 测试的目的是**用尽量少的用例发现尽量多的错误**（不是"证明程序正确"，也不是"演示功能可用"）。
2. **测试只能证明程序有错，不能证明程序无错**（穷举不可行，测试通过只说明这些用例没触发缺陷）。

**陷阱**
- ⚠️ **"测试的目的是证明程序中没有错误"→ 错**，这是最经典的错误叙述。
- ⚠️ **"测试通过说明软件不存在缺陷"→ 错**，同上。

## 第 3 层 · 完整算例

### 算例 1：McCabe 环路复杂度（三法互验）

对下面的代码画流程图并计算 V(G)。

```c
while (a != b) {      /* 判断① */
    if (a > b)        /* 判断② */
        a = a - b;    /* ③ */
    else
        b = b - a;    /* ④ */
                      /* ⑤ 汇合，回到① */
}
return a;             /* ⑥ */
```

**第 1 步，画流程图**（节点 = 语句/判断/汇合点，边 = 控制流走向）：

```
        ┌────────────┐
        ▼            │
   ①while a!=b ──假──┼──→ ⑥return
        │真          │
        ▼            │
   ②if a>b           │
    真│    │假        │
      ▼    ▼         │
   ③a=a-b ④b=b-a     │
      │    │         │
      └─→⑤←┘         │
          └──────────┘ (回到①)
```

**第 2 步，数节点 N**：① ② ③ ④ ⑤ ⑥，共 **N = 6**。
（提醒：汇合点 ⑤ 也是一个节点，容易漏。）

**第 3 步，数边 E（一条不漏）**：①→②（真）、①→⑥（假）、②→③（真）、②→④（假）、③→⑤、④→⑤、⑤→①（回边），共 **E = 7**。
（提醒：最容易漏的是 ①→⑥ 这条**假分支**和 ⑤→① 这条**回边**。）

**第 4 步，代入公式**：V(G) = E − N + 2 = 7 − 6 + 2 = **3**。

**第 5 步，验算（两条速算法，必须与上面一致）**：
- **判定节点法**：判定节点是 `while①` 和 `if②`，共 2 个 → V(G) = 2 + 1 = **3** ✓
- **区域法**：闭合区域有 2 个（if-else 那个菱形圈、while 那个回环圈），再加 1 个外部区域 → **3** ✓

**结论**：该程序的基本路径有 **3** 条，基本路径测试至少设计 **3** 个测试用例。

> **验算习惯**：考场上凡是算 V(G)，**至少用两种方法各算一遍**。公式法最容易在"数边"上出错，判定节点法几秒钟就能复核——两者不一致，就回头重数边。

### 算例 2：逐级设计覆盖用例（含"条件覆盖 ≠ 判定覆盖"的构造）

设 a、b 为输入，对下面这段代码逐级给出**最少用例**：

```c
if (a > 0 && b > 0) {     /* 判定 = (条件1: a>0) && (条件2: b>0) */
    x = x / a;            /* 语句 S1 */
}
y = x + 1;                /* 语句 S2 */
```

| 覆盖标准 | 要求 | 本例最少用例 | 逐步说明 |
|---|---|---|---|
| 语句覆盖 | 每条**语句**至少执行一次 | **(a=1,b=1)**，共 1 个 | 判定为真才能执行到 S1，取 (1,1) 即可；S2 无条件执行。此时判定取假的情况**完全没测**——最弱 |
| 判定覆盖（分支覆盖） | 每个**判定整体**取真、取假各至少一次 | **(1,1) 真、(−1,1) 假**，共 2 个 | 比语句覆盖强：假分支也走了。但两个用例里 b>0 **都为真**，条件2 从没取过假 |
| 条件覆盖 | 每个**条件**各取真、假至少一次 | **(1,−1)、(−1,1)**，共 2 个 | 条件1：真/假都有；条件2：假/真都有 → 条件覆盖成立。可两个用例的**判定整体都是假**（真分支一次没进）→ **满足条件覆盖却不满足判定覆盖**（经典考点） |
| 判定/条件覆盖 | 判定覆盖 + 条件覆盖同时满足 | **(1,1)、(−1,−1)**，共 2 个 | 全真 + 全假：判定真假都有、每个条件真假也都有。但"一真一假"的组合仍没测到 |
| 条件组合覆盖 | 每个判定内**条件的所有组合**都出现 | **(1,1)(1,−1)(−1,1)(−1,−1)**，共 4 个 | 2 个条件 → 2² = 4 种组合全上，自然蕴含前面**所有**标准 |
| 路径覆盖 | 程序**所有可执行路径**都走一遍 | 本例 **2 条路径**（进 if / 不进 if） | 本例的路径覆盖已被条件组合覆盖包含；但若程序有**多个判定串联**，路径数按判定组合翻倍，路径覆盖要求全部走到——最强也最贵 |

**这张表最值钱的一行是"条件覆盖"那行**：用 (1,−1) 与 (−1,1) 这一组，两个条件各自真假齐全、判定整体却始终为假，直接构成"条件覆盖 ⊅ 判定覆盖"的反例。考场上凡问"该用例组满足哪种覆盖"，先分别列出**每个条件的取值集合**和**判定整体的取值集合**再下结论，不要凭感觉。

## 第 4 层 · 速记

> 覆盖强弱：**语句判定条件、判条组合路径**（语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径）
> 条件覆盖的坑：条件各真假 ≠ 判定有真假——**条件覆盖不含判定覆盖**
> McCabe 三算法一口诀：**边减点加二；判定加一；数区域**（V(G) = E − N + 2 = 判定节点数 + 1 = 区域数）
> V(G) 的含义：**线性无关基本路径条数 = 基本路径测试最少用例数**；V(G) > 10 难测难维护
> 测试依据：**单详细、集概要、确认对需求**
> 集成策略：**自顶向下补桩（stub），自底向上补驱动（driver）**
> 静态测试**不运行程序**（桌前检查/代码审查/代码走查）；黑盒白盒都是**动态测试**
> **α 开发方、β 用户家；先 α 后 β**，主体都是用户
> 回归测试：改完重跑老用例，防"修一个坏一片"
> 黑盒挑输入（等价类、边界值、判定表、因果图、错误推测），白盒趟代码（覆盖标准、基本路径）
> 边界值取法：**边界本身 + 紧邻两侧**（[1,120] 取 0/1/2、119/120/121）
> 等价类：**有效类和无效类都要出用例**
> **测试只能证有错，不能证无错**

## 考题回顾

> 说明：已核实的是"覆盖标准强弱 / McCabe 计算 / 黑白盒"这几个**考点**在 2021上、2022下、2023上、2024上 出现过（见计划文件），**未逐题对应"哪一年考的正是这道题"**。下列题目按已核实考点自编重现，**非原题原文**。

**1.【模拟·重现2023上考点】** 白盒测试中，下列覆盖标准最强的是（ ）。
A. 语句覆盖　B. 判定覆盖　C. 条件覆盖　D. 路径覆盖

**解答**：按强弱链"语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径"，路径覆盖要求所有可执行路径全部走到，是最强标准。**答案：D**。（变体问"最弱"则选 **A 语句覆盖**。）

**2.【模拟·重现2024上考点】** 某程序的流程图中有 9 条边、7 个节点，其 McCabe 环路复杂度为（ ）。
A. 2　B. 3　C. 4　D. 16

**解答**：V(G) = E − N + 2 = 9 − 7 + 2 = **4**。**答案：C**。（干扰项 D=16 来自把公式记成乘法/加总；若题目给代码不给图，改用"判定节点数 + 1"。）

**3.【模拟】** 某输入框要求输入 1~100 的整数。按边界值分析法，下列用例组最恰当的是（ ）。
A. 50, 60, 70　B. 0, 1, 100, 101　C. 1, 50, 100　D. −1, 50, 102

**解答**：边界值分析取**边界本身及紧邻两侧**：下边界附近 0/1、上边界附近 100/101。A 全是内部值，一个边界都没碰；C 只有有效侧、缺无效侧；D 的 −1、102 都跳开了真正的紧邻边界值。**答案：B**。

**4.【模拟】** 集成测试的主要依据是（ ）。
A. 需求规格说明书　B. 概要设计说明书　C. 详细设计说明书　D. 源程序代码

**解答**：单元 ← 详细设计、**集成 ← 概要设计**、确认 ← 需求规格说明书。集成测试查的是模块之间的接口与调用结构，这正是概要设计定义的内容；源程序是被测对象，不是判卷依据。**答案：B**。

**5.【模拟】** 关于 α、β 测试，正确的是（ ）。
A. α 测试由开发人员在用户环境进行　B. β 测试由用户在开发环境进行
C. α 测试由用户在开发方受控环境进行　D. β 测试由开发人员在开发环境进行

**解答**：两者**主体都是用户**，区别只是场地：α 在开发方（受控环境），β 在用户实际环境。A、D 把主体错写成开发人员；B 把 β 的场地写成开发环境。**答案：C**。

## 自测练习

1. 【模拟】对判定 `if (x > 5 || y < 3)`，用例组 (x=6,y=5) 与 (x=1,y=1) 满足条件覆盖吗？满足判定覆盖吗？
2. 【模拟】某程序流程图有 3 个判定节点（均为二分支），其环路复杂度是多少？基本路径测试至少要几个用例？
3. 【模拟】程序修复了一个线上 bug 后，把以前通过的用例全部重新执行一遍，这属于哪种测试？
4. 【模拟】采用**自顶向下**的增量式集成测试时，需要额外编写的临时模块是（ ）。A. 驱动模块　B. 桩模块　C. 主控模块　D. 回归模块

### 参考答案

1. 用例1 (6,5)：条件1 (x>5)=真、条件2 (y<3)=假，判定 = 真；用例2 (1,1)：条件1=假、条件2=真，判定 = 真。每个条件都取过真假 → **满足条件覆盖**；但判定整体两次都为真、从没取过假 → **不满足判定覆盖**。这正是"条件覆盖不包含判定覆盖"的实例（与第 3 层算例 2 中 `&&` 的反例互为对照：一个恒真、一个恒假）。
2. V(G) = 判定节点数 + 1 = 3 + 1 = **4**；基本路径测试至少 **4** 个用例。
3. **回归测试**——修改后重跑原有用例，确认没有引入新错误。
4. **B**。自顶向下先接上层，**下层还没接上**，需要用**桩模块（stub）**冒充被调用的下层模块返回假结果；反之自底向上缺的是上层调用者，要写**驱动模块（driver）**。
