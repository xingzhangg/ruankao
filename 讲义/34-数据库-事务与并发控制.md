# 34 · 数据库：事务与并发控制

## 定位

一个人对着数据库敲命令一切正常，一群人同时敲就会出错。场景沿用内部报销系统：财务小王在改一张单的金额，主管老李同时给同一张单盖审批章。最朴素的做法是"谁的语句先到就先执行谁的"，它有四处不够用：① 两人同时改同一行，结果被覆盖；② 读到别人没定下来、随后又撤销的值；③ 同一事务前后两次读，中间被别人改掉；④ 三种毛病都不犯，也不等于结果与"一个一个排队做"相同。

本课先用事务与 ACID 把"一件事"框起来，再看三类并发问题，然后用 S 锁/X 锁与三级封锁协议补 ①②③，用可串行性与两段锁协议补 ④；加锁带来的活锁与死锁单开一节。

## 一、事务与 ACID

**事务（Transaction）**：把一组语句打包成不可分割的执行单位。例：审批一张报销单至少两条语句（单据状态改为"已通过"、把钱记进本月应付表），只做完第一条就断电，单子显示通过、钱却没记账。以 `BEGIN TRANSACTION` 开头，以 `COMMIT`（提交，全部生效）或 `ROLLBACK`（回滚，全部撤销）结尾。

- 原话｜事务"由一系列操作组成，这些操作，要么全做，要么全不做"。
- **并发控制**：原话｜"控制不同的事务并发执行"，为的是"提高系统效率"。**事务是并发控制的前提条件**——不先划出这个单位，"一件事"就没有边界。

| 特征 / 关键词 | 特性 | 原话 |
|---|---|---|
| 撤销、回滚、要么全做要么全不做、不许留半截 | **（操作）原子性** Atomicity | 要么全做，要么全不做 |
| 总额不变、约束仍满足、做完账对得上、转账 A 转出 B 一定收到 | **（数据）一致性** Consistency | 事务发生后数据是一致的，例如银行转账，不会存在 A 账户转出，但是 B 账户没收到的情况 |
| 提交前对别人不可见、互不干涉 | **（执行）隔离性** Isolation | 任一事务的更新操作直到其成功提交的整个过程对其他事务都是不可见的，不同事务之间是隔离的，互不干涉 |
| 提交之后断电也不丢 | **（改变）持续性** Durability，也叫**持久性** | 事务操作的结果是持续性的 |

括号里的提示词点出每条管的侧面。"持续性""持久性"是同一条。D 靠什么兑现（日志、转储、故障恢复）见讲义 35；本课只讲 I 如何被并发破坏。

**易混对：A 原子性 ／ C 一致性**
- 判据｜**A 说机制，C 说结果**：描述数据库做了什么动作（撤销、回滚）→ A；描述一条业务约束在事务前后都成立 → C。"数据没坏"不等于 C。
- 例子｜"审批失败后，已写进应付表的那条记录被自动删掉"＝A；换成"审批前后，已通过金额合计与应付表合计始终相等"＝C。

## 二、三类并发问题（计算：走时间线）

交错执行时，读和写在时间上交叉，产生三种错误结果。

**（1）丢失更新。** A=10，T1 减 5，T2 减 8：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=10 | |
| ② | | 读 A=10 |
| ③ | A=A−5 写回 | |
| ④ | | A=A−8 写回 |

1. 第 ② 步 T2 读到 10，而非 T1 改后的 5。
2. 第 ④ 步 T2 写回 10−8=**2**，盖掉 T1 写的 5。
3. 两笔都生效应为 10−5−8=**−3**，差的正是 T1 那 5。

原话｜"此时事务 2 写回的数据会覆盖事务 1 写回的数据，就丢失了事务 1 对 A 的更新。即对数据的更新会被覆盖。"两个事务各自代码都没错，错在"读"和"写"之间被插了队。

**（2）读脏数据。** "脏"＝还没提交、随后又被撤销的值。A=20：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=20，A←A+50，写回 70 | |
| ② | | 读 A=70 |
| ③ | ROLLBACK，A 恢复为 20 | |

T2 手里的 70 从没算数过，基于它的计算全部作废。原话｜"那么事务 2 对数据 A 做的事是无效的，读到了脏数据。"

**（3）不可重复读。** A=20、B=30：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=20，读 B=30，求和=50 | |
| ② | | 读 A=20，A←A+50，写 A=70 |
| ③ | 读 A=70，读 B=30，求和=100（验算不对） | |

T1 一个字节都没写，两次求和却得出 50 和 100。

**判型步骤**（只看"谁在写、提没提交"，不看事务编号——T1/T2 对调，现象不变）：
1. 两个事务都写同一份数据，且**后写的那个是拿"没算上前一个修改"的旧值去算的** → 丢失更新。（若后写者等前者写完才读，两笔都算上，不叫丢失更新——见第四节一级封锁协议那张表。）
2. 一写一读，读到的值写方回滚了（读的是未提交值）→ 读脏数据。
3. 一写一读，写方提交了，读方前后两次读到的值不同 → 不可重复读。

## 三、S 锁与 X 锁

病因是读写交叉，药就是不许交叉：动数据前先申请使用权，拿不到就等，这叫**封锁（Locking）**。**S 锁＝共享锁（读锁）**，**X 锁＝排它锁（写锁）**。

**相容表**（"相容"＝两把锁能同时挂在同一份数据上）：

| T2 请求 ＼ T1 已持有 | S 锁 | X 锁 |
|---|---|---|
| **请求 S 锁** | 相容，可同时读 | 不相容，等 |
| **请求 X 锁** | 不相容，等 | 不相容，等 |

四格只有一格相容：**只有"读+读"能共存，沾上写就得等。** 先加 S 锁再升级成 X 锁也绕不过相容表：别人的 S 锁还挂着就升不上去，仍要等。

- 原话｜X 锁："若事务 T 对数据对象 A 加上 X 锁，则只允许 T 读取和修改 A，**其他事务都不能再对 A 加任何类型的锁**，直到 T 释放 A 上的锁。"
- 原话｜S 锁："若事务 T 对数据对象 A 加上 S 锁，则只允许 T 读取，但不能修改，**其他事务只能再对 A 加 S 锁（也即能读不能修改）**，直到 T 释放 A 上的 S 锁。"

相容表从两句原话推得出：X 那条 → 凡 X 出现的格子一律不相容（划掉三格）；S 那条 → 剩下 S+S 那格相容。

**易混对：S 锁 ／ X 锁**
- 判据｜看**别人还能不能再加锁**：还能再加 S 锁＝S 锁；什么都加不上＝X 锁。别人持锁不等于我什么都加不上——S+S 相容。
- 例子｜T1 对 D1 加 S 锁，T2 对 D1 加 S 锁成功、加 X 锁失败；把 T1 那把换成 X 锁，T2 两种都失败。

## 四、三级封锁协议（计算：带锁重走时间线）

锁只是工具，决定治哪种病的是规矩：**读要不要加锁、锁什么时候放**。

**一级封锁协议**。原话｜"事务在修改数据 R 之前必须先对其加 X 锁，直到事务结束才释放。可解决丢失更新问题。"用丢失更新那组数（A=10、T1 减 5、T2 减 8）重跑：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 加写锁 | |
| ② | | 对 A 加写锁 → 拿不到 |
| ③ | 读 A=10 | 等待 |
| ④ | A=A−5 写回 | 等待 |
| ⑤ | 释放对 A 的写锁 | 等待 |
| ⑥ | | 读 A=**5** |
| ⑦ | | A=A−8 写回 |
| ⑧ | | 释放对 A 的写锁 |

第 ⑥ 步 T2 读到新值 5，写回 5−8=**−3**，正是两笔都生效的结果。X 锁保护的是"读—改—写"整段，不只是"写"。但一级**对纯读不加锁**，只读的事务照样能读到中间值 → 防不住读脏。

**二级封锁协议**。原话｜"一级封锁协议的基础上加上事务 T 在读数据 R 之前必须先对其加 S 锁，读完后即可释放 S 锁。可解决丢失更新、读脏数据问题。"用读脏那组数（A=20）重跑：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 加写锁 | |
| ② | 读 A=20 | |
| ③ | A←A+50 | |
| ④ | 写回 70 | |
| ⑤ | | 对 A 加读锁 → 拿不到（X 与 S 不相容） |
| ⑥ | ROLLBACK | 等待 |
| ⑦ | A 恢复为 20 | 等待 |
| ⑧ | | 读 A=**20**，释放对 A 的读锁 |

读前申请 S 锁＝必须等写方结束，70 根本看不见。但 S 锁**读完即放**，第一次读完别人就能拿 X 锁去改 → 防不住不可重复读。

**三级封锁协议**。原话｜"一级封锁协议加上事务 T 在读取数据 R 之前先对其加 S 锁，直到事务结束才释放。可解决丢失更新、读脏数据、数据重复读问题。"（"数据重复读"即标准术语**不可重复读**。）用不可重复读那组数（A=20、B=30）重跑：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 与 B 加 S 锁，读 A=20，读 B=30，求和=50 | |
| ② | | 对 A 加 X 锁 → A 已有读锁，等待 |
| ③ | 读 A=20，读 B=30，求和=**50**，释放 A、B 的读锁 | 等待 |
| ④ | | 读 A=20，A←A+50，写 A=70，释放对 A 的写锁 |

两次求和都是 50。差别只在 S 锁从"读完即放"改成"**事务结束才放**"。

**规则**：层层累加，级别越高越严、并发度越低。

| 协议 | 写之前 | 读之前 | 累计解决 |
|---|---|---|---|
| **一级** | 加 X 锁，事务结束才放 | 不加锁 | 丢失更新 |
| **二级** | 同上 | 加 S 锁，**读完即放** | ＋读脏数据 |
| **三级** | 同上 | 加 S 锁，**事务结束才放** | ＋不可重复读 |

## 五、活锁与死锁

> 本节与第六节按《软件设计师教程》第 5 版补。

锁把"抢数据"变成"排队等数据"，队排不好出两种事。

| 特征 / 关键词 | 是什么 |
|---|---|
| 一直轮不上、后到的反而先被批准，但没被卡死 | **活锁** |
| 互相等对方手里的锁、谁也不放、僵住 | **死锁** |
| **先来先服务**（按请求先后排队） | 活锁的解法 |
| **一次封锁法**（要用的数据一次全锁上，缺一个就一个都不锁）、**顺序封锁法**（所有事务按同一约定顺序申请锁，如永远先 A 后 B） | 死锁的**预防** |
| **超时法**（等待超过时限即判死锁）、**等待图法**（"谁在等谁"的有向图出现环即死锁） | 死锁的**诊断**；检出后回滚一个代价最小的事务，让出锁来**解除** |

**易混对：活锁 ／ 死锁**
- 判据｜**活锁单向等，死锁互相等**＝等待图有没有环。有环＝死锁，不动手永远解不开，靠回滚解除；无环、只是一直排在后面＝活锁，改排队策略即消失，不需要回滚。
- 例子｜T1 锁着 R，T2 申请只能等；T3 也来申请，T1 放锁后系统批准了后到的 T3，T4 又来……T2 一直等＝活锁；改成先来先服务，T2 立刻轮上。T1 锁 A 要 B、T2 锁 B 要 A＝死锁；两者都改成先 A 后 B（顺序封锁法），环就解开。

其余认名即可：操作系统里进程抢资源是同一类问题，工具是**信号量与 P/V 操作**（讲义 36），死锁定义与资源分配图见讲义 37。

## 六、可串行性与两段锁协议

**调度**：几个事务的读写操作实际交错成的执行次序表，第二节每张时间线都是一个调度。

**并发调度的可串行性**：多个事务的并发执行是正确的，**当且仅当其结果与按某一次序串行执行这些事务的结果相同**；满足的叫**可串行化的调度**。串行（一个做完再做下一个）绝不出错但慢，并发的目标是快得像并发、错得像串行一样少。例：丢失更新那张表，串行（不论谁先）都得 −3，交错得 2，与哪个串行次序都对不上 → 不可串行化。

**两段锁协议（Two-Phase Locking，2PL）**：每个事务的加锁放锁分两段——**扩展阶段（增长阶段）**只申请锁、一把不放；**收缩阶段**只释放锁、一把不再申请。**一旦开始放锁，就再也不许加锁。**

| 说法 | 对错 |
|---|---|
| 分扩展阶段和收缩阶段，一旦开始释放锁就不能再申请新锁 | 对（定义） |
| 若所有事务都遵守 2PL，则对这些事务的任何并发调度策略都是可串行化的 | 对（定理） |
| 可串行化的调度一定遵守 2PL | 错，充分条件说成了必要条件 |
| 遵守 2PL 的事务不会发生死锁 | 错，2PL 防不了死锁 |
| 先集中放锁，再集中加锁 | 错，两段顺序反了 |
| 三级封锁协议是 2PL 的一个特例 | 对：X、S 锁都持有到事务结束，放锁全挤在最后，两段天然分开，故三级保证可串行化 |
| 一级、二级封锁协议也保证可串行化 | 错：二级 S 锁读完就放、之后还会申请别的锁，不是两段的；一级对读完全不加锁，读到的值不受锁保护，定理前提（每次访问都受锁保护）不成立 |
| 三级封锁协议是"最严格的两段锁" | 错：一次封锁法开工前一次锁齐，加锁一头比三级更严，还能防死锁；三级只是 2PL 的一个特例 |

**易混对 1：守 2PL ⇒ 可串行化 ／ 可串行化 ⇒ 守 2PL**
- 判据｜**充分不必要**，箭头只有一个方向：守 2PL ⇒ 一定可串行化；可串行化的调度不一定守 2PL。
- 例子｜T1 写 A、放 A 的锁，T2 接着读 A、写 A，之后 T1 才锁 B、写 B。T1 放锁后又加锁，违反 2PL；但冲突只在 A 上、方向只有 T1→T2，等价于"先 T1 后 T2"串行，结果正确。把最后一步改成"T1 回头再改一次 A"，冲突变双向，立刻不可串行化。

**易混对 2：可串行化 ／ 不死锁**
- 判据｜**2PL 管"结果对不对"，不管"会不会卡住"**。
- 例子｜T1 锁 A 再申请 B，T2 锁 B 再申请 A：都在扩展阶段、完全守协议，却互等成环——**2PL 不能防止死锁**。把 T2 改成先 A 后 B，环消失，两者照样守 2PL。

四条短板对四个补丁：**互相覆盖 → X 锁＋一级；读到半成品 → S 锁＋二级；两次读不一样 → 三级把 S 锁持到底；整体结果对不对 → 可串行性，照 2PL 做一定合格。** 活锁与死锁是加锁手段的副作用，不在这条链上。

## 速记

- **ACID**：原子＝要么全做要么全不做（管半截）；一致＝做完账仍对得上（管结果）；隔离＝提交前对别人不可见、互不干涉；持久（＝持续）＝提交后断电也不丢。**A 说机制、C 说结果**
- **三类并发问题**：两个都写、后写拿旧值盖掉先写＝丢失更新；读了未提交且随后被回滚的值＝读脏；同一事务两次读不一样＝不可重复读
- **相容表只有一个 ✓**：S+S 相容，沾 X 就得等
- **三级封锁协议**：一级写前加 X 持到底、读不加锁 → 防丢失更新；二级读前加 S、**读完即放** → ＋防脏读；三级读前加 S、**持到事务结束** → ＋防不可重复读。口诀**一丢二脏三重复**
- **可串行化**：并发结果与某一串行次序的结果相同才算对
- **2PL**：扩展阶段只加、收缩阶段只放，**一旦放锁不再加锁**；守 2PL ⇒ 可串行化（**充分不必要**），**防不了死锁**。三级是 2PL 特例，一二级不是
- **活锁**＝单向久等、先来先服务可解；**死锁**＝互相等、等待图成环，一次封锁法/顺序封锁法预防，超时法/等待图法诊断后回滚一个事务解除
