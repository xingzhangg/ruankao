## 定位

一个人对着数据库敲命令一切正常，一群人同时敲就会出错。这一课先把"一件事"框起来（事务与 ACID），再看什么都不管会出的三种事（丢失更新、读脏数据、不可重复读），然后用 S 锁/X 锁与三级封锁协议一条条堵上，最后用可串行性这把尺子验收、用两段锁协议给出照着做就合格的操作规程。加锁本身还会带来活锁与死锁，另开一节。

## 开讲：报销系统上线第一天，财务和主管同时点了"审批"

还是那套内部报销系统：员工提单、主管审批、超 5000 元走二级审批、审完打款。前几课默认的场景是**你一个人对着数据库敲命令**，上线第一天这个假设就没了——财务小王在改一张单的金额，主管老李同时在给同一张单盖审批章，两个人手速差了半秒。

**最朴素的做法：什么都不管，谁的语句先到数据库就先执行谁的。** 这是每个 DBMS 出厂时的出发点，也是这一课全部名词的起点。它在四个地方不够用，后面每一节补一条：

- ① 两个人同时改同一行，两边的代码都没有 bug，结果却错了；
- ② 有人读到了别人还没定下来的中间值，对方转头一撤销，读到的那个值从来没真正存在过；
- ③ 同一个人前后读了两次同一份数据，中间被别人改掉，自己算的账对不上；
- ④ 就算上面三种毛病一次都不犯，也**不等于**这一批操作的最终结果，跟"一个一个排队做"是一样的。

补 ① 靠 **X 锁与一级封锁协议**，补 ② 靠 **S 锁与二级封锁协议**，补 ③ 靠**三级封锁协议**，补 ④ 靠**可串行性与两段锁协议**。加锁本身还会带来一种新麻烦（活锁与死锁），单开一节。

### 一、先把"一件事"框起来：事务与 ACID

**事务（Transaction）**就是把一组语句打包成一个不可分割的执行单位——审批一张报销单在库里至少是两条语句（把单据状态改成"已通过"、把这笔钱记进本月应付表），只做完第一条就断电，单子显示通过、钱却没记账。培训资料的原话是"由一系列操作组成，这些操作，要么全做，要么全不做"。写法上以 `BEGIN TRANSACTION` 开头，以 `COMMIT`（提交，全部生效）或 `ROLLBACK`（回滚，全部撤销）结尾。

**并发控制**，培训资料给的定义只有一句——"控制不同的事务并发执行"，为的是"提高系统效率"。**事务是并发控制的前提条件**：不先划出这个单位，"两个人同时干"里的"一件事"就没有边界。

事务对外给出四条承诺，取四个英文首字母合称 **ACID**。

| 题干里出现这些话 | 答 | 培训资料原话（选项常照抄） |
|---|---|---|
| 撤销、回滚、要么全做要么全不做、不许留半截 | **（操作）原子性** Atomicity | 要么全做，要么全不做 |
| 总额不变、约束仍然满足、做完账仍对得上、银行转账 A 转出 B 一定收到 | **（数据）一致性** Consistency | 事务发生后数据是一致的，例如银行转账，不会存在 A 账户转出，但是 B 账户没收到的情况 |
| 对其他事务不可见、互不干涉、提交前别人看不到中间值 | **（执行）隔离性** Isolation | 任一事务的更新操作直到其成功提交的整个过程对其他事务都是不可见的，不同事务之间是隔离的，互不干涉 |
| 提交之后断电也不丢、结果是持续的 | **（改变）持续性** Durability，卷面也叫**持久性** | 事务操作的结果是持续性的 |

括号里是培训资料给每条加的提示词，正好点出它管的是哪个侧面。**D 这条有两种叫法**：培训资料正文写"持续性"，选项里常印"持久性"，指的是同一条，看到哪个都别犹豫。**D 靠什么兑现**（日志、转储、断电后怎么把没落盘的补回来）不在本课，讲义 35 讲；本课只负责承诺是什么，以及承诺被并发破坏的那一半。

> 考试这样问：给一句场景描述，问它体现的是事务的哪一个特性。

**易混对：A 原子性 ／ C 一致性**（**A 和 C 是本课最容易混的一对**，因为它们的例子长得几乎一样）

- 判据｜**A 说的是机制，C 说的是结果**。题干在描述数据库做了什么动作 → A；在描述一条业务约束事务前后都成立 → C。
- 例子｜"审批失败后，已经写进应付表的那条记录被自动删掉"＝A；把这一句换成"审批前后，报销单已通过金额合计与应付表合计始终相等"，答案立刻变成 C。
- 错法｜看见"数据没坏"就选 C。凡题干在描述撤销、回滚这类动作的，一律选 A。

至于 I，就是下面几节的正题：并发到底怎么把它破坏掉。

### 二、不管的话会出三种事（补 ①②③ 的病因）

培训资料把这三件事直接列成"并发控制中存在下面三个问题"。下面三张时间线取自它的原始配图 `images/fig_d04_s033.png`。

**（1）丢失更新。** 表里字段 A 的当前值是 10。T1 想减 5，T2 想减 8，两人几乎同时动手：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=10 | |
| ② | | 读 A=10 |
| ③ | A=A−5 写回 | |
| ④ | | A=A−8 写回 |

**先别往下看：跑完这四步，库里的 A 是多少？两笔都算上本该是多少？丢的是谁那一笔？**

实际结果是 **A=2**。原因在第 ② 步：T2 读到的是 10，不是 T1 改过之后的 5——它手里那份 10 一直算到第 ④ 步，写回 10−8=2，把 T1 写下的 5 整个盖掉了。两笔都生效应当是 10−5−8=**−3**，差的正好是 T1 那 5。

培训资料的定性照录：**"此时事务 2 写回的数据会覆盖事务 1 写回的数据，就丢失了事务 1 对 A 的更新。即对数据的更新会被覆盖。"** 这就是短板 ①。注意 T1 和 T2 的代码各自都没有一行是错的，错在"读"和"写"之间被别人插了队。

**（2）读脏数据。** "脏"指的是**还没被提交、随后又被撤销掉的值**——它在库里出现过一瞬间，但从结果看它从来不该存在。A 初值 20：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=20，A←A+50，写回 70 | |
| ② | | 读 A=70 |
| ③ | ROLLBACK，A 恢复为 20 | |

T2 在第 ② 步读到 70，可第 ③ 步 T1 一回滚，A 又变回 20。T2 手里那个 70 是一个从没算数过的值，它后面所有基于 70 的计算全部作废。培训资料原文：**"那么事务 2 对数据 A 做的事是无效的，读到了脏数据。"** 这是短板 ②。

**（3）不可重复读。** 同一个事务前后读两次同一份数据，中间被别人改了。A=20、B=30：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=20，读 B=30，求和=50 | |
| ② | | 读 A=20，A←A+50，写 A=70 |
| ③ | 读 A=70，读 B=30，求和=100（验算不对） | |

T1 从头到尾一个字节都没写，它只是想把刚才那笔和验算一遍，两次却得出 50 和 100。这是短板 ③。

**三者的分界线只有两个问题，按顺序问就不会错**：

- 第一问，**有几个事务在写同一份数据**？两个都写，且**后写的那个是拿"还没算上前一个修改"的旧值去算的** → 丢失更新，判完收工。
- 只有一个在写、另一个在读，才问第二问：**读方读到的那个值，写方最后认不认账**？写方回滚了（读的是未提交值）→ 读脏数据；写方提交了、而读方前后读了两次值不一样 → 不可重复读。

（第一问那个附加条件不能省：若后写的那个是等前一个写完之后才读的，两笔就都算上了，虽然两个事务都写了，也不叫丢失更新——第四节一级封锁协议那张表正是这种情形。）

判类型只看"谁在写、提没提交"，不看事务编号。培训资料的文字和它自己的配图在这一点上打了架，见本节末的深入，跳过不影响后面。

> 考试这样问：给一段 T1/T2 时序表，问它属于三类并发问题中的哪一类。

#### 深入 · 培训资料的文字与配图把 T1/T2 说反了

培训资料的文字描述里，"不可重复读"那一条写的是"事务 2 读 A，而后事务 1 对数据 A 进行了修改并写回"，与配图 `fig_d04_s033` 中间那张表的 T1/T2 角色正好对调（图上是 T1 读两次、T2 改）。**现象是同一个，谁叫 T1 谁叫 T2 不影响判断**，对着资料看的时候别被绕住。

### 三、两把锁：S 锁与 X 锁（补 ① 的第一步）

三个问题的病因是同一个：**读和写在时间上交叉了**。既然交叉是病因，最直接的药就是**不许交叉**——谁要动这份数据，先申请一个"使用权"，别人拿不到就得等。这个使用权就叫**封锁（Locking）**，简称加锁。数据库只准备了两种：**S 锁是共享锁（读锁）**、**X 锁是排它锁（写锁）**。

**相容表**（"相容"就是"两把锁能同时挂在同一份数据上"）：

| T2 请求 ＼ T1 已持有 | S 锁 | X 锁 |
|---|---|---|
| **请求 S 锁** | 相容，可以同时读 | 不相容，等 |
| **请求 X 锁** | 不相容，等 | 不相容，等 |

四个格子里**只有一个格子相容**。一句话口径：**只有"读+读"能共存，沾上写就得等。**

**反查表：题干这么写 → 这么答**

| 题干里出现 | 答 |
|---|---|
| 数据上已有别人的 S 锁，我要加 S 锁 | 成功（四格里唯一相容的一格） |
| 数据上已有别人的 S 锁，我要加 X 锁 | 失败，等 |
| 数据上已有别人的 X 锁，我要加 S 锁或 X 锁 | 都失败，等 |
| 先加 S 锁再升级成 X 锁 | 绕不过相容表：别人的 S 锁还挂着就升不上去，仍要等 |
| "只允许 T 读取、不能修改，别人还能再加 S 锁" | S 锁（共享锁、读锁） |
| "只允许 T 读取和修改，别人任何类型的锁都加不上" | X 锁（排它锁、写锁） |

> 考试这样问：T1 对 D1 加了共享锁、T2 对 D2 加了排它锁，问谁还能对哪份数据加上什么锁。

**易混对：S 锁 ／ X 锁**

- 判据｜看**别人还能不能再加锁**：还能再加一把 S 锁＝S 锁；一把都加不上＝X 锁。
- 例子｜T1 对 D1 加了 S 锁，则 T2 对 D1 加 S 锁成功、加 X 锁失败；把 T1 手里那把换成 X 锁，T2 两种都失败。
- 错法｜"别人持着锁，我就什么锁都加不上"——S+S 是相容的，这是卷面最爱设的坑。
- 原话｜X 锁："若事务 T 对数据对象 A 加上 X 锁，则只允许 T 读取和修改 A，**其他事务都不能再对 A 加任何类型的锁**，直到 T 释放 A 上的锁。" S 锁："若事务 T 对数据对象 A 加上 S 锁，则只允许 T 读取，但不能修改，**其他事务只能再对 A 加 S 锁（也即能读不能修改）**，直到 T 释放 A 上的 S 锁。"

相容表不用背，从这两句原话两步就推得出来：X 那条说"其他事务不能再加任何类型的锁"，于是**凡是 X 出现的格子一律不相容**，一下划掉三个；S 那条说"其他事务只能再加 S 锁"，剩下的那个格子相容。

### 四、光有锁不够，还得规定什么时候放：三级封锁协议（补 ①②③）

锁只是工具，真正决定治得了哪种病的是**规矩**：读要不要加锁、锁在哪一步加、加完什么时候放。培训资料"共分为三级封锁协议"，三级的差别就在这两个旋钮上。下面三张时间线同样取自培训资料的原始配图。

**一级封锁协议**，原文：**"事务在修改数据 R 之前必须先对其加 X 锁，直到事务结束才释放。可解决丢失更新问题。"** 拿第二节丢失更新那组数字（A=10、T1 减 5、T2 减 8）重跑一遍，就是扫描图 `fig_d04_s034.png`：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 加写锁 | |
| ② | | 对 A 加写锁 → 拿不到 |
| ③ | 读 A=10 | 等待 |
| ④ | A=A−5 写回 | 等待 |
| ⑤ | 释放对 A 的写锁 | 等待 |
| ⑥ | | 读 A=**5** |
| ⑦ | | A=A−8 写回 |
| ⑧ | | 释放对 A 的写锁 |

关键在第 ⑥ 步：T2 是等 T1 完全结束之后才开始读的，读到的是 T1 写下的新值 5，最后写回 5−8=**−3**——正是两笔都生效应有的结果。**要点：X 锁保护的不是"写"这一个动作，而是"读—改—写"整段**；把读也圈进锁里，才不会出现"拿着过期的值去算"。

但一级封锁协议**对纯粹的读不加任何锁**。所以只想读一下的 T2，照样能在 T1 改到一半时读进那个中间值——**它防不住读脏数据**，短板 ② 还在。

**二级封锁协议**，原文：**"一级封锁协议的基础上加上事务 T 在读数据 R 之前必须先对其加 S 锁，读完后即可释放 S 锁。可解决丢失更新、读脏数据问题。"** 拿第二节读脏那组数字重跑，就是扫描图 `fig_d04_s035.png`：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 加写锁 | |
| ② | 读 A=20 | |
| ③ | A←A+50 | |
| ④ | 写回 70 | |
| ⑤ | | 对 A 加读锁 → 拿不到（X 与 S 不相容） |
| ⑥ | ROLLBACK | 等待 |
| ⑦ | A 恢复为 20 | 等待 |
| ⑧ | | 读 A=**20**，释放对 A 的读锁 |

T2 被挡在第 ⑤ 步，一直等到 T1 回滚完，读到的是回滚后的真值 20，那个昙花一现的 70 它根本没机会看见。**读之前先申请 S 锁，就意味着必须等写方把话说完**——这就是二级比一级多出来的全部本事。

代价也在这里：S 锁**读完就放**。T1 第一次读完 A 就把 S 锁交出去了，别人立刻可以拿 X 锁去改，等 T1 第二次读，值已经变了。**二级防不住不可重复读**，短板 ③ 还在。

**三级封锁协议**，原文：**"一级封锁协议加上事务 T 在读取数据 R 之前先对其加 S 锁，直到事务结束才释放。可解决丢失更新、读脏数据、数据重复读问题。"**（原文这里写的是"数据重复读"，标准术语是**不可重复读**，指的是同一件事。）拿第二节不可重复读那组数字重跑，就是扫描图 `fig_d04_s036.png`：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 与 B 加 S 锁（读锁），读 A=20，读 B=30，求和=50 | |
| ② | | 对 A 加 X 锁（写锁）→ 由于 A 已加了读锁，所以等待 |
| ③ | 读 A=20，读 B=30，求和=**50**，释放对 A 和 B 的读锁 | 等待 |
| ④ | | 读 A=20，A←A+50，写 A=70，释放对 A 的写锁 |

T1 两次求和都是 50，验算对得上。差别只有六个字：S 锁从"读完即放"改成"**事务结束才放**"，T2 在 T1 整个事务期间都拿不到 X 锁。

三级的关系是**层层累加**，级别越高管得越严、并发度越低：

| 协议 | 写之前 | 读之前 | 累计解决 |
|---|---|---|---|
| **一级** | 加 X 锁，事务结束才放 | 不加锁 | 丢失更新 |
| **二级** | 同上 | 加 S 锁，**读完即放** | ＋读脏数据 |
| **三级** | 同上 | 加 S 锁，**事务结束才放** | ＋不可重复读 |

> 考试这样问：防止某个并发问题"至少"需要哪一级封锁协议。

### 五、加了锁，冒出两种新麻烦：活锁与死锁

> 本节与第六节（活锁、死锁、可串行性、两段锁协议）**15 份转录本均未覆盖，按《软件设计师教程》（第 5 版）补**。

锁把"抢同一份数据"变成了"排队等同一份数据"，队排不好就出两种事。

| 题干里出现 | 答 |
|---|---|
| 一直轮不上、后到的反而先被批准、但它并没有被卡死 | **活锁** |
| 互相等对方手里的东西、谁也不肯先放、就这么僵住 | **死锁** |
| 按请求到达的先后排队，谁先来谁先拿＝**先来先服务** | 活锁的解法 |
| **一次封锁法**（要用的数据一次全锁上，缺一个就一个都不锁）、**顺序封锁法**（所有事务按同一个约定顺序申请锁，比如永远先 A 后 B） | 死锁的**预防** |
| **超时法**（等超过时限就判定死锁）、**等待图法**（画"谁在等谁"的有向图，出现环就是死锁） | 死锁的**诊断与解除**；检出后挑一个代价最小的事务回滚掉，把锁让出来 |

**易混对：活锁 ／ 死锁**

- 判据｜**活锁是单向等，死锁是互相等**；等价的说法是等待图上有没有环——有环＝死锁，不动手永远解不开；无环、只是一直排在后面＝活锁，理论上随时可能轮到它，只是运气一直不好。
- 例子｜T1 正锁着数据 R，T2 来申请只能等；这期间 T3 也来申请，T1 一放锁系统批准了后到的 T3，T2 接着等，T4 又来……＝活锁；把"批准后到的"改成先来先服务，T2 立刻轮上，活锁就没了。T1 锁住了 A 接着要 B、T2 锁住了 B 接着要 A＝死锁；把两个事务都改成先 A 后 B（顺序封锁法），环才解得开。
- 错法｜把活锁也说成"必须回滚掉一个事务才能解开"——活锁改一下排队策略就消失了，回滚是死锁的解法。

其余认名即可：操作系统里进程抢打印机、抢缓冲区遇到的是同一类问题，那边的工具是**信号量与 P/V 操作**（讲义 36），死锁的定义、资源分配图与判定在讲义 37；数据库这一侧换成了锁和事务，思路完全一样，本课只讲数据库这一边。

### 六、真正的验收标准：可串行性与两段锁协议（补 ④）

到这里三种病都治了，但短板 ④ 还没动：**"三种病都不犯"和"结果是对的"不是一回事。**

先说清**调度**这个词：它指的就是几个事务的那些读写操作实际交错成的那张执行次序表——第二节那三张 T1/T2 时间线，每一张就是一个调度。**并发调度的可串行性**：多个事务的并发执行是正确的，**当且仅当其结果与按某一次序串行执行这些事务的结果相同**；满足这个条件的并发调度，叫**可串行化的调度**。

"串行执行"就是一个事务从头做到尾再做下一个，那样绝不会出错，只是慢；并发的目标是**跑得像并发一样快、错得像串行一样少**。回头看第二节那张丢失更新的表：串行做（不论谁先）都是 −3，交错做出来是 2，两个串行次序都对不上，所以那个调度不可串行化——它错了。

尺子有了，还得有一条**照着做就一定合格**的操作规程，这就是**两段锁协议（Two-Phase Locking，2PL）**：每个事务的加锁和放锁分成截然分开的两段——**扩展阶段（增长阶段）**只能申请锁、**一把也不许放**；**收缩阶段**只能释放锁、**一把也不许再申请**。一句话记法：**一旦开始放锁，就再也不许加锁。**

**反查表：卷面这么说 → 对还是错**

| 题干说法 | 判 |
|---|---|
| 分扩展阶段和收缩阶段，一旦开始释放锁就不能再申请新的锁 | 对，这是定义 |
| 若所有事务都遵守两段锁协议，则对这些事务的任何并发调度策略都是可串行化的 | 对，这是那条定理 |
| 可串行化的调度一定遵守两段锁协议 | **错**，把充分条件说成了必要条件 |
| 遵守两段锁协议的事务之间不会发生死锁 | **错**，2PL 防不了死锁 |
| 先集中放锁，再集中加锁 | **错**，两段的顺序说反了 |
| 三级封锁协议是两段锁协议的一个特例 | 对：X 锁和 S 锁都持有到事务结束才释放，放锁全部挤在最后一刻，加锁段和放锁段天然分得干干净净，所以三级封锁协议保证可串行化 |
| 一级、二级封锁协议也像三级那样保证可串行化 | **错**：二级的 S 锁读完就放、放完之后事务还会去申请别的锁，放锁跑到了加锁前面，形式上就不是两段的；一级只对写加锁、对读完全不加锁，读到的值不在任何锁的保护之下，两段锁那条定理的前提（每一次访问都受锁保护）根本不成立 |

> 考试这样问：四个说法里挑出错误的那一个。

**易混对 1：守 2PL ⇒ 可串行化 ／ 可串行化 ⇒ 守 2PL**

- 判据｜**这是充分条件，不是必要条件**，箭头只有一个方向：遵守 2PL ⇒ 一定可串行化；可串行化的调度**不一定**遵守 2PL。
- 例子｜T1 先写 A，放掉 A 的锁，T2 接着读 A、写 A，之后 T1 才去锁 B、写 B。T1 放锁之后又加锁，明摆着违反 2PL；可这个调度里两个事务只在 A 上有冲突，冲突方向只有 T1→T2 一条，等价于"先 T1 后 T2"串行执行，**结果完全正确**。把最后一步从"T1 锁 B 写 B"改成"T1 回头再改一次 A"，冲突就成了双向，结果立刻不可串行化。
- 错法｜"可串行化的调度一定遵守两段锁协议"——反着说的，是本考点最常见的错项。

**易混对 2：可串行化 ／ 不死锁**

- 判据｜**2PL 管的是"结果对不对"，不管"会不会卡住"**，这是两个不同的问题，混起来就丢分。
- 例子｜T1 锁 A 再申请 B，T2 锁 B 再申请 A：两边都在扩展阶段，一把锁都没放过，**完全遵守协议**，却互相等成了环——**两段锁协议不能防止死锁**。把 T2 也改成先 A 后 B，环就没了，而两个事务照样守着 2PL。
- 错法｜"遵守两段锁协议的事务不会发生死锁"。

反查表最后两行把第四节和这一节接上了：三级是 2PL 的特例，一二级不是。至于为什么不能管三级叫"最严格的两段锁"，见本节末的深入，跳过不影响后面。

**收口**：四条短板对四个补丁。**两人对改互相覆盖 → X 锁 + 一级；读到别人的半成品 → S 锁 + 二级；两次读不一样 → 三级把 S 锁持到底；整体结果对不对 → 可串行性，照着两段锁协议做就一定合格。** 锁本身带来的活锁与死锁不在这条链上，是加锁这个手段的副作用，认得即可。

#### 深入 · 别把三级封锁协议叫成"最严格的两段锁"

第五节那个一次封锁法要求开工前把所有要用的数据一次锁齐，在加锁这一头比三级更严，还顺带把死锁也防住了。所以三级只是 2PL 的一个特例，不是"最严格"的那个。

## 速记

- **ACID**：原子＝要么全做要么全不做（管半截）；一致＝做完账仍对得上（管结果）；隔离＝提交前对别人不可见、互不干涉（管别人）；持久（＝持续）＝提交后断电也不丢。**A 说机制、C 说结果**
- **三类并发问题**：**两个都写、后写拿旧值盖掉先写＝丢失更新；读了未提交且随后被回滚的值＝读脏；同一事务两次读不一样＝不可重复读**
- **相容表只有一个 ✓**：S+S 相容，**别人一沾 X 就得等**
- **三级封锁协议**：一级写前加 X 持到底、读不加锁 → 防丢失更新；二级读前加 S、**读完即放** → ＋防脏读；三级读前加 S、**持到事务结束** → ＋防不可重复读。口诀**一丢二脏三重复**
- **可串行化**：并发结果与某一串行次序的结果相同才算对
- **两段锁 2PL**：扩展阶段只加、收缩阶段只放，**一旦放锁不再加锁**；守 2PL ⇒ 可串行化（**充分不必要**），但**防不了死锁**。三级封锁协议的锁全持到事务结束，是 2PL 的一个特例，故保证可串行化；一二级不是
- **活锁**＝单向久等、先来先服务可解；**死锁**＝互相等、等待图成环，靠一次封锁法/顺序封锁法预防，靠超时法/等待图法检测后回滚一个事务解除
