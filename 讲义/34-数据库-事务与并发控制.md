## 第 1 层 · 理解

### 一句话

> 前四课假设数据库是"你一个人、机器永不宕机"在用。本课把这两个假设拿掉——**旁边还有别的事务在抢同一行数据，脚下的机器随时会断电**。事务与并发控制，就是数据库为这两件事各准备的一套保险。

### 痛点

**痛点一：你写过的"读—改—写"，在并发下是错的。**

```java
int balance = query("select balance from acct where id=1");  // 读到 100
balance -= 10;                                                // 算成 90
update("update acct set balance=? where id=1", balance);      // 写回 90
```

这段代码单机单线程跑一万次都对。但只要**两个人同时扣款**，两边都读到 100，一个写回 90、一个写回 80——扣了两笔，账上只少了 20。你的代码没有任何一行有 bug，**错在"读"和"写"之间被别人插了队**。这类问题不能靠"再仔细一点"避免，只能靠数据库提供的机制。

**痛点二：你以为 `commit` 返回了就万事大吉，其实那一刻数据可能还在内存里。**

数据库为了性能，改动先落在内存缓冲区，稍后才刷盘。于是断电瞬间会出现两种尴尬：**已经提交的事务，改动还没写进磁盘**（用户看到"成功"，重启后钱没到账）；**还没提交的事务，改动却已经被刷盘了**（用户看到"失败"，重启后钱却少了）。两种都要在重启时被纠正过来。

**拍脑袋为什么会错**：凭直觉答"断电了嘛，把没做完的撤销掉就行"——漏掉了 REDO；凭直觉答"磁盘坏了，把日志重放一遍"——日志重放需要一个"底子"，磁盘都没了，没有底子可改。

### 一条主线

本课看起来是两块不相干的东西（左边讲锁，右边讲故障恢复），其实它们是**从同一个源头分出来的两条腿**：

```
数据库的现实：① 很多人同时用   ② 机器会坏
   ↓
先立一个【最小可靠单位】：事务 —— 一组"要么全做、要么全不做"的操作
   BEGIN TRANSACTION … COMMIT（全生效）/ ROLLBACK（全撤销）
   ↓
对这个单位提出四条承诺（ACID）：
   A 原子性  半截状态不许留下
   C 一致性  做完账目还得对
   I 隔离性  并发时互不干扰
   D 持久性  提交了就不能丢
   ↓
关键一步：这四条【不会自己成立】，而且它们的"敌人"不是同一个——
   I 的敌人是【别的事务】  →  要靠【并发控制 / 锁】
   A、D 的敌人是【故障】    →  要靠【恢复 / 日志 + 备份】
   C 不需要独立机制，它是 A、I、D 都做到之后的【结果】（此口径**待核实**，见考点②陷阱）
   ↓
   ┌──────── 左腿：隔离性 ────────┐   ┌──────── 右腿：原子性+持久性 ────────┐
   │                              │   │                                      │
   │ 完全不管并发 → 三种病：      │   │ 故障按【破坏范围】分三级：           │
   │   丢失更新（两写互相覆盖）   │   │   ① 只坏一个事务（事务故障）         │
   │   读脏数据（读了没提交的）   │   │   ② 内存全丢、磁盘还在（系统故障）   │
   │   不可重复读（两读之间被改） │   │   ③ 磁盘也没了（介质故障）           │
   │   ↓ 病因是同一个：           │   │   ↓ 手段只有两个动作 + 一份备份：    │
   │   读和写在时间上【交叉】了   │   │   UNDO 撤销没做完的（救原子性）      │
   │   ↓ 药方：加锁              │   │   REDO 重做已提交的（救持久性）      │
   │   S 锁（读）/ X 锁（写）     │   │   备份（把被毁的底子装回来）         │
   │   ↓ 光有锁不够，还得规定     │   │   ↓ 破坏范围决定用哪几样：           │
   │   【什么时候加、什么时候放】 │   │   事务故障 → 只 UNDO                 │
   │   ↓ 于是分三级强度：         │   │   系统故障 → UNDO 未交 + REDO 已交   │
   │   一级 / 二级 / 三级封锁协议 │   │   介质故障 → 装备份 + REDO           │
   │   每升一级多治一种病         │   │   ↓ 日志越长恢复越慢                 │
   │   ↓ 但"三种病都不犯"仍不等于 │   │   → 检查点：把扫描起点从日志开头     │
   │   整体调度是对的 → 要求它    │   │     前移到最近一次检查点             │
   │   【可串行化】= 等价于某个   │   │                                      │
   │   串行执行顺序               │   └──────────────────────────────────────┘
   │   ↓ 充分条件：两段锁协议 2PL │
   │   ↓ 代价：2PL 保串行化，     │
   │     但【防不了死锁】         │
   └──────────────────────────────┘
```

记住这个"两条腿"的框架，本课所有零散结论都能挂上去：看到"S 锁/X 锁/协议/串行化"就是左腿（管隔离性），看到"断电/磁盘坏/日志/备份"就是右腿（管原子性与持久性）。

## 第 2 层 · 考点：考试怎么问

### 考点① 三类故障与恢复手段的对应【真题·2022下/2024下·唯一有年份核实的考点，最高频】

**题目长相**：
- "某事务在运行过程中因输入数据错误而中止，这属于（ ）故障，恢复时应（ ）"
- "数据库因突然断电，重启后正确的恢复处理是（ ）"
- "磁盘损坏导致数据库文件不可读，应采取的恢复措施是（ ）"

题干总是先给你**一个故障场景**，让你**先判类型、再选手段**。

**动手之前先交代：恢复到底靠哪两样东西？**

- **日志文件（Log）**：按时间顺序记录每个事务对数据做的**每一次修改**（改了哪条记录、旧值是什么、新值是什么）。因为旧值新值都在，所以它**既能反向撤销（UNDO）也能正向重做（REDO）**——下面两个动作全靠它。
- **数据备份 / 转储（Dump）**：定期把**整个数据库**复制到另一份存储介质上。日志只记"改动"，本身不是数据库；一旦磁盘被毁，日志里的改动就没有"底子"可以往上改——这时只能先靠转储把底子装回来。

**怎么解——两步走**：

第一步，只问一个问题：**这次故障破坏到了哪一层？**

| 故障类型 | 典型例子 | 破坏范围 |
|---|---|---|
| **事务故障** | 运算溢出、除零、违反完整性约束、死锁被系统选中回滚 | 仅该事务自己没做完，**数据库未被破坏** |
| **系统故障**（软故障） | 断电、操作系统崩溃、DBMS 宕机 | **内存缓冲区内容丢失，磁盘上数据库完好** |
| **介质故障**（硬故障） | 磁盘损坏、磁头碰撞、强磁场干扰 | **磁盘上的数据库本身被破坏**，最严重 |

第二步，破坏范围直接决定用哪几个动作。可用的动作只有三个：

- **UNDO（撤销）**：对**未完成**的事务，沿日志**反向**扫描，把它做过的修改逐条改回去 —— 保**原子性**（没做完的等于没做）
- **REDO（重做）**：对**已提交**的事务，沿日志**正向**扫描，把它的修改重新执行一遍 —— 保**持久性**（提交了的不能丢）
- **重装备份（转储）**：把整个数据库恢复到上一次备份时刻的状态

| 故障类型 | 恢复手段 |
|---|---|
| 事务故障 | 系统自动对该事务 **UNDO**（利用日志反向撤销），**无需 DBA 干预** |
| 系统故障 | 重启后扫描日志：**未提交事务 UNDO ＋ 已提交事务 REDO** |
| 介质故障 | **重装最近一次备份（转储）**，再用日志对备份之后已提交的事务 **REDO**；需 DBA 介入 |

**理解性记忆（别死背这张表，按下面三句推出来）**：

- 事务故障只有"自己没做完"这一个问题 → **只 UNDO**
- 系统故障时磁盘是好的，但断电那一瞬间有两种半拉子状态：已提交但改动还在内存没刷盘（**要 REDO 补上**）、没做完却已经有一半改动刷了盘（**要 UNDO 擦掉**）→ **两样都要**
- 介质故障连磁盘都没了，日志里记的修改**没有"底子"可以改回去** → 必须**先用备份把底子装回来，再 REDO 追平**备份之后的进度

**陷阱**：

- ❌ **"断电了只要 UNDO 就行"** —— 漏掉 REDO。断电最常见的错误选项就是"对所有事务都 UNDO"或"对所有事务都 REDO"，正确的是**分开对待**：未提交的 UNDO、已提交的 REDO。
- ❌ **"磁盘坏了，重装最近的备份即可"** —— 只重装备份会**丢掉备份之后所有已提交的数据**，必须再用日志 REDO 追平。
- ❌ 把"死锁被系统选中回滚"当成系统故障 —— 它只弄死了一个事务，是**事务故障**。
- ⚠️ 分清"**故障名称**"和"**故障别名**"：系统故障=软故障，介质故障=硬故障。题干可能直接用别名。

### 考点② ACID 四特性辨析（题干给场景 → 选是哪一条）

**题目长相**："转账执行到'已扣 A 的钱、尚未给 B 加钱'时失败，系统把扣款撤销恢复原状，这**最直接**体现了事务的（ ）"；或"下列关于事务 ACID 特性的叙述，错误的是（ ）"。

**怎么解**：先明确事务是什么——转账"A 给 B 转 100 元"在数据库里至少是两条更新（`A余额−100`、`B余额+100`）。若第一条执行完就断电，钱凭空消失；若两人同时给同一账户转账，更新还可能互相覆盖。**事务（Transaction）**就是把这样一组操作打包成不可分割的执行单位：以 `BEGIN TRANSACTION` 开始，以 `COMMIT`（提交，全部生效）或 `ROLLBACK`（回滚，全部撤销）结束。

四条承诺各管一件事，**每条都用转账场景对号入座**：

| 特性 | 含义 | 转账场景 |
|---|---|---|
| **原子性 Atomicity** | 事务里的操作**要么全做、要么全不做** | 扣了 A 的钱后系统出错，B 没加上钱 → 整个事务回滚，A 的扣款被撤销，不会"钱消失" |
| **一致性 Consistency** | 事务把数据库从一个**一致状态**变到另一个一致状态 | 转账前 A+B 总额 300 元，转账后总额仍是 300 元；只扣不加的"中间状态"绝不能作为最终结果留下 |
| **隔离性 Isolation** | 并发执行的事务**彼此不干扰**，如同串行执行 | 你转账进行到一半时，别人查不到"A 已扣款、B 未到账"的中间账目 |
| **持久性 Durability** | 一旦提交，修改**永久保存**，之后任何故障都不丢 | 银行提示"转账成功"（COMMIT 完成）后哪怕机房断电，重启后这笔钱也已经到账 |

**判据口径（一句话锁定）**：**原子性管"半截"，一致性管"总账"，隔离性管"别人"，持久性管"断电"**。看题干里出现的是哪个关键词，就选哪一条。

**陷阱**：

- ⚠️ **原子性 vs 一致性最容易混**。"失败了把已做的部分撤销"——描述的是**机制**，属原子性；"转账前后总额不变"——描述的是**结果/约束**，属一致性。一致性是原子性、隔离性、持久性共同保障出来的结果（⚠️ **此口径待核实**：部分资料确实表述为"事务系统通过保证 A、I、D 来保证 C"，但维基百科 ACID 词条明确把一致性视为需**独立校验**完整性约束/级联/触发器的特性（并举例：原子性成立、一致性仍可能被违反而必须回滚），百度百科"数据库事务"词条亦未把它写成前三者的推论——外部口径不一致，**做题不要依赖这句**），**题干若描述的是"回滚撤销"这个动作，答原子性**。
- ⚠️ "别人看不到中间状态"是**隔离性**，不是原子性——原子性关心的是**最终留不留下半截**，隔离性关心的是**过程中别人看不看得见**。

### 考点③ 三类并发问题的识别（给时序表 → 判是哪一类）

**题目长相**：给一张两列（T1/T2）的时序表，问"上述调度存在（ ）问题"；或者不给表，直接用一句话描述现象让你归类。

**怎么解——只看两件事：谁在写？对方提没提交？**

**（1）丢失更新——两个写互相覆盖**

| 时刻 | 事务T1 | 事务T2 |
|---|---|---|
| t1 | 读A=100 | |
| t2 | | 读A=100 |
| t3 | A←A−10，写回A=90 | |
| t4 | | A←A−20，写回A=80 |

两笔扣款都成功的话 A 应为 70，实际最终 A=80——**T1 的修改被 T2 覆盖丢失**。
**特征：两个事务都写同一数据，后写的把先写的抹掉。**

**（2）读脏数据——读了"后来被撤销"的数据**

| 时刻 | 事务T1 | 事务T2 |
|---|---|---|
| t1 | 读A=100，A←A−50，写回A=50 | |
| t2 | | 读A=50 |
| t3 | ROLLBACK（A恢复为100） | |

T2 读到的 50 是 T1 **未提交**的中间值，T1 一回滚这个值就从没存在过——T2 拿着一个"脏"数据在做后续计算。
**特征：读了别人未提交的修改，且对方随后回滚。**

**（3）不可重复读——同一事务内两次读结果不同**

| 时刻 | 事务T1 | 事务T2 |
|---|---|---|
| t1 | 读A=100 | |
| t2 | | A←A−30，写回A=70，COMMIT |
| t3 | 再读A=70（≠第一次的100） | |

T1 没做任何修改，两次读却不一致，无法基于第一次读的值做校验。
**特征：一个事务两次读之间，数据被另一个（已提交的）事务改了。**

**三步判读流程（拿到时序表就这么走）**：

1. 数一数**有几个事务在写**同一个数据。两个都写 → **丢失更新**，判完收工。
2. 只有一个在写、另一个在读 → 看**写方最后是 COMMIT 还是 ROLLBACK**。
3. ROLLBACK（读方读的是**未提交**值）→ **读脏数据**；COMMIT（读方**读了两次**、值变了）→ **不可重复读**。

**陷阱**：

- ⚠️ **读脏 vs 不可重复读的唯一分界线是"对方提交了没有"**：脏读读到的是**未提交、随后被撤销**的值；不可重复读读到的是**已提交的正常修改**，值本身完全合法，只是"变了"。看到 ROLLBACK 就往脏读上想，看到 COMMIT 就往不可重复读上想。
- ⚠️ 不可重复读**必须是同一事务读了两次**。只读一次，不构成"不可重复"。

### 考点④ 两种锁与相容矩阵（送分题）

> 口径说明：考点④⑤⑥（封锁与封锁协议）在计划文件中标注为【综述提及，**待核实**具体年份】——属《软件设计师教程》（第 5 版）固定内容，仍需掌握，只是没有交叉核实到具体真题年份，不能当作"已核实真题考点"。

**题目长相**："事务 T1 已对数据 R 加了 S 锁，此时 T2 对 R 的下列请求中能被满足的是（ ）"。

**怎么解**：先记住两把锁的能力边界——

- **S 锁（Share，共享锁 / 读锁）**：加了 S 锁**只能读**。多个事务可以**同时**对同一数据各持一把 S 锁（大家都只读，不冲突）。
- **X 锁（eXclusive，排他锁 / 写锁）**：加了 X 锁**既能读又能写**，且**独占**——别人任何锁都加不上。

相容矩阵（T2 请求时，T1 已持有）：

| T2请求＼T1已持有 | S锁 | X锁 |
|---|---|---|
| 请求S锁 | ✓ 相容 | ✗ 等待 |
| 请求X锁 | ✗ 等待 | ✗ 等待 |

**一句话口径**：**只有"读+读"能共存，沾上写（X）就必须等**。四格里唯一的 ✓ 是 S+S。

**陷阱**：

- ⚠️ **"先加 S 锁再升级为 X 锁"是个诱人的错误选项**——升级 X 锁一样要求"没有别人持锁"，别人还持着 S 锁时升不上去，仍然要等。别被"分两步走"绕进去。
- ⚠️ "任何锁都不能加"也是错的——别人持 S 锁时，S 锁是可以加的。

### 考点⑤ 三级封锁协议：哪一级防哪个问题

**题目长相**："事务 T 在修改数据前加 X 锁直到事务结束才释放，这属于（ ）级封锁协议，可防止（ ）"；或"要防止不可重复读，至少需要（ ）级封锁协议"。

**怎么解**：三级协议的差别只在**两个旋钮**——「读要不要加 S 锁」和「S 锁什么时候放」。

| 协议 | 加锁规则 | 累计解决的问题 |
|---|---|---|
| **一级** | 修改数据前加 X 锁，**事务结束才释放**（读不加锁） | 丢失更新 |
| **二级** | 一级 ＋ 读数据前加 S 锁，**读完即可释放** | 丢失更新 ＋ 读脏数据 |
| **三级** | 一级 ＋ 读数据前加 S 锁，**事务结束才释放** | 丢失更新 ＋ 读脏数据 ＋ 不可重复读 |

**为什么逐级生效（对照考点③三张时序表理解，不要死记）**：

- **一级防丢失更新**：要修改的事务必须**先拿到 X 锁才能动手（读—改—写整段都在锁内）**，且持有到事务结束。T2 想改 A 就得等 T1 整个结束，拿到锁后重新读到的是 T1 写回的新值，不会再基于旧值覆盖。
- **二级再防读脏**：T2 读 A 前要加 S 锁，而未提交的 T1 正持有 X 锁 → T2 必须等 T1 提交或回滚之后才能读，读到的一定不是"脏"值。但 S 锁**读完就放**，所以挡不住"两次读之间被人改"。
- **三级再防不可重复读**：S 锁**持有到事务结束**，T1 两次读期间 T2 根本拿不到 X 锁去改 A。

**陷阱**：

- ⚠️ **一级封锁协议对"读"不加任何锁**，所以它防不住脏读——这是最常见的送分陷阱："一级封锁协议可防止读脏数据"是**错**的。
- ⚠️ 二级和三级的规则字面上只差**"读完即放" vs "事务结束才放"**六个字，题干经常只改这一处来区分二级/三级，读题要盯住这句。
- ⚠️ 问"**至少**需要哪一级"时，答**能覆盖该问题的最低那一级**：丢失更新→一级；读脏→二级；不可重复读→三级。

### 考点⑥ 两段锁协议（2PL）

**题目长相**："关于两段锁协议，下列说法**错误**的是（ ）"——考法几乎固定为四选一挑错。

**怎么解**：

**定义**：每个事务分两个阶段——**扩展阶段**只能加锁、不能放锁；**收缩阶段**只能放锁、不能再加任何锁。即"**一旦开始放锁，就再也不许加锁**"。

**两条性质（两条都是考点，也是错误选项的产地）**：

1. 所有事务都遵守两段锁协议 ⇒ 并发调度**一定可串行化**（结果等价于某个串行执行顺序）。注意这是**充分条件、不是必要条件**——可串行化的调度**不一定**都遵守两段锁协议。
2. 两段锁协议**不能防止死锁**。反例：T1 已锁 A 再申请 B，同时 T2 已锁 B 再申请 A——双方都还在扩展阶段、**完全遵守协议**，却互相等待，死锁。

**陷阱**：

- ❌ **"遵守两段锁协议的事务不会发生死锁"** —— 本课最高频的错误选项，见上面反例。2PL 解决的是**串行化**，不是**死锁**，这是两个不同的问题。
- ❌ **"可串行化的调度一定遵守两段锁协议"** —— 把充分条件说成必要条件，反了。正确方向只有一个：**遵守 2PL ⇒ 可串行化**。
- ⚠️ 别把 2PL 的"两段"和"三级封锁协议"的"三级"混成一个体系：三级协议管的是**防哪几种并发问题**，2PL 管的是**整体调度等不等价于串行**，两者是不同维度。

### 考点⑦ 检查点（Checkpoint）

**题目长相**："设置检查点的主要作用是（ ）"，选项里常混入"减少日志文件大小""提高事务并发度"等似是而非的说法。

**怎么解**：

- **解决什么问题**：系统故障恢复要扫日志判断每个事务该 UNDO 还是 REDO——运行越久日志越长，重启恢复越慢。
- **做法**：系统周期性地设置检查点——把内存中的日志和修改过的数据缓冲区**强制写入磁盘**，并记录此刻**正在运行的事务清单**。
- **效果**：恢复时只需**从最近的检查点开始**处理，不必扫全部日志；**检查点之前已经提交的事务，其修改已确定落盘，不必 REDO**。

**陷阱**：

- ❌ "检查点的作用是缩小日志文件" —— 不对，检查点**不删日志**，它缩短的是**恢复时的扫描起点**，即恢复时间。
- ❌ "检查点能提高并发度" —— 检查点属于**恢复**机制（右腿），跟并发控制（左腿）不是一回事。

## 第 4 层 · 速记

> **总框架**：事务是最小可靠单位 → ACID 四条承诺 → **隔离性靠锁，原子性+持久性靠日志，一致性是结果**
>
> **事务定义**：一组"要么全做、要么全不做"的操作序列，是数据库**并发与恢复的基本单位**；BEGIN TRANSACTION … COMMIT / ROLLBACK
>
> **ACID**：**原子管半截、一致管总账、隔离管别人、持久管断电**
>
> **并发三问题**：**两写覆盖是丢失，读了没提交是脏，两次不一样是不可重复读**
>
> **锁相容**：**读读共存，沾写就等**（四格里只有 S+S 相容）
>
> **三级封锁**：**一级管写防丢失，二级读完放防脏，三级读到底防重复**（**一丢二脏三重复**）
>
> **两段锁 2PL**：**先加后放两阶段，一旦放锁不再加；保证可串行化（充分非必要），防不了死锁**
>
> **故障恢复**：**事务故障只 UNDO；系统故障 UNDO 未交 + REDO 已交；介质故障装备份 + REDO**
> （UNDO＝撤未完成、沿日志**反向**扫，救原子性；REDO＝重做已提交、沿日志**正向**扫，救持久性）
>
> **检查点**：**从最近检查点扫日志，检查点前已提交的不必 REDO**（缩短的是恢复时间，不是日志大小）

## 考题回顾

**1.【模拟·重现2022下考点】** 某事务在运行过程中，因输入数据错误导致该事务未能继续执行而中止，这属于哪类故障？此时数据库的恢复方式是：
A. 系统故障；重启后REDO　B. 事务故障；利用日志UNDO该事务　C. 介质故障；重装备份　D. 系统故障；UNDO+REDO

**解**：**B**。按考点①第一步判破坏范围——只有一个事务因自身原因（输入数据错误）没做完，系统和磁盘都完好，是**事务故障**；第二步选手段——只有"自己没做完"这一个问题，故只需利用日志**反向撤销（UNDO）**该事务已做的修改，由系统自动完成，无需 DBA 干预。

**2.【模拟·重现2024下考点】** 数据库因突然断电重启后进行恢复，正确的处理是：
A. 对所有事务都执行REDO
B. 对所有事务都执行UNDO
C. 对故障发生时未提交的事务执行UNDO，对已提交的事务执行REDO
D. 重装最近的数据库备份即可

**解**：**C**。断电属**系统故障**：磁盘完好但内存丢失。未提交的事务可能已把部分修改刷到磁盘，要 UNDO 擦掉（保原子性）；已提交的事务可能修改还没来得及刷盘，要 REDO 补上（保持久性）。A、B 都犯了"一刀切"的错——系统故障必须**分开对待**。D 是介质故障的手段，且只重装备份会丢掉备份之后所有已提交数据。

**3.【模拟】** 转账事务执行到"已扣 A 账户 100 元、尚未给 B 账户加钱"时失败，系统将扣款撤销、恢复原状。这最直接体现了事务的：
A. 一致性　B. 隔离性　C. 原子性　D. 持久性

**解**：**C**。**"要么全做、要么全不做"、失败就把已做的部分撤销**——这正是原子性的定义（"管半截"）。一致性是原子性等特性共同保障出来的"总账不错"的**结果**，但题干描述的**机制本身**是原子性。

**4.【模拟】** 关于两段锁协议，下列说法错误的是：
A. 事务分为加锁阶段和解锁阶段，解锁开始后不能再加锁
B. 所有事务都遵守两段锁协议，则调度一定是可串行化的
C. 遵守两段锁协议的事务不会发生死锁
D. 可串行化的调度不一定都遵守两段锁协议

**解**：**C**。A 是 2PL 的定义，正确；B 正确（2PL 是可串行化的**充分**条件）；D 正确（充分而非必要）。C 错误——两段锁协议**不能防止死锁**：T1 锁 A 后申请 B、T2 锁 B 后申请 A，两个事务都还在扩展阶段、完全遵守协议，却互相等待。**2PL 管串行化，不管死锁。**

**5.【模拟】** 事务T1已对数据R加了S锁，此时事务T2对R的下列请求中能被满足的是：
A. 加X锁　B. 加S锁　C. 先加S锁再升级为X锁　D. 任何锁都不能加

**解**：**B**。查相容矩阵：S 与 S 相容（都只读），S 与 X 不相容。T2 可以再加一把 S 锁一起读；想加 X 锁必须等 T1 释放。C 的"升级为 X 锁"同样受制于"X 锁要独占"，T1 的 S 锁还在就升不上去，仍要等；D 与 S+S 相容矛盾。

## 自测练习

1. 【模拟】机房磁盘阵列物理损坏导致数据库文件不可读，这属于哪类故障？完整的恢复步骤是什么？
2. 【模拟】看时序判类型：T1读X=50；T2读X=50；T1把X改为40并写回；T2把X改为30并写回。最终X=30。这是哪类并发问题？三级封锁协议中最低哪一级就能防止它？
3. 【模拟】二级封锁协议为什么不能防止"不可重复读"？（用"S锁什么时候释放"来解释）

### 参考答案

1. **介质故障**（磁盘上的数据库本身被破坏，最严重的一类）。恢复步骤：①更换/修复存储介质；②**重装最近一次数据库备份（转储）**，把数据库恢复到备份时刻的状态；③利用日志文件，对备份时刻之后**已提交**的事务执行 **REDO**，把进度追到故障前最后一次提交。仅靠备份不够——会丢失备份之后所有已提交的修改。

2. **丢失更新**：T1、T2 都写 X，T2 后写回，把 T1 的修改覆盖了（两笔都生效应为 50−10−20＝**X=20**，实际却是 30）。**一级封锁协议**即可防止。
   > **机制说明**：一级封锁协议**对纯读操作不加锁**，所以不能笼统说成"T2 必须等 T1 结束后才能读"。准确的说法是——**要修改数据的事务必须先拿到 X 锁再执行"读—改—写"整段**，且 X 锁持有到事务结束。于是 T2 的整段"读—改—写"被推迟到 T1 结束之后，它拿到锁后读到的是 T1 写回的新值 40，写回 20，覆盖不再发生。也正因为"纯读不加锁"，一级封锁协议**防得住丢失更新、却防不住脏读**。

3. 二级封锁协议里 S 锁**读完即可释放**。T1 第一次读完 A 就把 S 锁放了，此时 T2 可以获得 X 锁修改 A 并提交；T1 第二次再读时值已不同——**两次读之间没有锁保护**。要防不可重复读必须把 S 锁**持有到事务结束**（三级封锁协议），让 T1 两次读期间任何人都拿不到 X 锁去改 A。
