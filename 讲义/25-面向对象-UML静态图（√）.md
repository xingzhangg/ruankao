# 25 · 面向对象：UML 静态图

> 真题：部署图与"汽车-组成关系"2019上、构件图 2022下、包图 2023上、类图关系 2017下、类图泛化 2024上（考点重现）；4+1 视图与用例泛化两题年份待核实｜无计算｜未讲

---

## 定位

**这一课回答**：一张 UML 图上允许出现哪些东西、东西之间能连哪几种关系、静态那几张图各画什么、谁看哪一张。七节顺着这四个问题走。第一到三节回答前三问：构造块与四类事物、五大关系加实现（本课分值中心）、13 种图怎么分成结构图与行为图。第四到六节逐张过静态六图（类图、对象图、用例图、构件图、部署图、包图）。第七节按"谁看"重新分一遍（4+1 视图）。全程跟着"给公司做内部报销系统"这一个例子走。

---

## 开讲：三个人画了三张图，谁也看不懂谁的

给公司做内部报销系统：员工填单、主管审批、财务打款。需求评审开完，三个人各交了一张图。产品经理画的是几个小人连着一串椭圆；开发画的是一堆三格方框，框之间连着实线虚线；运维画的是三个立方体，里面写着 MySQL。三个人互相说对方画的不对，其实谁也没看懂谁的。

最朴素的想法是：**大家约定一套画法**。可这句话要落地，得先答四个问题——这四个问题就是这一课的四块内容：

- ① 图上到底**允许出现哪些东西**？不然你画云朵我画圆柱，谁也不知道对方指什么。
- ② 东西和东西之间**能怎么连**、每种连法什么意思？开发那张图上三种线，看不出区别。
- ③ 一张图画不完整个系统，那要**画几张、每张管什么**？三个人画的根本不是一件事，却在互相挑错。
- ④ 画完之后，产品、开发、运维、老板**各看哪几张**？老板不看类图，程序员不看部署图。

UML（Unified Modeling Language，统一建模语言）就是逐条回答这四个问题的。它是一种**可视化的建模语言，而非程序设计语言**，支持从需求分析开始的软件开发的全过程。

**它只规定怎么画，不规定项目怎么走**——先做需求还是先搭架子，那是瀑布、RUP 那类过程模型管的事。"UML 是一种方法/过程"是最常见的错误选项。

### 一、图上能出现什么：构造块（补①）

UML 的结构包括**构造块、规则和公共机制**三个部分。**构造块**是零件（下面细讲）；**规则**是"构造块如何放在一起的规定"，比如同一个包里两个类不能重名；**公共机制**是画哪张图都通用的那几套小手段——给任何元素贴一张注解、加一个 `«component»` 这样的尖括号标签（这种标签叫**构造型**，用来说明"这个框其实是个构件"）。

构造块只有三种：**事物（thing）、关系（relationship）和图（diagram）**。事物是名词，关系是连线、把事物紧密联系在一起，图是多个相互关联的事物的集合——这一课后面几节正好对应这三样。

**先猜一下**：包（package，也就是 `com.company.reimburse` 这种代码目录）在 UML 里属于哪一类事物？多数人答"结构事物"，因为它装东西。不对。四类事物是：

- **结构事物**：模型的**静态部分**，如类、接口、用例、构件等
- **行为事物**：模型的**动态部分**，如交互、活动、状态机
- **分组事物**：模型的**组织部分**，如包
- **注释事物**：模型的**解释部分**，依附于一个元素或一组元素之上对其进行约束或解释的简单符号

判据是**它有没有在描述系统本身**。类、用例、构件说的是系统里有什么；交互、活动、状态机说的是系统怎么动；而包只是个文件夹、注解只是张便签，两者都不描述系统，所以各自单独占一类。

报销系统里对照着看：类是"报销单""员工"；用例是用户拿系统做的一件完整的事，比如"提交报销单"；构件是可以单独编译替换的软件块，比如打出来的 `reimburse-service.jar`；状态机是报销单从"草稿"走到"已打款"这一串状态；包是 `com.company.reimburse` 这样的代码目录；注解是图边上写的一句"金额单位为分"。

符号照下面这张图认：类是三格矩形，接口是小圆圈，协作是虚线椭圆（协作指一组类为完成某个功能凑在一起的配合），用例是实线椭圆，结点是立方体，构件带 `«component»`、制品带 `«artifact»`（制品就是打包落到磁盘上的那个文件），包是左上角带小标签的文件夹，注解是右上角折角的纸片。

![UML 中的事物：类/接口/协作/用例/主动类/构件/制品/结点/消息/状态/动作/包/注解](images/fig_d14_s012.jpg)

图上比上面这段多出四个符号，按刚讲完的四类事物归位就行：**主动类**（自己带一条控制线程的类）也是结构事物；**消息、状态、动作**是行为事物（状态是圆角矩形、动作是两头圆的体育场形，扫描件上几乎同形，本课不考画法，扫一眼即可）。图里接口画了两种（小圆圈和带 `«interface»` 的方框），是同一样东西的两种画法。

### 二、东西之间怎么连：五大关系（补②，本课分值中心）

UML 把关系归成四条：依赖、关联、泛化、实现，关联下面再分聚合和组合；画到图上就是六种线。软考卷面和下午题最常点名的是**泛化、关联、依赖、聚合、组合**这五种，所谓"五大关系"指的就是它们，实现单算一种，画法和泛化像，放在一起讲。

**先猜一下**：两组"整体—部分"——**报销单和它下面的费用明细**、**部门和部门里的员工**，哪个是聚合、哪个是组合？多数人一看见"整体-部分"四个字，要么两个都选组合，要么凭"哪个更紧密"的感觉猜。判据其实只有一句：**整体没了，部分还在不在。**

- 报销单删了，"餐费 120 元"这条明细就没有意义了，也不可能挪到别的单子上 → **组合**
- 部门撤了，员工还在，转去别的部门 → **聚合**

定义说的是同一件事：**关联**是一种结构关系，描述了一组链，链是对象之间的连接；关联分为**组合和聚合**，都是**部分和整体的关系**，其中**组合事物之间关系更强**。
"更强"强在两条，**两条都要用**：① 生命周期绑死；② 部分只能属于一个整体、不能拆去装到别的整体上（明细不能同时挂在两张单上，员工却可以借调）。第 ① 条分不开的时候就看第 ② 条——汽车报废了座位、车窗、发动机实物都还在，光看 ① 判不出来；但座位、车窗、发动机是随这辆车配的，音乐系统却能拆下来装到别的车上，所以只有音乐系统不是组合。

画法上两者都是实线加菱形，**菱形贴整体那一端**：空心菱形是聚合，实心菱形是组合。

![UML 六种关系的画法：关联/依赖/泛化/聚合/组合/实现](images/fig_d14_s013.jpg)

图里 (b) 依赖和 (f) 实现**都是虚线**，区别只在箭头：(b) 是填黑的小箭头，(f) 是空心三角。印刷件上看不清就放大看三角填没填色。

剩下四种，还是拿报销系统配例子：

- **关联**——报销单和员工。报销单一直记着"这单是谁提的"，两边长期认识。画成一条实线，两端可以标多重度和角色名（下面讲）。
- **依赖**——报销单和汇率服务。报外币差旅费时调一下汇率服务折算成人民币，算完就不再记着它。画成虚线加细箭头，箭头指向被用的那一方。定义是"**一个事物的语义依赖于另一个事物的语义的变化而变化**"——汇率服务改了方法签名，报销单的代码要跟着改，反过来不用。
- **泛化**——交通费报销单、招待费报销单和报销单。定义是"**一般/特殊的关系**，子类和父类之间的关系"。实线加空心三角，三角贴**父类**那一端。
- **实现**——"金额分级审批"这个类和"审批策略"这个接口。接口只写死一句"必须能审批"，类负责真去审。定义是"**一个类元指定了另一个类元保证执行的契约**"（"类元"是类、接口这类可以被实例化或被实现的建模元素的统称）。虚线加空心三角，三角贴接口。

两对最容易混的，各给一个判据：

**关联 vs 依赖，判据是"是不是长期持有"。** 写成代码一眼就分清：

```java
class 报销单 {
    private 员工 提单人;                       // 成员变量，一直持有 → 关联
    void 换算(汇率服务 s) { s.折算(this.金额); } // 只是方法参数，用完就走 → 依赖
}
```

方法参数、局部变量、返回值、静态调用都算依赖；只有成员变量才是关联。**泛化 vs 实现，箭头形状一样（都是空心三角），看线型**：实线是泛化（Java 里的 `extends`），虚线是实现（`implements`）。

**多重度**就是关联线两端写的那个数字，说明"对方的一个实例对应这一端多少个"：`1` 恰好一个，`0..1` 至多一个，`*` 任意多（含 0 个），`1..*` 至少一个，`m..n` 从 m 到 n 个。报销单 `1` ——— `1..*` 费用明细，读作"一张单至少一条明细，一条明细只属于一张单"。

同两个类之间还可以拉多条关联线，靠**角色名**区分：两个类之间的关联，实际上是两个类所扮演**角色**的关联，因此两个类之间可以有多个由不同角色标识的关联。员工和部门之间就是两条：一条标 member（我是这个部门的人），一条标 manager（我管这个部门）。

⚠️ 一个坑：下面这张教材类图里，有个**实心**菱形，旁边标的中文却是"聚集"。别被带跑——"聚集"是"整体-部分"这一族的统称，空心菱形的聚合、实心菱形的组合都在这一族里，图上那个标签给的是族名，不是说这个菱形该画成空心。**做题认菱形填不填色，不认旁边的中文标签。**

![教材 UML 类图示例：类/属性/操作/角色/多重度/关联/泛化/依赖/接口](images/fig_d14_s016.jpg)

顺带在这张图上认两样：上面说的**角色名**，图里就有——Department 和 Person 之间那两条线分别标着 `member` 和 `manager`；另外 Office 框的第三格里写着 `Department`，按"第三格是操作"读不通，那是原图画法，不用管。

> 考试这样问：给一段业务描述，问两个类之间属于哪种关系、菱形画在哪一端；下午题 3 还会让你在给定类图上补关系和多重度。

### 三、一张图画不完：图的分类（补③）

顶层分类只有一个维度：**画"系统里有什么"的叫结构图（静态图），画"什么时候发生什么"的叫行为图（动态图）**。UML 2.0 的图，按《软件设计师教程》第 5 版是：

- **结构图 6 种**：类图、对象图、包图、组合结构图、构件图、部署图
- **行为图 7 种**：用例图、顺序图、通信图、交互概览图、定时图、状态图、活动图

6 + 7 = 13，**考试按教材这个 13 答**。

⚠️ 「14 种」有两种说法，别搞混：教材的说法是「有的资料把**制品图**也单列，凑成 14」；而 **UML 官方规范**里的第 14 种其实是**剖面图**（profile diagram，用构造型扩展 UML 的那张），制品图在官方规范里不是独立图种、只是部署图上的元素。题目问「UML 2.0 一共几种图」按教材答 13，看到「剖面图」这个名字认得它是官方结构图之一即可。
真正展开讲的有十张：静态六张（类图、对象图、用例图、构件图、部署图、包图）都在本课；动态四张里，顺序图和通信图在讲义 26，状态图和活动图在讲义 27。

用例图到底算静态图还是行为图，两种口径打架，本节末的深入块说清楚，跳过不影响后面。

#### 深入 · 用例图算静态图还是行为图

国内教材与真题的口径把用例图标为"静态图"，沿用的是"用例图对系统的**静态用例视图**建模"这个老说法；而 UML 官方分类把用例图放在行为图里。卷面绝大多数题问的是"这张图画什么"，不受这个分歧影响；万一直接问静动归属，按**静态**答。

### 四、系统里有哪些类：类图，以及它的快照对象图

**类图**是静态图，为系统的**静态设计视图**，展现一组**对象、接口、协作和它们之间的关系**。（这句里的"对象"实指类——类图画的是类，真正画某一时刻具体对象的是下面的对象图。）

类画成三格矩形：第一格类名（**抽象类的类名用斜体**），第二格属性，第三格操作；每一项前面的可见性符号是 `+` 公有、`-` 私有、`#` 受保护。类图**不**管的事也考过：真题问"UML 类图通常不用于对（ ）进行建模"，答案是"对象快照"——快照是对象图的活。

**对象图**是静态图，展现**某一时刻一组对象及它们之间的关系**，为类图的某一快照；在没有类图的前提下，对象图就是静态设计视图。

看图分辨：对象图上每个方框写的是 `Zhang : Student` 这种"对象名 : 类名"并**加下划线**，也可以只写 `: Course`（不关心叫什么名字，叫匿名对象）；格子里放的是 `name = "计算机导论"` 这样的**具体值**，不是类型；对象之间的连线叫**链**，就是关联在这一刻的实例。

**类图 vs 对象图的判据**：看格子里是类型还是具体值；题干里出现"某一时刻""快照""实例"，就是对象图。

### 五、用户拿它能干什么：用例图

**用例图**（静动归属有两种口径，见第三节末的深入块，卷面按**静态**答）展现了一组**用例、参与者以及它们之间的关系**。用例图中的参与者是人、硬件或其他系统可以扮演的角色；用例是参与者完成的一系列操作，用例之间的关系有**扩展、包含、泛化**。

三要素：参与者画成小人，用例画成椭圆，系统边界画成一个大方框。要留意参与者的判据是"**在系统边界外**"而不是"是不是人"——参与者是人、硬件或其他系统可以扮演的**角色**，所以对接的银行打款接口、公司的单点登录系统同样是参与者。

三种关系，给判据，不背箭头。问一句：**去掉它，基用例（就是那个主流程用例）还走不走得完？**

- 走不完 → **包含 include**。"提交报销单"每次都要"校验预算余额"，这是抽出来复用的公共步骤。
- 走得完，只是少一个可选分支 → **扩展 extend**。"提交报销单"金额超过 5000 元才追加"二级审批"，不超过就没这一步。
- 两个东西是"同一件事的两种做法" → **泛化**。"扫描发票录入"和"手工录入"都是"录入发票"的一种。

箭头方向：include 和 extend 都是虚线加细箭头，方向正好相反——**include 从基用例指向被包含用例，extend 从扩展用例指向基用例**。对着下面这张图书管理系统的用例图看：登记外借信息 ⇢`«include»` 用户登录；修改书籍信息 ⇢`«extend»` 查询书籍信息。

真记不住方向，就用一句话统一记：**箭头永远指向"不知道对方存在也照样成立"的那一端**——"用户登录"用不着知道谁在包含它，"查询书籍信息"也用不着知道谁在扩展它。

这句话对**依赖、泛化、实现、include、extend** 五种都成立；但关联画的是不带箭头的实线，聚合、组合画的是菱形不是箭头，这两类不套这句话，另按"菱形贴整体端"记。泛化则是实线加空心三角，子指父，和类图一样。

![UML 用例图：参与者、用例、系统边界、include 与 extend](images/fig_d14_s018.jpg)

看这张图先注意一点：**用例名写在椭圆下方，不在椭圆里面**，别认错归属——两条 `«include»` 的箭头尖都落在中间那个椭圆上，它叫"用户登录"。

> 考试这样问：给一句"每次都要……"或"仅当……才……"的业务描述，问两个用例之间是哪种关系、虚线箭头朝哪一端。

### 六、代码打成什么包、装在哪台机器上：构件图、部署图与包图

**构件图（组件图）**是静态图，为系统**静态实现视图，展现了一组构件之间的组织和依赖**。（这个「实现」指**代码落地**，不是第二节那个虚线空心三角的「实现关系」。）构件就是可以独立替换的软件单元，报销系统里就是"审批服务""报销单管理"这样能整体换掉的模块；把它编译打包后落到磁盘上的那个 `reimburse-service.jar` 文件，UML 里另有名字，叫**制品**（artifact），下面部署图要用到。

图上除了方框还有两个符号：**供接口**（我对外提供的接口）画成一根线顶个**小圆圈**，像棒棒糖；**需接口**（我要别人提供给我的接口）画成**半圆插座**。画出来长这样：

```
  ┌──────────┐                    ┌──────────┐
  │ 审批服务  │───○           ⊂───│ 打款服务  │
  └──────────┘   ↑           ↑    └──────────┘
              供接口        需接口
              （棒棒糖）    （半圆插座）

        ○ 插进 ⊂ 就是「装配」：审批服务提供的，正好是打款服务要的
```

两个构件之间的虚线箭头，从需接口一端指向供接口一端。

⚠️ 又一个坑：**别的资料的构件图上，"供接口""需接口"两个中文标注常被标反**——"供接口"的引线拉到了半圆插座上，"需接口"的引线拉到了圆圈上。**认符号不认标签：圆圈＝供，半圆＝需。**

**部署图**是静态图，为系统**静态部署视图**，画的是**物理模块（结点）在系统里怎么分布**。它与构件图相关，通常一个结点包含一个或多个构件；结点之间的依赖和包之间的依赖一样，**是单向的**。

图上画的是**立方体**，一个立方体是一个结点（一台服务器、一台终端），立方体里装着 `«artifact»` 制品（就是上面说的打包落盘的文件，war 包、数据库文件都算），立方体之间的连线是通信路径，线上可以标协议和端口，比如 `https:80`。

**判据一句话：图上有没有立方体。** 构件图只画软件模块之间的供需关系，一台机器都不出现；部署图才有机器，也才回答"这个 jar 装在哪台服务器上"。所以题干**同时出现"软件"和"硬件"**时：问的是图，答部署图；问的是视图，答部署视图（4+1 里的部署视图也讲"软件到硬件的映射"，两者别答串）。

**包图**也考过。这里的"包"是 `com.company.reimburse` 那种源码目录的包，不是上面 jar 包的包。包是分组事物，包图画的是模型本身分解成的组织单元及其依赖关系。四条规则记住就够答题：包里可以装类、接口、构件、结点；**一个元素只能被一个包拥有**（归属唯一）；包可以嵌套包；**同一个包内的元素不能重名**——不同包里可以重名，靠包名限定，就像 Java 里 `java.util.List` 和 `java.awt.List` 能共存。

> 考试这样问：给一句定义让你选图名，构件图与部署图这一对最爱互换设错；包图那四条规则则是挑"哪一条不正确"。

### 七、同一套图，各人看各人那一面：4+1 视图（补④）

图都画完了，可产品经理不看部署图、运维不看类图。4+1 视图就是**按"谁看"把图重新分一遍**，"+1"的那个是用例视图，其余四个都围着它转。

| 视图 | 定义句 | 画的是什么 | 主要给谁看 |
|---|---|---|---|
| 逻辑视图（也称设计视图） | 设计模型中在架构方面具有重要意义的部分，即**类、子系统、包和用例实现的子集** | 类与对象 | 系统分析、设计人员 |
| 进程视图 | **可执行线程和进程作为活动类的建模**，它是**逻辑视图的一次执行实例，描述了并发与同步结构** | 线程、进程、并发 | 系统集成人员 |
| 实现视图 | 对组成基于系统的**物理代码的文件和构件**进行建模——**就是第六节构件图画的那一层** | 源代码结构 | 程序员 |
| 部署视图 | 把**构件部署到一组物理节点上**，表示软件到硬件的映射和分布结构 | 软件到硬件的映射 | 系统和网络工程师 |
| 用例视图 | **最基本的需求分析模型** | 用例 | 最终用户 |

## 速记

- UML 是**语言不是过程**；结构＝构造块＋规则＋公共机制；构造块＝事物＋关系＋图
- 事物四类：结构（类/接口/用例/构件）、行为（交互/活动/状态机）、分组（包）、注释（注解）
- 五大关系＋实现：菱形贴整体，**空心聚合、实心组合**；整体亡部分亡＝组合；成员变量＝关联、参数临时用＝依赖；空心三角指父，**实线泛化、虚线实现**
- 多重度：`1` 恰一、`0..1` 至多一、`*` 任意多、`1..*` 至少一；同两类之间可有多条关联，用角色名区分
- 图 **13 种**（教材口径，按它答）＝结构图 6（类/对象/包/组合结构/构件/部署）＋行为图 7（用例/顺序/通信/交互概览/定时/状态/活动）；教材说的「第 14 种」是制品图，而官方规范的第 14 种是**剖面图**，两者别串
- 认图：快照＝对象图，类接口协作＝类图，用例参与者＝用例图，构件组织依赖＝构件图（静态实现视图），软硬件物理关系＝部署图（有立方体）
- 用例三关系：每次都做＝include（基→被包含），有条件才做＝extend（扩展→基），两种做法＝泛化；包图四规则，元素只能属一个包
- 4+1：进程视图＝逻辑视图的一次执行实例、并发与同步；用例视图＝最基本的需求分析模型
