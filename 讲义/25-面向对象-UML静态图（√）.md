## 开讲：三个人画了三张图，谁也看不懂谁的

给公司做内部报销系统：员工填单、主管审批、财务打款。需求评审开完，三个人各画了一张图交上来。产品经理画的是几个小人连着一串椭圆；开发画的是一堆三格方框，框之间连着实线虚线；运维画的是三个立方体，里面写着 MySQL。三个人互相说对方画的不对，其实谁也没看懂谁的。

最朴素的想法是：**大家约定一套画法**。可这句话要落地，得先答四个问题——这四个问题就是这一课的四块内容：

- ① 图上到底**允许出现哪些东西**？不然你画云朵我画圆柱，谁也不知道对方指什么。
- ② 东西和东西之间**能怎么连**、每种连法什么意思？开发那张图上三种线，看不出区别。
- ③ 一张图画不完整个系统，那要**画几张、每张管什么**？三个人画的根本不是一件事，却在互相挑错。
- ④ 画完之后，产品、开发、运维、老板**各看哪几张**？老板不看类图，程序员不看部署图。

UML 就是逐条回答这四个问题的。先把名字说清：UML（Unified Modeling Language，统一建模语言），培训资料的原话是"是一种**可视化的建模语言，而非程序设计语言**，支持从需求分析开始的软件开发的全过程"。**它只规定怎么画，不规定项目怎么走**——先做需求还是先搭架子，那是瀑布、RUP 那类过程模型管的事。"UML 是一种方法/过程"是最常见的错误选项。

### 一、图上能出现什么：构造块（补①）

原文："从总体上来看，UML 的结构包括**构造块、规则和公共机制**三个部分。"三个词一句话说清：**构造块**是零件（下面细讲）；**规则**是"构造块如何放在一起的规定"，比如同一个包里两个类不能重名；**公共机制**是"达到特定目标的公共 UML 方法"，比如给任何元素都能贴一张注解、都能加一个 `«component»` 这样的标签（这种尖括号标签叫构造型，用来说明"这个框其实是个构件"）。

构造块只有三种："UML 有三种基本的构造块，分别是**事物（thing）、关系（relationship）和图（diagram）**。事物是 UML 的重要组成部分，关系把事物紧密联系在一起，图是多个相互关联的事物的集合。" 事物是名词，关系是连线，图是一组事物加连线的集合——这一课后面三节正好对应这三样。

**先猜一下**：包（package，也就是 `com.company.reimburse` 这种代码目录）在 UML 里属于哪一类事物？多数人答"结构事物"，因为它装东西。不对。四类事物是：

- **结构事物**：模型的**静态部分**，如类、接口、用例、构件等
- **行为事物**：模型的**动态部分**，如交互、活动、状态机
- **分组事物**：模型的**组织部分**，如包
- **注释事物**：模型的**解释部分**，依附于一个元素或一组元素之上对其进行约束或解释的简单符号

判据是**它有没有在描述系统本身**。类、用例、构件说的是系统里有什么；交互、活动、状态机说的是系统怎么动；而包只是个文件夹、注解只是张便签，两者都不描述系统，所以各自单独占一类。报销系统里对照着看：类是"报销单""员工"；用例是用户拿系统做的一件完整的事，比如"提交报销单"；构件是可以单独编译替换的软件块，比如打出来的 `reimburse-service.jar`；状态机是报销单从"草稿"走到"已打款"这一串状态；包是 `com.company.reimburse` 这样的代码目录；注解是图边上写的一句"金额单位为分"。

符号照着培训资料这张图认（类是三格矩形，接口是小圆圈，协作是虚线椭圆——协作指一组类为完成某个功能凑在一起的配合，用例是实线椭圆，结点是立方体，构件带 `«component»`、制品带 `«artifact»`——制品就是打包落到磁盘上的那个文件，包是左上角带小标签的文件夹，注解是右上角折角的纸片）：

### 二、东西之间怎么连：五大关系（补②，本课分值中心）

培训资料只列四条：依赖、关联、泛化、实现，关联下面再分聚合和组合；画到图上就是六种线。软考卷面和下午题最常点名的是**泛化、关联、依赖、聚合、组合**这五种，所谓"五大关系"指的就是它们，实现单算一种，画法和泛化像，放在一起讲。

**先猜一下**：两组"整体—部分"——**报销单和它下面的费用明细**、**部门和部门里的员工**，哪个是聚合、哪个是组合？多数人一看见"整体-部分"四个字，要么两个都选组合，要么凭"哪个更紧密"的感觉猜。判据其实只有一句：**整体没了，部分还在不在。**

- 报销单删了，"餐费 120 元"这条明细就没有意义了，也不可能挪到别的单子上 → **组合**
- 部门撤了，员工还在，转去别的部门 → **聚合**

原文说的是同一件事："**关联**：是一种结构关系，描述了一组链，链是对象之间的连接。分为**组合和聚合**，都是**部分和整体的关系**，其中**组合事物之间关系更强**。""更强"强在两点：生命周期绑死，而且部分只能属于一个整体（明细不能同时挂在两张单上，员工却可以借调）。画法上两者都是实线加菱形，**菱形贴整体那一端**：空心菱形是聚合，实心菱形是组合。

![UML 六种关系的画法：关联/依赖/泛化/聚合/组合/实现](../外部资源/转录md/images/fig_d14_s013.png)

剩下四种，还是拿报销系统配例子：

- **关联**——报销单和员工。报销单一直记着"这单是谁提的"，两边长期认识。画成一条实线，两端可以标多重度和角色名（下面讲）。
- **依赖**——报销单和汇率服务。报外币差旅费时调一下汇率服务折算成人民币，算完就不再记着它。画成虚线加细箭头，箭头指向被用的那一方。原文："**依赖**：**一个事物的语义依赖于另一个事物的语义的变化而变化**"——汇率服务改了方法签名，报销单的代码要跟着改，反过来不用。
- **泛化**——交通费报销单、招待费报销单和报销单。原文："**泛化**：**一般/特殊的关系**，子类和父类之间的关系。"实线加空心三角，三角贴**父类**那一端。
- **实现**——"金额分级审批"这个类和"审批策略"这个接口。接口只写死一句"必须能审批"，类负责真去审。原文："**实现**：**一个类元指定了另一个类元保证执行的契约**。"（"类元"是类、接口这类可以被实例化或被实现的建模元素的统称。）虚线加空心三角，三角贴接口。

两对最容易混的，各给一个判据：

**关联 vs 依赖，判据是"是不是长期持有"。** 写成代码一眼就分清：

```java
class 报销单 {
    private 员工 提单人;                       // 成员变量，一直持有 → 关联
    void 换算(汇率服务 s) { s.折算(this.金额); } // 只是方法参数，用完就走 → 依赖
}
```

方法参数、局部变量、返回值、静态调用都算依赖；只有成员变量才是关联。**泛化 vs 实现，箭头形状一样（都是空心三角），看线型**：实线是泛化（Java 里的 `extends`），虚线是实现（`implements`）。

**多重度**就是关联线两端写的那个数字，说明"对方的一个实例对应这一端多少个"：`1` 恰好一个，`0..1` 至多一个，`*` 任意多（含 0 个），`1..*` 至少一个，`m..n` 从 m 到 n 个。报销单 `1` ——— `1..*` 费用明细，读作"一张单至少一条明细，一条明细只属于一张单"。同两个类之间还可以拉多条关联线，靠**角色名**区分，原文："两个类之间的关联，实际上是两个类所扮演角色的关联，因此，两个类之间可以有多个由不同角色标识的关联。"员工和部门之间就是两条：一条标 member（我是这个部门的人），一条标 manager（我管这个部门）。

⚠️ 一个坑：培训资料引用的教材类图里，有个**实心**菱形，旁边标的中文却是"聚集"。别被带跑——"聚集"是"整体-部分"这一族的统称，空心菱形的聚合、实心菱形的组合都在这一族里，图上那个标签给的是族名，不是说这个菱形该画成空心。**做题认菱形填不填色，不认旁边的中文标签。**

### 三、一张图画不完：图的分类（补③）

原文只留了一句："UML 2.0 图，书上是 13 种，有的说法还包含制品图，一共 14 种，了解即可，总分类如下："——但它后面挂的那张图其实是两道真题的截图，说好的分类表并没有转录进来（下面练习 5 用的就是这张截图）。顶层分类只有一个维度：**画"系统里有什么"的叫结构图（静态图），画"什么时候发生什么"的叫行为图（动态图）**。按教材第 5 版补齐是：

- **结构图 6 种**：类图、对象图、包图、组合结构图、构件图、部署图
- **行为图 7 种**：用例图、顺序图、通信图、交互概览图、定时图、状态图、活动图

6 + 7 = 13，再加上制品图正好是原文那句"一共 14 种"。培训资料真正展开讲的只有九张：静态五张（类图、对象图、用例图、构件图、部署图）都在本课；动态四张里，顺序图和通信图在讲义 26，状态图和活动图在讲义 27。

一处口径要知道：培训资料给用例图标的是"静态图"，沿用的是"用例图对系统的**静态用例视图**建模"这个老说法；而 UML 官方分类把用例图放在行为图里。卷面绝大多数题问的是"这张图画什么"，不受这个分歧影响；万一直接问静动归属，按培训资料答**静态**。

### 四、系统里有哪些类：类图，以及它的快照对象图

原文："**类图**：静态图，为系统的**静态设计视图**，展现一组**对象、接口、协作和它们之间的关系**。"（这句里的"对象"实指类——类图画的是类，真正画某一时刻具体对象的是下面的对象图。）

类画成三格矩形：第一格类名（**抽象类的类名用斜体**），第二格属性，第三格操作；每一项前面的可见性符号是 `+` 公有、`-` 私有、`#` 受保护。类图**不**管的事也考过：培训资料收的真题问"UML 类图通常不用于对（ ）进行建模"，答案是"对象快照"——快照是对象图的活。

原文："**对象图**：静态图，展现**某一时刻一组对象及它们之间的关系**，为类图的某一快照。在没有类图的前提下，对象图就是静态设计视图。"看图分辨：对象图上每个方框写的是 `Zhang : Student` 这种"对象名 : 类名"并**加下划线**，也可以只写 `: Course`（不关心叫什么名字，叫匿名对象）；格子里放的是 `name = "计算机导论"` 这样的**具体值**，不是类型；对象之间的连线叫**链**，就是关联在这一刻的实例。

**类图 vs 对象图的判据**：看格子里是类型还是具体值；题干里出现"某一时刻""快照""实例"，就是对象图。

### 五、用户拿它能干什么：用例图

原文："**用例图**：静态图，展现了一组**用例、参与者以及它们之间的关系**。用例图中的参与者是人、硬件或其他系统可以扮演的角色；用例是参与者完成的一系列操作，用例之间的关系有**扩展、包含、泛化**。"

三要素：参与者画成小人，用例画成椭圆，系统边界画成一个大方框。要留意参与者的判据是"**在系统边界外**"而不是"是不是人"——原文写得很清楚，参与者是人、硬件或其他系统可以扮演的**角色**，所以对接的银行打款接口、公司的单点登录系统同样是参与者。

三种关系，给判据，不背箭头。问一句：**去掉它，基用例（就是那个主流程用例）还走不走得完？**

- 走不完 → **包含 include**。"提交报销单"每次都要"校验预算余额"，这是抽出来复用的公共步骤。
- 走得完，只是少一个可选分支 → **扩展 extend**。"提交报销单"金额超过 5000 元才追加"二级审批"，不超过就没这一步。
- 两个东西是"同一件事的两种做法" → **泛化**。"扫描发票录入"和"手工录入"都是"录入发票"的一种。

箭头方向：include 和 extend 都是虚线加细箭头，方向正好相反——**include 从基用例指向被包含用例，extend 从扩展用例指向基用例**。对着培训资料那张图书管理系统的图看：登记外借信息 ⇢`«include»` 用户登录；修改书籍信息 ⇢`«extend»` 查询书籍信息。真记不住方向，就用一句话统一记：**箭头永远指向"不知道对方存在也照样成立"的那一端**——"用户登录"用不着知道谁在包含它，"查询书籍信息"也用不着知道谁在扩展它。这句话对**依赖、泛化、实现、include、extend** 五种都成立；但关联画的是不带箭头的实线，聚合、组合画的是菱形不是箭头，这两类不套这句话，另按"菱形贴整体端"记。泛化则是实线加空心三角，子指父，和类图一样。

### 六、代码打成什么包、装在哪台机器上：构件图与部署图

原文："**构件图（组件图）**：静态图，为系统**静态实现视图，展现了一组构件之间的组织和依赖**。"构件就是可以独立替换的软件单元，报销系统里就是"审批服务""报销单管理"这样能整体换掉的模块；把它编译打包后落到磁盘上的那个 `reimburse-service.jar` 文件，UML 里另有名字，叫**制品**（artifact），下面部署图要用到。图上除了方框还有两个符号：**供接口**（我对外提供的接口）画成一根线顶个**小圆圈**，像棒棒糖；**需接口**（我要别人提供给我的接口）画成**半圆插座**，一个插进一个就是装配；两个构件之间的虚线箭头，从需接口一端指向供接口一端。

⚠️ 又一个坑：培训资料 2-12 那张构件图上，"供接口""需接口"两个中文标注的引线指反了——"供接口"的引线拉到了半圆插座上，"需接口"的引线拉到了圆圈上。**认符号不认标签：圆圈＝供，半圆＝需。**

原文："**部署图**：静态图，为系统**静态部署视图**，部署图**物理模块**的节点分布。它与构件图相关，通常一个结点包含一个或多个构件。其依赖关系类似于包依赖，因此部署组件之间的依赖是单向的类似于包含关系。"图上画的是**立方体**，一个立方体是一个结点（一台服务器、一台终端），立方体里装着 `«artifact»` 制品（就是上面说的打包落盘的文件，war 包、数据库文件都算），立方体之间的连线是通信路径，线上可以标协议和端口，比如 `https:80`。

**判据一句话：图上有没有立方体。** 构件图只画软件模块之间的供需关系，一台机器都不出现；部署图才有机器，也才回答"这个 jar 装在哪台服务器上"。所以题干**同时出现"软件"和"硬件"**时：问的是图，答部署图；问的是视图，答部署视图（4+1 里的部署视图也讲"软件到硬件的映射"，两者别答串）。

**包图**也考过。包是分组事物，包图画的是模型本身分解成的组织单元及其依赖关系。四条规则记住就够答题：包里可以装类、接口、构件、结点；**一个元素只能被一个包拥有**（归属唯一）；包可以嵌套包；**同一个包内的元素不能重名**——不同包里可以重名，靠包名限定，就像 Java 里 `java.util.List` 和 `java.awt.List` 能共存。

### 七、同一套图，各人看各人那一面：4+1 视图（补④）

图都画完了，可产品经理不看部署图、运维不看类图。4+1 视图就是**按"谁看"把图重新分一遍**，"+1"的那个是用例视图，其余四个都围着它转。五条原文加上培训资料图上标的读者（读者这一列只画在图里、正文没写）：

| 视图 | 原文的定义句 | 画的是什么 | 主要给谁看 |
|---|---|---|---|
| 逻辑视图（也称设计视图） | 设计模型中在架构方面具有重要意义的部分，即**类、子系统、包和用例实现的子集** | 类与对象 | 系统分析、设计人员 |
| 进程视图 | **可执行线程和进程作为活动类的建模**，它是**逻辑视图的一次执行实例，描述了并发与同步结构** | 线程、进程、并发 | 系统集成人员 |
| 实现视图 | 对组成基于系统的**物理代码的文件和构件**进行建模 | 源代码结构 | 程序员 |
| 部署视图 | 把**构件部署到一组物理节点上**，表示软件到硬件的映射和分布结构 | 软件到硬件的映射 | 系统和网络工程师 |
| 用例视图 | **最基本的需求分析模型** | 用例 | 最终用户 |

![4+1 视图：五个视图各画什么、各给谁看](../外部资源/转录md/images/fig_d14_s025.png)

### 收口

开头四条短板一条条对上了：图上能出现什么 → 构造块（事物四类、关系、图）；怎么连 → 五大关系加实现；画几张 → 结构图 6 种加行为图 7 种，本课占静态那五张；谁看哪张 → 4+1 视图。剩下的组合结构图、定时图、交互概览图、制品图不在这条链上，卷面只在"UML 2.0 一共几种图"里露过面，认得名字即可。下午题 3 要在给定类图上补类名、补关系、补多重度，那是把本课的五大关系反过来用，实战放在讲义 51。

## 考试怎么考

**给一句定义选图名**是最稳定的题型，抓关键词就行：出现"某一时刻/快照"选对象图，"类、接口、协作及其关系"选类图，"用例和参与者"选用例图，"一组构件之间的组织和依赖""静态实现视图"选构件图，"软件和硬件的物理关系""结点"选部署图。构件图和部署图这一对最爱互换设错，判据就是有没有硬件结点。

**给业务描述判关系**是本课最值钱的考点，上午下午都用。读题只做两件事：先看是不是"整体-部分"，是就问"整体没了部分还在不在"（在=聚合、空心菱形；不在=组合、实心菱形）；不是整体-部分，就问"是不是长期持有"（成员变量=关联；参数、局部变量=依赖），再看是不是"是一种"（泛化）或"承诺履行接口"（实现）。

**错误选项最常见三种造法**：把画法写反（"聚合用实心菱形"）、把方向写反（"include 从被包含用例指向基用例"）、张冠李戴（把"对象快照"安给类图、把"硬件结点"安给构件图、把"并发与同步"安给逻辑视图）。认出造法比逐字比对快；碰上四个选项只是四个无关名词（像 2022下 那道"静态（　）图"给的关联/实现/结构/行为）的，就回去背原文那句定义。

**用例三关系**看两个词就够：题干里出现"每次都要/必然/总是"选 include，出现"仅当……才/可选/异常时"选 extend，出现"××有两种方式"且两种方式各是一个用例，选泛化。

**4+1 视图**基本只考两句原话："逻辑视图的一次执行实例、描述并发与同步结构"是进程视图，"最基本的需求分析模型"是用例视图。**包图**只考那四条规则，最常拿来做错项的是"一个元素可以被多个包拥有"。

### 参考答案

1. **D**。"软件和硬件之间的物理关系"两头都点到了，只有部署图既画结点又画结点上的制品；组件（构件）图不出现硬件。
2. **D**（信管网参考答案）。四个部件里只有音乐系统是可选可拆、拆下来照样是个独立的东西，其余三样随整车生死。⚠️ **培训资料把本题答案印成了 B，与信管网不一致**，做题按 D，判据仍是"整体没了部分还在不在、能不能被别的整体共享"。
3. **B**。原文就是"为系统静态实现视图"，四个选项里只有"实现"能和"静态××图"搭成教材原话。
4. **B**。包图的规则是一个元素只能被一个包拥有；A、C、D 三条都对——包能拥有类、接口、构件、结点，包能嵌套，同包内不能重名（不同包内可以）。
5. **A、C、D**。Shop 和 Magazine 之间是一条光秃秃的实线，只是"卖"这层长期关系，选关联；Magazine 那端有个实心菱形连到 Page，实心即组合（杂志没了，页也就不存在）；第三空考的是类图不干什么——对象快照是对象图的活。
6. **A、D**。两句都是原话直接对号：进程视图是"逻辑视图的一次执行实例"，用例视图是"最基本的需求分析模型"。
7. **C**。电话注册、邮件注册是"会员注册"这同一件事的两种做法，不是"每次都要做"（那才是 include），也不是"满足条件才追加"（那才是 extend）。
8. **D**。原文给泛化下的定义是"一般/特殊的关系"，题干把两个词调了个个儿，说的是同一件事，对应 Java 的 `extends`。聚合、关联、依赖三项都描述不了"是一种"。
9. **A**。整体没了部分也没了 → 组合，实心菱形贴整体端即报销单端；整体没了部分还在 → 聚合，空心菱形贴部门端。菱形永远贴整体，C 项把它贴到了部分端。
10. **B**。"每次都要"是 include，箭头由基用例指向被包含用例；"超过 5000 元才"是 extend，箭头由扩展用例指回基用例。两者方向相反，D 把方向抹平了。
11. 前者是**部署图**（立方体＝结点，`«artifact»`＝制品，连线＝通信路径）；后者是**构件图**（只有软件构件和供/需接口，没有硬件）。
12. ①分组事物　②行为事物　③结构事物　④注释事物。
13. `A ⇢▷ B` 虚线空心三角是**实现**（`implements B`）；`A ─▷ C` 实线空心三角是**泛化**（`extends C`）；`A ⇢ D` 虚线细箭头是**依赖**（D 只出现在方法参数或局部变量里）。

## 速记

- UML 是**语言不是过程**；结构＝构造块＋规则＋公共机制；构造块＝事物＋关系＋图
- 事物四类：结构（类/接口/用例/构件）、行为（交互/活动/状态机）、分组（包）、注释（注解）
- 五大关系＋实现：菱形贴整体，**空心聚合、实心组合**；整体亡部分亡＝组合；成员变量＝关联、参数临时用＝依赖；空心三角指父，**实线泛化、虚线实现**
- 多重度：`1` 恰一、`0..1` 至多一、`*` 任意多、`1..*` 至少一；同两类之间可有多条关联，用角色名区分
- 图 13 种（加制品图 14 种）＝结构图 6（类/对象/包/组合结构/构件/部署）＋行为图 7（用例/顺序/通信/交互概览/定时/状态/活动）
- 认图：快照＝对象图，类接口协作＝类图，用例参与者＝用例图，构件组织依赖＝构件图（静态实现视图），软硬件物理关系＝部署图（有立方体）
- 用例三关系：每次都做＝include（基→被包含），有条件才做＝extend（扩展→基），两种做法＝泛化；包图四规则，元素只能属一个包
- 4+1：进程视图＝逻辑视图的一次执行实例、并发与同步；用例视图＝最基本的需求分析模型
