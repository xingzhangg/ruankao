## 定位

这一课要分清五组东西：**测试在求什么**（目标，外加两把最容易混的尺子——跑不跑程序、看不看代码）、**用例怎么挑**（黑盒四法、白盒六级覆盖）、**"走遍"最少要几条**（McCabe 环路复杂度，全课唯一要套公式的地方；第三节判用例落在哪条路径同样要动笔代入）、**什么时候测、拿哪份文档判对错**（各级测试与集成策略）、**报错之后怎么定位**（调试三法）。五组东西摊成六节（「用例怎么挑」一组占了二、三两节）。其中第三、四节跟着同一段报销系统代码走，是全课重心。

## 开讲：卷面只问两种问题

一种是"给一句话，选它是哪个词"，另一种是"给一段代码和几条用例，问覆盖到哪一级、最少要几条"。前者占大头，所以每节先给一张**反查表**（题干里出现什么 → 答什么），再把最容易二选一犯难的几对单拎出来；后者集中在第三、四节。看不懂某个词再回头找它的解释，不必从头顺读。

### 一、先把目标摆正：两句定论、两把尺子

**反查表 · 判断题里的定论，看见就能定对错**

| 题干里出现 | 判 |
|---|---|
| **软件测试是为了发现错误而执行程序的过程，成功的测试是发现了至今尚未发现的错误的测试** | 对。Myers 的定义原话 |
| 一轮测试跑完什么错都没找出来，说明测得好 | 错。你的任务是砸出 bug，不是给系统颁奖，这轮白做了 |
| 穷举测试可以发现软件中的所有错误 | 错。报销金额这个整数输入框，32 位整数就有 40 多亿种取值，工程上跑不完 |
| 测试可以用来证明软件没有错误 | 错。**测试只能证明程序有错，不能证明程序无错**——试了 50 个都对，只说明这 50 个没触发缺陷 |
| 错误很多的程序段在修改后错误一般会非常少 | 错。**缺陷聚集**：已经查出错误多的那段程序，改完之后残存的错误往往还是多，下一轮更该往那块使劲 |
| 路径覆盖法往往比语句覆盖法发现更多的错误 | 对。路径要求**每条走法**都跑到，语句只要求**每行至少跑到一次**，前者当然更严（第三节展开） |

⚠️ 第一行那句定义说的是「测试」这件事整体，有的资料在这里印成「系统测试」，那是讹字。

**反查表 · 两把尺子，四份名单**

尺子一：**要不要把程序跑起来**。尺子二：**设计用例的时候看不看代码**。注意两把**不是并列的两级**，第二把只在动态测试内部再分。

| 题干里出现 | 答 |
|---|---|
| 被测试程序**不在机器上运行**，采用**人工检测和计算机辅助静态分析的手段**对程序进行检测 | **静态测试**（分对文档的和对代码的两类） |
| 拿一张事先列好"该有的条目有没有"的清单，对着文档逐条打钩 | 静态测试对文档的做法，叫**检查单** |
| **桌前检查**（也译**桌面检查**，考题两种写法都出现）＝自己把自己写的代码从头读一遍；**代码审查**＝一组人开会照着规程逐段过；**代码走查**＝一组人拿一组测试数据、用脑子当 CPU 顺着代码走一遍 | 对代码的静态测试，三种合起来能有效地发现 **30%–70%** 的逻辑设计和编码错误 |
| 在计算机上**实际运行程序**进行软件测试 | **动态测试**，一般采用白盒测试和黑盒测试方法 |
| **功能性测试**：不了解软件代码结构，根据功能设计用例，测试软件功能 | **黑盒测试法**（第二节） |
| **结构性测试**：明确代码流程，根据代码逻辑设计用例，进行用例覆盖 | **白盒测试法**（第三节） |
| 边界值分析、逻辑覆盖、基本路径 | 都要跑程序，全是动态测试 |

**易混对 · 代码走查 vs 白盒测试**

- 判据｜**分界不在眼睛看不看代码，在机器跑不跑程序。** 走查、审查、桌前检查眼睛也盯着代码，却压根不运行程序，所以是静态测试，不是白盒测试。
- 例子｜同一段报销代码：一组人开会逐段念一遍＝代码审查（静态）；把 (amt=2000, rcpt=1) 真喂进去跑一遍＝白盒（动态）。把"用脑子当 CPU 走"改成"真跑一遍"，答案就从静态变动态。
- 错法｜把"桌前检查、代码审查、代码走查"塞进白盒那一栏——这是本节唯一的坑，题库第 2 题考的就是这个交叉点。

其余认名即可：**测试原则**八条是上面这些结论的展开，原话见本节末的深入，跳过不影响后面。其中两条最常单独考：

- **测试工作应该避免由原开发软件的人或小组承担**——自己写的代码，测的时候会顺着当初的思路走，当初没想到的分支现在照样想不到；
- 用例**既包含有效、合理的测试用例，也包含不合理、失效的用例**——不光试"金额填 800"，还要试"金额填 −5""金额填 abc"，看程序能不能正确地把它挡回去。

> 考试这样问：给一串方法名，问哪几个属于动态测试、哪几个属于静态测试；或给四句关于测试的叙述，问哪句正确。

#### 深入 · 八条测试原则（教材原话）

- 应尽早并不断的进行测试；
- 测试工作应该避免由原开发软件的人或小组承担；
- 在设计测试方案时，不仅要确定输入数据，而且要根据系统功能确定预期的输出结果；
- 既包含有效、合理的测试用例，也包含不合理、失效的用例；
- 检验程序是否做了该做的事，且是否做了不该做的事；
- 严格按照测试计划进行；
- 妥善保存测试计划和测试用例；
- 测试用例可以重复使用或追加测试。

### 二、黑盒：输入是无限的，挑哪几个

报销系统的"报销金额"输入框，需求写的是**填 1 到 5000 的整数（元）**。不看代码，你打算填哪几个数去试？四种黑盒方法各给一套挑法。

**反查表 · 题干出现什么 → 答哪种黑盒方法**

| 题干里出现 | 答 |
|---|---|
| 把所有的数据**按照某种特性进行归类**，然后在每类的数据里**选取一个**即可 | **等价类划分** |
| 把**每类的边界值作为测试用例** | **边界值划分**（也常叫**边界值分析**） |
| **没有固定的方法，凭经验而言，来推测有可能产生问题的地方**，作为测试用例进行测试 | **错误推测** |
| **由一个结果来反推原因**，具体结果具体分析；用在多个输入条件组合决定一个输出的场合 | **因果图** |
| 把各输入条件的真假**组合列成表格**，每一列写出对应该走的动作，一列就是一条用例 | **判定表法**（别的教材才并列它，认名即可） |
| 问「**哪一条不是好的测试用例**」，某一条同时踩了**两个**无效等价类（年龄 18 ＋ 学历大专） | 就是它——无效类一条用例**只许犯一个错**，见易混对① |
| 给定范围 1–5000，问**边界值取哪几个** | 1、5000、0、5001（教材口径再加上界内紧邻的 2、4999），见易混对② |

直觉上大家会说"随便挑几个有代表性的：100、1000、3000"——这个直觉里已经有对的一半了，"有代表性"正是**等价类划分**。它成立的理由是，程序处理"金额 100"和"金额 3000"走的是同一段代码，一个通过另一个多半也通过，测两个和测一个收获一样。

归类要分两种。**有效等价类**是合法输入的集合，程序应当正常接受，这里就是 1–5000 的整数；**无效等价类**是非法输入的集合，程序应当正确地拒绝，这里至少三类：小于 1（如 0）、大于 5000（如 6000）、不是整数（如 12.5 或 `abc`）。无效类**必须也出用例**——你要测的是"程序会不会挡"，不是"程序能不能算"。

两条设计原则措辞不同，差别就是考点：**设计一个新的测试用例，使其尽可能多地覆盖尚未被覆盖的有效等价类**，重复这一步直到所有有效等价类都被覆盖；**设计一个新的测试用例，使其仅覆盖一个尚未被覆盖的无效等价类**，重复这一步直到所有无效等价类都被覆盖。

**易混对① 有效类的用例 vs 无效类的用例**

- 判据｜有效类一条用例可以扫掉好几个，无效类**一条用例只许犯一个错**。为什么不对称？因为无效输入是被挡回去的，程序碰到第一个错就报错返回了。
- 例子｜一条用例同时填"金额 −5"和"发票没传"，程序报了句"金额非法"就走人，"发票没传"这条校验到底写没写，你根本没测到。把"发票没传"改成"发票已上传"，这条立刻又成为合格的无效类用例。
- 错法｜题库第 3 题（招聘系统那道真题）问"哪一条不是好的测试用例"，答案就是同时踩了两个无效类的那条。

**易混对② 等价类 vs 边界值**

- 判据｜等价类取的是**每类当中的代表值**，边界值取的是**类与类的接缝**。边界值不是替代等价类，是**补在等价类的接缝上**，两者配合用。
- 例子｜报销金额 1–5000：等价类取 2500 这样的代表值；边界值取 **1、5000、0、5001** 四个点（**教材口径**）；另有资料再加上界内紧邻的两个（**2 和 4999**）凑成六个点。程序员最常写错的就在边界，`amt <= 5000` 手滑写成 `amt < 5000`，取 2500 一个都碰不到，取 5000 和 5001 一试就露。做题时不必纠结取四个还是六个，认准"取的是边界本身和紧挨着它的值"这个形状就行。
- 原话｜**教材口径（四点）**："**边界值一般为范围的两端值以及在此范围之外的与此范围间隔最小的两个值**"，配的例子是年龄范围 0–150，边界值为 0、150、−1、151 四个。上面那句"六个点"是另一套资料的口径，两者只差界内紧邻的两个。
- 错法｜边界值题的错项三种造法：全取内部值（一个边界都没碰到）、只取有效侧（缺界外的紧邻值）、取的不是紧邻值（跳开了真正的边界邻居）。

其余认名即可：**错误推测**落到报销系统上，就是老手一眼看出该试"同一张单连点两次提交""审批人给自己审批"；**因果图**实际画的时候是把原因（输入条件）和结果（输出动作）连成图再反向导出用例，比如"金额超 1000 且有发票才走二级审批"。

> 考试这样问：给一个输入范围问边界值取哪几个，或给四条用例问哪一条"不是好的测试用例"。

### 三、白盒：还有整段代码从没跑到

黑盒用例全过了，能收工吗？打开报销系统那段定审批级别的代码看一眼。

白盒方法两类：**逻辑覆盖**（本节主角，按强弱分六级）和**基本路径测试**（按环路复杂度算出的条数设计用例，第四节讲）。真题选项里出现的「边界值分析、逻辑覆盖、基本路径」就是按这个口径列的。

**先只看第一行判断，把两个术语立住**：

```c
if (amt > 1000 && rcpt == 1) { ... }
```

`if` 括号里的**整个**表达式叫**判定**——这里就是 `amt > 1000 && rcpt == 1` 一整句。判定里被 `&&`、`||` 连起来的**每一小段**叫**条件**——这里有两个：`amt > 1000` 和 `rcpt == 1`。

记住这个区别，整节都靠它：**判定管的是"这个 if 走真还是走假"，条件管的是"括号里每一小段各自真还是假"。** 两个条件都真，判定才真；有一个假，判定就假。

**反查表 · 题干出现什么 → 答哪一级覆盖**

| 题干里出现 | 答 |
|---|---|
| 逻辑代码中的**所有语句都要被执行一遍，覆盖层级最低** | **语句覆盖 SC** |
| 逻辑代码中的**所有判断语句的条件的真假分支都要覆盖一次** | **判定覆盖 DC**，又称**分支覆盖** |
| 针对每一个判断条件内的**每一个独立条件都要执行一遍真和假** | **条件覆盖 CC** |
| **同时满足判定覆盖和条件覆盖** | **判定/条件覆盖 CDC**，也写作**条件判定组合覆盖** |
| 一个判定里各条件的**所有取值组合**都排一遍（两个条件就是 2² = 4 种） | **条件组合覆盖** |
| 逻辑代码中的**所有可行路径都覆盖了，覆盖层级最高** | **路径覆盖** |

⚠️ 上表第二、三行的原话里，「条件」「判断条件」指的都是**判定**，「独立条件」才是本节说的**条件**——是原文措辞，别被绕进去。

强弱链（**考试口径的经验排序，不是包含关系**——判定与条件其实互不包含，本节末易混对④给反例）：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径。常见的五级清单里没有条件组合覆盖，教材有，选项里出现别当是编的。

只想答上表那类题，可以直接跳到本节末的易混对；下面这段阶梯讲的是每一级**漏掉了什么**，考点多半从那儿来。

**现在看完整的函数**：

```c
/* 输入：amt 本次报销金额，rcpt 是否已上传发票(1/0)，lvl 员工职级 */
if (amt > 1000 && rcpt == 1) {      /* 判定 1 */
    amt = amt - 1000;               /* 语句 S1：公司每月给 1000 元免审额度，凭发票抵扣 */
}
if (lvl >= 3 || amt > 500) {        /* 判定 2 */
    level = 2;                      /* 语句 S2：升为二级审批 */
}
```

两个判定、四个条件（`amt>1000`、`rcpt==1`、`lvl>=3`、`amt>500`）。

⚠️ **这里有个机关，后面每一级都要用到**：语句 `S1` 会把 `amt` 减掉 1000，所以**第二个 if 判的是抵扣之后的金额**，不是原始金额。

画成流程图（第四节算 McCabe 还用这张图）。**结点字母沿用教材经典图的编号，不是按走向排的**，所以 `b` 在 `c` 后面：

```
   s（入口）
   │
   ▼
   a：amt>1000 && rcpt==1 ?
   │真                    │假
   ▼                      │
   c：amt = amt - 1000     │
   │                      │
   ▼                      ▼
   ├──────────────────────┘
   ▼
   b：lvl>=3 || amt>500 ?
   │真                    │假
   ▼                      │
   e：level = 2           │
   │                      │
   ▼                      ▼
   ├──────────────────────┘
   ▼
   d（出口）
```

代码里的 `S1` 就是图上的 `c`，`S2` 就是图上的 `e`，下文两套记号都会用到。

一条用例走过的结点连起来就是一条**路径**，例如 (amt=2000, rcpt=1, lvl=1) 走 s→a→c→b→e→d，记作 **sacbed**。

下面开始爬阶梯。覆盖级别"**从低至高**"分几种，关键在于**每一级都是上一级漏掉某类缺陷之后的回应**，全程就用这一段代码。

**第 0 级，最朴素的想法：每行代码都执行到——语句覆盖 SC。** 本例一条用例就够：**(amt=2000, rcpt=1, lvl=1)**——判定 1 真（2000 超 1000 且有票）走 S1，amt 变 1000；判定 2 真（1000 > 500）走 S2。路径 sacbed，两条语句全执行了。

**漏掉了什么**：两个判定的**假分支一次都没走**。要是"没传发票时应该报错"这条逻辑写漏了，这条用例永远发现不了。标准说法是"因为执行了所有的语句，不代表执行了所有的条件判断"。

**第 1 级：让每个判定的真假两边都走一次——判定覆盖 DC（又称分支覆盖）。** 两条用例：**(2000, 1, 1)** 判定 1 真、判定 2 真；**(300, 0, 1)** 判定 1 假、判定 2 假（职级 1，且 300 不到 500）。

**漏掉了什么**：数一下 `lvl >= 3` 这个条件——两条用例的职级都填 1，它**两次都是假**。假设程序员手抖把 `lvl >= 3` 敲成了 `lvl >= 30`，这两条用例的结果一个字都不会变（第一条靠 `amt>500` 撑着判定 2 为真，第二条本来就该假），笔误查不出来。

**第 2 级：管到每个条件头上——条件覆盖 CC。**

**先猜一下**：条件比判定更细，那么满足条件覆盖是不是就自动满足判定覆盖了？

不是。看这两条：**(amt=2000, rcpt=0, lvl=1)** 和 **(amt=300, rcpt=1, lvl=3)**。四个条件全齐了——`amt>1000` 真/假、`rcpt==1` 假/真、`lvl>=3` 假/真、`amt>500` 真/假，条件覆盖成立。

**漏掉了什么**：判定 1 第一条是"真 && 假 = 假"、第二条是"假 && 真 = 假"，**真分支一次没进**；判定 2 两条都是真，**假分支一次没走**。判定覆盖不成立，连语句覆盖都不成立（S1 从头到尾没执行）。

**这是本课最值钱的一个反例：满足条件覆盖不一定满足判定覆盖。** 道理不难——`&&` 里两个条件一真一假，整体照样是假；你把条件的真假凑齐，判定的真假可以纹丝不动。

好消息是这组把上一级漏掉的笔误抓住了：第二条 (300, 1, 3) 里 `lvl>=3` 是判定 2 为真的唯一理由，改成 `lvl>=30` 就由真变假，结果不同，bug 现形。

**第 3 级：两个都要——判定/条件覆盖 CDC（也写作"条件判定组合覆盖"）。** 最省事的凑法是"全真 + 全假"：**(2000, 1, 3)** 四个条件全真、两个判定全真；**(300, 0, 1)** 四个条件全假、两个判定全假。

**漏掉了什么**：判定 1 里 `amt>1000` 和 `rcpt==1` 只出现过"同真"和"同假"，**没出现过一真一假**。要是把 `&&` 写成了 `||`，这两条用例的结果完全一样（真‖真还是真，假‖假还是假），bug 照样溜过去。而现实里"金额够但没传发票"恰恰是最常见的一种单子。

**第 4 级：把一个判定里条件的所有取值组合都排出来——条件组合覆盖。** 两个条件就是 2² = 4 种组合。判定 1 的四种和判定 2 的四种，四条用例可以同时凑齐：

| 用例 | amt | rcpt | lvl | 判定1 的 (amt>1000, rcpt==1) | 判定2 的 (lvl>=3, amt>500) | 走的路径 |
|---|---|---|---|---|---|---|
| W1 | 2000 | 1 | 3 | 真 真 | 真 真 | sacbed |
| W2 | 2000 | 0 | 1 | 真 假 | 假 真 | sabed |
| W3 | 300 | 1 | 3 | 假 真 | 真 假 | sabed |
| W4 | 300 | 0 | 1 | 假 假 | 假 假 | sabd |

W2 正是上一级漏掉的"金额够但没票"，`&&` 写成 `||` 这回被抓住了。

**漏掉了什么**：看最右边一列——四条用例只走了 sacbed、sabed、sabd **三条路径**，缺了 **sacbd**（判定 1 真、判定 2 假，也就是"抵扣掉 1000 后金额降到 500 以下、低职级只需一级审批"这种单子）。**组合全了，路径仍然没走全。**

**第 5 级：所有可行路径全走一遍——路径覆盖，最强。** 本例共 4 条路径，在上面四条用例外补一条 (amt=1200, rcpt=1, lvl=1) 走 sacbd 就齐了。

代价也在这里：**两个 if 顺序排**时，路径数随判定个数翻倍，两个判定 4 条、十个判定上千条，再遇上循环就是天文数字。（若判定是**嵌套**的，走了这边就不走那边，路径数只等于叶子数，要照着图数，不能直接算 2 的几次方。）所以路径覆盖只在很小的模块上做得起——问题于是被推到下一节：**"走遍"到底要几条**。

顺带记一个反过来的事实：走全这 4 条路径最少只要 4 条用例——(2000,1,1)、(1200,1,1)、(2000,0,1)、(300,0,1)——它们的职级全填 1，`lvl>=3` 一次没取真，所以**路径覆盖了却不满足条件覆盖**。

**易混对① 语句覆盖 vs 判定覆盖**（这一对方向是确定的）

- 判据｜判定覆盖要求真假两边都走，**走到了两边，沿途的语句自然都执行过**，所以判定强于语句，反过来不成立。
- 例子｜(2000,1,1) 一条就满足语句覆盖，可假分支一次没走；补 (300,0,1) 才上到判定覆盖。
- 错法｜"语句都覆盖到了，判断也就都覆盖到了"。

**易混对② 条件覆盖 vs 判定覆盖**（互不包含，最常考）

- 判据｜条件管括号里的小段、判定管整句，**谁都不含谁**。
- 例子｜`&&` 版就是第 2 级那两条用例：四个条件真假全翻过面，判定 1 两次都是假。换成 `||` 结论一样：`if (x > 5 || y < 3)` 取 (x=6, y=5) 与 (x=1, y=1)，两个条件真假齐了，判定两次都是真——只是从"恒假"变成"恒真"。反过来看第 1 级那两条用例：两个判定真假都齐，可 `lvl>=3` 一次没取真。
- 错法｜把"满足条件覆盖就一定满足判定覆盖"当成对的。

**易混对③ 条件判定组合覆盖 vs 条件组合覆盖**

- 判据｜名字里**有"判定"两个字的是第 3 级**（判定/条件覆盖的别名，只要求两者同时成立）；**没有"判定"的是第 4 级**（要求一个判定里各条件的真假组合全排一遍）。
- 例子｜(2000,1,3) + (300,0,1) 满足第 3 级；但判定 1 里 `amt>1000` 与 `rcpt==1` 只有同真、同假，没出现一真一假，第 4 级不成立，要补上 W2、W3。
- 错法｜两个名字只差两个字，选项里对调；或者把"条件组合覆盖等于路径覆盖"当成对的——W1–W4 组合全齐了，路径还缺 sacbd。

**易混对④ 强弱链 vs 真包含关系**

- 判据｜这条从弱到强的链是**考试口径的经验排序**，不是严格的数学包含关系；真含得住的只有"判定强于语句"那一对。考场按口径答就行。
- 例子｜心里记住这**三个**反例就够了：**条件覆盖 ⇏ 判定覆盖**（第 2 级那两条用例）、**判定覆盖 ⇏ 条件覆盖**（第 1 级那两条用例）、**路径覆盖 ⇏ 条件覆盖**（上面那四条路径用例，职级全填 1）。
- 错法｜"路径覆盖最强，所以它把其余五级都含住了"。**条件覆盖和判定覆盖是互不包含的**，别以为强的一定含住弱的。

> 考试这样问：给一组用例问它满足的最强覆盖是哪一级，或问"以下叙述错误的是"。

别处的资料讲同一套覆盖标准时常换另一张示例图，那张图上有一组数据容易印错，见本节末的深入；跳过不影响后面。

#### 深入 · 另一张常见示例图上的数据

那张图上判定 a 是 `(y>1)&&(z==0)`、真分支执行 `x=x/y`，判定 b 是 `(y==2)||(x>1)`。

路径覆盖一行的第二组数据，**应是 `X=3，Y=2，Z=0 → sacbed`**（代入验算：a 真，x 由 3 整除 2 得 1；b 的 `y==2` 真，走 e）。有的版本把 Y 印成了 3：按 `X=3，Y=3，Z=0` 代入实际走 sacbd，会和第三组重复——以 Y=2 为准。

### 四、"走遍"要几条：McCabe 环路复杂度

**先数，不给公式。** 把上一节那张流程图原样搬过来，免得回翻：

```
   s（入口）
   │
   ▼
   a：amt>1000 && rcpt==1 ?
   │真                    │假
   ▼                      │
   c：amt = amt - 1000     │
   │                      │
   ▼                      ▼
   ├──────────────────────┘
   ▼
   b：lvl>=3 || amt>500 ?
   │真                    │假
   ▼                      │
   e：level = 2           │
   │                      │
   ▼                      ▼
   ├──────────────────────┘
   ▼
   d（出口）
```

结点：s、a、c、b、e、d，**6 个**。箭头逐条数：s→a、a→c（真）、a→b（假）、c→b、b→e（真）、b→d（假）、e→d，**7 条**。

⚠️ 图上两处 `├───┘` 是**汇合点，不是结点**：`a→b` 和 `c→b` 是两条不同的边，汇合之后那一小段不再另算。所以图上看到的箭头数比 7 多，别照着箭头数。

换个角度看同一张图：图上围出了几个"圈"？a→c→b 和 a→b 围出一个，b→e→d 和 b→d 围出一个，**闭合区域 2 个**；再把图外面无边无际的那一片也算一个区域，一共 **3 个区域**。

再换个角度：图上会分叉的结点，也就是**判定结点**，是 a 和 b，**2 个**；2 + 1 = **3**。

三个角度都得 3。这不是巧合——这个 3 就是 **McCabe 环路复杂度 V(G)**（也译环形复杂度、圈复杂度，同一个东西），三种数法互为验算：

> ① **公式法**　V(G) = 有向边数 − 结点数 + 2 = 7 − 6 + 2 = **3**　（**+2 的来历**：③数的是闭合区域再加外面那一片，换成边和点就是「面 = 边 − 点 + 2」）
> ② **判定结点法**　V(G) = 判定结点数 + 1 = 2 + 1 = **3**
> ③ **区域法**　V(G) = 闭合区域数 + 1（外面那一片）= 2 + 1 = **3**

考试口径给的是①：**McCabe 度量法**又称为**环路复杂度**，假设有向图中**有向边数为 m，节点数为 n，则此有向图的环路复杂度为 m-n+2**；并提醒"m 和 n 代表的含义不能混淆"，以及"针对一个程序流程图，**每一个分支边（连线）就是一条有向边，每一条语句（语句框）就是一个顶点**"。

**V(G) 的含义**是这张图里**线性无关的独立路径条数**——独立路径就是彼此拼不出对方的那几条骨架路径——也就是"要把这段代码的结构走遍，最少需要几条用例"。工程上还拿它当模块复杂度的尺子，一般认为 V(G) 超过 10 的模块难测也难维护。三种数法为什么必然得同一个数，见本节末的推演，跳过不影响后面。

**这里有个必须分清的坑**：V(G) = 3，可上一节数过，这段代码的**全部可行路径是 4 条**。两者不是一回事：V(G) 数的是独立路径，路径覆盖要的是全部路径。所以基本路径测试（按 V(G) 条数设计用例）比路径覆盖便宜，也比它弱。考题常把"图中有几条路径"和"环路复杂度是多少"两问连着出，**两个空的答案可能相同也可能不同，必须分别数**。

**再验一次，动一下图。** 把入口结点 s 去掉、直接拿 a 当入口：结点 5 个、边 6 条，V(G) = 6 − 5 + 2 = 3，一点没变——它同时让边和点各少 1。真正会把答案数错的是另外两处：**判定的假分支**（那条"假"箭头最容易看漏）和**循环的回边**（`while` 从循环体末尾拐回判定框那一条）。漏一条边，答案就少 1。

**回边长什么样，看一眼就够**。一个 `while` 加一个循环体：

```
结点 3 个：p（while 判定）、q（循环体）、r（出口）

边 3 条：
  p ──真──► q    条件成立，进循环体
  p ──假──► r    条件不成立，跳出循环
  q ───────► p   循环体走完回到判定 ← 这条就是回边，最容易漏的就是它
```

**V(G) = 3 − 3 + 2 = 2**。判定结点法也是 1 + 1 = 2，对上了。**那条回边不数进去，就会算成 1。**（这里不画图改成逐条列边，是因为回边在 ASCII 图里极易和「假」分支挤在同一列，反而看反。）

环路复杂度属于「软件度量」这一小节的内容，因为它本质上是一把量代码的尺子。

其余认名即可：同一小节的**软件两种属性**——**外部属性**面向管理者和用户、**可直接测量**（性能指标）；**内部属性**是软件产品本身的属性如可靠性、**只能间接测量**。

> 考试这样问：一题两空，先问"图中有几条路径"，再问"用 McCabe 度量法算环路复杂性是多少"。

#### 推演 · 三种数法为什么必然得同一个数

**「独立路径」到底怎么算独立**：本例 V(G)=3，三条骨架可取 `sabd`、`sacbd`、`sabed`。第四条 `sacbed` 不是新骨架——它等于前两条各自的改动叠加（`sacbd` 的 s→a→c→b 段 ＋ `sabed` 的 b→e→d 段），拼得出来，所以不算独立。这就是「彼此拼不出对方」的意思。

**公式为什么长这样**：欧拉公式。一张连通的平面图，面数 = 边数 − 点数 + 2，这里的"面"正是包括外部那一片在内的区域，所以①和③必然相等；而每插入一个二分叉的判定，**边比点多长出一条**，图上也就多围出一个圈，所以②跟着相等。

### 五、什么时候测、拿哪份文档判卷

卷面问两件事："这一级验的是哪个开发阶段的产物"和"**依据哪份文档**"。前者就是 **V 模型**——左边一路往下拆、右边一路往上验，**同一高度的左右两格互相对应**，编码在 V 的底点：

```
用户需求 ─────────────────────── 验收测试
  需求分析 ─────────────────── 系统测试
    概要设计 ─────────────── 集成测试
      详细设计 ─────────── 单元测试
            编码（底点）
```

**两套是一致的，不是两回事**：同一层的产物和同一层的文档本来就对应，下表第二列第三列一行行对着看就行。

**反查表 · 各级测试**

| 测试级别 | 对应的开发阶段 | 测试依据 | 题干里的其他特征 |
|---|---|---|---|
| **单元测试**，也称模块测试 | 详细设计 | **软件详细设计说明书** | 测试对象是**可独立编译或汇编的程序模块、软件构件或 OO 软件中的类**（统称为模块），报销系统里就是那个"定审批级别"的函数 |
| **集成测试** | 概要设计 | **软件概要设计文档** | 目的是**检查模块之间，以及模块和已集成的软件之间的接口关系**，并验证已集成的软件是否符合设计要求 |
| **系统测试** | 需求分析 | **用户需求或开发合同** | 由测试方做，**测试对象是完整的、集成的计算机系统**；目的是在真实系统工作环境下，验证完成的软件配置项能否和系统正确连接，并满足系统/子系统设计文档和软件开发合同规定的要求 |
| **验收测试** | 用户需求 | 开发技术合同或 **SRS** | **针对 SRS，在交付前以用户为主进行的测试**，结论是**用户确定是否接收该软件的主要依据**；做它之前应确认已通过系统测试 |
| **确认测试**，也叫有效性测试 | —— | **SRS**（软件需求规格说明书，需求分析阶段签字定下来的那份"系统该做什么"） | **验证软件的功能、性能和其他特性是否与用户需求一致**；确认测试计划通常在需求分析阶段就完成 |
| **配置项测试** | —— | **SRS** | 对象是**软件配置项**——被单独管起来、有版本号、可独立交付的那一份，比如"审批服务"；目的是**检验软件配置项与 SRS 的一致性**；之前应确认已通过单元测试和集成测试 |
| **回归测试** | —— | 以前通过的那批用例 | 目的是**测试软件变更之后，变更部分的正确性和对变更需求的符合性**，以及软件原有的、正确的功能、性能和其他规定的要求的不损害性——大白话就是：改完一处，把以前通过的用例再跑一遍，确认没有"修一个、坏一片" |

选项里出现"源程序代码"一律排除：代码是被测对象，不是判卷标准。

**反查表 · 集成的三种顺序 → 补哪种临时模块**

一个模块单独跑不起来：上面调它的人可能还没写，它要调的下层（比如"查员工职级"这个接口）也可能还没写。缺哪头就补哪头的替身。

| 顺序 | 先测哪头 | 缺的是谁 | 补什么 | 优点 / 缺点 |
|---|---|---|---|---|
| **自底向上** | 从**最底层模块开始测试** | 上面调它的人 | **需要编写驱动程序** | 优点是**较早的验证了底层模块** |
| **自顶向下** | 先测顶层，而后逐步向下直至最后测试最底层模块 | 下面被调的人 | **需要编写桩程序** | 优点是**较早的验证了系统的主要控制和判断点** |
| **三明治** | 两头一起来 | 两头都缺 | 桩和驱动**二者都包括** | 兼有二者的**优点，缺点是测试工作量大** |

（有的资料把自顶向下的第一句写成"先测试整个系统"，按"先测最顶上那个模块、下层用桩顶上"理解，否则和后半句"逐步向下直至最后测试最底层模块"对不上。）

**易混对① 桩模块 vs 驱动模块**（本课最容易对调的两个词，对调了整题就废）

- 判据｜（**桩程序＝桩模块、驱动程序＝驱动模块**，两种写法卷面都出现。）**驱动模块（driver）**冒充**上层调用者**，负责把测试数据喂进来、启动被测模块、收结果；**桩模块（stub）**冒充**下层被调者**，被调到就直接返回一个假结果（比如职级固定返回 2）。一句话：**缺下面补桩，缺上面补驱动。**
- 例子｜单测"定审批级别"这个函数：没人调它 → 写驱动；它要调的"查员工职级"还没写 → 写桩。把没写的那一头从下换到上，答案就从桩变驱动。
- 错法｜自顶向下手里已经有上层、缺的是下层，却答"驱动"。

**易混对② Alpha 测试 vs Beta 测试**

- 判据｜区别只有**场地**一条：**Alpha 测试**是**用户在开发环境**下进行测试（用户来公司试，开发人员在旁边看着）；**Beta 测试**是**用户在实际使用环境下**进行测试（开发方不在场），通过该测试后产品才能交付用户。
- 错法｜两者的**主体都是用户**，选项写成"由开发人员进行"的一律排除。

**易混对③ 系统测试 vs 验收测试**

- 判据｜两者的测试对象都是完整的、集成的计算机系统，区别只有两条：**主体**——系统测试由测试方做、验收测试以用户为主；**用途**——验收测试的结论是用户收不收货的依据。
- 错法｜把"验证软件功能、性能及其他特性是否与用户需求一致"当成系统测试——那是确认测试的定义原话。

**反查表 · 确认测试按用户参与程度分四类**（真题考过，别只当认名）

| 题干里出现 | 答 |
|---|---|
| 由**软件开发组织内部按照 SRS 进行测试**，用户还没上场 | **内部确认测试** |
| 用户到开发方场地试用，开发人员在旁边看着 | **Alpha 测试** |
| 用户在自己的场地用，开发人员不在场 | **Beta 测试** |
| 交付前以用户为主，结论是用户收不收货的依据 | **验收测试** |

其余认名即可：

- 系统测试的主要内容：功能测试、健壮性测试（故意喂脏数据、拔网线，看它会不会崩）、性能测试、用户界面测试、安全性测试、安装与反安装测试等，其中**最重要的工作是进行功能测试与性能测试**。
- 功能测试主要采用**黑盒**测试方法；性能测试主要指标有**响应时间、吞吐量、并发用户数和资源利用率**等。

> 考试这样问：给一个测试阶段问它的依据文档；或给一种集成顺序问需要额外编写哪种临时模块。

#### 深入 · 有资料把整条对应关系往下挪了一格

另有资料写成"单元测试针对编码、集成测试针对详细设计、系统测试针对概要设计"。那种画法**给编码也配了一级测试（编码↔单元测试）**，于是下面各级整体下移。本讲义按教材口径；遇到选项整体差一格时，先看它是不是给编码也配了测试。

### 六、报错之后：调试

测试跑出一堆红叉，接下来的活儿就不叫测试了，叫调试。一句话划清界线：**测试是发现错误，调试是找出错误的代码和原因。**

调试要做三件事：**确定错误的准确位置；确定问题的原因并设法改正；改正后要进行回归测试**——最后一步正好把上一节的回归测试接了回来，闭环。

**反查表 · 给一段描述 → 答哪种调试方法**

| 题干里出现 | 答 |
|---|---|
| 到处打印、开全量日志、把内存全导出来翻；最不动脑子也最费时间，什么线索都没有时才用 | **蛮力法** |
| **从出错的地方开始，向回找**——报表数字算错了，就从输出那一行往回一层层看是谁传进来的；小程序好用，代码一大就分叉太多 | **回溯法** |
| **找出所有可能的原因，逐一进行排除** | **原因排除法** |
| 先摊开所有可能原因，再用数据一条条否掉 | 原因排除法之**演绎法** |
| 从几次错误现象里找共性，归纳出假设再验证 | 原因排除法之**归纳法** |
| 在中间打一刀，看错误落在哪一半，再对那一半打一刀 | 原因排除法之**二分法** |

判据｜演绎和归纳最容易对调，看方向：**从一般到个别＝演绎**（先列出全部可能，再逐条删）；**从个别到一般＝归纳**（先看几次错误现象，再提出假设）。

> 考试这样问：给一种调试方法的描述问它是哪一种，或问调试与测试的区别。

## 速记

- 覆盖阶梯从弱到强：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径；常见的五级清单里没有条件组合覆盖，教材有
- 条件真假齐 ≠ 判定真假齐：`&&` 一真一假仍为假、`||` 一真一假仍为真；条件覆盖与判定覆盖互不包含，路径覆盖也不含条件覆盖
- McCabe：V(G) = 边 − 点 + 2 = 判定结点数 + 1 = 闭合区域数 + 1；它是独立路径数，不等于全部路径数；> 10 难测难维护
- 依据文档：单元 ← 详细设计，集成 ← 概要设计，确认/配置项 ← SRS，系统 ← 用户需求或开发合同
- 自顶向下补桩、自底向上补驱动；三明治两头夹、工作量大
- 静态不跑程序（桌前检查／代码审查／代码走查，可发现 30%–70% 逻辑设计与编码错误）；黑盒白盒都是动态；软件**外部属性可直接测**（性能指标）、**内部属性只能间接测**（可靠性）
- 黑盒四法：等价类（无效类一次只许犯一个错）、边界值（两端值 + 界外紧邻）、错误推测、因果图
- α 在开发方场地、β 在用户场地，主体都是用户；调试三法：蛮力、回溯、原因排除（演绎／归纳／二分）
