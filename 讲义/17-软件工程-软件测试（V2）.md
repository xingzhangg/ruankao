# 17 · 软件工程：软件测试

## 定位

这一课分五组东西：**测试在求什么**（目标，加上两把尺子——跑不跑程序、看不看代码）、**用例怎么挑**（黑盒四法、白盒六级覆盖）、**"走遍"最少要几条**（McCabe 环路复杂度，全课唯一套公式的地方）、**什么时候测、拿哪份文档判对错**（各级测试与集成策略）、**报错之后怎么定位**（调试三法）。第三、四节跟着同一段报销系统代码走，是全课重心；第一、二、五、六节是概念型，第三、四节要动笔代入或计算。

## 一、目标：两句定论、两把尺子（概念）

**速查表 · 关于测试的定论**

| 叙述 | 对错 |
|---|---|
| **软件测试是为了发现错误而执行程序的过程，成功的测试是发现了至今尚未发现的错误的测试** | 对。Myers 定义原话（说的是「测试」整体，有的资料印成「系统测试」，是讹字） |
| 一轮测试什么错都没找出来，说明测得好 | 错。测试的任务是找出 bug，这轮白做了 |
| 穷举测试可以发现软件中的所有错误 | 错。报销金额这个整数输入框，32 位整数就有 40 多亿种取值，工程上跑不完 |
| 测试可以用来证明软件没有错误 | 错。**测试只能证明程序有错，不能证明程序无错**——试了 50 个都对，只说明这 50 个没触发缺陷 |
| 错误很多的程序段在修改后错误一般会非常少 | 错。**缺陷聚集**：查出错误多的那段，改完后残存错误往往还是多，下一轮更该往那块使劲 |
| 路径覆盖法往往比语句覆盖法发现更多的错误 | 对。路径要求**每条走法**都跑到，语句只要求**每行至少跑一次**（第三节） |

**速查表 · 两把尺子**

尺子一：**要不要把程序跑起来**；尺子二：**设计用例时看不看代码**。两把不是并列的两级，第二把只在动态测试内部再分。

| 特征 / 关键词 | 是什么 |
|---|---|
| 被测程序**不在机器上运行**，采用**人工检测和计算机辅助静态分析的手段**对程序进行检测 | **静态测试**（分对文档的和对代码的两类） |
| 拿一张事先列好的清单对着文档逐条打钩 | 静态测试对文档的做法：**检查单** |
| **桌前检查**（也译**桌面检查**）＝自己把自己的代码从头读一遍；**代码审查**＝一组人开会照规程逐段过；**代码走查**＝一组人拿一组测试数据、用脑子当 CPU 顺着代码走一遍 | 对代码的静态测试，三种合起来能有效发现 **30%–70%** 的逻辑设计和编码错误 |
| 在计算机上**实际运行程序**进行软件测试 | **动态测试**，一般采用白盒和黑盒测试方法 |
| **功能性测试**：不了解代码结构，根据功能设计用例 | **黑盒测试法**（第二节） |
| **结构性测试**：明确代码流程，根据代码逻辑设计用例，进行用例覆盖 | **白盒测试法**（第三节） |
| 边界值分析、逻辑覆盖、基本路径 | 都要跑程序，全是动态测试 |

**易混对 · 代码走查 vs 白盒测试**

- 判据｜**分界不在眼睛看不看代码，在机器跑不跑程序。** 走查、审查、桌前检查都盯着代码却不运行程序，是静态测试，不属于白盒。
- 例子｜同一段报销代码：一组人开会逐段念＝代码审查（静态）；把 (amt=2000, rcpt=1) 真喂进去跑＝白盒（动态）。

**测试原则（教材原话，八条）**：

- 应尽早并不断的进行测试；
- 测试工作应该避免由原开发软件的人或小组承担——自己测会顺着当初的思路走，没想到的分支现在照样想不到；
- 在设计测试方案时，不仅要确定输入数据，而且要根据系统功能确定预期的输出结果；
- 既包含有效、合理的测试用例，也包含不合理、失效的用例——不光试"金额填 800"，还要试"−5""abc"，看程序能否挡回去；
- 检验程序是否做了该做的事，且是否做了不该做的事；
- 严格按照测试计划进行；
- 妥善保存测试计划和测试用例；
- 测试用例可以重复使用或追加测试。

## 二、黑盒：输入无限，挑哪几个（概念）

贯穿例子：报销系统"报销金额"输入框，需求是**填 1 到 5000 的整数（元）**。

**速查表 · 黑盒方法**

| 特征 / 关键词 | 是什么 |
|---|---|
| 把所有数据**按照某种特性进行归类**，然后在每类数据里**选取一个**即可 | **等价类划分** |
| 把**每类的边界值作为测试用例** | **边界值划分**（也常叫**边界值分析**） |
| **没有固定的方法，凭经验而言，来推测有可能产生问题的地方** | **错误推测** |
| **由一个结果来反推原因**，具体结果具体分析；用于多个输入条件组合决定一个输出 | **因果图** |
| 各输入条件的真假**组合列成表格**，每一列对应一个动作、一条用例 | **判定表法**（别的教材才并列它，认名即可） |

**等价类划分**：程序处理"金额 100"和"金额 3000"走同一段代码，测一个和测两个收获一样，所以每类取一个代表。

- **有效等价类**：合法输入的集合，程序应正常接受——1–5000 的整数。
- **无效等价类**：非法输入的集合，程序应正确拒绝——至少三类：小于 1（如 0）、大于 5000（如 6000）、不是整数（如 12.5 或 `abc`）。无效类**也必须出用例**，测的是"程序会不会挡"。
- 两条设计原则（原话）：**设计一个新的测试用例，使其尽可能多地覆盖尚未被覆盖的有效等价类**，重复直到有效类全覆盖；**设计一个新的测试用例，使其仅覆盖一个尚未被覆盖的无效等价类**，重复直到无效类全覆盖。

**易混对① 有效类的用例 vs 无效类的用例**

- 判据｜有效类一条用例可以扫掉好几个；无效类**一条用例只许犯一个错**——程序碰到第一个错就报错返回，后面的校验测不到。同时踩两个无效类的用例不是好用例。
- 例子｜一条用例同时填"金额 −5"和"发票没传"，程序报"金额非法"就返回，发票校验根本没测到；把"发票没传"改成"已上传"，它就是合格的无效类用例。同理，招聘系统里一条用例同时填年龄 18 和学历大专（两个都不合要求），不是好用例。

**易混对② 等价类 vs 边界值**

- 判据｜等价类取**每类当中的代表值**，边界值取**类与类的接缝**：边界本身加界外紧邻值。两者配合用，边界值补在等价类的接缝上。全取内部值、只取有效侧、取的不是紧邻值，都不算边界值。
- 例子｜金额 1–5000：等价类取 2500；边界值取 **1、5000、0、5001**（教材口径），另有资料再加界内紧邻的 **2、4999** 凑六个点。`amt <= 5000` 手滑写成 `amt < 5000`，取 2500 碰不到，取 5000 一试就露。
- 原话｜"**边界值一般为范围的两端值以及在此范围之外的与此范围间隔最小的两个值**"，教材例子：年龄 0–150，边界值为 0、150、−1、151。

其余认名即可：**错误推测**——老手一眼看出该试"同一张单连点两次提交""审批人给自己审批"；**因果图**——把原因（输入条件）和结果（输出动作）连成图再导出用例，如"金额超 1000 且有发票才走二级审批"。

## 三、白盒：逻辑覆盖六级（要代入用例判定走向）

白盒方法两类：**逻辑覆盖**（本节，按强弱分六级）和**基本路径测试**（按环路复杂度算出的条数设计用例，第四节）。

**两个术语**。`if (amt > 1000 && rcpt == 1)` 括号里的**整个**表达式叫**判定**；被 `&&`、`||` 连起来的**每一小段**叫**条件**（这里是 `amt > 1000` 和 `rcpt == 1`）。判定管"这个 if 走真还是走假"，条件管"括号里每一小段各自真还是假"。

**速查表 · 覆盖级别**

| 特征 / 关键词 | 是什么 |
|---|---|
| 逻辑代码中的**所有语句都要被执行一遍，覆盖层级最低** | **语句覆盖 SC** |
| 逻辑代码中的**所有判断语句的条件的真假分支都要覆盖一次** | **判定覆盖 DC**，又称**分支覆盖** |
| 针对每一个判断条件内的**每一个独立条件都要执行一遍真和假** | **条件覆盖 CC** |
| **同时满足判定覆盖和条件覆盖** | **判定/条件覆盖 CDC**，也写作**条件判定组合覆盖** |
| 一个判定里各条件的**所有取值组合**都排一遍（两个条件 2² = 4 种） | **条件组合覆盖** |
| 逻辑代码中的**所有可行路径都覆盖了，覆盖层级最高** | **路径覆盖** |

⚠️ 第二、三行原话里的「条件」「判断条件」指的是**判定**，「独立条件」才是本节的**条件**。

强弱链（**经验排序，不是包含关系**，见易混对④）：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径。常见五级清单里没有条件组合覆盖，教材有。

**贯穿代码**：

```c
/* 输入：amt 本次报销金额，rcpt 是否已上传发票(1/0)，lvl 员工职级 */
if (amt > 1000 && rcpt == 1) {      /* 判定 1 */
    amt = amt - 1000;               /* 语句 S1：每月 1000 元免审额度，凭发票抵扣 */
}
if (lvl >= 3 || amt > 500) {        /* 判定 2 */
    level = 2;                      /* 语句 S2：升为二级审批 */
}
```

两个判定、四个条件。⚠️ `S1` 会把 `amt` 减掉 1000，**第二个 if 判的是抵扣后的金额**。

流程图（第四节还用）。结点字母沿用教材经典图编号，所以 `b` 在 `c` 后面；`S1` 即 `c`，`S2` 即 `e`：

```
   s（入口）
   │
   ▼
   a：amt>1000 && rcpt==1 ?
   │真                    │假
   ▼                      │
   c：amt = amt - 1000     │
   │                      │
   ▼                      ▼
   ├──────────────────────┘
   ▼
   b：lvl>=3 || amt>500 ?
   │真                    │假
   ▼                      │
   e：level = 2           │
   │                      │
   ▼                      ▼
   ├──────────────────────┘
   ▼
   d（出口）
```

一条用例走过的结点连起来是一条**路径**，如 (amt=2000, rcpt=1, lvl=1) 走 s→a→c→b→e→d，记作 **sacbed**。

**逐级构造用例，每一级补上一级的漏洞**（用例写作 (amt, rcpt, lvl)）：

| 级别 | 用例 | 满足的理由 | 漏掉什么 |
|---|---|---|---|
| 语句覆盖 | (2000,1,1) | 判定 1 真走 S1，amt 变 1000；判定 2 真（1000>500）走 S2 | 两个判定的**假分支一次没走**，"没传发票应报错"写漏了发现不了。"执行了所有的语句，不代表执行了所有的条件判断" |
| 判定覆盖 | (2000,1,1)、(300,0,1) | 两个判定各真一次、假一次 | `lvl>=3` 两次都假，敲成 `lvl>=30` 结果一字不变 |
| 条件覆盖 | (2000,0,1)、(300,1,3) | 四个条件真假各一次 | 判定 1 两次都假（真&&假、假&&真），判定 2 两次都真；判定覆盖、语句覆盖都不成立（S1 没执行）。但抓住了 `lvl>=30`：第二条里 `lvl>=3` 是判定 2 为真的唯一理由 |
| 判定/条件覆盖 | (2000,1,3)、(300,0,1) | "全真 + 全假" | 判定 1 的两个条件只有同真同假，`&&` 写成 `||` 结果不变；"金额够但没票"没测到 |
| 条件组合覆盖 | W1–W4（下表） | 两个判定各自 4 种组合齐 | 只走了 3 条路径，缺 **sacbd** |
| 路径覆盖 | W1–W4 ＋ (1200,1,1) | 4 条可行路径全走 | 代价大 |

| 用例 | amt | rcpt | lvl | 判定1 (amt>1000, rcpt==1) | 判定2 (lvl>=3, amt>500) | 路径 |
|---|---|---|---|---|---|---|
| W1 | 2000 | 1 | 3 | 真 真 | 真 真 | sacbed |
| W2 | 2000 | 0 | 1 | 真 假 | 假 真 | sabed |
| W3 | 300 | 1 | 3 | 假 真 | 真 假 | sabed |
| W4 | 300 | 0 | 1 | 假 假 | 假 假 | sabd |

W2 就是"金额够但没票"，`&&` 写成 `||` 这回被抓住。缺的 sacbd 是"抵扣 1000 后降到 500 以下、低职级只需一级审批"的单子，补 (1200,1,1) 即齐。

**路径覆盖的代价**：**两个 if 顺序排**时路径数随判定个数翻倍，两个判定 4 条、十个判定上千条，遇上循环是天文数字；若判定**嵌套**，路径数只等于叶子数，要照图数，不能直接算 2 的几次方。所以路径覆盖只在很小的模块上做得起。

**易混对① 语句覆盖 vs 判定覆盖**（方向确定）

- 判据｜判定覆盖要求真假两边都走，走到两边，沿途语句自然都执行过，所以判定强于语句，反之不成立。
- 例子｜(2000,1,1) 一条满足语句覆盖，假分支没走；补 (300,0,1) 才到判定覆盖。

**易混对② 条件覆盖 vs 判定覆盖**（互不包含）

- 判据｜条件管小段、判定管整句，谁都不含谁：`&&` 一真一假仍为假，`||` 一真一假仍为真，条件真假凑齐，判定可以纹丝不动。
- 例子｜`&&`：条件覆盖那两条用例，判定 1 两次都假。`||`：`if (x > 5 || y < 3)` 取 (x=6, y=5) 与 (x=1, y=1)，条件齐了，判定两次都真。反过来，判定覆盖那两条用例里 `lvl>=3` 一次没取真。

**易混对③ 条件判定组合覆盖 vs 条件组合覆盖**

- 判据｜名字里**有"判定"的是判定/条件覆盖**（两者同时成立即可）；**没有"判定"的是条件组合覆盖**（各条件真假组合全排）。条件组合覆盖也不等于路径覆盖。
- 例子｜(2000,1,3) + (300,0,1) 满足判定/条件覆盖；要到条件组合覆盖须补 W2、W3；W1–W4 组合全齐，路径仍缺 sacbd。

**易混对④ 强弱链 vs 真包含关系**

- 判据｜强弱链是经验排序，真能包含的只有"判定强于语句"这一对；强的不一定含住弱的，路径覆盖也不含其余五级。
- 例子｜三个反例：**条件 ⇏ 判定**（条件覆盖那两条）、**判定 ⇏ 条件**（判定覆盖那两条）、**路径 ⇏ 条件**：走全 4 条路径最少 4 条用例 (2000,1,1)、(1200,1,1)、(2000,0,1)、(300,0,1)，职级全填 1，`lvl>=3` 一次没取真。

**另一张常见示例图的勘误**：那张图判定 a 是 `(y>1)&&(z==0)`、真分支执行 `x=x/y`，判定 b 是 `(y==2)||(x>1)`。路径覆盖第二组数据**应是 `X=3，Y=2，Z=0 → sacbed`**（a 真，x 由 3 整除 2 得 1；b 的 `y==2` 真，走 e）。有的版本印成 Y=3，代入实际走 sacbd，与第三组重复——以 Y=2 为准。

## 四、"走遍"要几条：McCabe 环路复杂度（计算）

**解决什么**：要把一段代码的结构走遍，最少需要几条用例。

**算例**（第三节流程图）：

1. 数结点：s、a、c、b、e、d，**6 个**。
2. 数有向边：s→a、a→c（真）、a→b（假）、c→b、b→e（真）、b→d（假）、e→d，**7 条**。图上两处 `├───┘` 是**汇合点，不是结点**，`a→b` 与 `c→b` 是两条边，汇合后那一小段不另算。
3. 数判定结点（会分叉的）：a、b，**2 个**。
4. 数区域：a→c→b 与 a→b 围一个，b→e→d 与 b→d 围一个，**闭合区域 2 个**，加外面那一片共 **3 个区域**。
5. 三种算法：

> ① **公式法**　V(G) = 有向边数 − 结点数 + 2 = 7 − 6 + 2 = **3**
> ② **判定结点法**　V(G) = 判定结点数 + 1 = 2 + 1 = **3**
> ③ **区域法**　V(G) = 闭合区域数 + 1（外面那一片）= 2 + 1 = **3**

**规则**：这个数就是 **McCabe 环路复杂度 V(G)**（也译环形复杂度、圈复杂度）。原话：**McCabe 度量法**又称为**环路复杂度**，假设有向图中**有向边数为 m，节点数为 n，则此有向图的环路复杂度为 m-n+2**；m 和 n 含义不能混淆；针对程序流程图，**每一个分支边（连线）就是一条有向边，每一条语句（语句框）就是一个顶点**。

- **为什么三法相等**：欧拉公式——连通平面图的面数 = 边数 − 点数 + 2，"面"含外部那一片，所以①＝③；每插入一个二分叉判定，边比点多长一条、图上多围一个圈，所以②也相等。
- **含义**：图里**线性无关的独立路径条数**。独立＝彼此拼不出对方：本例三条骨架取 `sabd`、`sacbd`、`sabed`；`sacbed` 等于 `sacbd` 的 s→a→c→b 段 ＋ `sabed` 的 b→e→d 段，拼得出，不独立。一般认为 V(G) 超过 10 的模块难测也难维护。
- **V(G) ≠ 全部路径数**：本例 V(G)=3，可行路径 4 条。基本路径测试（按 V(G) 条数设计用例）比路径覆盖便宜，也比它弱。"图中有几条路径"和"环路复杂度"可能相同也可能不同，须分别数。

**验证一：去掉入口 s**，直接以 a 为入口：结点 5、边 6，V(G) = 6 − 5 + 2 = 3，不变（边和点各少 1）。真正会数错的是**判定的假分支**和**循环的回边**，漏一条边答案少 1。

**验证二：循环回边**（逐条列边，ASCII 图里回边易与假分支挤在一列）：

```
结点 3 个：p（while 判定）、q（循环体）、r（出口）
边 3 条：
  p ──真──► q    进循环体
  p ──假──► r    跳出循环
  q ───────► p   循环体走完回到判定 ← 回边
```

V(G) = 3 − 3 + 2 = **2**；判定结点法 1 + 1 = 2。漏数回边会算成 1。

**所属小节**：环路复杂度属于「软件度量」，本质是量代码的尺子。同一小节认名即可：**外部属性**面向管理者和用户、**可直接测量**（性能指标）；**内部属性**是软件产品本身的属性如可靠性、**只能间接测量**。

## 五、什么时候测、拿哪份文档判对错（概念）

**V 模型**：左边一路往下拆、右边一路往上验，同一高度左右对应，编码在底点。

```
用户需求 ─────────────────────── 验收测试
  需求分析 ─────────────────── 系统测试
    概要设计 ─────────────── 集成测试
      详细设计 ─────────── 单元测试
            编码（底点）
```

**速查表 · 各级测试**

| 测试级别 | 对应开发阶段 | 测试依据 | 特征 |
|---|---|---|---|
| **单元测试**，也称模块测试 | 详细设计 | **软件详细设计说明书** | 对象是**可独立编译或汇编的程序模块、软件构件或 OO 软件中的类**（统称模块），如"定审批级别"函数 |
| **集成测试** | 概要设计 | **软件概要设计文档** | **检查模块之间，以及模块和已集成的软件之间的接口关系**，并验证已集成的软件是否符合设计要求 |
| **系统测试** | 需求分析 | **用户需求或开发合同** | 由测试方做，**对象是完整的、集成的计算机系统**；在真实系统工作环境下，验证软件配置项能否和系统正确连接，并满足系统/子系统设计文档和软件开发合同规定的要求 |
| **验收测试** | 用户需求 | 开发技术合同或 **SRS** | **针对 SRS，在交付前以用户为主进行的测试**，结论是**用户确定是否接收该软件的主要依据**；之前应确认已通过系统测试 |
| **确认测试**，也叫有效性测试 | —— | **SRS**（需求分析阶段签定的"系统该做什么"） | **验证软件的功能、性能和其他特性是否与用户需求一致**；确认测试计划通常在需求分析阶段完成 |
| **配置项测试** | —— | **SRS** | 对象是**软件配置项**（单独管理、有版本号、可独立交付的一份，如"审批服务"）；**检验软件配置项与 SRS 的一致性**；之前应确认已通过单元测试和集成测试 |
| **回归测试** | —— | 以前通过的那批用例 | **测试软件变更之后，变更部分的正确性和对变更需求的符合性**，以及软件原有的、正确的功能、性能和其他规定的要求的不损害性——改完一处，把旧用例再跑一遍，防"修一个、坏一片" |

源程序代码是被测对象，不是任何一级的测试依据。

另有资料把对应关系整体下移一格（单元↔编码、集成↔详细设计、系统↔概要设计），那是给编码也配了一级测试；本讲义按教材口径。

**速查表 · 集成顺序与临时模块**

模块单独跑不起来：上面调它的可能没写，它要调的下层（如"查员工职级"）也可能没写，缺哪头补哪头的替身。

| 顺序 | 先测哪头 | 补什么 | 优点 / 缺点 |
|---|---|---|---|
| **自底向上** | 从**最底层模块开始测试** | **需要编写驱动程序** | **较早的验证了底层模块** |
| **自顶向下** | 先测顶层，逐步向下直至最后测试最底层模块 | **需要编写桩程序** | **较早的验证了系统的主要控制和判断点** |
| **三明治** | 两头一起 | 桩和驱动**二者都包括** | 兼有二者**优点，缺点是测试工作量大** |

（有的资料把自顶向下写成"先测试整个系统"，按"先测最顶上那个模块、下层用桩"理解。）

**易混对① 桩模块 vs 驱动模块**（桩程序＝桩模块、驱动程序＝驱动模块）

- 判据｜**驱动模块（driver）**冒充**上层调用者**，喂测试数据、启动被测模块、收结果；**桩模块（stub）**冒充**下层被调者**，被调到就返回假结果（如职级固定返回 2）。**缺下面补桩，缺上面补驱动**；自顶向下已有上层、缺下层，所以补桩。
- 例子｜单测"定审批级别"：没人调它 → 写驱动；它要调的"查员工职级"没写 → 写桩。

**易混对② Alpha 测试 vs Beta 测试**

- 判据｜**主体都是用户**，区别只在**场地**：**Alpha** 是**用户在开发环境**下测试（开发人员在旁边看）；**Beta** 是**用户在实际使用环境下**测试（开发方不在场），通过后产品才能交付用户。
- 例子｜用户到公司机房试用新版＝α；同一版本装回用户自己单位用＝β。

**易混对③ 系统测试 vs 验收测试**

- 判据｜对象都是完整的、集成的系统，区别两条：**主体**——系统测试由测试方做，验收测试以用户为主；**用途**——验收结论是用户收不收货的依据。"验证软件功能、性能及其他特性是否与用户需求一致"是**确认测试**的定义，不是系统测试。
- 例子｜测试团队在仿真环境压测＝系统测试；用户代表按合同逐项签字＝验收测试。

**速查表 · 确认测试按用户参与程度分四类**

| 特征 / 关键词 | 是什么 |
|---|---|
| **软件开发组织内部按照 SRS 进行测试**，用户未参与 | **内部确认测试** |
| 用户到开发方场地试用，开发人员在旁 | **Alpha 测试** |
| 用户在自己场地用，开发人员不在场 | **Beta 测试** |
| 交付前以用户为主，结论是收不收货的依据 | **验收测试** |

其余认名即可：系统测试主要内容有功能测试、健壮性测试（喂脏数据、拔网线看会不会崩）、性能测试、用户界面测试、安全性测试、安装与反安装测试等，**最重要的是功能测试与性能测试**；功能测试主要用**黑盒**方法；性能测试主要指标有**响应时间、吞吐量、并发用户数和资源利用率**等。

## 六、报错之后：调试（概念）

**测试是发现错误，调试是找出错误的代码和原因。** 调试三件事：**确定错误的准确位置；确定问题的原因并设法改正；改正后要进行回归测试**。

**速查表 · 调试方法**

| 特征 / 关键词 | 是什么 |
|---|---|
| 到处打印、开全量日志、导出内存；最费时，没线索时才用 | **蛮力法** |
| **从出错的地方开始，向回找**；小程序好用，代码大了分叉太多 | **回溯法** |
| **找出所有可能的原因，逐一进行排除** | **原因排除法** |
| 先摊开所有可能原因，再用数据逐条否掉 | 原因排除法之**演绎法** |
| 从几次错误现象找共性，归纳假设再验证 | 原因排除法之**归纳法** |
| 在中间打一刀，看错误落在哪一半，再对那一半打一刀 | 原因排除法之**二分法** |

**易混对 · 演绎 vs 归纳**

- 判据｜**从一般到个别＝演绎**（先列全部可能，再逐条删）；**从个别到一般＝归纳**（先看几次错误现象，再提假设）。
- 例子｜报表数字错：先列"公式错/数据源错/精度截断"再逐条排除＝演绎；发现三次出错都在月末，推测跨月逻辑有问题＝归纳。

## 速记

- 覆盖从弱到强：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径；经验排序，只有判定⊃语句是真包含
- 条件覆盖与判定覆盖互不包含（`&&` 一真一假仍假、`||` 一真一假仍真）；路径覆盖也不含条件覆盖
- McCabe：V(G) = 边 − 点 + 2 = 判定结点数 + 1 = 闭合区域数 + 1；独立路径数 ≠ 全部路径数；> 10 难测难维护；别漏假分支和回边
- 依据文档：单元 ← 详细设计，集成 ← 概要设计，确认/配置项 ← SRS，系统 ← 用户需求或开发合同，验收 ← 合同或 SRS
- 自顶向下补桩、自底向上补驱动；三明治两头都要、工作量大
- 静态不跑程序（桌前检查／代码审查／代码走查，发现 30%–70% 错误）；黑盒白盒都是动态；外部属性可直接测、内部属性只能间接测
- 黑盒：等价类（无效类一条只犯一个错）、边界值（两端值 + 界外紧邻）、错误推测、因果图
- α 在开发方场地、β 在用户场地，主体都是用户；调试：蛮力、回溯、原因排除（演绎／归纳／二分）
