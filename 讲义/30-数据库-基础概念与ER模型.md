# 30 · 数据库：基础概念与 E-R 模型

## 定位

这一课讲两件事：库里的表夹在系统的哪一层（外模式／模式／内模式），又从哪来（现实业务 → E-R 图 → 关系模式）。第一节分清数据、DB、DBMS、DBS；二、三节讲三级模式与两级映像，回答"某一层变了、别的层要不要跟着改"；四、五节讲 E-R 图和它怎么转成关系模式，全课唯一要动笔数数的在第五节；第六节把这一路排成数据库设计的六个阶段。全课例子：内部报销系统——员工提单、主管审批。

---

## 一、数据、DB、DBMS、DBS

| 特征 / 关键词 | 是什么 |
|---|---|
| "描述事物的符号记录"；文本、图形、图像、音频、视频、学生的档案记录、货物的运输情况 | **数据**——不是只有数字才叫数据 |
| "长期存储在计算机内、有组织的、可共享的大量数据的集合" | **DB（数据库）**，磁盘上那堆数据本身 |
| "实现对共享数据有效的组织、管理和存取"的软件；MySQL、Oracle | **DBMS（数据库管理系统）** |
| "采用了数据库技术，有组织地、动态地存储大量相关数据，方便多用户访问的计算机系统" | **DBS（数据库系统）** |
| DBS 的组成 | **数据库、硬件、软件、人员**四部分；人员分系统分析和数据库设计人员、应用程序员、最终用户、数据库管理员 **DBA** |
| DBMS 的功能 | 数据定义、数据库操作、数据库运行管理、数据的存储管理、数据库的建立和维护，共**五项**（原文第五项后跟一个"等"字） |
| 数据库的基本特征 | 数据按一定的数据模型组织、描述和存储；可为各种用户共享；冗余度较小；数据独立性较高（第三节展开）；易扩展，共**五条** |

**DB / DBMS / DBS**
判据｜一堆**数据**＝DB，管它的**软件**＝DBMS，连机器带人**整套**＝DBS。定义句落脚在"集合"上是 DB，落在"软件""系统"上分别是 DBMS、DBS；"数据库系统"不是"数据库"的全称。

## 二、三级模式

同一句"报销库"，三个人指的不是一个东西：财务小王要"本月已审批通过的单号和金额"，是全部数据里裁出来的一小块；开发要"报销单表 12 个字段、员工表 6 个、用工号关联"，是全体表的结构；DBA 要"按单号聚簇存储、审批日期上加索引、放在哪块盘"，是文件和索引。三者合称**三级模式**，列举次序为**外→模→内**（从人看得见的一头排到磁盘那一头）。

| 特征 / 关键词 | 是什么 |
|---|---|
| **视图**；"将表进行一定的处理后再提供给用户使用" | **外模式**，一个数据库可以有**很多个**，一个应用一份；图上叫外部视图 |
| **基本表**；全体数据的全局逻辑结构；"根据应用、需求将物理数据划分成一张张表"；又称**概念模式** | **模式**，一个数据库**只有一个**；图上叫概念视图 |
| **存储文件**；"管理如何存储物理的数据"、**对应具体物理存储文件**；聚簇、索引、压缩 | **内模式**，同样**只有一个**；图上叫内部视图 |
| 谁建立维护、谁管理 | 三层都由 **DBA 建立和维护**、由 **DBMS 统一管理**；用户只有一个入口——用**主语言**（Java、C 这类宿主语言）嵌 **DML**（数据操纵语言，`SELECT`、`UPDATE` 这类语句），够不到下面任何一层 |

**外模式 vs 模式**
判据｜是不是裁出来的一小块：一个应用看到的那一份＝外模式；全体表的结构＝模式。能有多个的只有外模式。
例子｜"本月已审批通过的单号和金额"＝外模式；去掉"本月已审批"这个筛选、变成整张报销单表的结构，就成了模式。

## 三、两级映像与数据独立性

分层之后还要允许各层自己变。报销单加一列"发票张数"，**模式变了**；DBA 把这张表从堆存储（行按写入先后堆放）改成按单号聚簇（单号相邻的行物理上挨着存）、再加两个索引，**内模式变了**。两次上层都不用改，靠的是两块"减震器"——**映像**（映射关系）。判据不看哪个听起来更"物理"，只看**变的是哪一层**：表是逻辑层的东西，所以加列是逻辑独立性。

| 变更 / 关键词 | 独立性 | 由哪级映像顶住 |
|---|---|---|
| 改表的逻辑结构：加列、拆表、改字段名 | **逻辑独立性** | **外模式—模式映像** |
| 改物理存储：换存储结构、加索引、换引擎 | **物理独立性** | **模式—内模式映像** |
| "**表和视图之间的映射**"，存在于概念级和外部级之间 | —— | 外模式—模式映像 |
| "**表和数据的物理存储之间的映射**"，存在于概念级和内部级之间 | —— | 模式—内模式映像 |

**逻辑独立性 vs 物理独立性**
判据｜独立性按"变的那一层是逻辑层还是物理层"命名；映像是"变的那一层和它上面一层"，名字一律**上层在前**（写"外模式—模式"，不写"模式—外模式"）。逻辑独立性对应外模式—模式映像，物理独立性对应模式—内模式映像，两者不能对调。
例子｜报销单加一列，小王只查单号和金额的旧视图、旧程序不用改＝逻辑独立性；把"加一列"换成"加两个索引"，就成了物理独立性。
原话｜外模式—模式映像："若表中数据发生了修改，只需要修改此映射，而无需修改应用程序"；模式—内模式映像："若修改了数据存储方式，只需要修改此映射，而不需要去修改应用程序"。

数据一致性、数据完整性不是独立性，与"某层变了上层不用改"无关。

## 四、数据模型与 E-R 图

模式那一层的表不能从人话直接跳到 `CREATE TABLE`——漏一条联系、定错主键，数据灌进去后再改就是一场迁移。中间先画一张只说"有哪些东西、东西间有什么关系"的蓝图，**不提 DBMS、字段类型、索引**。

| 特征 / 关键词 | 是什么 |
|---|---|
| 从用户的角度进行建模；现实世界到信息世界的**第一抽象**；"真正的实体-联系模型" | **概念模型**——画给人看，工具是 E-R 图 |
| 用**二维表**表示的实体-联系模型；由实体-联系模型**转换而来**、经开发人员设计；由行列组成，**用表格结构表达实体集，用外键标识实体间的联系** | **关系模型**——给 DBMS 用；一列叫**属性**，一行叫**元组** |
| 用**树形结构**表示实体之间的联系，有且仅有一个根节点 | **层次模型** |
| 表示实体类型及其实体之间的联系，一个事物和另外几个都有联系，形成一张网 | **网状模型** |
| 用面向对象的方法设计数据库，以对象为单位，每个对象包括属性和方法，具有类和继承等特点 | **面向对象模型** |
| 数据模型三要素 | **数据结构**（所研究的对象类型的集合）、**数据操作**（对数据库中各种对象的实例允许执行的操作的集合）、**数据的约束条件**（一组完整性规则的集合） |
| 关系模型优缺点 | 优点：建立在严格的数学概念基础上，概念单一、结构简单、清晰，用户易懂易用，**存取路径对用户透明**，从而数据独立性、安全性好，简化数据库开发工作；缺点也来自存取路径透明——查询效率往往不如非关系数据模型 |

一字之差：第二节的**概念模式**是三级模式里的"模式"（全体表的结构），这里的**概念模型**是 E-R 图那一层的蓝图。

**E-R 图的形状与配套术语**

| 特征 / 关键词 | 是什么 | 画法 |
|---|---|---|
| 客观存在并可相互区别的事物，可以是具体的人、事、物或抽象概念（人、汽车、图书、账户、贷款；部门、员工、报销单） | **实体** | **长方形** |
| 实体所具有的特性（工号、姓名） | **属性** | **椭圆**（常省去椭圆，另列文字属性清单） |
| 现实世界中事物内部以及事物之间的联系，反映为**实体内部的联系**（如员工的上下级）**和实体之间的联系** | **联系** | **菱形**，两端写联系类型 |
| 属性的取值范围（"金额"的域是非负数） | **域** | —— |
| 能唯一标识实体的属性集 | **码（key）** | —— |
| 具有相同类型和共享相同属性的实体的集合（全体学生、全部课程） | **实体集** | —— |
| 依赖强实体的存在而存在，强实体没了它就没有意义 | **弱实体** | **双线长方形** |

原话｜世界是由一组称作实体的基本对象和这些对象之间的联系构成的。

**概念模型 vs 关系模型**
判据｜概念模型画给人看、与 DBMS 和物理实现无关；关系模型给 DBMS 用、由概念模型转换而来。
例子｜"员工和报销单之间有一个'审批'菱形"＝概念模型；把它写成**关系模式** `审批(工号, 单号, 审批意见)`（关系模式就是一张表的结构，写成 `表名(列1, 列2, …)`，主键画下划线或另行标注）并标出主键，就成了关系模型。

**强实体 vs 弱实体**
判据｜离开对方还有没有意义，没有意义的是弱实体。这与多对多无关：多对多看两个方向各能对几个，弱实体看离开对方有没有意义。
例子｜"审批意见"离开所属报销单毫无意义 → 弱实体；"家长"依赖"学生"，学生离校后单独的家长信息没有用 → 弱实体；把"家长"换成"班主任"，班主任独立存在，就不是弱实体。

属性分四组，认名即可：简单／复合属性（"地址"可拆成省市区，是复合的）、单值／多值属性（一个员工可有多个电话）、NULL 属性（可以没值）、派生属性（能由别的属性算出，如由出生日期算年龄）。

另一套常见记法（扩展 E-R，EER）：联系两端标 UML 风格的 `1` 和 `*`，而不是 `1:1`、`1:N`、`M:N`；子类型（如"经理""部门经理""业务员"都是"员工"的一种身份）画成**左右双竖线**方框，与父实体的连线上带**小圆圈**，表示**特化**。这不是弱实体——经理离开员工表照样是个人。本课按矩形实体、椭圆属性、菱形联系、两端写 1:1／1:N／M:N 这一套为准。

## 五、联系类型与 E-R 图转关系模式

同一个菱形转成表的做法，取决于两端的联系类型。

**判联系类型**：站在每一端问"这一端的一个个体，最多对上对面几个"，**两个方向都要问**。

| 类型 | 两个方向各问一次 | 报销系统例子 |
|---|---|---|
| **一对一 1:1** | 两个方向都最多对 1 个 | 部门↔员工"主管"：一个部门一位主管，一个人最多主管一个部门 |
| **一对多 1:N** | 一个方向对多个，反方向最多对 1 个 | 部门↔员工"所属"：一个部门多名员工，一个员工只属一个部门 |
| **多对多 M:N** | 两个方向都能对多个 | 员工↔报销单"审批"：一张单多人审批，一个人审批多张单 |

部门和员工之间同时挂着 1:1 的"主管"和 1:N 的"所属"：**基数**（菱形两端的 1 或 N，即"最多对上几个"）由业务规则定，不由哪两个实体定，同一对实体间可以有多个不同基数的联系。**联系自己也能带属性**："审批意见""审批时间"既不属于员工（一个人审过很多单），也不属于报销单（一张单被很多人审过），属于"某人审了某单"这件事，挂在"审批"菱形上。

**为什么 M:N 必须单独建表**：审批记录 (E01,R01)、(E02,R01)、(E01,R02)、(E03,R02)、(E02,R03)，若把审批人塞进报销单表：

```
R01  2026-01-05  1200  E01
R01  2026-01-05  1200  E02      ← R01 的日期、金额整行抄第二遍
R02  2026-01-07   380  E01
R02  2026-01-07   380  E03      ← R02 同样抄第二遍
R03  2026-01-09  5600  E02
```

R01、R02 各出现 2 次，**单号不再唯一，主键失效**（主键：能唯一钉住一行、不许重复也不许为空的那一列或几列），金额和日期重复抄写 2 次；塞进员工表同样 E01、E02 各出现 2 次。两头都是"多"，并进哪头都整行重复——只能给联系单独建第三张表，即常说的"中间表"，共**三张**。

**为什么 1:N 只能并 N 端**："提交"联系里一张单只由一个人提交，把提交人工号放进报销单表，每行只装一个值（R01→E01、R02→E02、R03→E01），单号仍唯一；反过来并进员工表，E01 一行要同时装 R01 和 R03，装不下。

**转换规则**（前提：**每个实体都对应一个关系模式**，无条件执行）：

| 联系类型 | 能否合并 | 合并怎么做 | 单独建表时主键 |
|---|---|---|---|
| **1:1** | 能，并到**任意一端** | 该端加入对方的码 + 联系属性 | 任一端的码 |
| **1:N** | 能，只能并到 **N 端** | N 端加入 1 端的码 + 联系属性 | N 端的码 |
| **M:N** | **不能**，必须单独建关系模式 | —— | **M 端和 N 端码的联合主键** |

从别的表搬过来的码在本表里都是**外键**（外码）：被并入端里对方的码是外键，联系表里两端的码各自是外键。

**算例**：实体三个——部门（码：部门号；部门名、办公地点）、员工（码：工号；姓名、职级）、报销单（码：单号；提交日期、金额）；联系四个——主管（部门:员工，1:1，联系属性：任命日期）、所属（部门:员工，1:N）、提交（员工:报销单，1:N）、审批（员工:报销单，M:N，联系属性：审批意见、审批时间）。求最少的关系模式。

1. 三个实体各转一张表，属性照搬，主键是实体的码。
2. "主管" 1:1，并到任意一端，这里并进部门表：加工号 + 任命日期。
3. "所属" 1:N，N 端是员工：员工表加部门号。
4. "提交" 1:N，N 端是报销单：报销单表加工号。
5. "审批" M:N，单独建表：工号 + 单号 + 审批意见 + 审批时间。

```
部门(部门号, 部门名, 办公地点, 工号, 任命日期)   主键:部门号   外键:工号→员工
员工(工号, 姓名, 职级, 部门号)                   主键:工号     外键:部门号→部门
报销单(单号, 提交日期, 金额, 工号)               主键:单号     外键:工号→员工
审批(工号, 单号, 审批意见, 审批时间)             主键:(工号,单号)   外键:工号→员工、单号→报销单
```

四张表、17 个属性、5 个外键，只有"审批"用组合主键。

**规则**：**最少关系模式数 = 实体数 + M:N 联系数**（仅限二元联系，即每个菱形只连两个实体）——3 + 1 = 4。原因：实体必各成一表，1:1、1:N 求"最少"时全部并掉，只有 M:N 无处可并。这条式子只管"最少"；若要求为每个联系都建一个关系模式，则为 3 + 4 = 7。

**多元联系**：三个或三个以上实体之间也可以有一个联系。如"课程"标 1、"教师"标 m、"参考书"标 n 连到同一个"讲授"菱形（两个以上实体型间 1:n 联系）；"供应商"m、"项目"n、"零件"p 连到同一个"供应"菱形（两个以上实体型间 m:n 联系）。转换时单独建一个关系模式，属性为各实体的码加联系自身的属性。

## 六、数据库设计的阶段

六个阶段：需求分析 → 概念结构设计 → 逻辑结构设计 → 物理结构设计 → **数据库实施** → **数据库运行和维护**。（后两阶段按《软件设计师教程》第 5 版补。）

| 动作 / 产物 | 阶段 |
|---|---|
| 分析数据存储的要求；输入是"当前和未来应用的数据要求"和"数据处理要求" | **需求分析** |
| **数据流图、数据字典、需求说明书**（逻辑结构设计的依据） | **需求分析**的产出 |
| 设计 E-R 图，也即实体-属性图；说明有哪些实体、实体有哪些属性；**与物理实现无关**；"用户的数据模型（即与 DBMS 无关的概念模型）" | **概念结构设计**，产出 ER 模型 |
| 将 E-R 图转换成关系模式，也即转换成实际的表和表中的列属性；输入是"转换规则、规范化理论" | **逻辑结构设计**，产出关系模式 |
| 根据生成的表等概念生成物理数据库；输入是"DBMS 特性""硬件、OS 特性""视图、完整性约束及应用处理说明书"；决定表放哪块盘、建哪些索引 | **物理设计**（＝**物理结构设计**，两种叫法） |
| 把表建出来、灌入老数据、试运行 | **数据库实施** |
| 上线后的备份、性能调优和结构调整 | **数据库运行和维护** |

三份需求产出物：数据流图是"数据从谁流到谁、中间被谁加工"的图（报销单从员工流到主管、再到财务）；数据字典逐条写清每个数据项的含义和取值（"金额：人民币元，两位小数，非负"）；需求说明书把功能和约束成文。三样都是结构化分析的现成产物。"规范化"是判断表拆得对不对的理论，逻辑结构设计会用到。

**概念结构设计 vs 逻辑结构设计**
判据｜还是图＝概念；已经是关系模式＝逻辑；开始谈索引和存储＝物理。逻辑结构设计的依据是需求说明文档、数据字典和数据流图，不含程序文档（实施阶段才有）。
例子｜"画 E-R 图"＝概念结构设计（与 DBMS 无关）；改成"把 E-R 图转成关系模式"＝逻辑结构设计（已是表和列，绑定关系型 DBMS）。

## 速记

- DB＝数据本身，DBMS＝管数据的软件，DBS＝数据库＋硬件＋软件＋人员；数据模型三要素＝数据结构、数据操作、数据的约束条件
- **视图＝外模式、基本表＝模式、存储文件＝内模式**；外模式可多个，模式与内模式各一个
- **改表不改应用＝逻辑独立性＝外模式—模式映像；改存储不改表＝物理独立性＝模式—内模式映像**（映像名上层在前）
- E-R 图：矩形实体、椭圆属性、菱形联系（两端写类型）、双线矩形弱实体；联系也能带属性
- 判基数：两端各问一次"最多对上几个"；弱实体＝离开强实体就没有意义
- 转换：实体必成表；**1:1 任意并、1:N 并 N 端、M:N 单独建表且两端码合成主键**；搬过来的码是外键
- **最少关系模式数＝实体数＋M:N 联系数**（仅二元联系）；每个联系都建表则＝实体数＋全部联系数
- 六阶段：需求分析→概念结构设计→逻辑结构设计→物理结构设计→数据库实施→运行和维护；**画图在概念、转表在逻辑**
