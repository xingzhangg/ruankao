# 30 · 数据库：基础概念与 E-R 模型

> 真题：E-R 转关系模式 2022下、逻辑结构设计依据 2014下（两题均核到信管网软件设计师卷面）；2021上 E-R 同考点题依赖配图、各来源转录均有讹字，已降级为重现题；三级模式配对与教务系统弱实体两题录自培训资料，年份待核实｜轻量计算（数关系模式条数），阶段B｜未讲

## 定位

这一课讲两件事：库里那些表从哪来（现实业务 → E-R 图 → 关系模式），又被夹在系统的哪一层（外模式／模式／内模式）。开讲先把数据、DB、DBMS、DBS 四个天天混着说的词分开；一、二两节讲分层与两级映像，答的是"某一层变了、别的层要不要跟着改"；三、四两节讲表的来路——先画一张与 DBMS 无关的 E-R 图，再按联系类型转成关系模式，全课唯一要动笔数数的地方就在第四节；第五节把这一路排成数据库设计的六个阶段。

## 开讲：五个坑，五节补丁

全课跟着一个例子走：内部报销系统——员工提单、主管审批。最朴素的建库做法是打开数据库客户端、想到一个字段就加一列，它在五个地方不够用，五节正好是这五个坑的补丁：①三个人嘴里的"报销库"根本不是同一个东西；②一层变，另外两层被迫跟着改；③"表"这一层本身从哪来；④图上那根线怎么变成表；⑤这一路分几步、每步交什么。

**反查表 · 四个天天混着说的词**

| 题干里出现 | 答 |
|---|---|
| "描述事物的符号记录"；文本、图形、图像、音频、视频、学生的档案记录、货物的运输情况 | **数据**——不是只有数字才叫数据 |
| "长期存储在计算机内、有组织的、可共享的大量数据的集合" | **DB（数据库）**，磁盘上那堆数据本身 |
| "实现对共享数据有效的组织、管理和存取"的那个软件；MySQL、Oracle | **DBMS（数据库管理系统）** |
| "采用了数据库技术，有组织地、动态地存储大量相关数据，方便多用户访问的计算机系统" | **DBS（数据库系统）** |
| 问 **DBS 由哪几部分组成** | **数据库、硬件、软件、人员**四部分——最容易漏的是"人员" |
| 问 **DBMS 的功能**有哪些 | 数据定义、数据库操作、数据库运行管理、数据的存储管理、数据库的建立和维护，共**五项**（原文第五项后还跟着一个"等"字，考试按这五项答） |
| 问**数据库的基本特征** | 数据按一定的数据模型组织、描述和存储；可为各种用户共享；冗余度较小；数据独立性较高；易扩展，共**五条** |

**易混对：DB / DBMS / DBS**

- 判据｜一堆**数据**＝DB，管它的那个**软件**＝DBMS，连机器带人**整套**＝DBS。看定义句的落脚词：落在"集合"上是 DB，落在"软件/系统"上分别是 DBMS 和 DBS。
- 错法｜把"数据库系统"当成"数据库"的全称。

"人员"这一项还要认得四种人：系统分析和数据库设计人员、应用程序员、最终用户、数据库管理员 **DBA**。五条基本特征里的"数据独立性较高"，正是第二节要展开的那件事。

### 一、三个人说的不是同一个库：三级模式（补①）

同一句"报销库"，三个人心里想的东西完全不同：财务小王要的是"本月已审批通过的单号和金额"，是全部数据里被裁出来的一小块；你要的是"报销单表有 12 个字段，员工表有 6 个，两张表用工号关联"，是全体表的结构；DBA 要的是"这张表按单号做聚簇存储，审批日期上加个索引，放在哪块盘上"，是文件和索引。三种说法被固定成三个名字，合称**三级模式**，列举时的次序永远是**外→模→内**，从人看得见的一头排到磁盘那一头。**注意这只是列举次序**——题干若问"物理独立性和逻辑独立性分别由谁保证"，就按**题干问的先后**答，别照搬外→模→内。

**反查表 · 给一样东西，问它是哪一级**

| 题干里出现 | 答 |
|---|---|
| **视图**；"将表进行一定的处理后再提供给用户使用" | **外模式**，一个数据库可以有**很多个**，一个应用一份 |
| **基本表**；全体数据的全局逻辑结构；"根据应用、需求将物理数据划分成一张张表"；又称**概念模式** | **模式**，一个数据库**只有一个** |
| **存储文件**；"管理如何存储物理的数据"、**对应具体物理存储文件**；聚簇、索引、压缩 | **内模式**，同样**只有一个** |
| 视图、基本表、存储文件三样按序分别对应哪三级 | 外模式、模式、内模式 |
| 这三层由谁建立维护、由谁统一管理 | 三层都由 **DBA 建立和维护**、由 **DBMS 统一管理**；用户手里只有一个入口——用**主语言**（Java、C 这类写程序的语言）嵌**DML**（`SELECT`、`UPDATE` 这类操作数据的语句），够不到下面任何一层 |

**易混对：外模式 vs 模式**

- 判据｜**是不是裁出来的一小块**：一个应用看到的那一份＝外模式；全体表的结构＝模式。
- 例子｜"本月已审批通过的单号和金额"＝外模式；"报销单表 12 个字段、员工表 6 个、用工号关联"＝模式。把"本月已审批"这个筛选条件去掉、变成整张报销单表，答案就从外模式变成模式。
- 错法｜三空题把次序打乱成"模式、外模式、内模式"；或说"一个数据库可以有多个模式"——能有多个的只有外模式。

其余认名即可：**DML**（数据操纵语言，`SELECT`/`UPDATE` 这类语句）、**主语言**（把 DML 嵌进去用的 Java、C 这类宿主语言）；三级在图上分别叫外部视图、概念视图、内部视图。

> 考试这样问：给"视图、基本表、存储文件"三样，问它们的结构分别与哪三级对应。

### 二、分了层，还得允许各层自己变：两级映像（补②）

层次分清楚只解决了"各人说的是哪一层"，没解决"某一层变了怎么办"。两件真事：业务方要求报销单加一列"发票张数"，**模式变了**；DBA 半夜把这张表从堆存储（行按写入先后随便堆着）改成按单号聚簇（物理上把单号相邻的行排在一起存）、还加了两个索引，**内模式变了**。两次答案都是"上层不用改"，靠的是两块**减震器**，学名**映像**（映射关系）。

**先别往下看：加一列"发票张数"、旧程序不用改——这叫哪种独立性？** 很多人张口就答"物理独立性"，理由是"表是实实在在存在磁盘上的东西"。错了。判据不看你觉得哪个更"物理"，只看**变的是哪一层**。

**反查表 · 给一次变更，问独立性和映像**

| 题干里出现 | 是哪种独立性 | 由哪级映像顶住 |
|---|---|---|
| 改表的逻辑结构：加列、拆表、改字段名 | **逻辑独立性** | **外模式—模式映像** |
| 改物理存储：换存储结构、加索引、换引擎 | **物理独立性** | **模式—内模式映像** |
| "**表和视图之间的映射**"，存在于概念级和外部级之间 | —— | 外模式—模式映像 |
| "**表和数据的物理存储之间的映射**"，存在于概念级和内部级之间 | —— | 模式—内模式映像 |
| 数据一致性、数据完整性 | 都不是 | 同族干扰项，跟"某层变了上层不用改"没有关系 |

**易混对：逻辑独立性 vs 物理独立性**

- 判据｜**独立性按"变的那一层在逻辑层还是物理层"命名；映像就是"变的那一层和它上面那一层"这两级，写名字时一律上层在前。** 表（模式）是逻辑层的东西，所以是逻辑独立性，减震器架在它和上面的外模式之间，写成"外模式—模式映像"；存储（内模式）是物理层的东西，所以是物理独立性，减震器架在它和上面的模式之间，写成"模式—内模式映像"。
- 例子｜报销单加一列"发票张数"，小王那份只查单号和金额的旧视图、旧程序不用改＝逻辑独立性；把"加一列"换成"加两个索引"，答案立刻变成物理独立性。
- 错法｜选项里最常见的假话是"逻辑独立性通过修改模式—内模式映像实现"，把两者对调；其次是把名字写反成"模式—外模式映像"。这一对是本课最稳的送分点，**记反就是白丢一分**。
- 原话｜外模式—模式映像："若表中数据发生了修改，只需要修改此映射，而无需修改应用程序"；模式—内模式映像："若修改了数据存储方式，只需要修改此映射，而不需要去修改应用程序"。

### 三、"表"这一层本身从哪来：先画一张与 DBMS 无关的蓝图（补③）

模式那一层的表不能凭空冒出来。从"一个员工能提多张单、一张单要多人审批"这样的人话，直接跳到 `CREATE TABLE`，跨度太大——漏掉一条联系、把主键定错，等数据灌进去再改就是一场迁移工程。中间要垫一张**蓝图**：只说清"业务里有哪些东西、东西之间有什么关系"，**完全不提 MySQL、不提字段类型、不提索引**。这一节要分清两件事：蓝图用的是哪种模型，蓝图上能画哪三种形状。

**反查表 · 给一句定义，问是哪种数据模型**

| 题干里出现 | 答 |
|---|---|
| 从用户的角度进行建模；现实世界到信息世界的**第一抽象**；"真正的实体-联系模型" | **概念模型**——画给人看的，工具是 E-R 图 |
| 用**二维表**的形式表示的实体-联系模型；由实体-联系模型**转换而来**、经过开发人员设计；由行列组成，**用表格结构表达实体集，用外键标识实体间的联系** | **关系模型**——给 DBMS 用的 |
| 用**树形结构**表示实体之间的联系，有且仅有一个根节点 | **层次模型** |
| 表示实体类型及其实体之间的联系，一个事物和另外几个都有联系，形成一张网 | **网状模型** |
| 采用面向对象的方法设计数据库，以对象为单位，每个对象包括属性和方法，具有类和继承等特点 | **面向对象模型** |
| 问**数据模型三要素** | **数据结构**（所研究的对象类型的集合）、**数据操作**（对数据库中各种对象的实例允许执行的操作的集合）、**数据的约束条件**（一组完整性规则的集合） |
| 关系模型里一列叫什么、一行叫什么 | **一列叫属性，一行叫元组** |
| 问关系模型的优点、缺点 | 优点：建立在严格的数学概念基础上，概念单一、结构简单、清晰，用户易懂易用，**存取路径对用户透明**，从而数据独立性、安全性好，简化数据库开发工作；缺点也来自"存取路径透明"这一条——查询效率往往不如非关系数据模型 |

> 留意一字之差：第一节的**概念模式**是三级模式里的"模式"那一层（全体表的结构），这里的**概念模型**是 E-R 图那一层的蓝图，两回事。

**反查表 · E-R 图上的三种形状，外加四个配套术语**

| 题干里出现 | 答 | 画成什么形状 |
|---|---|---|
| 客观存在并可相互区别的事物，可以是具体的人、事、物或抽象概念（人、汽车、图书、账户、贷款；报销系统里是部门、员工、报销单） | **实体** | **长方形** |
| 实体所具有的特性（员工的工号、姓名） | **属性** | **椭圆**（考卷上常为省地方不画椭圆，改用文字另给一份属性清单，下午题 2 就是这个样子） |
| 现实世界中事物内部以及事物之间的联系，反映为**实体内部的联系**（同一个实体自己跟自己有关系，比如员工的上下级）**和实体之间的联系** | **联系** | **菱形**，两端要填写联系类型 |
| 属性的取值范围（"金额"的域是非负数） | **域** | —— |
| 能唯一标识实体的属性集 | **码（key）** | —— |
| 具有相同类型和共享相同属性的实体的集合（全体学生、全部课程） | **实体集** | —— |
| 依赖强实体的存在而存在，强实体没了它就没有意义 | **弱实体** | **双线长方形**（与普通实体的单线框相区别） |

一句原话常被照抄进选项：**世界是由一组称作实体的基本对象和这些对象之间的联系构成的**。

**易混对：概念模型 vs 关系模型**

- 判据｜**概念模型是画给人看的，关系模型是给 DBMS 用的**；概念模型与物理实现无关，关系模型由它转换而来。
- 例子｜"员工和报销单之间有一个'审批'菱形"＝概念模型；把这个菱形写成**关系模式** `审批(工号, 单号, 审批意见)`（**关系模式就是一张表的结构**，写成 `表名(列1, 列2, …)`，主键画下划线或另行标注）并标上主键，同一件事就变成了关系模型。
- 错法｜把"与 DBMS 无关"安给关系模型。另外两种模型（网状、面向对象）不在"现实世界→信息世界"这条链上，认名即可。

**易混对：强实体 vs 弱实体**

- 判据｜**离开对方还有没有意义**，没有意义的那一个是弱实体。
- 例子｜"审批意见"离开了它所属的那张报销单毫无意义 → 弱实体；"家长"依赖"学生"，学生不在这个学校了，单独一条家长信息没有任何用处 → 弱实体。把"家长"换成"班主任"，答案就变了——班主任本身是独立存在的实体。
- 错法｜把"多对多的那两个实体"当成弱实体依赖。两问经常挨着出，判据完全不同：多对多问的是两个方向各能对几个，弱实体问的是离开对方还有没有意义。

属性还分四组，认名即可：简单属性和复合属性（"地址"能再拆成省市区，是复合的）、单值属性和多值属性（一个员工可能有多个电话）、NULL 属性（可以没值）、派生属性（能从别的属性算出来，比如由出生日期算年龄）。

#### 深入 · 培训资料 4-2 示例图上那三种记号

培训资料 4-2 配的示例图画的是超市／经理／员工／部门／部门经理／业务员／商品，**用的却不是正文这套记法**：联系两端标的是 UML 风格的 `1` 和 `*`，不是 `1:1`、`1:N`、`M:N`。

图上还有两处记号值得说明白，免得和刚学的弱实体搞混："经理""部门经理""业务员"三个方框画的是**左右双竖线**边框，"员工"与这三个框之间的连线上各有一个**小圆圈**。它们**不是弱实体**——看连接关系就清楚：这三者都是"员工"的一种身份，是**子类型**，小圆圈是扩展 E-R（EER）里表示**特化**的记号。弱实体确实也画双线框（见上面反查表），但弱实体是"离开强实体就没有意义"（审批意见离开报销单），而经理离开员工表照样是个人——两者形状像、意思完全不同。

软设按正文那一套答：矩形实体、椭圆属性、菱形联系，两端写 1:1／1:N／M:N；特化那套记号不考。

### 四、那根线怎么变成表：联系类型与转换规则（补④）

蓝图上"员工"和"报销单"之间画了一个菱形。可**同样一个菱形，转成表的做法完全不同**，取决于菱形两端写的是什么。

判定联系类型只有一个动作：**站在每一端，问"这一端的一个个体，最多对上对面几个"，两个方向都要问**。只问一个方向就下结论，是这里最常见的错法。报销系统里刚好三种都有：

| 类型 | 两个方向各问一次的结果 | 报销系统里的例子 |
|---|---|---|
| **一对一 1:1** | 两个方向都最多对 1 个 | 部门↔员工的"主管"联系：一个部门只有一位主管，一个人最多主管一个部门 |
| **一对多 1:N** | 一个方向对多个，反方向最多对 1 个 | 部门↔员工的"所属"联系：一个部门有多名员工，一个员工只属一个部门 |
| **多对多 M:N** | 两个方向都能对多个 | 员工↔报销单的"审批"联系：一张单要多人审批，一个人审批多张单 |

注意"部门"和"员工"之间同时挂着 1:1 的"主管"和 1:N 的"所属"两个菱形——**基数（就是菱形两端写的那个 1 或 N，说的是"最多对上几个"）是业务规则定的，不是由哪两个实体定的**，同一对实体之间完全可以有多个不同基数的联系。

还有一件常被忽略的事：**联系自己也能带属性**。"审批意见"和"审批时间"既不属于员工（一个人审过很多单），也不属于报销单（一张单被很多人审过），它属于"某人审了某单"这件事，所以挂在"审批"这个菱形上。

**先别往下看：把"审批"这个多对多联系转成关系模式，一共要几张表？** 多数人答两张——员工一张、报销单一张，联系"塞进"其中一张。试一下就知道不行。假设审批记录是 (E01,R01)、(E02,R01)、(E01,R02)、(E03,R02)、(E02,R03)，把审批人塞进报销单表：

```
R01  2026-01-05  1200  E01
R01  2026-01-05  1200  E02      ← R01 的日期、金额被整行抄了第二遍
R02  2026-01-07   380  E01
R02  2026-01-07   380  E03      ← R02 同样抄了第二遍
R03  2026-01-09  5600  E02
```

单号 R01 出现 2 次、R02 出现 2 次，**单号不再唯一，主键当场失效**（主键就是能唯一钉住一行、不许重复也不许为空的那一列或那几列），金额和日期被重复抄写 2 次。反过来塞进员工表也一样：E01 出现 2 次、E02 出现 2 次，工号也不唯一了。**多对多两头都是"多"，并进任何一头都会整行重复、主键失效——所以只能给联系单独建第三张表**，也就是你工作中见惯的"中间表"。答案是**三张**。

对照着看 1:N 为什么就可以并。"提交"联系里一张报销单只由一个人提交，把提交人工号放进报销单表，一行只需要装**一个值**：R01→E01、R02→E02、R03→E01，单号仍然唯一。反方向就不行了——并进员工表的话，E01 这一行要同时装下 R01 和 R03 两个单号，一行装不下。**所以 1:N 只能往 N 端并。**

把这些整理成培训资料 4-4 那三条规则（**每个实体都对应一个关系模式**是前提，无条件执行）：

| 联系类型 | 能不能合并 | 合并怎么做 | 单独建表时主键是什么 |
|---|---|---|---|
| **1:1** | 能，并到**任意一端** | 该端加入对方的码 + 联系属性（要保证 1:1 的两端关联） | 任一端的码 |
| **1:N** | 能，只能并到 **N 端** | N 端加入 1 端的码 + 联系属性 | N 端的码 |
| **M:N** | **不能**，必须单独建关系模式 | —— | **M 端和 N 端码的联合主键** |

凡是"从别的表搬过来的码"，在本表里都是**外键**（外码）：被并入端里对方的那个码是外键，联系表里两端的码各自是外键。下午题 2 按点给分，外键漏标要扣分。

**完整走一遍：报销系统的 E-R 图转成关系模式。** 实体三个——部门（码：部门号；另有部门名、办公地点）、员工（码：工号；另有姓名、职级）、报销单（码：单号；另有提交日期、金额）；联系四个——主管（部门:员工，1:1，联系属性：任命日期）、所属（部门:员工，1:N）、提交（员工:报销单，1:N）、审批（员工:报销单，M:N，联系属性：审批意见、审批时间）。求最少的关系模式。

第 1 步，三个实体各转一张表，属性照搬，主键就是实体的码。第 2 步，"主管"是 1:1，并到任意一端都合法，这里并进部门表，加入对方的码"工号"和联系属性"任命日期"。第 3 步，"所属"是 1:N，1 端是部门、N 端是员工，把部门号加进员工表。

第 4 步，"提交"是 1:N，1 端是员工、N 端是报销单，把工号加进报销单表。第 5 步，"审批"是 M:N，单独建表，属性 = 工号 + 单号 + 审批意见 + 审批时间。结果：

```
部门(部门号, 部门名, 办公地点, 工号, 任命日期)   主键:部门号   外键:工号→员工
员工(工号, 姓名, 职级, 部门号)                   主键:工号     外键:部门号→部门
报销单(单号, 提交日期, 金额, 工号)               主键:单号     外键:工号→员工
审批(工号, 单号, 审批意见, 审批时间)             主键:(工号,单号)   外键:工号→员工、单号→报销单
```

四张表、17 个属性、5 个外键，只有"审批"用组合主键。用一条速算式反查条数：**最少关系模式数 = 实体数 + M:N 联系数**（前提是图上只有二元联系，即每个菱形只连两个实体；三元及以上见本节末的深入，跳过不影响做题）——3 + 1 = 4 ✓。

道理就写在上面那张规则表里：实体必各成一表，1:1 和 1:N 追求"最少"时全部合并、不新增表，只有 M:N 无路可走。**但这条式子只回答"最少"**；题目若改成"为每个联系都建立一个关系模式"，答案变成 3 + 4 = 7。

> 考试这样问：给实体数与各类联系数，问最少能转成几个关系模式；或问 M:N 联系单独建表后关键字由什么组成。

#### 深入 · 三个以上实体共用一个联系（多元联系）

推广一句：**三个或三个以上实体之间也可以有一个联系**。培训资料 4-3 配的图里并排画着两个例子：左边"课程"标 1、"教师"标 m、"参考书"标 n，三根线连到同一个"讲授"菱形，图注写"两个以上实体型间1:n联系"；右边"供应商"标 m、"项目"标 n、"零件"标 p，连到同一个"供应"菱形，图注写"两个以上实体型间m:n联系"。这类**多元联系**转换时单独建一个关系模式，属性是各实体的码加上联系自身的属性。培训资料对多元联系只给了这一张图、没有展开，按"看得懂图、认得出这是三个实体共用一个联系"记就够。

### 五、这一路一共分几步：数据库设计的阶段划分（补⑤）

上面四节其实已经把动作做完了，只是没给它们排序号。**考试按六个阶段答**：需求分析 → 概念结构设计 → 逻辑结构设计 → 物理结构设计 → **数据库实施** → **数据库运行和维护**。

**反查表 · 给一个动作或产物，问它属于哪个阶段**

| 题干里出现 | 答 |
|---|---|
| 分析数据存储的要求；输入是"当前和未来应用的数据要求"和"数据处理要求" | **需求分析** |
| **数据流图、数据字典、需求说明书**这三样产出物（问"逻辑结构设计以哪个阶段形成的什么为依据"，答的就是它们） | **需求分析**的产出 |
| 设计 E-R 图，也即实体-属性图；说明有哪些实体、实体有哪些属性；**与物理实现无关**；"用户的数据模型（即与 DBMS 无关的概念模型）" | **概念结构设计**，产出 ER 模型 |
| 将 E-R 图，转换成关系模式，也即转换成实际的表和表中的列属性；输入是"转换规则、规范化理论" | **逻辑结构设计**，产出关系模式 |
| 根据生成的表等概念生成物理数据库；输入是"DBMS 特性""硬件、OS 特性""视图、完整性约束及应用处理说明书"；决定表放在哪块盘、建哪些索引 | **物理设计**（＝**物理结构设计**，同一个阶段的两种叫法，选项里两种写法都出现过） |
| 真把表建出来、把老数据灌进去、试运行 | **数据库实施** |
| 上线后的备份、性能调优和结构调整 | **数据库运行和维护** |

三份需求产出物各是什么：数据流图是"数据从谁流到谁、中间被谁加工"的那张图（报销单从员工流到主管、再流到财务），数据字典是逐条写清每个数据项含义和取值的那份清单（"金额：人民币元，两位小数，非负"），需求说明书是把功能和约束成文的那一份。这三样正好是结构化分析的现成产物，数据库设计直接拿来用。（"规范化"是判断表拆得对不对的那套理论，本课只需知道逻辑结构设计这一步会用到它。）

**易混对：概念结构设计 vs 逻辑结构设计**

- 判据｜**还是图 = 概念；已经是关系模式 = 逻辑；开始谈索引和存储 = 物理。**
- 例子｜"画 E-R 图"＝概念结构设计（还是图、与 DBMS 无关）；把这句改成"把 E-R 图转成关系模式"＝逻辑结构设计（已经是表和列，绑定关系型 DBMS 了）。
- 错法｜问"逻辑结构设计要以哪个阶段形成的什么作为设计依据"时，选项里凡是混进"程序文档"的都是错的——程序文档要到实施阶段才有；正确的三样是需求说明文档、数据字典和数据流图。

培训资料只画到物理设计、一共四步，和教材六阶段的口径差异见本节末的深入；按六阶段答不会错，跳过不影响做题。

> 考试这样问：画 E-R 图属于哪个阶段、E-R 图转关系模式属于哪个阶段、逻辑结构设计以什么为依据。

#### 深入 · 培训资料四步与教材六阶段的口径差异

培训资料的正文和流程图都**只画到物理设计为止，一共四步**；而教材（《软件设计师教程》第 5 版）的完整说法是**六个阶段**，后面还有数据库实施、数据库运行和维护（这两阶段转录本未收，此处按教材补）。培训资料不是把后两步说错了，是没往下讲——实施是把表真的建出来、把老数据灌进去、试运行，运行和维护是上线后的备份、性能调优和结构调整。**考试按六阶段答。**

## 速记

- DB＝数据本身，DBMS＝管数据的软件，DBS＝数据库＋硬件＋软件＋人员四部分；数据模型三要素＝数据结构、数据操作、数据的约束条件
- 三级模式对应物：**视图＝外模式、基本表＝模式、存储文件＝内模式**；外模式可多个，模式与内模式各一个
- **改表不改应用＝逻辑独立性＝外模式—模式映像；改存储不改表＝物理独立性＝模式—内模式映像**（映像名字一律上层在前）
- E-R 图：矩形实体、椭圆属性、菱形联系，菱形两端写联系类型；联系也能带属性，属性跟着联系走
- 判基数：站两端各问一次"最多对上几个"；弱实体＝离开强实体就没有意义
- 转换：实体必成表；**1:1 随便并、1:N 并 N 端、M:N 单独建表且两端码合成主键**；搬过来的码就是外键
- **最少关系模式数＝实体数＋M:N 联系数**（仅限二元联系）；若要求每个联系都建表则＝实体数＋全部联系数
- 六阶段：需求分析→概念结构设计→逻辑结构设计→物理结构设计→数据库实施→运行和维护；**画图在概念、转表在逻辑**
