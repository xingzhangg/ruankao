## 第 1 层 · 理解

### 一句话

> 对象都造好了、也装配好了，接下来的问题是**它们运行时怎么互相打交道**——谁通知谁、谁替谁干活、请求交给谁处理、行为怎么随情况切换。行为型 11 个模式就是这些问题的现成答案。

### 一条主线（11 个模式 = 4 类问题，别当 11 个孤立名词背）

```
行为型管：跑起来之后，对象之间怎么打交道
   ↓ 11 个模式其实在回答【4 类】不同的问题：

 ① 一个对象变了，怎么让别人知道？
      观察者 ── 一对多【广播】：我变了，所有订阅者自动收到通知
      中介者 ── 多对多【收成星形】：谁也不直接找谁，都找中介转发

 ② 一件事该由谁干、怎么干？
      策略     ── 客户端【主动挑】一个算法装进去
      状态     ── 对象随【自身状态】自动切换行为
      责任链   ── 【沿链传】，谁能干谁干，发送者不知道是谁干的
      模板方法 ── 骨架父类定死，个别步骤留给子类填

 ③ "请求"和"状态"能不能变成【可存储的东西】？
      命令   ── 把【请求】封装成对象 → 才能排队、记日志、撤销
      备忘录 ── 把【状态】存成快照   → 才能恢复、读档

 ④ 怎么在【不动原结构】的前提下访问或扩展它？
      迭代器 ── 遍历聚合，但不暴露它的内部表示
      访问者 ── 不改元素类，却能给它加新操作
      解释器 ── 给一门小语言定文法，并解释它的句子
```

**这四问就是本课的骨架**——遇到题干先判断它在问哪一类，候选立刻从 11 个缩到 2–4 个。

## 第 2 层 · 考点：考试怎么问

上午题的考法与讲义 28 一致，主要是两种：**给一句 GoF 意图原句 → 选模式名**、**判断分类归属**（属创建型/结构型/行为型）；此外还会以**中英文名称对应**或**适用场景**的形式来问。所以每个模式最该记的是**意图 + 识别关键词 + 分类**。

### 考点① 观察者 Observer【下午题高频】

**痛点**：订单支付成功后要发短信、发邮件、加积分。直接在支付方法里挨个调用，每加一个"后续动作"就得改支付代码。希望反过来：**支付模块只管喊一嗓子"我变了"，谁关心谁自己来订阅**。

**意图（GoF）**：定义对象间的一种**一对多**的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都**得到通知并被自动更新**。

**角色**：Subject（抽象目标：维护观察者列表 + attach/detach/notify）、ConcreteSubject、Observer（声明 update）、ConcreteObserver。

```java
interface Observer { void update(Order order); }             // 抽象观察者
class SmsNotifier implements Observer {                      // 加一个后续动作 = 加一个类
    public void update(Order order) { /* 发短信 */ }
}
class Order {                                                // 目标（被观察者）
    private List<Observer> observers = new ArrayList<>();
    public void attach(Observer o) { observers.add(o); }     // 订阅
    public void paySuccess() {
        /* 支付逻辑 */
        for (Observer o : observers) o.update(this);         // 通知所有观察者 ← 骨架线
    }
}
```
**识别关键词**：**"一对多依赖"、"状态改变 → 所有依赖者自动收到通知并更新"、"发布-订阅"**

### 考点② 策略 Strategy【下午题高频】

**痛点**：结算时促销有满减、打折、无优惠，全堆在 if-else 里；每加一种就改一次结算代码。

**意图（GoF）**：定义**一系列的算法**，把它们一个个封装起来，并且使它们**可相互替换**。本模式使得算法可**独立于使用它的客户**而变化。

**角色**：Strategy（统一算法接口）、ConcreteStrategy（每种算法一个类）、Context（持有 Strategy 引用，把计算委托给它）。

```java
interface Promotion { int discount(int total); }             // 抽象策略
class FullReduce implements Promotion {                      // 具体策略：满减
    public int discount(int total) { return total >= 200 ? 30 : 0; }
}
class Checkout {                                             // 上下文
    private Promotion promotion;                             // ← 骨架线：字段是抽象类型
    public Checkout(Promotion p) { this.promotion = p; }     // 客户端选定注入
    public int pay(int total) { return total - promotion.discount(total); }
}
```
**识别关键词**：**"一系列算法"、"可相互替换"、"算法独立于客户变化"**

### 考点③ 责任链 Chain of Responsibility

**痛点**：报销审批——1000 元内组长批，1 万元内经理批，再大总监批。提交人不该关心"这单该找谁"。

**意图（GoF）**：使多个对象**都有机会处理**请求，从而**避免请求的发送者和接收者之间的耦合**。将这些对象连成一条**链**，并**沿着这条链传递**该请求，直到有一个对象处理它为止。

```java
abstract class Approver {
    protected Approver next;                                 // ← 骨架线：后继者引用
    public void setNext(Approver next) { this.next = next; }
    public abstract void approve(int amount);
}
class GroupLeader extends Approver {
    public void approve(int amount) {
        if (amount < 1000) { /* 组长审批 */ }
        else if (next != null) next.approve(amount);         // 处理不了 → 传给下家
    }
}
// 组装：leader.setNext(manager); manager.setNext(director);
```
**识别关键词**：**"多个对象都有机会处理"、"沿链传递直到被处理"、"发送者与接收者解耦"**

### 考点④ 命令 Command

**痛点**：编辑器要支持撤销/重做；遥控器一个按钮今天开灯明天开空调。共同点：**"一次请求"本身需要被存起来**——进历史栈才能撤销、进队列才能延迟执行。可"方法调用"转瞬即逝存不住，所以**把请求封装成对象**。

**意图（GoF）**：将一个**请求封装为一个对象**，从而使你可用不同的请求对客户进行**参数化**；对请求**排队**或**记录请求日志**，以及支持**可撤销**的操作。

**角色**：Command（execute / undo）、ConcreteCommand（绑定一个 Receiver）、Invoker（调用者，只认 Command 接口）、Receiver（真正干活的对象）。

```java
interface Command { void execute(); void undo(); }
class Light { void on() {} void off() {} }                   // 接收者：真正干活
class LightOnCommand implements Command {                    // 把"开灯"这件事变成对象
    private Light light;
    LightOnCommand(Light l) { this.light = l; }
    public void execute() { light.on(); }
    public void undo()    { light.off(); }
}
class Button {                                               // 调用者：只认命令接口
    private Command command;                                 // 换绑定 = 换命令对象
    void click() { command.execute(); }                      // 并可压入历史栈供撤销
}
```
**识别关键词（四信号，沾上就选它）**：**"请求封装为对象"、"参数化"、"排队/日志"、"撤销"**

### 考点⑤ 状态 State

**痛点**：讲义 27 画过的订单状态机。若每个方法里都 `switch(status)`，加一个状态要改所有方法，漏一处就是 bug。
**思路**：**每个状态做成一个类**，行为委托给"当前状态对象"，**状态迁移 = 换掉这个对象**。
> **状态图的每个圆角矩形 = 一个状态类。状态模式就是状态图的代码实现。**

**意图（GoF）**：允许一个对象在其**内部状态改变时改变它的行为**。对象看起来似乎**修改了它的类**。

```java
interface OrderState { void pay(Order o); void ship(Order o); }
class UnpaidState implements OrderState {
    public void pay(Order o)  { /* 收款 */ o.setState(new PaidState()); }  // 迁移=换状态对象
    public void ship(Order o) { /* 待支付不能发货：拒绝 */ }
}
class Order {
    private OrderState state = new UnpaidState();
    void setState(OrderState s) { this.state = s; }
    void pay()  { state.pay(this); }                         // 行为委托给当前状态
    void ship() { state.ship(this); }
}
```
**识别关键词**：**"内部状态改变时改变行为"、"看起来修改了它的类"**

> ⚠️ **策略 vs 状态（最高频辨析）**：两者结构几乎一样（Context 持有一个接口引用并委托）。区别**只看谁来换**：
> **客户端主动挑一个算法装进去 = 策略**（各策略互不认识）
> **对象随自身状态自动切换 = 状态**（状态类之间知道彼此，迁移时 new 下一个）
> 一句话：**客户挑的是策略，自己变的是状态。**

### 考点⑥ 其余六个行为型（意图 + 识别关键词）

| 模式 | 意图（GoF 要点） | **识别关键词** | 场景一句话 |
|---|---|---|---|
| **模板方法** | 定义操作中的**算法骨架**，将某些**步骤延迟到子类**，使子类不改变算法结构即可重定义特定步骤 | **"算法骨架"、"步骤延迟到子类"** | 泡茶和泡咖啡都是"烧水→冲泡→倒杯→加料"，父类定死流程，个别步骤子类实现 |
| **迭代器** | **顺序访问**聚合对象的各元素，而**不暴露该对象的内部表示** | **"遍历聚合"、"不暴露内部表示"** | Java 的 `Iterator` / 增强 for |
| **中介者** | 用一个**中介对象封装一系列对象交互**，使各对象**不需显式相互引用**，耦合松散 | **"对象不互相引用"、"星形转发"** | 聊天室：成员不互发，都发给聊天室转发 |
| **备忘录** | 在**不破坏封装性**的前提下捕获对象**内部状态**，并在该对象**之外保存**，以后可**恢复** | **"保存快照"、"恢复/撤销到之前状态"** | 游戏存档 |
| **访问者** | 在**不改变各元素的类**的前提下，定义作用于这些元素的**新操作** | **"不改元素类而加新操作"、"操作与结构分离"** | 稳定的对象结构 + 频繁新增操作 |
| **解释器** | 给定一个**语言**，定义它的**文法**表示，并定义解释器**解释语言中的句子** | **"文法"、"语言"、"表达式求值"** | 自己实现简易 SQL / 正则 / 公式引擎 |

> **观察者 vs 中介者**：观察者是**一对多的单向广播**（目标一变，所有订阅者收到同样通知）；中介者是**多对多交互的集中转发**（中介按内容决定转给谁，各同事对象地位对等）。
> **命令 vs 备忘录**：命令记"**做过什么**"，备忘录存"**当时的样子**"。两者常配合实现撤销。

### 考点⑦ 补讲·生成器 Builder —— ⚠️ 它是**创建型**

> **分类必背**：生成器属于**创建型 5 成员**（工厂方法、抽象工厂、**生成器**、原型、单例）。它出现在这一课纯属排课，**千万别因此把分类记错**——"XX 属于哪一类"本身就是考点。

**痛点**：装机配置单十几个部件、有的可选。构造函数传十几个参数没人看得懂，写一堆重载又组合爆炸。更进一步：同样的装机**流程**（装CPU→装内存→装显卡），既要能装出"游戏主机"也要能装出"办公主机"——**过程稳定、成品多样**。

**意图（GoF）**：将一个**复杂对象的构建与它的表示分离**，使得**同样的构建过程可以创建不同的表示**。

**角色**：Builder（声明各部件构建方法）、ConcreteBuilder（实现步骤 + getResult）、**Director**（指挥者：按固定顺序调用各步骤，只掌握流程）、Product。

```java
interface ComputerBuilder {                                  // 抽象生成器
    void buildCpu(); void buildRam(); void buildGpu();
    Computer getResult();
}
class GamingBuilder implements ComputerBuilder {             // 具体生成器：游戏主机的建法
    private Computer c = new Computer();
    public void buildCpu() { c.cpu = "i9"; }
    public void buildRam() { c.ram = "64G"; }
    public void buildGpu() { c.gpu = "RTX5090"; }
    public Computer getResult() { return c; }
}
class Director {                                             // 指挥者：只掌握流程顺序
    Computer construct(ComputerBuilder b) {
        b.buildCpu(); b.buildRam(); b.buildGpu();            // 同样的构建过程
        return b.getResult();                                // 换 Builder = 不同表示
    }
}
// 日常 Java 的链式写法 new X.Builder().cpu("i9").build() 是它的简化变体
```
**识别关键词**：**"构建与表示分离"、"同样的构建过程创建不同的表示"、"分步骤构建复杂对象"**

## 第 4 层 · 速记

> 行为型串记：**一对多通知找观察者，算法互换找策略，沿链传递找责任链，请求成对象找命令，状态变行为找状态；骨架留步找模板，遍历不露找迭代，星形转发找中介，存档恢复找备忘录，不改类加操作找访问者，文法句子找解释器**
> **策略 vs 状态：客户挑的是策略，自己变的是状态**
> 命令四信号：**参数化、排队、日志、可撤销**
> **观察者 vs 中介者：一对多广播是观察者，多对多收成星形是中介者**
> **命令记"做过什么"，备忘录存"当时的样子"**
> ⚠️ **生成器是创建型**：构建与表示分离、同样过程不同表示
> 下午题 5/6：C++/Java 同场景同模式，**只练 Java**；填空必挖**模式骨架线**

## 考题回顾

> 说明：核实考点为"高频设计模式"，见于 2021上/2022下/2024上/2025上 多场次（清单含责任链/命令/状态/观察者/生成器），未逐题对应年份。以下按已核实考点自编重现，**非原题原文**。

**1.【模拟·考点重现】** 欲定义对象间一对多的依赖关系，当一个对象状态改变时所有依赖者都得到通知并被自动更新，应采用（ ）模式。
A. 中介者　B. 观察者　C. 命令　D. 迭代器
**解**：**B**。"一对多 + 状态改变 + 自动通知更新"三个信号齐了。中介者是多对多收成星形，不是一对多通知。

**2.【模拟·考点重现】** 请假单依次经组长、经理、总监传递，直到某一级有权限者处理为止，提交者无需知道最终由谁审批。适合采用（ ）模式。
A. 责任链　B. 观察者　C. 策略　D. 状态
**解**：**A**。"多个处理者 + 沿链传递 + 直到被处理 + 提交者不知接收者"。观察者是所有订阅者**都**收到通知，本题只有一级真正处理。

**3.【模拟·考点重现】** "允许一个对象在其内部状态改变时改变它的行为，对象看起来似乎修改了它的类"是（1）模式的意图；该模式与（2）模式结构相似，但后者由客户端主动选择并注入所用算法。
A. 状态/策略　B. 策略/状态　C. 状态/命令　D. 观察者/策略
**解**：**A**。第一空是状态模式的 GoF 意图原句；第二空考"结构相似看谁来换"。

**4.【模拟】** 文本编辑器需支持撤销、重做，并把用户操作记入日志、放入队列延迟执行。最适合把每个用户操作设计为（ ）。
A. 一个策略对象　B. 一个命令对象　C. 一个备忘录对象　D. 一个状态对象
**解**：**B**。"撤销/重做/日志/排队"四个词都指向命令模式。备忘录是干扰项——它保存的是**对象状态快照**（"当时的样子"），不是"用户的操作"本身。

**5.【模拟·下午题6风格】** 商城结算支持多种促销算法且可运行时更换，采用策略模式，补全空缺：
```java

class PercentOff implements __(1)__ {

}
class Checkout {
    private __(2)__ promotion;
    public Checkout(Promotion p) { this.promotion = p; }
    public int pay(int total) { return total - __(3)__; }
}
```
**解**：(1) `Promotion`；(2) `Promotion`——上下文字段必须声明为**抽象策略类型**（若写成 PercentOff 就换不了，"可相互替换"就没了）；(3) `promotion.discount(total)`——把算法**委托**给当前策略对象。三个空全在"模式之所以成立"的骨架线上，是下午题最典型的挖空位置。

## 自测练习

1. 【模拟】"聊天室中所有成员的消息都先发给聊天室对象，由它转发给目标成员，成员之间互不持有引用"是哪个模式？它与观察者的通知有何不同？
2. 【模拟】"游戏在每关开始前保存玩家完整进度，失败后可恢复重来"是哪个模式？该模式强调的"不破坏封装性"指什么？
3. 【模拟】下列哪个模式**不属于**行为型？A. 解释器　B. 访问者　C. 生成器　D. 备忘录

### 参考答案

1. **中介者**模式——多对多网状交互收拢为"都只跟中介说话"的星形。与观察者的区别：观察者是**一对多的单向广播**（目标一变，所有订阅者收到同样通知）；中介者是**多对多交互的集中转发**（中介按消息内容决定转给谁，各同事对象地位对等）。
2. **备忘录**模式。"不破坏封装性"指：对象内部状态**不必对外公开字段**就能被保存——由对象自己生成备忘录（快照）交给外部保管者存放，保管者只负责存、看不懂也不修改快照内容，恢复时再把备忘录交还对象自己去还原。
3. **C**。生成器属于**创建型**（本课反复强调的排课陷阱）；解释器、访问者、备忘录都是行为型 11 成员。
