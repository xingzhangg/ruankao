# 27 · 面向对象：状态图 / 活动图 / 构件图 / 部署图

> 真题：UML 各图定义与要素 2021上/2022下｜无计算｜未讲（自学讲义）

## 第 0 层 · 定位

**这一课回答**：UML 剩下四种图各画什么：状态图、活动图（下午题 3 可考的补空图）、构件图、部署图（上午认图即可）。

**前后关系**：UML 三课收尾；构件图/部署图按标准属结构图，与本课标题「动态图」只是排课习惯；51 是实战。

**分值与去向**：板块 9–11 分，上午「给场景选图」1 题；下午题 3 出过「用例图 + 状态图/活动图」组合填空。零计算。

## 第 1 层 · 理解

### 一句话

> 同一个系统，站在不同位置看，就该画不同的图。这四张图各自站在一个新的"观察位"上：一个对象的一辈子、一件事的全过程、模块怎么拼、软件落到哪台机器。

### 一条主线（七张图 = 七个观察位）

```
UML 七张图，其实是七个【站在哪里看系统】的位置：

 已学的三张：
   用例图 ── 站在【系统外面】：谁用它、能做什么功能
   类图  ── 站在【代码里面】：有哪些类、静态关系
   顺序图 ── 站在【一次交互里】：消息按时间怎么走

 本课补齐的四张，各换一个观察位：
   状态图 ── 盯住【一个对象】：它这辈子有哪些状态，什么事件能让它从A迁到B
   活动图 ── 盯住【一件事】  ：从发起到办结怎么走，跨几个角色，哪些步骤能并发
   构件图 ── 拉远到【模块层】：软件由哪些可替换部件拼成，接口怎么对插
   部署图 ── 再拉远到【机器层】：这些软件文件最终落到哪几台硬件上
                    ↑ 构件图和部署图是同一条轴上的前后两步：
                      构件图还在"逻辑模块"，部署图才落到"物理机器"
   ↓
所以上午题的考法只有一个：给一段建模需求，问用哪张图
   判据 = 题干在盯着什么：一个对象？一件事？模块？机器？
```

**这条线记住了，选图题就不会错。**

## 第 2 层 · 考点：考试怎么问

### 考点① 状态图——盯住"一个对象的一辈子"

**它解决什么问题（程序员一定有共鸣）**：订单表有个 `status` 字段，代码里如果不检查当前状态就随手 `setStatus()`，就会出"已取消的订单被发货"这种 bug。真正的规则是：**在什么状态下、发生什么事件、才允许迁到什么状态**。这套规则画出来就是状态图。

> **主角是单个对象**——这是它与活动图最大的区别。

**要素**：

| 要素 | 画法 | 说明 |
|---|---|---|
| **初态** | 实心圆 ● | 起点，**一张图只有 1 个** |
| **终态** | 圆环套实心圆 ◉ | 可有多个，也可没有 |
| 状态 | 圆角矩形 | 一个稳定阶段，框内可写 entry/do/exit 内部活动 |
| 迁移 | 带箭头实线 | 线上标注触发规则 |

**迁移标注格式（必背）**：
> **`事件 [守卫条件] / 动作`**
> - **事件**：触发迁移的外部刺激（"支付成功""超时"）
> - **守卫条件**：方括号里的布尔条件，事件发生时**守卫为真才真的迁移**
> - **动作**：迁移那一瞬间执行的操作（"发短信""释放库存"）
> - 三段都可省略

**算例：订单状态机**
```
        ●
        │ 提交订单
        ▼
   ┌──────────┐  支付成功[金额足额]/发确认短信  ┌──────────┐
   │  待支付   │ ──────────────────────────► │  已支付   │
   └──────────┘                              └──────────┘
        │ 超时30分钟/释放库存                       │ 发货/生成运单
        ▼                                         ▼
   ┌──────────┐                              ┌──────────┐
   │  已取消   │──► ◉                         │  已发货   │
   └──────────┘                              └──────────┘
                                                  │ 确认收货
                                                  ▼
                                             ┌──────────┐
                                             │  已完成   │──► ◉
                                             └──────────┘
```
**关键理解**：**图上没画的迁移就是不允许的**（"已取消"没有任何出边通往"已发货"）——这正是状态机防 bug 的价值。

**高频陷阱**：守卫条件**自己不会触发迁移**，它只是事件发生那一刻的"放行闸门"。选项说"只要条件成立、事件未发生迁移也会自动发生" → **错**。

### 考点② 活动图——盯住"一件事的办理全过程"

**它解决什么问题**：状态图盯一个对象，但"员工报销"这类**业务流程**要跨好几个角色（员工→经理→财务），每人做几步，有的步骤还能同时进行。

**要素**：

| 要素 | 画法 | 含义 |
|---|---|---|
| 初始/终止节点 | ● / ◉ | 流程开始/结束 |
| 动作 | 圆角矩形 | 流程中的一步 |
| **分支 / 合并** | **菱形 ◇** | **互斥选择**：出边各带守卫 `[条件]`，只走一条（if/else） |
| **分岔 fork / 汇合 join** | **粗黑横线**（同步条） | **并发**：分岔一入多出 = 同时开跑；汇合多入一出 = **全到齐**才继续 |
| **泳道** | 分栏 | 按职责把动作划归不同角色/部门 |

**⚠️ 分支 vs 分岔（本课最重要辨析，上午必考）**：

| | **分支（菱形）** | **分岔（粗横线）** |
|---|---|---|
| 语义 | **互斥**：按条件选一条走 | **并发**：所有出边同时走 |
| 出边标注 | 各带守卫 `[条件]` | **不带条件** |
| 代码类比 | `if / else` | 多线程同时执行 |
| 对应的汇拢 | **合并**（菱形）：谁来了都直接过 | **汇合**（粗横线）：**等所有分支到齐**才放行 |

> **口诀：粗线并发、菱形选一；汇合等人到齐，合并来了就走。**

**算例：网购下单流程（含泳道与并发）**
```
│    顾客     │        商家        │      物流      │  ← 三条泳道（职责归属）
│   ●         │                   │               │
│   提交订单   │                   │               │
│      ──────►│ 校验库存           │               │
│             │   ◇[库存不足]──► 通知缺货 ──► ◉    │
│             │   [库存充足]       │               │
│             │ ━━━━━━━┳━━━━━━━━  │               │  ← 分岔 fork：以下并发
│             │ 打印发票 ┃          │ 安排配送       │
│             │ ━━━━━━━┻━━━━━━━━  │               │  ← 汇合 join：都完成才继续
│             │ 更新订单为已发货     │               │
│             │        ◉          │               │
```

**活动图 vs 流程图（常考；"教材明确强调"这一来源归属【待核实】）**：
1. 活动图有**分岔/汇合，能表达并发**；流程图**不能**
2. 活动图有**泳道**，能标明每一步由谁负责
3. 活动图属 UML 行为建模，可与对象挂钩（对象流）；流程图只是孤立的过程描述

> **⚠️【待核实】补正**：上面三点里，第 1 点在各来源中口径完全一致、可放心用；但**第 2 点"泳道"未能在任何来源中查到被列为"活动图 vs 流程图"的区别点**——跨职能流程图（泳道流程图）同样有泳道，所以它是实用差异、不是严格区别；"教材明确强调"这个归属也未能证实（未见到《教程》原文），暂标待核实。检索到的**主流三点表述**是：①流程图着重描述**处理过程**，活动图着重表现**系统行为**；②活动图能表示**并发**，流程图不能；③活动图**面向对象**，流程图**面向过程**。其中第③条在选项里出现频率高，**上午题作答时优先写①②③这三条**。

### 考点③ 构件图——盯住"模块怎么拼"

**它解决什么问题**：类图粒度太细（成百上千个类），要表达"系统由订单模块、支付模块、库存模块组成，支付模块对外提供支付接口、又依赖银行网关接口"这种**模块级组装关系**。

- **构件**：封装的、**可替换的**模块化部件，只通过接口与外界打交道（一个 jar、一个微服务模块）
- **供给接口**（提供接口）：对外**提供**的服务 → **棒棒糖 ○—**
- **需求接口**：**依赖别人**提供的服务 → **半圆插座 ⊃—**
- **装配**：一个构件的棒棒糖插进另一个的插座

```
┌──────────┐  支付接口   ┌──────────┐  网关接口   ┌────────────┐
│ 订单构件  │ ⊃——————○  │ 支付构件  │ ⊃——————○  │ 银行网关构件 │
└──────────┘ (需求)(供给) └──────────┘ (需求)(供给) └────────────┘
```

> **记法：圆圈像糖 = 我端出来给人吃（供给）；半圆像嘴 = 我张嘴要吃（需求）。**

### 考点④ 部署图——盯住"软件落到哪台机器"

**它解决什么问题**：构件图还停留在"逻辑模块"；上线时要回答"Web 服务器几台、war 包部署在哪、数据库单独一台吗、机器之间怎么连"。

- **节点 Node**：运行时的计算资源（服务器、PC、手机、打印机），画作**立方体**——立体感就是"这是台真机器"的提示
- **制品 Artifact**：软件的**物理产物**（war/jar/exe/配置文件），标 «artifact»
- **通信路径**：节点间连线，可标协议（HTTP、TCP/IP、JDBC）

```
┌───────────────┐  HTTP  ┌───────────────┐  JDBC  ┌────────────────┐
│ 节点:Web服务器  │────────│ 节点:应用服务器 │────────│ 节点:数据库服务器 │
│ «artifact»    │        │ «artifact»    │        │ «artifact»     │
│  static.zip   │        │  shop.war     │        │  shop.db       │
└───────────────┘        └───────────────┘        └────────────────┘
```

> **构件图 vs 部署图一句话**：构件图管**逻辑模块怎么装配**（还没落地到机器）；部署图管**物理文件放到哪台机器**。这是本课最强的干扰项组合。

### 考点⑤ 给场景选图——七类图总对比（上午题核心考法）

| 图 | 回答什么 | 关键要素 | **题干信号词** |
|---|---|---|---|
| 用例图 | 有哪些功能、给谁用 | 参与者、用例、include/extend | 功能需求、参与者、系统边界 |
| 类图 | 有哪些类、什么关系 | 类、泛化/关联/依赖/聚合/组合 | 静态结构、类之间的关系 |
| 顺序图 | 一次交互中消息的**时间顺序** | 生命线、激活条、组合片段 | 按时间顺序、对象间消息交互 |
| **状态图** | **一个对象**一生的状态变化 | 状态、迁移、事件[守卫]/动作 | **生命周期、状态变迁、事件触发** |
| **活动图** | **一项业务流程**的动作流 | 动作、分支、分岔/汇合、泳道 | **工作流、业务流程、并发步骤** |
| **构件图** | 软件由哪些**模块**组成、接口如何装配 | 构件、供给/需求接口 | **模块组织、可替换部件、接口依赖** |
| **部署图** | 软件**物理上**部署在哪些机器 | 节点（立方体）、制品、通信路径 | **硬件拓扑、物理配置、服务器分布** |

**易混三连的快速区分**：
> **顺序图** = 主角是"消息的时间线"（多对象一次交互）
> **状态图** = 主角是"一个对象"（它的一辈子）
> **活动图** = 主角是"一件事"（跨对象的办理流程）

补充：与顺序图**语义等价**、但强调对象间链接结构的还有**通信图（协作图）**，知道名字即可。

## 第 4 层 · 速记

> 选图口诀：**一物一生状态图，一事全程活动图，消息排队顺序图，功能边界用例图，静态关系是类图，模块装配构件图，机器分布部署图**
> 状态图迁移三段式：**事件[守卫]/动作**——事件触发、守卫放行、动作随行；守卫自己不触发迁移
> 活动图：**菱形分支互斥选一（if），粗线分岔同时并发（fork）；汇合等人到齐，合并来了就放行**
> 活动图强于流程图之处：**能表达并发**、**面向对象（流程图面向过程）**、着重表现系统行为而非处理过程；"有泳道"这条**待核实**（见考点②的补正框）
> 构件接口：**圆圈棒棒糖 = 供给（端糖给人），半圆张口 = 需求（张嘴要糖）**
> 部署图认脸：**立方体 = 硬件节点**，«artifact» = 物理软件制品
> 构件图管**逻辑装配**，部署图管**物理落地**

## 考题回顾

> 说明：核实考点为"UML 七类图各自定义与要素"【真题·2021上/2022下】。以下重现题按该已核实考点自编，**非原题原文**。

**1.【模拟·重现2021上考点】** 描述一个对象在其生命周期内所经历的状态序列、以及引起状态迁移的事件的图是（ ）。
A. 活动图　B. 状态图　C. 顺序图　D. 构件图
**解**：**B**。"一个对象 + 生命周期 + 状态 + 事件触发迁移"是状态图的定义句式。

**2.【模拟·重现2022下考点】** 需要表示各软件制品（war 包、数据库文件）分布在哪些硬件节点上以及节点间通信连接，应采用（ ）。
A. 构件图　B. 类图　C. 部署图　D. 活动图
**解**：**C**。"软件制品 + 硬件节点 + 物理分布"= 部署图。构件图是最强干扰项——它只管逻辑模块与接口装配，不落到具体机器。

**3.【模拟】** 活动图中，一入多出且出边**不带条件**的粗黑横线表示（1）；菱形节点多条出边各带守卫、只能走一条表示（2）。
A. 分支/分岔　B. 分岔/分支　C. 汇合/合并　D. 分岔/汇合
**解**：**B**。粗横线一入多出 = **分岔（fork）**，并发所以不需条件；菱形按守卫**互斥选一** = **分支（decision）**。

**4.【模拟】** 状态图中迁移标注为"提交订单 [购物车非空] / 锁定库存"，理解**错误**的是（ ）。
A. "提交订单"是触发迁移的事件
B. 方括号内是守卫条件，事件发生且条件为真时迁移才发生
C. "锁定库存"是迁移发生时执行的动作
D. 只要"购物车非空"成立，即使"提交订单"事件未发生，迁移也会自动发生
**解**：**D**。迁移由**事件触发**，守卫只是放行闸门，条件本身不会触发迁移。

**5.【模拟】** 构件图中画在构件边缘的"短线顶一个小圆圈（棒棒糖）"表示该构件的（ ）。
A. 需求接口　B. 供给接口　C. 部署节点　D. 泛化关系
**解**：**B**。棒棒糖 ○ = **供给接口**；半圆插座 ⊃ = 需求接口。

## 自测练习

1. 【模拟】为下列建模需求各选一种 UML 图：①描述电梯从"停止→上行→开门"等状态间的转换规则；②描述"员工提交报销→经理审批→财务打款"的完整办理流程（其中打款和归档可同时进行）；③描述系统的支付模块对外提供支付接口、并依赖短信网关接口。
2. 【模拟】活动图中"汇合（join）"与"合并（merge）"都是多条边汇成一条，行为区别是什么？
3. 【模拟】给订单状态机补一条规则："已发货"状态下发生"用户申请退货"事件、且守卫"[未超过7天]"为真时迁往"退货中"，并执行"通知物流拦截"。写出这条迁移的完整标注文字。

### 参考答案

1. ①**状态图**（单个对象"电梯"的状态与迁移规则）；②**活动图**（跨角色业务流程；"可同时进行"提示要用分岔/汇合表达并发，还可用泳道分员工/经理/财务）；③**构件图**（模块 + 供给接口"支付接口" + 需求接口"短信网关接口"）。
2. **汇合（粗横线）**是并发的收口：必须等**所有**汇入分支都到达才放行，**带同步等待语义**。**合并（菱形）**是互斥分支的汇拢：几条互斥路径实际只走过一条，**到了就直接通过**，不存在等待。一句话：**汇合等人到齐，合并来了就走**。
3. `用户申请退货 [未超过7天] / 通知物流拦截`（从"已发货"引一条带箭头实线指向新状态"退货中"，线上标这三段式文字）。
