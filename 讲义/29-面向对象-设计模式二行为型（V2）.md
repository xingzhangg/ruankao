# 29 · 面向对象：设计模式（二）——行为型

> 真题：状态 2017下·44-47、访问者 2018下·44-47、责任链与迭代器 2019上·44-46、观察者 2019上·47、命令 2021上·44-47、责任链 2022下·44-46、策略 2023上·46-47（题干、选项、标答逐条核到软件设计师卷面转写；题号按"累计空数＋专业英语必落 71–75"反算或按题干内嵌空号核定）｜无计算｜未讲

## 定位

上午卷第 44–47 题那四分，考的就是"看到这段话该答哪个模式"。这一课处理行为型 11 个，它们管的都是跑起来之后对象之间怎么打交道。先用一张"题干关键词 → 模式名"的反查表把 11 个一次分开，再用八对易混堵住最容易互换的地方，最后补两个副坐标：类图里哪个类扮哪个角色、这个模式算类模式还是对象模式。创建型与结构型那 12 个在讲义 28。

---

## 开讲：认模式，认的是那几个词

**设计模式**是前人把"反复出现的同一类设计难题 + 已被验证过的解法"整理成的 23 个条目，遇到同样的难题照着搭就行。其中**行为型**这 11 个管的是**跑起来之后对象之间怎么打交道**，不是对象怎么被造出来（创建型），也不是对象怎么拼装成更大的结构（结构型）。

下面的例子统一用一个内部报销系统：提单、审批、预算、财务四个模块，报销单从草稿走到已通过。

### 一、题干关键词 → 模式名（先查这张表）

左栏是题干和选项里真会出现的词，不是定义；查到哪一行就落笔。

| 题干/选项里出现这些词 | 答 | 教材给的口诀（不一定出现在题干里） |
|---|---|---|
| 一族算法可相互替换；按情况挑一套规则（淡季打折 / 一口价 / 按金额分级）；一个类定义了多种行为，并且以多个条件语句的形式出现 | 策略 Strategy | 算法替换 |
| 内部状态改变时改变其行为；走到哪一步就有哪种行为（草稿 / 待审批 / 已通过；售货机的库存与找零能力）；行为决定于其状态且必须在运行时刻根据状态改变行为 | 状态 State | 状态变成类 |
| 多个对象都有机会处理请求；连成一条链沿链传递，直到有一个对象处理为止；避免请求的发送者和接收者之间的耦合；可处理一个请求的对象集合应被动态指定；不明确指定接收者，向多个对象中的一个提交请求 | 职责链（卷面多印作**责任链**）Chain of Responsibility | 传递请求、职责、链接 |
| 把请求封装为对象；参数化 / 排队 / 日志 / 撤销（沾一个基本就是它）；抽象出待执行的动作以参数化某对象；在不同的时刻指定、排列和执行请求 | 命令 Command | 日志记录、可撤销 |
| 一对多的依赖关系；一个对象变了，依赖它的对象全部自动得到通知并更新；一个对象必须通知其他对象，而它又不能假定其他对象是谁 | 观察者 Observer | 通知、自动更新 |
| 各对象不显式地相互调用、都只跟中间人说话；减少多个对象或类之间的通信复杂性；一个对象引用其他对象并且直接与这些对象通信而导致难以复用该对象 | 中介者 Mediator | 不直接引用 |
| 不改变各元素的类的前提下定义新操作；需要对一个对象结构中的对象进行很多不同的并且不相关的操作；类图里元素类有 `accept` 方法 | 访问者 Visitor | 数据和操作分离 |
| 顺序访问一个聚合对象中的各个元素；无须暴露它的内部表示 | 迭代器 Iterator | 顺序访问，不暴露内部 |
| 算法骨架定在父类、某些步骤延迟到子类；子类不改变算法结构就能重新定义其中某几步 | 模板方法 Template Method | 骨架固定、步骤下放 |
| 不破坏封装性地捕获对象的内部状态、在该对象之外保存；必须保存一个对象在某一个时刻的（部分）状态；恢复到先前保存的状态 | 备忘录 Memento | 保存，恢复 |
| 文法、语言、句子三个词一起出现；给定一种语言，定义它的文法表示并解释句子 | 解释器 Interpreter | 解释器，虚拟机 |

**这 11 行就是行为型的全部。** 选项里出现表外的名字，只有两种可能——它是创建型或结构型（去讲义 28 查），或者它根本不在 GoF 23 个里（"过滤器 Filter"就是卷面常见的假模式）。

表里两个词先说清：**聚合对象**＝内部装着一堆别的对象的对象（装满明细的报销单、一个列表）；**耦合**＝改 A 就得跟着改 B 的牵连程度。模板方法那一行的口诀「骨架固定、步骤下放」是本讲义补的，教材原表这一格空着。

**上表按词查，下表只在选项整句照抄定义时回来核。** 选项常常照抄教程的意图原句、用词只差一两个虚词，所以要认关键词组合，别背整句：

| 模式 | 意图原话 |
|---|---|
| 策略 | 定义一系列算法，把它们一个个封装起来，并且使它们之间可相互替换，从而让算法可以独立于使用它的用户而变化 |
| 状态 | 允许一个对象在其内部状态改变时改变它的行为 |
| 职责链 | 通过给多个对象处理请求的机会，减少请求的发送者与接收者之间的耦合。将接收对象链接起来，在链中传递请求，直到有一个对象处理这个请求 |
| 命令 | 将一个请求封装为一个对象，从而可用不同的请求对客户进行参数化，将请求排队或记录请求日志，支持可撤销的操作 |
| 观察者 | 定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并自动更新 |
| 中介者 | 用一个中介对象来封装一系列的对象交互。它使各对象不需要显式地相互调用，从而达到低耦合，还可以独立的改变对象间的交互 |
| 访问者 | 表示一个作用于某对象结构中的各元素的操作，使得在不改变各元素的类的前提下定义作用于这些元素的新操作 |
| 迭代器 | 提供一种方法来顺序访问一个聚合对象中的各个元素而不需要暴露该对象的内部表示 |
| 模板方法 | 定义一个操作中的算法骨架，而将一些步骤延迟到子类中，使得子类可以不改变一个算法的结构即可重新定义算法的某些特定步骤 |
| 备忘录 | 在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态，从而可以在以后将该对象恢复到原先保存的状态 |
| 解释器 | 给定一种语言，定义它的文法表示，并定义一个解释器，该解释器用来根据文法表示来解释语言中的句子 |

> 考试这样问：给一句意图原话、或一段业务场景，问"适合采用（ ）模式""体现的最主要的意图是（ ）"。

### 二、八对易混：一句判据分开它俩

**1）策略 vs 状态**

先看一段最常见的重构。报销单在"草稿 / 待审批 / 已通过"之间流转，同一个"提交"在三个状态下行为完全不同——最朴素的写法是在 `提交()` 里写一串 `if 状态 == "草稿" … elif …`。把这串 if 拆开，每个状态各自成一个类，主对象把活**委托**给"当前那个"（**委托**＝自己不干，交给手里攥着的那个对象去干）：

```python
# 每个状态一个类，主对象把活委托给"当前状态"
class 草稿:
    def 提交(self, 单): 单.状态 = 待审批(); return "已送审"   # ← 自己把自己换掉
class 待审批:
    def 提交(self, 单): return "已在审批中，不能重复提交"

class 报销单:
    def __init__(self): self.状态 = 草稿()
    def 提交(self): return self.状态.提交(self)   # 委托给"当前状态"

d = 报销单(); d.提交()   # → 已送审
d.提交()                 # → 已在审批中，不能重复提交
```

这段里有两件事要分开看：一是**把 if-else 拆成几个平级的类**，二是**换掉"当前那个"的人是谁**——这里是 `草稿` 自己在 `提交()` 里把 `单.状态` 改成了 `待审批()`，没有任何外人插手。

现在**只改一个细节**：让外面来决定用哪一个，对象自己不换。

```python
# 换人的决定权交给外面
class 按比例:
    def 级别(self, 金额): return "二级审批" if 金额 > 5000 else "一级审批"
class 一律二级:
    def 级别(self, 金额): return "二级审批"

class 报销单:
    def __init__(self, 金额, 规则):
        self.金额, self.规则 = 金额, 规则     # ← 规则由外面塞进来，这一行是命根子
    def 审批级别(self): return self.规则.级别(self.金额)

报销单(6000, 按比例()).审批级别()     # → 二级审批
报销单(100,  按比例()).审批级别()     # → 一级审批
报销单(100,  一律二级()).审批级别()   # → 二级审批
```

两段的类结构一模一样：几个平级的类实现同一个方法，主对象持有其中一个、把活委托过去。**差别只在换的方式**——上面是对象自己换，下面是外面塞。

**先别往下看，猜一个**：这两段，哪段是状态模式、哪段是策略模式？

上面那段是**状态**，下面那段是**策略**。结构一样却是两个模式，分家的就是这一条：

- 判据｜**谁来换那个对象**。**外面**挑一个塞进来是策略；**对象自己**在运行中换成下一个是状态。
- 例子｜财务今年用"按比例"、明年改成"一律二级"，报销单自己不会主动换规则 → 策略。草稿单被提交之后自己就变成了待审批单，没有任何外人做这个决定 → 状态。（改一个细节答案就变：旅游定价包由运营按季节挑一套，是策略；改成系统按当前日期自己切到下一档，就成了状态。）
- 错法｜看见"几个类实现同一个方法、主对象把活委托过去"就填策略。得再问一句谁来换。辅助线索：状态类之间**知道彼此**（"草稿"类里写着下一站是待审批），几个策略之间互不认识。另有一处细节常被顺带考到：`self.规则` 必须声明成**抽象类型**（Java 里就是那个接口名），写死成 `按比例` 就换不掉了，"可相互替换"五个字也就没了。

**2）职责链 vs 观察者**

- 判据｜**一个人办** vs **人人都收到**。职责链沿链找到第一个能办的就停，**最终只有一个对象真的处理了**请求，其余的只是"有机会处理"；观察者是**一对多**，目标一变，观察者**统统**收到同一条通知。
- 例子｜一笔报销顺着组长 → 经理 → 总监往上找，谁的权限够谁批，只批一次 → 职责链模式。单子一通过，短信、台账、报表、预算**全部**被触发 → 观察者。（改一个细节答案就变：把"批不了就转给上级，直到有人批"改成"每一级都要留一份记录"，职责链就变成了观察者。）
- 错法｜题干出现"多个对象"就填观察者。要分清是"传到有人接手为止"还是"所有人都收到"。

```python
# 职责链：批不了就往下传，最终只有一个人真批
class 审批人:
    def __init__(self, 名, 上限): self.名, self.上限, self.下家 = 名, 上限, None
    def 接单(self, 金额):
        if 金额 <= self.上限: return f"{self.名}批"
        if self.下家: return self.下家.接单(金额)
        return "无人可批"

组长, 经理, 总监 = 审批人("组长",1000), 审批人("经理",10000), 审批人("总监",100000)
组长.下家, 经理.下家 = 经理, 总监
[组长.接单(x) for x in (800, 6000, 50000, 200000)]
# → ['组长批', '经理批', '总监批', '无人可批']
```

```python
# 观察者：一变，全体收到
class 报销单:
    def __init__(self): self.订阅者 = []
    def 订阅(self, f): self.订阅者.append(f)
    def 通过(self):
        self.结论 = "已通过"
        return [f(self) for f in self.订阅者]

s = 报销单()
s.订阅(lambda x: "发短信:"+x.结论); s.订阅(lambda x: "记台账:"+x.结论); s.订阅(lambda x: "刷报表:"+x.结论)
s.通过()   # → ['发短信:已通过', '记台账:已通过', '刷报表:已通过']
```

职责链还有一句要记：**链的组装是运行时决定的**——`组长.下家 = 经理` 这两行随时能改，链的长短随公司组织架构变，所以它的适用场景写成"可处理一个请求的对象集合应被动态指定"。观察者那边则是：**审批通过只管喊一嗓子"我变了"，谁关心谁自己来登记**，接一个新下游不用回来改它。

**3）职责链 vs 命令**

- 判据｜**传下去** vs **存起来**。沿链找第一个能办的是职责链；把请求本身变成一个能排队、能进历史栈、能撤销的对象是命令。
- 例子｜组长批不了转经理 → 职责链。主管要撤回刚才那次审批、月底批量审批要先排队、审计要求每次审批都留痕 → 命令模式：**"审批这一次"本身得是一样能拿在手里的东西**，而"调一次方法"是个动作，执行完就没了，塞不进历史栈也塞不进队列。
- 错法｜把"参数化"这个词读漏。命令的定义里藏着**四个信号词**——**参数化、排队、日志、撤销**，题干沾上任何一个基本就是它。"参数化"是最绕的一个：调用方（那个"批量审批"按钮）不需要知道自己按下去会发生什么，它只拿着一个命令对象，换个命令对象就换了行为，请求成了可以传来传去的参数。

**4）观察者 vs 中介者**

- 判据｜**方向和对称性**。观察者是**一对多的单向广播**，一群订阅者被动收到同一条消息，订阅者之间毫无关系；中介者是**多对多交互的集中调停**，各方地位对等，中介看消息内容决定转给谁，可能转给一个，也可能谁都不转。
- 例子｜**报销单变了要通知短信台账报表，是观察者；四个模块想互相说话都得过中介，是中介者。**（改一个细节答案就变：把"审批模块通知下游"改成"提单、审批、预算、财务四个模块互相都要说话"，观察者就变成了中介者模式。）
- 错法｜把中介者的"减少多个对象或类之间的通信复杂性"安到观察者头上——这是卷面最爱设的一个错项。

**5）模板方法 vs 策略**

- 判据｜**改一步用模板方法，换整套用策略。** 模板方法靠**继承**：父类把"校验 → 算级别 → 落库 → 通知"四步的顺序焊死，子类只能改其中某一步；策略靠**组合**：整个算法作为一个对象被整体替换。
- 例子｜招待费报销只换四步里"算级别"那一步 → 模板方法。整套算级别的规则在运行时被换掉 → 策略。
- 错法｜看到"可以有多种做法"就填策略。先看有没有一个焊死的骨架，再看换的是一步还是全部。

**6）迭代器 vs 访问者**

- 判据｜**遍历** vs **加操作**。只是把元素挨个取出来是迭代器；在不改元素类的前提下给它们加新操作是访问者。
- 例子｜挨个读报销单的明细 → 迭代器（Python 的 `for x in 列表`、Java 的 `Iterator` 都是它）。报销单类、明细类、附件类几年不变，变的是**要对它们做的操作**——今天按部门统计，明天导税务报表——于是把每一套新操作打包成一个访问者对象 → 访问者模式。
- 错法｜"遍历所有明细做汇总"就填迭代器。迭代器只解决"怎么一个个取出来"，没解决"新统计写在哪"。

访问者的代价也是考点：**元素类必须先留一个 `accept(访问者)` 的口子**。它只适合"结构稳定、操作频繁新增"；要是元素类本身老加新种类，反而是灾难——每加一种元素，所有访问者都得改。

**7）命令 vs 备忘录**

- 判据｜两个都能做撤销。**命令记的是"做过什么"（把操作反着做一遍），备忘录存的是"当时的样子"（整个覆盖回去）。**
- 例子｜历史栈里放的是"批准了 3 号单"这个命令对象，撤销＝调它的 `撤销` → 命令。历史栈里放的是"点下去之前整张单子的快照" → 备忘录。
- 错法｜看见"撤销"直接填备忘录——因为撤销的直觉做法就是"退回上一版"，而"退回上一版"正是备忘录的画面感。备忘录的题眼是"不破坏封装性"加"保存 / 恢复状态"：对象不用把自己的字段公开出去，而是自己生成一份快照交给外面的保管者存着，保管者只负责保管、看不懂也不改，要恢复时再把快照还给对象自己去还原。

**8）状态模式 vs UML 状态图**（同名，不是一回事）

- 判据｜问"该 UML 图为（ ）"的是图，归讲义 27；问"该设计采用（ ）模式"的才是这里。
- 例子｜一张画着圆角矩形和迁移箭头的图＝**UML 状态图**；一段"每个状态一个类、当前状态自己迁移"的代码＝状态模式。
- 错法｜两者关系确实近——状态图上的每一个圆角矩形，落到状态模式里正好是一个状态类——近到容易把两道题答串。

### 三、配了类图的大题，第二空只问角色

第 44–47 题常合成**一道四空大题**（配一张类图）：一空认模式名、二空认角色、三空判分类、四空选适用场景。一、三、四空靠前面两张表就能答，**第二空看着非看图不可，其实靠角色名和选项特征多半也能排掉**——下面这张表就是为它准备的。

| 模式 | 角色 | 在类图里长什么样 |
|---|---|---|
| 策略 / 状态 | **上下文（Context）** | 持有策略或状态对象、把活委托出去的那个主对象（报销单、售货机）。题干说的"客户程序使用的主要接口，可用状态来对其进行配置"就是它；候选里以 State 结尾的都是状态类，剩下那个才是上下文 |
| 策略 / 状态 | 具体策略 / 具体状态 | 各自实现同一个方法名的那几个平级类 |
| 命令 | 抽象命令 | "声明执行操作的接口"的那一层 |
| 命令 | 具体命令 | 实现抽象命令的那几个平级类 |
| 命令 | **调用者** | 只认抽象命令、负责触发，还可以把命令压进历史栈或队列 |
| 命令 | **接收者** | 真正干活的那个对象（报销单本身、被买卖的股票） |
| 访问者 | **元素** | 开 `accept(访问者)` 口子的是元素，不是访问者；那几个平级的操作类才是具体访问者 |
| 访问者 | **对象结构** | 装着一堆元素的那个**容器**（购物车、装满明细的报销单）。它只负责把元素一个个交出来，`accept` 开在**被装的元素**身上（Item、明细），不开在容器上——这一条专门用来在"元素"和"容器"之间做取舍 |
| 职责链 | 处理者 | 每个处理者只认自己的**下家**，链在运行时组装 |
| 观察者 | 目标 / 观察者 | 目标持有一串观察者，自己一变就逐个通知 |

### 四、第二个坐标：类模式还是对象模式

卷面上反复出现一个空：**该模式属于（ ）模式**，四个选项长这样——创建型对象 / 结构型对象 / 行为型类 / 行为型对象。所以每个模式要记两个坐标：属于哪一型（本课全是行为型），以及是类模式还是对象模式。

行为型 11 个里，既可以是类模式也可以是对象模式的只有 **2 个：解释器、模板方法**，其余 9 个都只是对象模式。道理很简单：**类模式靠继承，在编译期就把关系定死；对象模式靠对象组合，运行时才装配。** 解释器和模板方法都是"子类继承父类、覆盖某个方法"；观察者、策略、状态这些都是"持有一个别的对象、把活委托过去"。

**答题口径就固定这一句：考到解释器、模板方法填「行为型类模式」，其余九个一律「行为型对象模式」。**（"既可以是类也可以是对象"是教材图例的来历说法，见本节末的深入；落到选项上按这句答。）

**已核到的、带这个空的五道真题（2017下、2018下、2019上、2021上、2022下）里，答案全是"行为型对象"**——被考到的状态、访问者、责任链、迭代器、命令，没有一个是那两个类模式。答题时别背选项位置，同一个"行为型对象"在不同卷子上可能排 C 也可能排 D。

这条区分是从哪看出来的，看本节末的深入，跳过不影响答题。

#### 深入 · 类模式/对象模式这条线索藏在哪

培训资料那张 11 个模式的表格里根本没有这一栏，它藏在分类总览那张图上：图里少数几个模式名带**下划线**，图右下角的说明写着"有下划线的表示既可以是类模式，也可以是对象模式；无下划线的表示只是对象模式"。

放大逐条数下来，行为型带下划线的就是解释器和模板方法两个（迭代器那一行下面是拼写检查的红色波浪线，不是下划线，别数错）。创建型和结构型两列的下划线情况归讲义 28。

## 速记

- 场景直映：规则常变→策略、自己走到下一步→状态、逐级往上审→职责链、要撤销要留痕→命令、一变全都动→观察者、模块互相直调→中介者、不改类加新统计→访问者
- 剩下四个只认关键字：迭代器「顺序访问，不暴露内部」、模板方法「骨架固定、步骤下放」、备忘录「保存，恢复」、解释器「解释器，虚拟机」
- 上面那七个的教材关键字：职责链「传递请求、职责、链接」、命令「日志记录、可撤销」、中介者「不直接引用」、观察者「通知、自动更新」、状态「状态变成类」、策略「算法替换」、访问者「数据和操作分离」
- 策略 vs 状态：**外面挑的是策略，自己变的是状态**；职责链只有一个人真办，观察者人人都收到
- 模板方法靠继承改一步，策略靠组合换整套；命令记"做过什么"，备忘录存"当时的样子"
- 类模式只有**解释器、模板方法**两个，其余九个是对象模式；"该模式属于（ ）"绝大多数填**行为型对象模式**
- 设计模式固定考第 44–47 题共 4 分，或一道四空大题（配类图），或拆成两三道小题（不配图）
- 状态模式 ≠ UML 状态图：图归讲义 27，模式在这里，状态图上一个圆角矩形＝一个状态类
