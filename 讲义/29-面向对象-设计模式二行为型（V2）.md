# 29 · 面向对象：设计模式（二）——行为型

## 定位

**设计模式**是前人把"反复出现的同一类设计难题 + 已被验证过的解法"整理成的 23 个条目。**行为型** 11 个管的是**跑起来之后对象之间怎么打交道**——不是对象怎么被造出来（创建型），也不是对象怎么拼装成更大的结构（结构型），那 12 个在讲义 28。本课先用一张关键词速查表把 11 个分开，再用八对易混分清最容易互换的，最后补两个坐标：类图里的角色、类模式还是对象模式。

例子统一用一个内部报销系统：提单、审批、预算、财务四个模块，报销单从草稿走到已通过。

---

## 一、关键词 → 模式名

| 特征 / 关键词 | 模式 | 教材口诀 |
|---|---|---|
| 一族算法可相互替换；按情况挑一套规则（淡季打折 / 一口价 / 按金额分级）；一个类定义了多种行为，并且以多个条件语句的形式出现 | 策略 Strategy | 算法替换 |
| 内部状态改变时改变其行为；走到哪一步就有哪种行为（草稿 / 待审批 / 已通过；售货机的库存与找零能力）；行为决定于其状态且必须在运行时刻根据状态改变行为 | 状态 State | 状态变成类 |
| 多个对象都有机会处理请求；连成一条链沿链传递，直到有一个对象处理为止；避免请求的发送者和接收者之间的耦合；可处理一个请求的对象集合应被动态指定；不明确指定接收者，向多个对象中的一个提交请求 | 职责链（也常写作**责任链**）Chain of Responsibility | 传递请求、职责、链接 |
| 把请求封装为对象；参数化 / 排队 / 日志 / 撤销；抽象出待执行的动作以参数化某对象；在不同的时刻指定、排列和执行请求 | 命令 Command | 日志记录、可撤销 |
| 一对多的依赖关系；一个对象变了，依赖它的对象全部自动得到通知并更新；一个对象必须通知其他对象，而它又不能假定其他对象是谁 | 观察者 Observer | 通知、自动更新 |
| 各对象不显式地相互调用、都只跟中间人说话；减少多个对象或类之间的通信复杂性；一个对象引用其他对象并且直接与这些对象通信而导致难以复用该对象 | 中介者 Mediator | 不直接引用 |
| 不改变各元素的类的前提下定义新操作；需要对一个对象结构中的对象进行很多不同的并且不相关的操作；元素类有 `accept` 方法 | 访问者 Visitor | 数据和操作分离 |
| 顺序访问一个聚合对象中的各个元素；无须暴露它的内部表示 | 迭代器 Iterator | 顺序访问，不暴露内部 |
| 算法骨架定在父类、某些步骤延迟到子类；子类不改变算法结构就能重新定义其中某几步 | 模板方法 Template Method | 骨架固定、步骤下放（本讲义补，教材原表空） |
| 不破坏封装性地捕获对象的内部状态、在该对象之外保存；必须保存一个对象在某一个时刻的（部分）状态；恢复到先前保存的状态 | 备忘录 Memento | 保存，恢复 |
| 文法、语言、句子三个词一起出现；给定一种语言，定义它的文法表示并解释句子 | 解释器 Interpreter | 解释器，虚拟机 |

这 11 行就是行为型的全部。表外的名字要么是创建型/结构型（查讲义 28），要么根本不在 GoF 23 个里（如"过滤器 Filter"）。

术语：**聚合对象**＝内部装着一堆别的对象的对象（装满明细的报销单、一个列表）；**耦合**＝改 A 就得跟着改 B 的牵连程度。

教材意图原话（认关键词组合，不必背整句）：

| 模式 | 原话 |
|---|---|
| 策略 | 定义一系列算法，把它们一个个封装起来，并且使它们之间可相互替换，从而让算法可以独立于使用它的用户而变化 |
| 状态 | 允许一个对象在其内部状态改变时改变它的行为 |
| 职责链 | 通过给多个对象处理请求的机会，减少请求的发送者与接收者之间的耦合。将接收对象链接起来，在链中传递请求，直到有一个对象处理这个请求 |
| 命令 | 将一个请求封装为一个对象，从而可用不同的请求对客户进行参数化，将请求排队或记录请求日志，支持可撤销的操作 |
| 观察者 | 定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并自动更新 |
| 中介者 | 用一个中介对象来封装一系列的对象交互。它使各对象不需要显式地相互调用，从而达到低耦合，还可以独立的改变对象间的交互 |
| 访问者 | 表示一个作用于某对象结构中的各元素的操作，使得在不改变各元素的类的前提下定义作用于这些元素的新操作 |
| 迭代器 | 提供一种方法来顺序访问一个聚合对象中的各个元素而不需要暴露该对象的内部表示 |
| 模板方法 | 定义一个操作中的算法骨架，而将一些步骤延迟到子类中，使得子类可以不改变一个算法的结构即可重新定义算法的某些特定步骤 |
| 备忘录 | 在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态，从而可以在以后将该对象恢复到原先保存的状态 |
| 解释器 | 给定一种语言，定义它的文法表示，并定义一个解释器，该解释器用来根据文法表示来解释语言中的句子 |

## 二、八对易混

**1）策略 vs 状态**

报销单在"草稿 / 待审批 / 已通过"之间流转，同一个"提交"在三个状态下行为不同。把 `提交()` 里那串 `if 状态 == …` 拆开，每个状态一个类，主对象把活**委托**（自己不干，交给手里攥着的那个对象去干）给当前那个：

```python
# 每个状态一个类，主对象把活委托给"当前状态"
class 草稿:
    def 提交(self, 单): 单.状态 = 待审批(); return "已送审"   # ← 自己把自己换掉
class 待审批:
    def 提交(self, 单): return "已在审批中，不能重复提交"

class 报销单:
    def __init__(self): self.状态 = 草稿()
    def 提交(self): return self.状态.提交(self)   # 委托给"当前状态"

d = 报销单(); d.提交()   # → 已送审
d.提交()                 # → 已在审批中，不能重复提交
```

只改一个细节——由外面决定用哪一个，对象自己不换：

```python
# 换人的决定权交给外面
class 按比例:
    def 级别(self, 金额): return "二级审批" if 金额 > 5000 else "一级审批"
class 一律二级:
    def 级别(self, 金额): return "二级审批"

class 报销单:
    def __init__(self, 金额, 规则):
        self.金额, self.规则 = 金额, 规则     # ← 规则由外面塞进来，这一行是命根子
    def 审批级别(self): return self.规则.级别(self.金额)

报销单(6000, 按比例()).审批级别()     # → 二级审批
报销单(100,  按比例()).审批级别()     # → 一级审批
报销单(100,  一律二级()).审批级别()   # → 二级审批
```

两段类结构一样（几个平级类实现同一方法，主对象持有一个并委托），上面是**状态**，下面是**策略**。

- 判据｜**谁来换那个对象**：外面挑一个塞进来是策略；对象自己在运行中换成下一个是状态。辅助线索：状态类之间**知道彼此**（"草稿"里写着下一站是待审批），策略之间互不认识。`self.规则` 必须声明成**抽象类型**（Java 里就是那个接口名），写死成 `按比例` 就换不掉，"可相互替换"也就没了。
- 例子｜财务今年用"按比例"、明年改"一律二级"，报销单不会主动换 → 策略；草稿单提交后自己变成待审批单 → 状态。旅游定价包由运营按季节挑一套是策略，改成系统按当前日期自己切到下一档就成了状态。

**2）职责链 vs 观察者**

- 判据｜**一个人办** vs **人人都收到**。职责链沿链找到第一个能办的就停，最终只有一个对象真处理，其余只是"有机会处理"；观察者一对多，目标一变，观察者统统收到同一条通知。光有"多个对象"不足以判定。
- 例子｜一笔报销顺着组长 → 经理 → 总监往上找，权限够的批，只批一次 → 职责链；单子一通过，短信、台账、报表、预算全部被触发 → 观察者。把"批不了就转上级"改成"每一级都要留一份记录"，就变成观察者。

```python
# 职责链：批不了就往下传，最终只有一个人真批
class 审批人:
    def __init__(self, 名, 上限): self.名, self.上限, self.下家 = 名, 上限, None
    def 接单(self, 金额):
        if 金额 <= self.上限: return f"{self.名}批"
        if self.下家: return self.下家.接单(金额)
        return "无人可批"

组长, 经理, 总监 = 审批人("组长",1000), 审批人("经理",10000), 审批人("总监",100000)
组长.下家, 经理.下家 = 经理, 总监
[组长.接单(x) for x in (800, 6000, 50000, 200000)]
# → ['组长批', '经理批', '总监批', '无人可批']
```

```python
# 观察者：一变，全体收到
class 报销单:
    def __init__(self): self.订阅者 = []
    def 订阅(self, f): self.订阅者.append(f)
    def 通过(self):
        self.结论 = "已通过"
        return [f(self) for f in self.订阅者]

s = 报销单()
s.订阅(lambda x: "发短信:"+x.结论); s.订阅(lambda x: "记台账:"+x.结论); s.订阅(lambda x: "刷报表:"+x.结论)
s.通过()   # → ['发短信:已通过', '记台账:已通过', '刷报表:已通过']
```

职责链的**链在运行时组装**——`组长.下家 = 经理` 随时能改，链长随组织架构变，故适用场景写作"可处理一个请求的对象集合应被动态指定"。观察者则是目标只管喊"我变了"，谁关心谁自己来登记，接新下游不用改目标。

**3）职责链 vs 命令**

- 判据｜**传下去** vs **存起来**。沿链找第一个能办的是职责链；把请求本身变成能排队、进历史栈、能撤销的对象是命令。命令的四个信号词：**参数化、排队、日志、撤销**。"参数化"指调用方（如"批量审批"按钮）不需要知道按下去会发生什么，只拿着一个命令对象，换个命令对象就换了行为，请求成了可以传来传去的参数。
- 例子｜组长批不了转经理 → 职责链。撤回刚才那次审批、月底批量审批先排队、每次审批都留痕 → 命令："审批这一次"得是一样能拿在手里的东西，而"调一次方法"执行完就没了，塞不进历史栈和队列。

**4）观察者 vs 中介者**

- 判据｜**方向和对称性**。观察者是一对多的单向广播，订阅者被动收同一条消息、彼此无关；中介者是多对多交互的集中调停，各方对等，中介看内容决定转给谁（可能一个，也可能谁都不转）。"减少多个对象或类之间的通信复杂性"属于中介者，不属于观察者。
- 例子｜报销单变了通知短信、台账、报表 → 观察者；提单、审批、预算、财务四个模块互相都要说话、都得过中介 → 中介者。

**5）模板方法 vs 策略**

- 判据｜**改一步用模板方法，换整套用策略。** 模板方法靠**继承**：父类把"校验 → 算级别 → 落库 → 通知"四步顺序焊死，子类只改其中某一步；策略靠**组合**：整个算法作为一个对象整体替换。先看有没有焊死的骨架，再看换一步还是全部。
- 例子｜招待费报销只换"算级别"那一步 → 模板方法；整套算级别规则在运行时被换掉 → 策略。

**6）迭代器 vs 访问者**

- 判据｜**遍历** vs **加操作**。迭代器只解决"怎么一个个取出来"；在不改元素类的前提下给它们加新操作（新统计写在哪）是访问者。
- 例子｜挨个读报销单明细 → 迭代器（Python 的 `for x in 列表`、Java 的 `Iterator`）。报销单、明细、附件类几年不变，变的是要做的操作——今天按部门统计、明天导税务报表——每套新操作打包成一个访问者对象 → 访问者。

访问者的代价：元素类必须先留 `accept(访问者)` 口子；只适合"结构稳定、操作频繁新增"，若元素类老加新种类，每加一种所有访问者都得改。

**7）命令 vs 备忘录**

- 判据｜两个都能撤销。**命令记"做过什么"（把操作反着做一遍），备忘录存"当时的样子"（整个覆盖回去）。** 备忘录的标志是"不破坏封装性"加"保存 / 恢复状态"：对象不公开字段，而是自己生成快照交给外面的保管者；保管者只保管、看不懂也不改，恢复时把快照还给对象自己还原。
- 例子｜历史栈里放"批准了 3 号单"这个命令对象，撤销＝调它的 `撤销` → 命令；放"点下去之前整张单子的快照" → 备忘录。

**8）状态模式 vs UML 状态图**（同名，不是一回事）

- 判据｜问的是一张图属于哪种 UML 图，归讲义 27；问设计采用哪种模式，才是这里。两者关系近：状态图上每个圆角矩形，落到状态模式里正好是一个状态类。
- 例子｜画着圆角矩形和迁移箭头的图＝UML 状态图；"每个状态一个类、当前状态自己迁移"的代码＝状态模式。

## 三、类图里的角色

| 模式 | 角色 | 在类图里长什么样 |
|---|---|---|
| 策略 / 状态 | **上下文（Context）** | 持有策略或状态对象、把活委托出去的主对象（报销单、售货机）。原话："客户程序使用的主要接口，可用状态来对其进行配置"。类名以 State 结尾的都是状态类，剩下那个才是上下文 |
| 策略 / 状态 | 具体策略 / 具体状态 | 各自实现同一个方法名的那几个平级类 |
| 命令 | 抽象命令 | "声明执行操作的接口"的那一层 |
| 命令 | 具体命令 | 实现抽象命令的那几个平级类 |
| 命令 | **调用者** | 只认抽象命令、负责触发，还可以把命令压进历史栈或队列 |
| 命令 | **接收者** | 真正干活的对象（报销单本身、被买卖的股票） |
| 访问者 | **元素** | 开 `accept(访问者)` 口子的是元素，不是访问者；那几个平级的操作类才是具体访问者 |
| 访问者 | **对象结构** | 装着一堆元素的**容器**（购物车、装满明细的报销单），只负责把元素一个个交出来；`accept` 开在**被装的元素**身上（Item、明细），不开在容器上 |
| 职责链 | 处理者 | 每个处理者只认自己的**下家**，链在运行时组装 |
| 观察者 | 目标 / 观察者 | 目标持有一串观察者，自己一变就逐个通知 |

## 四、类模式还是对象模式

每个模式有两个坐标：属于哪一型（本课全是行为型），是类模式还是对象模式。

- 原理｜**类模式靠继承，编译期定死关系；对象模式靠对象组合，运行时装配。** 解释器、模板方法都是"子类继承父类、覆盖某个方法"；观察者、策略、状态等都是"持有别的对象、把活委托过去"。
- 结论｜行为型里既可以是类模式也可以是对象模式的只有 **2 个：解释器、模板方法**，其余 9 个只是对象模式。归类时解释器、模板方法记作「行为型类模式」，其余九个记作「行为型对象模式」。
- 出处｜设计模式分类总览图（讲义 28 第一节）中带**下划线**的模式名"既可以是类模式，也可以是对象模式"，无下划线的"只是对象模式"；行为型带下划线的就是解释器和模板方法（迭代器那行下面是拼写检查的红色波浪线，不是下划线）。创建型、结构型的情况见讲义 28。

## 五、其余认名即可

解释器：报销系统里要用上它，得是"允许财务自己写一行规则表达式 `金额>5000 && 类型=='招待'`，系统读懂并执行"的场合；认"文法""语言""句子"三个词即可。

## 速记

- 场景直映：规则常变→策略、自己走到下一步→状态、逐级往上审→职责链、要撤销要留痕→命令、一变全都动→观察者、模块互相直调→中介者、不改类加新统计→访问者
- 其余四个认关键字：迭代器「顺序访问，不暴露内部」、模板方法「骨架固定、步骤下放」、备忘录「保存，恢复」、解释器「解释器，虚拟机」
- 七个的教材口诀：职责链「传递请求、职责、链接」、命令「日志记录、可撤销」、中介者「不直接引用」、观察者「通知、自动更新」、状态「状态变成类」、策略「算法替换」、访问者「数据和操作分离」
- **外面挑的是策略，自己变的是状态**；职责链只有一个人真办，观察者人人都收到
- 模板方法靠继承改一步，策略靠组合换整套；命令记"做过什么"，备忘录存"当时的样子"
- 类模式只有**解释器、模板方法**，其余九个是行为型对象模式
- 状态模式 ≠ UML 状态图（归讲义 27）：状态图上一个圆角矩形＝一个状态类
