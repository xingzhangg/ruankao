## 第 1 层 · 理解

### 一句话

> 设计想清楚了，得画出来给别人看。UML 就是把"画法"统一掉的一套**记号语言**——它只规定怎么画，不规定开发过程怎么走。

### 痛点

OO 方法早期各家画图记号不统一，同一份设计换个团队就看不懂，图纸没法当交流媒介。UML（Unified Modeling Language）把记号标准化，让"图"成为可交流的正式产物。

**关键澄清（常考陷阱）**：**UML 是一种语言，不是一种方法/过程**。它不告诉你先做什么后做什么（那是 RUP 之类过程模型的事）。

### 一条主线

```
要看懂一个系统，得从两个角度看：
   ┌── 静态 · 结构图：系统里【有什么】、什么关系
   │      类图（核心）/ 对象图 / 构件图 / 部署图
   └── 动态 · 行为图：随时间【发生什么】
          用例图 / 顺序图 / 状态图 / 活动图
      ↓
本课取其中最重要的两张：
   用例图 ── 从【外部】看：谁用这个系统做什么（功能清单，刻意不涉及内部实现）
   类图  ── 从【内部】看：有哪些类、类之间什么关系（可直接翻译成代码）
      ↓
这两张图的考点，几乎全都落在【关系的类型和箭头方向】上：
   用例图三关系：include / extend / 泛化
   类图六关系：依赖 < 关联 < 聚合 < 组合，外加泛化 / 实现
      ↓
而所有关系的判断，都能归结成同一个问题：
             【谁离了谁不行？】
   依赖：用完就走 ─ 关联：一直认识 ─ 聚合：整体亡、部分还在 ─ 组合：整体亡、部分同亡
   include：基用例离不开被包含的 ─ extend：扩展离不开基，基自己却完整
```

**记住最后那个统一问题，六种关系就不用背表了。**

## 第 2 层 · 考点：考试怎么问

### 考点① UML 常考 8 种图辨认——给定义认图名（几乎年年考）

**题目长相**："UML 中，（ ）展现了运行时处理节点以及其中构件的配置……"——给一句教材定义句式，选图名。

| 大类 | 图 | **定义句式里的关键词** |
|---|---|---|
| **结构图**（静态） | **类图** | "一组类、接口、协作及其关系"，**最常见**的图 |
| | 对象图 | 某一时刻**对象及连接的快照**（类图的实例版） |
| | **构件图** | **软件**由哪些构件（模块/包/库）组成及依赖 |
| | **部署图** | **硬件节点** + 节点上**部署**的软件，物理拓扑 |
| **行为图**（动态） | **用例图** | 谁（参与者）用系统做什么，**功能需求全景** |
| | **顺序图** | 一次交互中**多个对象按时间顺序**交换消息 |
| | **状态图** | **单个对象**一生的**状态及迁移事件** |
| | **活动图** | 业务**流程 / 工作流**，支持**分支与并发** |

**抓关键词秒选**：
> 功能/角色 → **用例图**｜类和关系 → **类图**｜时间顺序消息 → **顺序图**
> 状态变迁 → **状态图**｜流程/并发 → **活动图**｜软件模块组成 → **构件图**｜硬件节点 → **部署图**

**最常见的两个陷阱**：
- "多个对象**按时间顺序**交换消息" → **顺序图**，不是状态图。状态图讲的是**单个对象**的状态变迁。
- **构件图 vs 部署图**：构件图只画**软件**构件的组成与依赖，**不涉及硬件**；部署图才有硬件节点。

### 考点② 用例图三要素

- **参与者 Actor**（小人）：在系统**外部**与系统交互的人、组织或**外部系统**。
  → **判断标准是"在边界外"**，所以对接的第三方支付网关**也是参与者**（这是常考点）。
- **用例 Use Case**（椭圆）：系统对外提供的一项完整功能，动宾短语命名（"下单""查询订单"）
- **系统边界**（方框）：框内是本系统的用例，框外是参与者

```
        ┌───────── 网上商城系统（系统边界）─────────┐
        │   （下单）      （支付）     （退货）      │
 顾客 ──│     ↑椭圆=用例                          │── 支付网关
（小人）  └────────────────────────────────────┘   （外部系统也是参与者）
```

### 考点③ include vs extend——方向相反，最高频陷阱

| 关系 | 语义 | **判断口诀** | 画法与**方向** |
|---|---|---|---|
| **包含 include** | 基用例执行时**一定**会执行被包含用例（公共步骤抽出复用） | **"每次都要做"** | 虚线箭头 + «include»，**基用例 → 被包含用例** |
| **扩展 extend** | 满足特定条件时**才**追加执行（可选/异常分支） | **"有时才做"** | 虚线箭头 + «extend»，**扩展用例 → 基用例** |
| **泛化** | 子用例是父用例的一种特殊方式 | **"是一种"** | 实线 + 空心三角，**子 → 父** |

```
（下单）╌╌╌«include»╌╌▶（核对库存）     下单必然核对库存：基 → 公共
（下单）◀╌╌╌«extend»╌╌╌（使用优惠券）   有券才用：扩展 → 基
（电话下单）───────▷（下单）            泛化：特殊 → 一般
```

**方向记忆（背这个）**：两者都是虚线箭头，方向**相反**——
> **include 是基用例"伸手去拿"公共步骤**（基 → 被包含）；
> **extend 是可选功能"贴上去"依附基用例**（扩展 → 基）。
> 统一判据仍是"谁离了谁不行"：include 里**基用例离不开**被包含用例；extend 里**扩展用例依附基用例**，基用例自己独立完整。

### 考点④ 类的画法（三层矩形）

```
┌─────────────────┐        可见性符号：
│      Order      │ ← 类名（斜体 = 抽象类）      + public
├─────────────────┤        - private
│ - id: long      │ ← 属性：可见性 名: 类型      # protected
├─────────────────┤        ~ 包内可见
│ + pay(): void   │ ← 操作：可见性 名(): 返回型
└─────────────────┘
```
**送分细节**：**抽象类的类名用斜体**表示。

### 考点⑤ 类图六种关系（本课最重要，下午题3 必用）

耦合从弱到强：**依赖 < 关联 < 聚合 < 组合**；泛化/实现属另一维度的"是不是"关系。

| 关系 | 画法（箭头指向） | 代码对应 | **判断标准** |
|---|---|---|---|
| **依赖** | 虚线 + **开放箭头** → 被用者 | 方法参数、局部变量、返回值——**临时用一下** | "用完就走"，不长期持有 |
| **关联** | **实线**（可加开放箭头表导航方向） | **成员变量**长期持有引用 | "一直认识"，如 老师—学生 |
| **聚合** | 实线 + **空心菱形**贴**整体**端 | 成员变量，部分从**外部传入**，可共享 | 整体消失，部分**还能独立存在** |
| **组合** | 实线 + **实心菱形**贴**整体**端 | 成员变量，整体**内部创建**，独占 | 整体消失，部分**跟着消失** |
| **泛化** | **实线** + **空心三角** → **父类** | `extends` | is-a："狗是一种动物" |
| **实现** | **虚线** + **空心三角** → **接口** | `implements` | 类承诺履行接口契约 |

```
Car ╌╌╌╌╌╌▶ GasStation        依赖：加油时临时用一下（方法参数）
Teacher ────── Student         关联：互相长期持有引用
Wheel ──────◇ Car              聚合：车没了轮子还在（可拆下共享）
Engine ─────◆ Car              组合：本例设定发动机随整车报废
Dog ────────▷ Animal           泛化：实线空心三角 → 父类
ArrayList ╌╌╌▷ List            实现：虚线空心三角 → 接口
```

```java
class Car {
    private List<Wheel> wheels;                 // 聚合：部分外部传入，可独立存在
    private Engine engine = new Engine();       // 组合：整体内部创建，同生命周期
    Car(List<Wheel> ws) { this.wheels = ws; }
    void refuel(GasStation s) { s.fill(this); } // 依赖：只在方法里临时用
}
```

**聚合 vs 组合（上午下午都爱考）**——问一句：
> **"整体销毁后，部分还能不能独立存在、被别的整体共享？"**
> 能 → **聚合**（空心菱形）：车—轮子、部门—员工
> 不能 → **组合**（实心菱形）：房子—房间、订单—订单明细（订单删了明细无意义）

⚠️ 判断要看**题目给的语义**，同一对事物在不同系统里可能建模不同。

**泛化 vs 实现**：目标是**类**（继承已有实现）→ 泛化、**实线**；目标是**接口**（只承诺契约）→ 实现、**虚线**。箭头同为空心三角，**靠线型区分**。

### 考点⑥ 多重性（下午题3 常让你补）

| 标记 | 含义 | 标记 | 含义 |
|---|---|---|---|
| `1` | 恰好 1 个 | `0..1` | 0 或 1 个 |
| `*`（= `0..*`） | 0 到任意多 | `1..*` | 至少 1 个 |
| `m..n` | m 到 n 个 | | |

**读法**：贴在哪端，就说明"对方的一个实例对应**这端**多少个实例"。
例：`Order 1 ── * OrderItem` = 一个订单含任意多明细，一条明细只属于一个订单。

**下午题解法**：从题干里找"一个……可以有多个……""每个……必须属于一个……"这类句子，**直接翻译**成多重性，不用推理。

## 第 4 层 · 速记

> 结构图画"有什么"（类/对象/构件/部署），行为图画"发生什么"（用例/顺序/状态/活动）
> UML 是**语言**不是过程；抽象类**斜体**
> 用例三要素：小人（参与者）、椭圆（用例）、方框（边界）；**外部系统也算小人**
> **"必做"include 基指公共；"选做"extend 扩指基** —— 两条虚线，方向相反
> 类图六关系强弱：**依赖 < 关联 < 聚合 < 组合**；参数临时是依赖、成员长期是关联
> **空心菱形聚、实心菱形组，菱形贴整体**；整体亡部分存→聚合，整体亡部分亡→组合
> 空心三角指父类：**实线泛化**（extends）、**虚线实现**（implements）
> 多重性：`1` 恰一、`0..1` 至多一、`*` 随便多、`1..*` 至少一
> **统一判据：谁离了谁不行**

## 考题回顾

**1.【模拟·重现2021上考点】** UML 中，（1）展现运行时处理节点及其中构件的配置，描述硬件的物理拓扑及在此结构上部署的软件；（2）描述一组类、接口、协作及其关系，是最常见的图。
A. 构件图/类图　B. 部署图/类图　C. 部署图/对象图　D. 构件图/用例图
**解**：**B**。"硬件物理拓扑 + 节点上部署的软件"= 部署图；"类/接口及其关系、最常见"= 类图。构件图不涉及硬件；对象图是某时刻实例快照。⚠️ 少数中文资料把类图这句写成"一组**对象**、接口、协作"，不管哪种措辞，答案都是**类图**——对象图的判别词是"**某一时刻 / 快照**"，不是"对象"二字。

**2.【模拟·重现2022下考点】** "支付订单"执行中**必须**执行"验证用户身份"；**仅当**用户选择开发票时才执行"开具发票"。两组关系分别是（ ）。
A. include、include　B. extend、include　C. include、extend　D. extend、extend
**解**：**C**。"必须/每次都做"→ include；"仅当……才"→ extend。方向：支付订单 ╌«include»╌▶ 验证用户身份；开具发票 ╌«extend»╌▶ 支付订单。

**3.【模拟】** "公司与部门：公司撤销则部门不复存在"、"车队与车辆：车队解散后车辆仍可转入其他车队"，应分别建模为（ ）。
A. 聚合、组合　B. 组合、聚合　C. 关联、依赖　D. 组合、组合
**解**：**B**。部门随公司消亡 → **组合**（实心菱形贴公司端）；车辆可独立存在并被共享 → **聚合**（空心菱形贴车队端）。

**4.【模拟】** `class A implements B { private C c; void m(D d){ d.run(); } }` 对应的类图关系是（ ）。
A. A实现B；A与C关联；A依赖D　B. A泛化B；A与C聚合；A依赖D
C. A实现B；A与C依赖；A与D关联　D. A泛化B；A与C组合；A与D关联
**解**：**A**。`implements B` → 实现（虚线空心三角）；`private C c` 成员变量长期持有 → 关联（仅凭字段无法断定聚合/组合语义，一般标关联）；`D` 只作方法参数 → 依赖。

**5.【模拟】** 关于 UML 各类图，**错误**的是（ ）。
A. 用例图中的参与者可以是与系统交互的外部系统
B. 活动图可以描述含分支与并发的业务流程
C. 状态图描述多个对象之间按时间顺序的消息交互
D. 类图中抽象类的类名用斜体表示
**解**：**C**。"多个对象按时间顺序交换消息"是**顺序图**；状态图描述**单个对象**的状态变迁。

## 自测练习

1. 【模拟】"图书馆系统中，一名读者最多可同时借 5 本书，一本书某时刻至多被一名读者借出。"写出 Reader 与 Book 关联两端的多重性。
2. 【模拟】"订单(Order)与订单明细(OrderItem)"应建模为聚合还是组合？菱形画在哪一端？依据是什么？
3. 【模拟】ATM 中，"取款"每次都要"验证密码"，余额不足时才触发"打印余额不足凭条"。写出两组关系类型及虚线箭头方向。

### 参考答案

1. `Reader 0..1 ── 0..5 Book`。Reader 端标 **`0..1`**（一本书某时刻至多被一名读者借出，也可能没被借出）；Book 端标 **`0..5`**（一名读者同时借 0 到 5 本）。
2. **组合**，**实心菱形画在整体 Order 端**。依据："整体消失部分是否消失"——订单删除后明细失去存在意义、不能转属其他订单，生命周期一致。
3. "取款"与"验证密码"是 **include**：虚线箭头**从基用例"取款"指向"验证密码"**，标 «include»；"打印余额不足凭条"与"取款"是 **extend**：虚线箭头**从扩展用例指向基用例"取款"**，标 «extend»。记忆：必做 include 基指公共，选做 extend 扩指基。
