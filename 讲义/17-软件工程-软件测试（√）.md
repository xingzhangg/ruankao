## 开讲：报销系统写完了，怎么知道它对不对

还是讲义 15、18 那套内部报销系统。代码写完、排期也没拖，老板问一句："测过了吗？"

你的第一反应多半是：把系统点一遍——提一张单、审一下、看眼报表，都正常，那就叫测过了。这一课的全部名词，都是在指出这个第一反应有多少条漏洞，以及每条漏洞对应的补法：

- ① 你点一遍是在**证明它能用**，方向就反了；
- ② 报销金额能填任意数，你只填了一个，**输入该挑哪几个**没有依据；
- ③ 你点得通的那条路只是代码的一部分，**还有整段代码从没执行过**，你却不知道；
- ④ 就算要"把代码走遍"，**到底几条用例才算走遍**，没有数；
- ⑤ **什么时候开始测、拿哪份文档判对错、模块还没配齐怎么先跑起来**；
- ⑥ 真报错了，**错在哪一行、改完怎么保证没改坏别处**。

下面六节一条一条补。

### 一、先把"测试"两个字的目标摆正

培训资料开篇第一句就把方向掰过来：**系统测试是为了发现错误而执行程序的过程，成功的测试是发现了至今尚未发现的错误的测试。** 一轮测试跑完什么错都没找出来，不叫"测得好"，叫"这轮白做了"——你的任务是砸出 bug，不是给系统颁奖。

由此跟出一条年年考的硬结论：**测试只能证明程序有错，不能证明程序无错。** 报销金额是个整数输入框，32 位整数有 40 多亿种取值，穷举在工程上根本不可行；你试了 50 个都对，只说明这 50 个没触发缺陷。

八条**测试原则**是这个目标的展开，照录：应尽早并不断的进行测试；测试工作应该避免由原开发软件的人或小组承担；在设计测试方案时，不仅要确定输入数据，而且要根据系统功能确定预期的输出结果；既包含有效、合理的测试用例，也包含不合理、失效的用例；检验程序是否做了该做的事，且是否做了不该做的事；严格按照测试计划进行；妥善保存测试计划和测试用例；测试用例可以重复使用或追加测试。

其中两条落到报销系统上是这样：**不该由原开发人员测**——自己写的代码，测的时候会顺着当初的思路走，当初没想到的分支现在照样想不到；**要有不合理、失效的用例**——不光试"金额填 800"，还要试"金额填 −5""金额填 abc"，看程序能不能正确地把它挡回去。

方法分类有**两把尺子，互相正交，最容易混**。

第一把：**要不要把程序跑起来**。**静态测试**指被测试程序**不在机器上运行**，而采用**人工检测和计算机辅助静态分析的手段**对程序进行检测，包括对文档的静态测试和对代码的静态测试。对文档主要以**检查单**的形式进行——检查单就是一张事先列好"该有的条目有没有"的清单，拿着文档逐条打钩。对代码有三种：**桌前检查**（程序员自己把自己写的代码从头读一遍）、**代码审查**（一组人开会照着规程逐段过）、**代码走查**（一组人拿一组测试数据，用脑子当 CPU 顺着代码走一遍）。这套办法能有效地发现 **30%–70%** 的逻辑设计和编码错误。**动态测试**则指在计算机上**实际运行程序**进行软件测试，一般采用白盒测试和黑盒测试方法。

第二把：**设计用例的时候看不看代码**。**黑盒测试法**是**功能性测试**，不了解软件代码结构，根据功能设计用例，测试软件功能；**白盒测试法**是**结构性测试**，明确代码流程，根据代码逻辑设计用例，进行用例覆盖。

两把尺子的交叉点就是本节唯一的坑：黑盒和白盒**都属于动态测试**，都要跑程序。所以"桌前检查、代码审查、代码走查"虽然眼睛也盯着代码，却**不是白盒测试**——它们压根不运行程序，属于静态测试。练习第 2 题考的就是这个交叉点。

### 二、黑盒：输入是无限的，挑哪几个

报销系统的"报销金额"输入框，需求写的是**填 1 到 5000 的整数（元）**。不看代码，你打算填哪几个数去试？**先别往下看，自己先说三个数。**

多数人会说"随便挑几个有代表性的：100、1000、3000"。这个直觉里已经有对的一半了——"有代表性"正是**等价类划分**：把所有的数据按照某种特性进行归类，然后在每类的数据里选取一个即可。它成立的理由是，程序处理"金额 100"和"金额 3000"走的是同一段代码，一个通过另一个多半也通过，测两个和测一个收获一样。

归类要分两种。**有效等价类**是合法输入的集合，程序应当正常接受，这里就是 1–5000 的整数；**无效等价类**是非法输入的集合，程序应当正确地拒绝，这里至少三类：小于 1（如 0）、大于 5000（如 6000）、不是整数（如 12.5 或 `abc`）。无效类**必须也出用例**——你要测的是"程序会不会挡"，不是"程序能不能算"。

培训资料给了两条设计原则，措辞不同，差别是考点：**设计一个新的测试用例，使其尽可能多地覆盖尚未被覆盖的有效等价类**，重复这一步直到所有有效等价类都被覆盖；**设计一个新的测试用例，使其仅覆盖一个尚未被覆盖的无效等价类**，重复这一步直到所有无效等价类都被覆盖。

有效类一条用例可以扫掉好几个，无效类**一条用例只许犯一个错**。为什么不对称？因为无效输入是被挡回去的，程序碰到第一个错就报错返回了。假如一条用例同时填"金额 −5"和"发票没传"，程序报了句"金额非法"就走人，"发票没传"这条校验到底写没写，你根本没测到。练习第 3 题（招聘系统那道真题）考的正是这一条。

**边界值划分**（也常叫边界值分析）把**每类的边界值作为测试用例**。培训资料的口径是"**边界值一般为范围的两端值以及在此范围之外的与此范围间隔最小的两个值**"，配的例子是年龄范围 0–150，边界值为 0、150、−1、151 四个。照这个口径，报销金额 1–5000 的边界值就是 **1、5000、0、5001**。教材还会再加上界内紧邻的两个（**2 和 4999**）凑成六个点；做题时不必纠结取四个还是六个，认准"取的是边界本身和紧挨着它的值"这个形状就行。

为什么边界值比等价类更容易砸中 bug？因为程序员最常写错的就在边界：`amt <= 5000` 手滑写成 `amt < 5000`，循环多跑一次少跑一次。等价类的代表值取 2500，这类错一个都碰不到；取 5000 和 5001，一试就露。所以边界值不是替代等价类，是**补在等价类的接缝上**，两者配合用。

剩下两种培训资料写得很短，考试也只要求认得：**错误推测**没有固定的方法，凭经验而言，来推测有可能产生问题的地方，作为测试用例进行测试——落到报销系统就是老手一眼看出该试"同一张单连点两次提交""审批人给自己审批"；**因果图**是由一个结果来反推原因的方法，具体结果具体分析，没有固定方法，用在"多个输入条件组合决定一个输出"的场合，比如"金额超 1000 且有发票才走二级审批"，把原因（输入条件）和结果（输出动作）连成图，再从图上导出用例。（培训资料列的黑盒方法就这四种；别的教材还会并列一个**判定表法**——把各输入条件的真假组合列成表格，每一列写出对应该走的动作，一列就是一条用例，认得名字即可。）

### 三、白盒：还有代码从没跑到

黑盒用例全过了，能收工吗？打开报销系统那段定审批级别的代码看一眼：

```c
/* 输入：amt 本次报销金额，rcpt 是否已上传发票(1/0)，lvl 员工职级 */
if (amt > 1000 && rcpt == 1) {      /* 判定 1 */
    amt = amt - 1000;               /* 语句 S1：公司每月给 1000 元免审额度，凭发票抵扣 */
}
if (lvl >= 3 || amt > 500) {        /* 判定 2 */
    level = 2;                      /* 语句 S2：升为二级审批 */
}
```

两个术语先说死：一个 `if` 括号里的整个表达式叫**判定**，这里有两个；判定里被 `&&`、`||` 连起来的每一小段叫**条件**，这里有四个：`amt>1000`、`rcpt==1`、`lvl>=3`、`amt>500`。

画成流程图（第四节算 McCabe 还用这张图）：

```
 s 入口
 │
 ▼
 a  amt>1000 && rcpt==1 ──真──→ c  amt = amt - 1000
 │假                              │
 ▼←───────────────────────────────┘
 b  lvl>=3 || amt>500 ──真──→ e  level = 2
 │假                           │
 ▼←────────────────────────────┘
 d 出口
```

一条用例走过的结点连起来就是一条**路径**，例如 (amt=2000, rcpt=1, lvl=1) 走 s→a→c→b→e→d，记作 **sacbed**。

下面开始爬阶梯。培训资料的原话是覆盖级别"**从低至高**"分成几种；关键在于**每一级都是上一级漏掉某类缺陷之后的回应**，全程就用这一段代码。

**第 0 级，最朴素的想法：每行代码都执行到——语句覆盖 SC。** 定义是逻辑代码中的**所有语句都要被执行一遍，覆盖层级最低**。本例一条用例就够：**(amt=2000, rcpt=1, lvl=1)**——判定 1 真（2000 超 1000 且有票）走 S1，amt 变 1000；判定 2 真（1000 > 500）走 S2。路径 sacbed，两条语句全执行了。
**漏掉了什么**：两个判定的**假分支一次都没走**。要是"没传发票时应该报错"这条逻辑写漏了，这条用例永远发现不了。培训资料的解释就是"因为执行了所有的语句，不代表执行了所有的条件判断"。

**第 1 级：让每个判定的真假两边都走一次——判定覆盖 DC（又称分支覆盖）。** 定义是逻辑代码中的**所有判断语句的条件的真假分支都要覆盖一次**。两条用例：**(2000, 1, 1)** 判定 1 真、判定 2 真；**(300, 0, 1)** 判定 1 假、判定 2 假（职级 1，且 300 不到 500）。
**漏掉了什么**：数一下 `lvl >= 3` 这个条件——两条用例的职级都填 1，它**两次都是假**。假设程序员手抖把 `lvl >= 3` 敲成了 `lvl >= 30`，这两条用例的结果一个字都不会变（第一条靠 `amt>500` 撑着判定 2 为真，第二条本来就该假），笔误查不出来。

**第 2 级：管到每个条件头上——条件覆盖 CC。** 定义是针对每一个判断条件内的**每一个独立条件都要执行一遍真和假**。
**先猜一下**：条件比判定更细，那么满足条件覆盖是不是就自动满足判定覆盖了？
不是。看这两条：**(amt=2000, rcpt=0, lvl=1)** 和 **(amt=300, rcpt=1, lvl=3)**。四个条件全齐了——`amt>1000` 真/假、`rcpt==1` 假/真、`lvl>=3` 假/真、`amt>500` 真/假，条件覆盖成立。可判定呢？判定 1 第一条是"真 && 假 = 假"、第二条是"假 && 真 = 假"，**真分支一次没进**；判定 2 两条都是真，**假分支一次没走**。判定覆盖不成立，连语句覆盖都不成立（S1 从头到尾没执行）。
**这是本课最值钱的一个反例：满足条件覆盖不一定满足判定覆盖。** 道理不难——`&&` 里两个条件一真一假，整体照样是假；你把条件的真假凑齐，判定的真假可以纹丝不动。
好消息是这组把上一级漏掉的笔误抓住了：第二条 (300, 1, 3) 里 `lvl>=3` 是判定 2 为真的唯一理由，改成 `lvl>=30` 就由真变假，结果不同，bug 现形。

**第 3 级：两个都要——判定/条件覆盖 CDC（培训资料写作"条件判定组合覆盖"）。** 定义直白：**同时满足判定覆盖和条件覆盖**。最省事的凑法是"全真 + 全假"：**(2000, 1, 3)** 四个条件全真、两个判定全真；**(300, 0, 1)** 四个条件全假、两个判定全假。
**漏掉了什么**：判定 1 里 `amt>1000` 和 `rcpt==1` 只出现过"同真"和"同假"，**没出现过一真一假**。要是把 `&&` 写成了 `||`，这两条用例的结果完全一样（真‖真还是真，假‖假还是假），bug 照样溜过去。而现实里"金额够但没传发票"恰恰是最常见的一种单子。

**第 4 级：把一个判定里条件的所有取值组合都排出来——条件组合覆盖。**（培训资料的清单里只有五级，没列这一级；教材有，选项里出现别当是编的。）两个条件就是 2² = 4 种组合。判定 1 的四种和判定 2 的四种，四条用例可以同时凑齐：

| 用例 | amt | rcpt | lvl | 判定1 的 (amt>1000, rcpt==1) | 判定2 的 (lvl>=3, amt>500) | 走的路径 |
|---|---|---|---|---|---|---|
| W1 | 2000 | 1 | 3 | 真 真 | 真 真 | sacbed |
| W2 | 2000 | 0 | 1 | 真 假 | 假 真 | sabed |
| W3 | 300 | 1 | 3 | 假 真 | 真 假 | sabed |
| W4 | 300 | 0 | 1 | 假 假 | 假 假 | sabd |

W2 正是上一级漏掉的"金额够但没票"，`&&` 写成 `||` 这回被抓住了。
**漏掉了什么**：看最右边一列——四条用例只走了 sacbed、sabed、sabd **三条路径**，缺了 **sacbd**（判定 1 真、判定 2 假，也就是"抵扣掉 1000 后金额降到 500 以下、低职级只需一级审批"这种单子）。**组合全了，路径仍然没走全。**

**第 5 级：所有可行路径全走一遍——路径覆盖，最强。** 定义是逻辑代码中的**所有可行路径都覆盖了，覆盖层级最高**。本例共 4 条路径，在上面四条用例外补一条 (amt=1200, rcpt=1, lvl=1) 走 sacbd 就齐了。代价也在这里：路径数随判定个数**翻倍增长**，两个判定 4 条，十个判定上千条，再遇上循环就是天文数字。所以路径覆盖只在很小的模块上做得起——问题于是被推到下一节：**"走遍"到底要几条**。

（顺带记一个反过来的事实：走全这 4 条路径最少只要 4 条用例——(2000,1,1)、(1200,1,1)、(2000,0,1)、(300,0,1)——它们的职级全填 1，`lvl>=3` 一次没取真，所以**路径覆盖了却不满足条件覆盖**。可见这条从弱到强的链是**考试口径的经验排序**，不是严格的数学包含关系；考场按口径答，心里记住"条件覆盖不含判定覆盖""路径覆盖不含条件覆盖"这两个例外就够了。）

**看培训资料那张示例图时注意一处转录讹字**：图上判定 a 是 `(y>1)&&(z==0)`、真分支执行 `x=x/y`，判定 b 是 `(y==2)||(x>1)`。路径覆盖一行的第二组数据，**原图印的是 `X=3，Y=2，Z=0 → sacbed`**（代入验算：a 真，x 由 3 整除 2 得 1；b 的 `y==2` 真，走 e），转成文字稿时 Y 被抄成了 3。按 `X=3，Y=3，Z=0` 代入实际走 sacbd，会和第三组重复——以原图的 Y=2 为准。

### 四、"走遍"要几条：McCabe 环路复杂度

> 这一节和本课别处讲法不同：前面都是先摆困境再给方案，这一节要动手算，所以改成**先拿一张图数一遍，再从数出来的东西里长出公式**。

**先数，不给公式。** 还是上一节那张流程图。结点：s、a、c、b、e、d，**6 个**。箭头逐条数：s→a、a→c（真）、a→b（假）、c→b、b→e（真）、b→d（假）、e→d，**7 条**。

换个角度看同一张图：图上围出了几个"圈"？a→c→b 和 a→b 围出一个，b→e→d 和 b→d 围出一个，**闭合区域 2 个**；再把图外面无边无际的那一片也算一个区域，一共 **3 个区域**。

再换个角度：图上会分叉的结点，也就是**判定结点**，是 a 和 b，**2 个**；2 + 1 = **3**。

三个角度都得 3。这不是巧合——这个 3 就是 **McCabe 环路复杂度 V(G)**（也译环形复杂度、圈复杂度，同一个东西），三种数法互为验算：

> ① **公式法**　V(G) = 有向边数 − 结点数 + 2 = 7 − 6 + 2 = **3**
> ② **判定结点法**　V(G) = 判定结点数 + 1 = 2 + 1 = **3**
> ③ **区域法**　V(G) = 闭合区域数 + 1（外面那一片）= 2 + 1 = **3**

培训资料给的是①：**McCabe 度量法**又称为**环路复杂度**，假设有向图中**有向边数为 m，节点数为 n，则此有向图的环路复杂度为 m-n+2**；并提醒"m 和 n 代表的含义不能混淆"，以及"针对一个程序流程图，**每一个分支边（连线）就是一条有向边，每一条语句（语句框）就是一个顶点**"。

**公式为什么长这样**：欧拉公式。一张连通的平面图，面数 = 边数 − 点数 + 2，这里的"面"正是包括外部那一片在内的区域，所以①和③必然相等；而每插入一个二分叉的判定，**边比点多长出一条**，图上也就多围出一个圈，所以②跟着相等。**V(G) 的含义**是这张图里**线性无关的独立路径条数**——独立路径就是彼此拼不出对方的那几条骨架路径——也就是"要把这段代码的结构走遍，最少需要几条用例"。工程上还拿它当模块复杂度的尺子，一般认为 V(G) 超过 10 的模块难测也难维护。

**这里有个必须分清的坑**：V(G) = 3，可上一节数过，这段代码的**全部可行路径是 4 条**。两者不是一回事：V(G) 数的是独立路径，路径覆盖要的是全部路径。所以基本路径测试（按 V(G) 条数设计用例）比路径覆盖便宜，也比它弱。考题常把"图中有几条路径"和"环路复杂度是多少"两问连着出，**两个空的答案可能相同也可能不同，必须分别数**。

**再验一次，动一下图。** 把入口结点 s 去掉、直接拿 a 当入口：结点 5 个、边 6 条，V(G) = 6 − 5 + 2 = 3，一点没变——它同时让边和点各少 1。真正会把答案数错的是另外两处：**判定的假分支**（那条"假"箭头最容易看漏）和**循环的回边**（`while` 从循环体末尾拐回判定框那一条）。漏一条边，答案就少 1。

这一节的知识点在培训资料里归在「软件度量」下，因为环路复杂度本质上是一把量代码的尺子。同一节还有一条纯记忆的送分点：**软件的两种属性**——**外部属性**指面向管理者和用户的属性，**可直接测量**，一般为性能指标；**内部属性**指软件产品本身的属性，如可靠性等，**只能间接测量**。

### 五、什么时候测、拿哪份文档判卷

讲义 15 的 V 模型给过骨架：测试分级，每一级对着左边某个开发阶段。这一节填的是另一套口径——**依据哪份文档**。题目问"针对哪个阶段"用 V 模型那套，问"依据什么文档"用下面这套，别混；最容易撞车的是系统测试：按 V 模型那套，它**针对概要设计**（培训资料 3-2 原文，讲义 15 同口径）；按本节这套，它的**依据是用户需求或开发合同**。两句问的不是一件事，别互相套。

**单元测试**，也称模块测试。测试对象是**可独立编译或汇编的程序模块、软件构件或 OO 软件中的类**（统称为模块），报销系统里就是上面那个"定审批级别"的函数。测试依据是**软件详细设计说明书**——详细设计写的正是每个模块内部该怎么算。

麻烦在于一个模块单独跑不起来：上面调它的人可能还没写，它要调的下层（比如"查员工职级"这个接口）也可能还没写。于是临时补两段代码：**驱动模块（driver）**冒充**上层调用者**，负责把测试数据喂进来、启动被测模块、收结果；**桩模块（stub）**冒充**下层被调者**，被调到就直接返回一个假结果（比如职级固定返回 2）。

**集成测试**。目的是**检查模块之间，以及模块和已集成的软件之间的接口关系**，并验证已集成的软件是否符合设计要求。测试依据是**软件概要设计文档**——模块怎么划、接口长什么样，正是概要设计定的。

往一起拼的顺序有三种策略，**该补哪种临时模块由顺序决定**：**自底向上**是从**最底层模块开始测试，需要编写驱动程序**，而后开始逐一合并模块，最终完成整个系统的测试，优点是**较早的验证了底层模块**（底层已经在手，缺的是上面调它的人，所以补驱动）；**自顶向下**是先测顶层、**需要编写桩程序**，而后逐步向下直至最后测试最底层模块，优点是**较早的验证了系统的主要控制和判断点**（上层已经在手，缺的是下面被调的人，所以补桩）；**三明治**既有自底向上也有自顶向下，**二者都包括**，兼有二者的**优点，缺点是测试工作量大**。（培训资料把自顶向下的第一句写成"先测试整个系统"，按"先测最顶上那个模块、下层用桩顶上"理解，否则和后半句"逐步向下直至最后测试最底层模块"对不上。）

**确认测试**，也叫有效性测试。主要用于**验证软件的功能、性能和其他特性是否与用户需求一致**，依据是 **SRS**（软件需求规格说明书，需求分析阶段签字定下来的那份"系统该做什么"）。根据用户的参与程度分四类：**内部确认测试**主要由**软件开发组织内部按照 SRS 进行测试**，用户还没上场；**Alpha 测试**是**用户在开发环境**下进行测试；**Beta 测试**是**用户在实际使用环境下**进行测试，通过该测试后产品才能交付用户；**验收测试**是**针对 SRS，在交付前以用户为主进行的测试**，其测试对象为完整的、集成的计算机系统，目的是在真实的用户工作环境下检验软件系统是否满足开发技术合同或 SRS，结论是**用户确定是否接收该软件的主要依据**，做它之前应确认被测软件系统已通过系统测试。

α 和 β 的区别只有**场地**一条：α 在开发方的地盘（用户来公司试，开发人员在旁边看着），β 在用户自己的环境（开发方不在场）。两者的**主体都是用户**，选项写成"由开发人员进行"的一律排除。

**系统测试**。**测试对象是完整的、集成的计算机系统**，目的是在真实系统工作环境下，验证完成的软件配置项能否和系统正确连接，并满足系统/子系统设计文档和软件开发合同规定的要求，测试依据是**用户需求或开发合同**。主要内容包括功能测试、健壮性测试（故意喂脏数据、拔网线，看它会不会崩）、性能测试、用户界面测试、安全性测试、安装与反安装测试等，其中**最重要的工作是进行功能测试与性能测试**；功能测试主要采用**黑盒**测试方法，性能测试主要指标有**响应时间、吞吐量、并发用户数和资源利用率**等。

**配置项测试**。测试对象是**软件配置项**——配置管理里被单独管起来、有版本号、可独立交付的那一份东西，报销系统里比如"审批服务"这个能单独发布的部件。目的是**检验软件配置项与 SRS 的一致性**，依据是 SRS；在此之间，应确认被测软件配置项已通过单元测试和集成测试。

**回归测试**。目的是**测试软件变更之后，变更部分的正确性和对变更需求的符合性**，以及软件原有的、正确的功能、性能和其他规定的要求的不损害性——大白话就是：改完一处，把以前通过的用例再跑一遍，确认没有"修一个、坏一片"。报销政策每年变一次，每变一次就得回归一次。

### 六、报错之后：调试

测试跑出一堆红叉，接下来的活儿就不叫测试了，叫调试。培训资料一句话划清界线：**测试是发现错误，调试是找出错误的代码和原因。**

调试要做三件事：**确定错误的准确位置；确定问题的原因并设法改正；改正后要进行回归测试**——最后一步正好把上一节的回归测试接了回来，闭环。

方法三种。**蛮力法**：到处打印、开全量日志、把内存全导出来翻，最不动脑子也最费时间，但什么线索都没有时只能靠它。**回溯法**：**从出错的地方开始，向回找**——报表数字算错了，就从输出那一行往回一层层看是谁传进来的；小程序好用，代码一大就分叉太多。**原因排除法**：**找出所有可能的原因，逐一进行排除**，具体包括**演绎法**（先摊开所有可能原因，再用数据一条条否掉）、**归纳法**（从几次错误现象里找共性，归纳出假设再验证）、**二分法**（在中间打一刀，看错误落在哪一半，再对那一半打一刀）。

**收口**：开头六条短板，正文六节一一回应——① 目标摆正（顺带：不跑程序先审一遍，就能揪出三到七成的逻辑与编码错）→ ② 输入怎么挑 → ③ 代码有没有走遍 → ④ 走遍要几条 → ⑤ 什么时候测、拿什么判卷 → ⑥ 报错怎么定位、改完怎么保证没改坏。做题时先认出题干踩的是链条上哪一环，再对定义，比背表快。

## 考试怎么考

**考点① 覆盖标准，三种问法。** 问"最强/最弱"：最弱是**语句覆盖**，最强是**路径覆盖**，别惯性反着选。问"这组用例满足哪种覆盖"：不要凭感觉，动笔列两张小表——每个**条件**的取值集合、每个**判定**的取值集合，再逐条对定义。问"以下叙述错误的是"：错项三种造法——把"满足条件覆盖就一定满足判定覆盖"当对的（第三节那两条用例就是专打它的）、把"条件组合覆盖等于路径覆盖"当对的（W1–W4 那张表缺了 sacbd）、把强弱链里的判定和条件对调。

**考点② McCabe 环路复杂度，要算，阶段B。** 给边数点数就套 V(G) = E − N + 2；只给代码不给图，用"判定结点数 + 1"最快；图已画好就数区域验算。**考场规矩：算完必须换一种方法复核一遍**，公式法最容易在数边上出错。三个常见错法：把公式记反成 N − E + 2（记"**边**字在前，边比点多，多出来的再加 2"）；漏数判定的假分支或循环的回边；把"路径条数"和"环路复杂度"当成一个数。

**考点③ 测试阶段的依据文档，送分。** 四组对应见速记。最常互换的是单元和集成，抓住"集成测的是模块**之间**的接口，而接口是概要设计定的"。选项里出现"源程序代码"一律排除：代码是被测对象，不是判卷标准。

**考点④ 桩与驱动。** 本课最容易对调的两个词，对调了整题就废：**缺下面补桩（stub），缺上面补驱动（driver）**。

**考点⑤ 两把尺子的归属题。** 四份名单见速记。最爱设的陷阱是把代码走查塞进白盒选项里——它眼睛盯着代码，却不跑程序，是静态测试。

**考点⑥ 黑盒用例的好坏。** 无效等价类的用例**一次只许犯一个错**，同时踩两个无效类的选项就是"不是好的测试用例"。边界值题的错项造法有三种：全取内部值（一个边界都没碰到）、只取有效侧（缺界外的紧邻值）、取的不是紧邻值（跳开了真正的边界邻居）。

**考点⑦ 概念判断题。** 拿第一节那三句定论去筛："穷举测试可以发现所有错误""测试可以证明软件没有错误"一律是错项。再加一句反直觉的**缺陷聚集**：错误越多的程序段，改完之后残存的错误一般**还是多**（那一段本来就复杂），写成"修改后错误一般会非常少"就是错的。

2. **A、C**。动态测试要跑程序，边界值分析、逻辑覆盖（即各级覆盖）、基本路径都要跑；静态测试不跑程序，就是桌面检查、代码审查、代码走查这三样。B、D 各混进了一个动态方法。（题干选项写"桌面检查"，培训资料正文写"桌前检查"，是同一个词的两种译法，都要认得。）

3. **C**。用等价类的设计原则判：无效等价类的用例应"**仅覆盖一个尚未被覆盖的无效等价类**"。A 三项全合法，是有效类的用例；B 只有年龄 18 不合法，D 只有专业不合法，都只犯一个错，是合格的无效类用例；C 的年龄 18 和学历"大专"**同时**不合法，程序报了第一个错就返回，学历那条校验有没有写根本测不出来，所以不是好用例。

4. **D**。A 错在穷举不可行，B 错在缺陷聚集，C 错在测试只能证明有错、不能证明无错——三个错项正好是第一节三句定论的反面。D 对：路径覆盖最强、语句覆盖最弱，前者当然发现更多错误。

5. **B**。第一条判定 1 真（5000>1000 且有票）、扣减后 amt=4000 使判定 2 真，走 sacbed；第二条两个判定都假，走 sabd。两个判定的真假都取到了，判定覆盖成立，语句也全执行了，所以 A 对但不是最强。C 不成立：`rcpt==1` 两条都真、`lvl>=3` 两条都假，这两个条件各自只取到一个值；D 要求先满足条件覆盖，随之不成立。这是"**判定覆盖不蕴含条件覆盖**"的实例，和第 13 题正好反向对照。

6. **B、D**。做法是先把四条用例的两个判定真假和路径一次性算出来：①判定1真、判定2真，走 sacbed；②假、假，走 sabd；③真、假，走 sacbd；④假、真，走 sabed。第一空要两个判定各取到真和假，①②就够（真真 + 假假），A 只有一条不可能同时有真有假，C 的①③判定1 全真、D 的②④判定1 全假，都缺一半。第二空四条路径互不相同，缺一条都不叫路径覆盖，只能①②③④全上。

7. **B、B**。路径：①真→②真→A、①真→②假→B、①假→③真→C、①假→③假→D，共 **4** 条。环路复杂度三法互验：N = 9（入口、①②③、A、B、C、D、出口），E = 11（入口→①，①→②③，②→AB，③→CD，A/B/C/D→出口），V(G) = 11 − 9 + 2 = **4**；判定结点 3 个，3 + 1 = 4 ✓；闭合区域 3 个 + 外部 1 = 4 ✓。这张图上两个空的答案相同，是因为它是**树形分叉**：三个判定各占一层、走了这边就不走那边，叶子数正好等于判定数 + 1。第三节那段代码是**两个 if 顺序排**，两个判定的真假自由组合，路径 2² = 4 条而 V(G) = 3，两个空就不同了。**所以只能分别数，不能看见一个就抄给另一个。**

8. **B、B**。集成测试查的是模块**之间**的接口关系，接口正是概要设计文档定的；需求规格说明书是确认测试的依据，详细设计说明书是单元测试的依据，源程序是被测对象不是判卷标准。第二空：自顶向下先接上层，下层还没接上，要写**桩模块**冒充被调用者返回假结果；反过来自底向上缺的是上层调用者，要写驱动模块。

9. **C**。A、D 把主体错写成开发人员，B 把 Beta 的场地写成开发环境——主体都是用户，α 在开发环境、β 在实际使用环境。

10. V(G) = 判定结点数 + 1 = 5 + 1 = **6**，基本路径测试至少 **6** 个用例。**不能**直接拿 6 回答"共有几条路径"：V(G) 数的是线性无关的独立路径，全部可行路径通常更多（第三节那段代码 V(G)=3 而路径 4 条），必须照着图另外数。

11. 按培训资料口径取**两端值加界外紧邻两个**：**1、30、0、31**；教材口径再加界内紧邻的 **2 和 29**。"填 15"落在有效等价类正中间，和填 10、填 20 走同一段代码，只能算等价类的一条代表用例，碰不到边界错。

12. ①**错**，代码走查不运行程序，属于静态测试。②**错**，判定覆盖不蕴含条件覆盖（第三节第 1 级那两条用例里 `lvl>=3` 从没取真就是反例），反过来也不蕴含，两者互不包含。③**对**。④**对**，调试三步是确定错误位置、确定原因并改正、改正后进行回归测试。

13. 用例1 (6,5)：条件 `x>5` 真、`y<3` 假，判定 = 真‖假 = **真**；用例2 (1,1)：`x>5` 假、`y<3` 真，判定 = 假‖真 = **真**。两个条件各自的真假都取到了，**满足条件覆盖**；但判定两次都是真，假分支一次没走，**不满足判定覆盖**。这是 `||` 版本的反例，和第三节 `&&` 版本（判定恒假）互为对照：**无论 `&&` 还是 `||`，条件凑齐真假都不保证判定凑齐真假。**

## 速记

- 覆盖阶梯从弱到强：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径；培训资料只列五级，没有条件组合覆盖
- 条件真假齐 ≠ 判定真假齐：`&&` 一真一假仍为假、`||` 一真一假仍为真；条件覆盖与判定覆盖互不包含，路径覆盖也不含条件覆盖
- McCabe：V(G) = 边 − 点 + 2 = 判定结点数 + 1 = 闭合区域数 + 1；它是独立路径数，不等于全部路径数；> 10 难测难维护
- 依据文档：单元 ← 详细设计，集成 ← 概要设计，确认/配置项 ← SRS，系统 ← 用户需求或开发合同
- 自顶向下补桩、自底向上补驱动；三明治两头夹、工作量大
- 静态不跑程序（桌前检查／代码审查／代码走查，可发现 30%–70% 逻辑设计与编码错误）；黑盒白盒都是动态
- 黑盒四法：等价类（无效类一次只许犯一个错）、边界值（两端值 + 界外紧邻）、错误推测、因果图
- α 在开发方场地、β 在用户场地，主体都是用户；调试三法：蛮力、回溯、原因排除（演绎／归纳／二分）
