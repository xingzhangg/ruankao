# 23 · 面向对象：基础概念与设计原则（SOLID）

## 定位

面向对象那十来个名词（对象、类、抽象、封装、继承、多态、消息、接口、覆盖、重载、绑定）各自挡什么麻烦，以及用好这些能力的规矩（SOLID 等设计原则）。全课跟着报销系统的"审批"走：一个大 if-else 会在十处翻车，①～③靠三大特性（封装、继承、多态）补，④～⑩靠设计原则补。最少知识原则不在这条链上。全课无计算。

---

## 一、起点：一个大 if-else 的十个坑

```python
单据 = {"类型": "差旅", "金额": 6000, "状态": "草稿"}

def 审批(单据):
    if 单据["类型"] == "差旅":
        return "二级审批" if 单据["金额"] > 5000 else "一级审批"
    elif 单据["类型"] == "招待":
        return "二级审批" if 单据["金额"] > 2000 else "一级审批"
    elif 单据["类型"] == "办公":
        return "一级审批"
```

| 坑 | 表现 | 补丁 |
|---|---|---|
| ① | 谁都能写 `单据["状态"] = "已审批"`，绕开校验改数据 | 封装 |
| ② | 三种类型逻辑大段重复，改一处得改三处 | 继承 |
| ③ | 调用方先判断类型才知道怎么办，判断遍地开花 | 多态 |
| ④ | 加第四种类型（培训费）得撬开这个函数 | 开闭 |
| ⑤ | "实习生报销单"偷偷收窄规矩，老代码套上就崩 | 里氏替换 |
| ⑥ | 审批里写死 MySQL、钉钉，换一个就动业务代码 | 依赖倒置 |
| ⑦ | 一个类同时管算钱、存库、导 Excel | 单一责任 |
| ⑧ | 只管签字的主管被迫实现"打款""对账" | 接口分离 |
| ⑨ | 为复用"金额格式化"去继承工具类 | 合成复用 |
| ⑩ | 报表只用公共包里一个类，却得把整包拖进来 | 共同重用 / 共同封闭 |

抽象、消息、接口、绑定、覆盖、重载是描述前三样绕不开的词。

## 二、对象、类、抽象、封装（坑①）

病根是**数据（字典）和操作（函数）分家**，绑在一起就是对象。

| 术语 | 原话 |
|---|---|
| **对象** | 由**数据及其操作所构成的封装体**，是系统中用来**描述客观事物的一个实体**，是构成系统的一个基本单位；由**对象名、属性和方法** 3 部分组成 |
| **类** | 现实世界中**实体的形式化描述**，将该实体的属性（数据）和操作（函数）封装在一起。**对象是类的实例，类是对象的模板** |
| **封装** | **一种信息隐蔽技术**，将相关概念组成一个单元模块并通过一个名称引用；把数据和基于数据的操作封装成一个整体对象，**对数据的访问或修改只能通过对象对外提供的接口进行** |
| **抽象** | 通过**特定的实例抽取共同特征以后形成概念的过程**，强调主要特征，**忽略次要特征**；一个对象是一个实体的抽象，一个类是一组对象的抽象 |

张三那张 6000 元差旅单是对象：属性是类型和金额，方法是"算审批级别"。

```python
class 差旅单:
    def __init__(self, 金额):
        self._金额 = 金额          # 一根下划线：约定"外面别碰"
        self._状态 = "草稿"
    @property
    def 金额(self): return self._金额        # 只读出口
    def 审批级别(self):
        return "二级审批" if self._金额 > 5000 else "一级审批"

d = 差旅单(6000)      # d 是对象，差旅单 是类
d.审批级别()          # → '二级审批'
d.金额 = 999999       # → AttributeError：没有 setter，改不动（坑①堵上）
```

想改金额只能走 `修改金额()` 方法，方法里先查"是否已审过"。

**易混对 抽象 vs 封装**
- 判据｜抽象是造类时决定"留哪些特征"（管内容）；封装是类造好后决定"露哪些接口"（管边界）。抽象丢的是不相关的特性，封装藏的是不给外人看的实现。
- 例子｜从张三、李四身上只抽出"工号、姓名、部门"定义员工类＝抽象；员工类的余额设为私有、只能调 `扣款(金额)` 且先查余额够不够＝封装。

**类的三种角色**

| 角色 | 原话 | 例子 |
|---|---|---|
| **实体类** | 对象表示**现实世界中真实的实体**，如人、物 | 报销单、员工 |
| **接口类（边界类）** | 对象**为用户提供一种与系统合作交互的方式**；分人和系统两类：人的接口如显示屏、窗口、Web 窗体、对话框、菜单、列表框、条形码、二维码，系统接口涉及与其他系统收发数据 | 登录窗口、二维码 |
| **控制类** | 对象用来**控制活动流，充当协调者** | 审批流程引擎 |

例子｜客户扫二维码支付：客户是真实的人＝实体类；二维码是人机交互入口＝接口类。
⚠️ 这里的「接口」指系统边界、对外入口，和 Java 的 `interface`、和第四节"只说做什么"的接口都不是一回事，记成「边界类」。

## 三、继承、覆盖、重载、绑定（坑②）

差旅、招待、办公三类只有"二级线"不同，把相同部分提到上一层就是继承。

**原话｜继承**：表示**类之间的层次关系（父类与子类）**，使某类对象可以继承另外一类对象的特征；分**单继承**（只有一个直接父类，如 Java 的类）和**多继承**（多个直接父类，C++ 支持）。

```python
class 报销单:                        # 父类（超类、基类）
    def __init__(self, 金额): self._金额 = 金额
    def 二级线(self): raise NotImplementedError    # 留给子类填
    def 审批级别(self):
        return "二级审批" if self._金额 > self.二级线() else "一级审批"

class 差旅单(报销单):                 # 子类（派生类）
    def 二级线(self): return 5000
class 招待单(报销单):
    def 二级线(self): return 2000
class 办公单(报销单):
    def 二级线(self): return float("inf")   # 办公费永远只走一级
```

子类里的 `二级线` 就是**覆盖**（override，重写）——原话：子类在原有父类接口的基础上，用**适合于自己要求的实现去置换父类中的相应实现**，即在子类中重定义一个与父类**同名同参**的方法。**重载**则与父子类无关：函数**同名不同参数**。

**原话｜绑定**：把**过程调用和响应调用所需要执行的代码加以结合**的过程。一般语言中绑定**在编译时进行，叫静态绑定**；**动态绑定在运行时进行**，调用和代码的结合直到调用发生时才进行。

```java
class Bill { String type() { return "通用单据"; } }
class TravelBill extends Bill { @Override String type() { return "差旅报销单"; } }

static String route(Bill b)       { return "route(Bill)"; }        // ┐同名不同参
static String route(TravelBill t) { return "route(TravelBill)"; }  // ┘重载

Bill b = new TravelBill();      // 声明类型 Bill，实际对象 TravelBill
b.type();                       // "差旅报销单"  ← 覆盖看实际对象
route(b);                       // "route(Bill)" ← 重载看声明类型
route((TravelBill) b);          // "route(TravelBill)"
```

| | 覆盖 override | 重载 overload |
|---|---|---|
| 出现在哪 | **子类与父类之间** | **同一个类里**，与父子类无关 |
| 参数表 | **同名同参** | **同名不同参**（类型、个数或类型顺序不同） |
| 何时定下 | **运行时**按对象实际类型 | **编译时**按参数表 |
| 绑定 | 动态绑定 | 静态绑定 |

## 四、多态、消息、接口（坑③）

**原话｜多态**：**不同的对象收到同一个消息时产生完全不同的结果**。**多态由继承机制支持，将通用消息放在抽象层，具体不同的功能实现放在低层。**

```python
for 单 in [差旅单(6000), 招待单(6000), 办公单(6000)]:
    print(单.审批级别())     # 二级审批 / 二级审批 / 一级审批
```

通用消息＝父类的 `审批级别()`，低层实现＝各子类的 `二级线()`，调用方一个 if 都不用写。

| 术语 | 原话 | 要点 |
|---|---|---|
| **消息** | 体现**对象间的交互**，通过它向目标对象发送操作请求 | 不同类的对象之间靠消息通信；消息一定有**接收者**，接收者可换，同一句话才有不同回答 |
| **接口** | 描述对操作规范的说明，**只说明操作应该做什么**，并没有定义操作如何做 | 如父类只写名字不写实现的 `二级线()`；与第二节的边界类无关 |

**多态四种形式**

| 形式 | 定义口径 | 例子 |
|---|---|---|
| **参数多态** | 不同类型参数多种结构类型 | `max([3,9,2])` 得 9，`max(["a","z"])` 得 `"z"`；Java 泛型 `List<T>`、C++ 模板 |
| **包含多态** | 父子类关系 | 三张单子的 `审批级别()` 各答各的 |
| **过载多态** | 类似重载，一个名字不同含义 | `1+2` 得 3、`"报"+"销"` 得 `"报销"`（含方法重载、运算符重载） |
| **强制多态** | 强制类型转换 | `1 + 2.5` 得 `3.5`（int 先转 float）；不转则 `"1" + 1` 报错 |

**易混对 过载多态 vs 包含多态**
- 判据｜过载看**名字**（一名多义，编译期定）；包含看**对象**（一消息多果，运行期定）。
- 例子｜同一个 `+` 对数字求和、对字符串拼接＝过载；同一个 `审批级别()` 对差旅单、办公单答案不同＝包含。

## 五、设计原则（坑④～⑩）

三大特性是能力，设计原则是用这些能力的规矩，都在回答：**需求一定会变，怎么让变化的代价最小**。**SOLID**＝单一责任 SRP、开闭 OCP、里氏替换 LSP、接口分离 ISP、依赖倒置 DIP 的首字母；另补合成复用、共同重用、共同封闭、最少知识四条。每条的定义句本身就是判据。

| 原则 | 原话（判据） | 报销系统里 |
|---|---|---|
| **开闭** ④ | 软件实体（类、模块、函数等）应该**可以扩展（开放），但不可修改（封闭）** | 加培训费只写 `class 培训单(报销单): def 二级线(self): return 3000`，老类一字不动 |
| **里氏替换** ⑤ | **子类必须能够替换掉他们的基类型**，任何父类可出现的地方都可以用子类实例赋给父类型的引用；**单向**，父类实例顶不了子类（是鸟不一定是鹦鹉） | 见下方代码 |
| **依赖倒置** ⑥ | **抽象不应该依赖于细节，细节应该依赖于抽象**；**高层模块不应该依赖于低层模块，二者都应该依赖于抽象**；针对接口编程，不针对实现编程 | 审批服务只认"通知渠道"抽象，具体渠道从外面传入 |
| **单一责任** ⑦ | 就一个类而言，应该**仅有一个引起它变化的原因**，**让一个类只做一种类型责任** | 报销单拆成 报销单（业务）+ 仓储（存储）+ 导出器（报表） |
| **接口分离** ⑧ | **不应该强迫客户依赖于它们不用的方法**；接口属于客户，不属于它所在的类层次结构；即依赖于抽象，不要依赖于具体，同时在抽象级别不应该有对于细节的依赖 | 胖接口 `审批流程{签字();打款();对账();}` 拆成 `可签字`、`可打款`、`可对账` |
| **合成复用**（合成聚合复用） ⑨ | **优先使用组合、聚合，而不是继承，来达到复用的目的** | 报销单**持有**一个金额工具，而不是继承它 |
| **共同重用** ⑩ | 一个包里的类应当一起被重用，**重用了包中的一个类，就要重用包中的所有类** | 别把用不着的类塞进同一个包 |
| **共同封闭** ⑩ | 包中的类应对**同一类变化**共同封闭，一个变化若影响某包，就影响该包所有类，而不影响其他包 | 见下方易混对 |
| **最少知识**（迪米特法则） | 一个对象应当对其他对象有尽可能少的了解，只和直接朋友说话（"不和陌生人说话"） | 不对应十个坑 |

里氏替换的反例（老代码 `批一批` 一行没改，被换进来的子类坑死）：

```python
class 审批人:
    def 可审(self, 金额): return 金额 > 0                  # 父类：正数金额都能审
class 实习审批人(审批人):
    def 可审(self, 金额):
        if 金额 > 1000: raise ValueError("超出实习生权限")   # 收窄 + 抛父类没声明的异常
        return True

def 批一批(p, 金额): return p.可审(金额)
批一批(审批人(), 5000)        # → True
批一批(实习审批人(), 5000)     # → 抛 ValueError，老流程崩了
```

子类**收窄参数取值范围、抛出父类没声明的异常、把父类的承诺打折**，都是违反里氏替换的典型样子；改法是实习审批人单独成类，不硬认父类。

依赖倒置的改法（坑⑥原样：`self.渠道 = 钉钉客户端()` 写死在业务里）：

```python
class 通知渠道:                                   # 抽象：只规定"要能发"
    def 发(self, 文本): raise NotImplementedError
class 邮件(通知渠道):
    def 发(self, 文本): return "MAIL:" + 文本
class 钉钉(通知渠道):
    def 发(self, 文本): return "DING:" + 文本

class 审批服务:                                    # 高层模块，只认抽象
    def __init__(self, 渠道): self.渠道 = 渠道     # 外面塞进来，自己不 new
    def 通过(self): return self.渠道.发("审批通过")

审批服务(邮件()).通过()      # → 'MAIL:审批通过'
审批服务(钉钉()).通过()      # → 'DING:审批通过'，审批服务一字没动
```

**易混对 开闭 vs 里氏替换**
- 判据｜开闭管"加新东西时改不改老代码"；里氏替换管"子类替父类站岗顶不顶得住"。
- 例子｜加培训单要撬开 if-else＝违反开闭；老代码不动、换进实习审批人就抛异常＝违反里氏替换。

**易混对 单一责任 vs 接口分离**
- 判据｜单一责任拆**类**，按"有几种人会来提改动"拆（维护者角度，两种以上就拆）；接口分离拆**接口**，按"谁在用它"拆（调用者角度）。
- 例子｜报销单因政策、数据库、Excel 模板三种原因都要改＝单一责任；主管只签字却得实现打款、对账＝接口分离。

**易混对 接口分离 vs 依赖倒置**
- 判据｜接口分离的定义后半句也写着"依赖于抽象，不要依赖于具体"，只认前半句：出现"不强迫客户依赖不用的方法""接口属于客户"＝接口分离；出现"抽象不依赖细节""高层不依赖低层""针对接口编程"＝依赖倒置。依赖倒置的动作判据是"高层要不要自己 new 出低层具体类"。
- 例子｜`审批服务` 里自己 `new 钉钉客户端()`＝违反依赖倒置；胖接口逼主管写空的 `打款()`＝违反接口分离。

**易混对 合成复用 vs 继承**
- 判据｜继承答"我是一种什么"（is-a），组合答"我有一个什么"（has-a）。组合与聚合都是"甲里装着一个乙"，细分归讲义 25。
- 例子｜报销单继承金额工具类：工具类全部方法挂到报销单上对外暴露，且报销单不是一种金额工具；改成报销单持有一个金额工具，复用照拿、方法不外泄。

**易混对 共同重用 vs 共同封闭**（都管**包**——一组类打包发布的单位——而不是单个类）
- 判据｜讲"重用"＝共同重用；讲"变化/封闭"＝共同封闭。共同封闭看"这个包会被几种原因牵动"，不止一种就没封好。
- 例子｜报销政策一变，报销单、审批规则、单据校验都得改，放一个包里改动被关在包内＝共同封闭的正例；把报销单和邮件模板塞一个包，政策变、邮件样式变都要动它＝反例，应拆成两个包。

## 速记

- 对象＝数据+操作的封装体（对象名/属性/方法）；类是模板、对象是实例；实体类是人和物、**边界类（接口类）**是交互入口、控制类是流程协调者
- 抽象管"留哪些特征"（造类前），封装管"露哪些接口"（造类后）；继承是父子层次，分单继承、多继承
- 多态＝同一消息不同结果，由继承支持；消息＝对象间交互手段，有接收者；**接口（只声明不实现）**只说做什么——和边界类不是一回事
- 覆盖：父子同名同参、运行时定、动态绑定；重载：同类同名不同参、编译时定、静态绑定
- 多态四形式：参数（一段代码多种类型）、包含（父子类）、过载（一名多义）、强制（类型转换）
- SOLID：一个原因改＝单一责任、可扩展不可改＝开闭、子类替父类＝里氏替换、抽象不依赖细节＝依赖倒置、不强迫客户依赖不用的方法＝接口分离
- 补四条：组合优先于继承＝合成复用；重用一个就重用整包＝共同重用；同类变化封闭在包内＝共同封闭；了解越少越好＝最少知识（迪米特）
- 接口分离定义后半句也写"依赖于抽象"，只认前半句；重载在编译时定，不是运行时
