# 15 · 软件工程：软件生存周期与过程模型

> 真题：瀑布选型 2012上、螺旋判断 2017上、结构化方法判断 2014下、Scrum 2016下（培训资料收录，年份 2026-09-06 审核核实）；开发模型对比 2021上/2022下；系统分析产出物一题年份待核实｜无计算｜未讲，2026-09-05 按新讲法重写，09-06 按两轮审核意见修订

---

## 定位

这一课要分清三组东西：**一辈子分几段**（生存周期，两套口径）、**这几段按什么节奏走**（过程模型，八个）、**分析设计用什么思路**（开发方法，五类）。三节各管一组。节奏和思路是正交的——同一个瀑布里，可以用结构化，也可以用面向对象。

---

## 开讲：这一课全是辨析题

卷面几乎不问"什么是瀑布模型"，只问"给这么一句话，选哪个"。所以每节都先给一张**反查表**（题干里出现什么词 → 答什么），再把最容易二选一犯难的几对单拎出来。看不懂某个词再回头找它的解释，不必从头顺读。

### 一、软件的一辈子分几段：生存周期

**反查表 · 给一个活动或产物，问它落在哪个阶段**

| 题干里出现 | 软件生存周期（七阶段） | 信息系统口径 |
|---|---|---|
| 值不值得做、花多少钱多久 | 可行性分析与项目开发计划 | 系统规划 |
| 写需求规格说明书、确定"做什么"、产出**逻辑模型**（谁给谁、按什么规则，不涉及用什么技术） | 需求分析 | 系统分析（逻辑设计） |
| 划分模块并定义接口 | 概要设计 | 系统设计之总体设计 |
| 设计模块内部的算法和数据结构 | 详细设计 | 系统设计之详细设计 |
| 翻译成源程序 | 编码 | 系统实施 |
| **找错**（不是证明没错） | 测试 | 系统实施 |
| 上线后修错、适配、增强——**持续最久、花钱最多** | 维护 | 系统运行和维护 |
| 系统下线、数据归档 | —— | **消亡**（属四大阶段，不在五阶段里） |

两套口径**只有三处对不齐**，记住这三处就够：系统设计劈成总体、详细两行；系统实施占了编码、测试两行；消亡只属于四大阶段。第三列去掉消亡、去掉重复，**剩下的正好是五阶段**：系统规划、系统分析、系统设计、系统实施、系统运行和维护。

还有四行只在信息系统口径里出现，也考：

| 题干里出现 | 答 |
|---|---|
| 对组织现状做**初步调查** | 系统规划 |
| 对现行系统做**详细调查** | 系统分析 |
| 把逻辑模型落成**物理模型**（MySQL 表和接口上的技术方案） | 系统设计，所以它又叫**物理设计阶段** |
| 设备购置安装调试、程序编写调试、人员培训、数据文件转换、系统调试与转换（多项任务同时展开，要精心安排） | **系统实施** |

**反查表 · 问工作产品**

| 题干里出现 | 答 |
|---|---|
| 可行性阶段结束 | 可行性研究报告、系统设计任务书 |
| 需求阶段结束 | 软件需求规格说明书（信息系统口径叫**系统说明书**） |
| 概要设计 / 详细设计结束 | 概要设计说明书 / 详细设计说明书 |
| 编码结束 | 源程序 |
| 测试阶段 | 测试报告；信息系统口径另有实施进展报告、系统测试分析报告 |
| **系统分析阶段结束后的工作产品** | **系统方案建议书** |
| **系统测试完成后的工作产品** | **操作手册**——手册要等系统定型才写得出来；其余选项（验收测试计划、测试标准、系统测试计划）都是测试**前**就该定好的 |

**易混对① 分析 vs 设计**

- 判据｜**分析回答"做什么"，设计回答"怎么做"**。两套口径同一条分水岭。
- 例子｜"报销单经过谁、按什么规则流转"＝分析（逻辑模型）；"存成哪几张 MySQL 表"＝设计（物理模型）。把"按什么规则流转"换成"用哪个字段存状态"，答案就从分析变成设计。
- 错法｜教材说系统分析是整个建设的关键，也是信息系统建设与一般工程项目的重要区别所在——这句话常被搬去形容系统设计。

**易混对② 系统说明书 vs 系统方案建议书**

- 判据｜**看写给谁**。系统说明书写给开发方看——"这个系统要做成什么样"；**系统方案建议书写给管理层看**——"有哪几个候选方案、建议选哪个"。两者**同属分析阶段**，不是前后两个阶段的产物。
- 例子｜"报销单经过谁、按什么规则流转，共八个功能点"＝系统说明书；"方案一自研六个月、方案二采购两个月，建议采购"＝系统方案建议书。
- 错法｜把系统方案建议书当成系统说明书的别名。它出自另一套方法（Whitten 的 FAST）。真题问"系统分析阶段结束后得到的工作产品"时，用阶段归属排除即可——系统设计规格说明属设计阶段、程序规格说明属详细设计或编码、单元测试数据属测试阶段，只剩它。

**易混对③ 四大阶段 vs 五阶段**

- 判据｜四大阶段是**立项、开发、运维、消亡**；五阶段是**系统规划、系统分析、系统设计、系统实施、系统运行和维护**（上表第三列去掉消亡再去重，三处对不齐的地方已在表下写明）。
- 错法｜在五阶段里找"消亡"。它只在四大阶段里。

其余认名即可：**软件工程三要素**＝**过程**（第二节）、**方法**（第三节）、**工具**（画图建模的软件，本课不展开）；六十年代项目普遍超支、延期、改不动称**软件危机**，第一剂药就是**分阶段**——每阶段有明确产出物，做完评审再进下一阶段。

> 考试这样问：给一个活动（写需求规格说明书／划分模块并定义接口／设计模块内部算法），问它落在哪个阶段；或问哪个阶段花钱最多。

#### 深入 · Boehm 七条基本原理

用分阶段的生命周期计划严格管理、坚持阶段评审、实行严格的产品控制、采用现代程序设计技术、结果应能清楚地审查、开发小组人员少而精、承认不断改进软件工程实践的必要性。偶尔点名，认得即可。

### 二、按什么节奏走：过程模型

八个模型只回答三件事：**需求定不下来**（原型、螺旋）、**用户等不及用**（增量）、**测试来不及**（V）；剩下三个是换了实现思路——喷泉＝面向对象、CBSD＝买现成、形式化＝数学证明。瀑布是原点，其余七个都是在补它的某一条。

**反查表 · 上午题几乎只考这一列**

| 题干里出现 | 答 |
|---|---|
| **文档驱动**；阶段不回头；**需求明确、稳定**、工期与成本卡死 | **瀑布模型** |
| 用户说不清要什么；先造个能点的给他看；对需求动态响应、逐步纳入 | **原型化模型** |
| 每次交付一个**可独立运行**的部分；**优先级最高的服务最先交付** | **增量模型** |
| **风险分析**；四个象限；**庞大复杂、高风险**的系统 | **螺旋模型** |
| 开发阶段与测试级别**一一对应**；测试尽早准备 | **V 模型** |
| 面向对象；阶段之间**无间隙**、可交叠；以用户需求为动力，以对象作为驱动 | **喷泉模型** |
| 买现成构件拼装；构件库供其他系统复用；**复用性强** | **基于构件的开发模型 CBSD** |
| 建立在严格数学基础上；生成形式化的数学规格说明，再证明代码满足它（比如把"两台飞控计算机的输出必须在 5000 微秒内一致"写成数学规则）；航天核电 | **形式化方法模型** |

四条补充口径，卷面照抄过：

- **瀑布的规矩四条**：从上一项活动接受成果作为输入、完成本项活动、把成果作为输出传给下一项、对成果评审通过才往下走，否则退回前面。
- **螺旋每圈四件事**：制订计划、风险分析、实施工程、客户评估。它把原型的迭代和瀑布的系统化结合起来，开发是一系列增量发布；代价是依赖有经验的人、成本高，小项目不划算。**它的圈里也包含维护**——维护相当于再转一圈，所以螺旋模型下「维护与开发没有本质区别」。
- **原型的两头要求**：必须**实际可行、有最终系统的基本特征**（不然看不出问题），又要**构造方便、快速、造价低**（不然扔不起）。
- **增量的缺点**：不从整体规划各模块，**不利于模块划分**，难点在怎么把需求切成增量。

**易混对① 瀑布 vs V**

- 判据｜**题干提到测试、质量、验证才选 V；只说需求明确、工期紧，选瀑布。**
- 例子｜"需求已冻结，三个月内交付"→ 瀑布。把它改成"需求已冻结，要求测试用例随设计同步产出"→ V。
- 错法｜两个都写着"需求明确"，光看这四个字分不开。

**易混对② 原型 vs 增量**

- 判据｜**抛弃式原型只演示、不上线**；增量的每一块不同——**每个增量都是可独立运行的作品**。（演化式原型是例外，它会长成产品，见易混对⑤。）
- 例子｜三个页面能点跳转但不存数据＝原型；先上线"提单＋审批"、员工真的开始用＝增量。把"不存数据"改成"真的入库并上线"，答案就从原型变成增量。
- 错法｜两者都"先交一部分"。分界在这一部分能不能直接拿去用。

**易混对③ 原型 vs 螺旋**

- 判据｜**原型治"需求不清"，螺旋治"风险大"；螺旋＝增量的迭代 + 每圈先做风险分析。**
- 例子｜"老板说不清要什么"→ 原型；"老数据可能迁不出来，先做实验验证再投钱"→ 螺旋。
- 错法｜螺旋每圈也造原型，见"原型"二字就抢答。

**易混对④ 水平原型 vs 垂直原型**（按是否实现功能分）

- 判据｜**水平原型只做导航不做深**（又叫行为原型）；**垂直原型只做一条线但做到底**（又叫结构化原型）。
- 例子｜菜单点得动、点进去全是空页＝水平；只做"提单"一条路但真的能存进库＝垂直。
- 错法｜"结构化原型"和第三节的结构化方法**无关**，它指的是结构做完整。

**易混对⑤ 抛弃式 vs 演化式**（按最终结果分）

- 判据｜用完扔掉重写＝抛弃式；直接长成产品＝演化式。

**V 模型的一一对应**（教材口径，考的就是这张图）

```
 开发↓                              ↑测试
用户需求 ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ 验收测试
  需求分析 ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ 系统测试
    概要设计 ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ 集成测试
      详细设计 ┄┄┄┄┄┄┄┄┄┄┄ 单元测试
            编码（底点）
```

读法：沿左臂**自上而下**开发，触底编码，再沿右臂**自下而上**测试；横的虚线只表示"**谁验谁**"，不表示先后。

**拆得多细，就验得多细**——右边每一级验的都是左边同高度那一格定下来的东西：

- **单元测试**测一个函数或模块 ← 详细设计定的是模块内部怎么写
- **集成测试**测模块拼起来接口对不对 ← 概要设计定的是模块怎么划、接口长什么样
- **系统测试**测整个系统是否满足需求 ← 需求分析定的是系统整体该做什么
- **验收测试**由用户按自己的业务确认能不能用 ← 用户需求是业务上的话

V 模型不改瀑布的节奏，只把测试分成四级，好处是各级测试的计划和用例可以在对应阶段就准备。它补的只是测试**准备**太晚，**执行仍在最后**——"测试介入晚"仍是它公认的短板，本质还是线性的，同样用于需求明确、变更不频繁的项目。

⚠️ **有一套培训资料把整条对应关系往下挪了一格**（写成"单元针对编码、集成针对详细设计、系统针对概要设计"），那是把编码也算成一个测试级别的画法。本讲义按教材口径；万一题目选项整体差一格，先看它有没有给编码也配一级测试。

> 考试这样问：给一组"开发阶段—测试级别"的对应，问哪一组不正确。

#### 深入 · V 模型的另一套口径：测试依据哪份文档

单元测试依据详细设计说明书、集成测试依据概要设计说明书、系统测试依据需求规格说明书（讲义 17 展开）。这套和上面那张 V 字图**是一致的**——同一层的产物与同一层的文档本来就是一回事，一个问"验的是哪一层"，一个问"手里拿的是哪份文件"。

### 三、再往上一层：开发方法

节奏和思路是正交的：同样走瀑布，设计阶段可以画数据流图把系统拆成模块（结构化），也可以画类图找对象（面向对象）。敏捷和 RUP 是"节奏＋思路"打包的完整方法论，两边都沾，一并放这里。

**反查表**

| 题干里出现 | 答 |
|---|---|
| **自顶向下、逐步求精、模块化**；数据流图；又叫生命周期法 | **结构化方法** |
| 用例、类图、对象互相发消息 | **面向对象方法** |
| 以用户为中心；造个东西给你点，代替写文档问你 | **原型化方法** |
| 以人为核心、迭代、循序渐进；拥抱变化 | **敏捷开发** |
| **分派任务和责任的纪律化方法**；通用过程框架 | **统一过程 RUP** |

#### 三法：结构化、面向对象、原型化

**反查表 · 结构化方法的四句定论**（2014 下真题四个选项就是这四句，问"哪句不正确"）

| 题干里出现 | 判 |
|---|---|
| 总的指导思想是**自顶向下，逐层分解** | 对 |
| **基本原则是功能的分解与抽象** | 对 |
| **特别适合于数据处理领域**的项目 | 对 |
| 与面向对象方法相比，更适合于**大规模、特别复杂**的项目 | **错**。反了——面向对象才更适合复杂项目 |

- **组成**：**结构化分析 SA、结构化设计 SD、结构化程序设计 SP**；因为严格按生存周期一个阶段一个阶段走，又叫**生命周期法**。精髓是**自顶向下、逐步求精和模块化设计**。
- **四个特点**：开发目标清晰化（用户第一）、开发工作阶段化（每阶段审查）、开发文档规范化、设计方法结构化（分析设计自顶向下分解，实现时自底向上一块块拼）。
- **三个不足**：**开发周期长**（要走完全部阶段用户才能用）、**难以适应需求变化**、**很少考虑数据结构**。
- **常用工具**：**数据流图**（画数据往哪流，讲义 21）、**数据字典**（给图上每个名字登记含义）、**结构化语言**（用受限的中文写处理逻辑）、**判定表**与**判定树**（把多条件规则排成表或树）。

**面向对象方法**的特点每条都有原因：

- **复用性更好**——"审批人"这个类可以原样搬到采购系统去，关键是建立统一的用例模型和分析模型
- 分析、设计、实现三阶段**没有缝隙**——从头到尾用的都是"对象/类"这一套概念，前一阶段没做细后一阶段可以补
- 普遍适用于各类系统

三条不足：必须依靠一定的面向对象技术支持、**在大型项目的开发上具有一定的局限性**、**不能涉足系统分析以前的环节**（它只回答"有哪些对象"，答不了"这个系统值不值得做"）。

**易混对① 结构化 vs 面向对象**

- 判据｜结构化盯**功能怎么拆**，面向对象盯**谁带着数据和动作**。
- 例子｜同一个报销系统："先画数据流图，把系统拆成提单、审批、打款三块"＝结构化；"先找出报销单、审批人这些类，各自带着自己的数据和动作"＝面向对象。把"画数据流图拆模块"换成"找类"，答案就翻过来。结构化**很少考虑数据结构**的后果也在这里——报销单要加附件字段时改得很痛，而面向对象里字段长在"报销单"这个类身上，改一处即可。
- 错法｜真题判错句"结构化方法与面向对象方法相比更适合于大规模、特别复杂的项目"——**反了**，面向对象比结构化更能对付复杂系统。这和上面"面向对象在大型项目上有局限性"不矛盾：那条说的是它自身也不够，所以大型系统常常**先用结构化自顶向下整体划分，再自底向上用面向对象开发**，两者相互依存（讲义 23、24 展开）。

**易混对② 原型化模型 vs 原型化方法**（第二节 vs 第三节，同名不同物）

- 判据｜**模型**说的是整个项目以"造原型、改、再造"为主循环；**方法**说的是需求分析这一步用"造个东西给你点"代替"写文档问你"，**任何节奏里都能用**。
- 例子｜项目走瀑布，需求分析那一格照样可以用原型化方法——这时它是方法不是模型。
- 错法｜见"原型"二字就往第二节的模型上套。

原型化方法的优点是周期短、成本和风险低、用户容易理解和接受；两个不足是**对开发环境要求高**（得有能快速搭页面的工具）、**对管理水平要求高**（不管住会无限改下去）。五步流程见本节末的深入块，跳过不影响后面。它**不是完整的方法论体系**，必须和其他方法结合使用，适合**需求不明确、分析层面难度大而技术层面难度不大**的系统。

敏捷针对的是结构化、面向对象、RUP 共同的另一类毛病——**流程本身太重**，文档和计划先行，改一次要动一摞文档。

#### 敏捷家族

**敏捷宣言四句**：**个体和交互胜过过程和工具；可以工作的软件胜过面面俱到的文档；客户合作胜过合同谈判；响应变化胜过遵循计划**。敏捷强调团队与业务专家紧密协作、面对面沟通胜过文档、频繁交付。

**反查表 · 敏捷家族**

| 认它的关键词 | 答 |
|---|---|
| 四个价值观**沟通、简单性、反馈、勇气**；**测试先行**（先写测试再写代码）；初期不写很多文档 | **极限编程 XP** |
| **30 天一次迭代叫"冲刺"**（实际 1–4 周都有，认"固定长度迭代"即可）；按需求优先级实现；多个**自组织**小组并行递增 | **并列争球法 Scrum** |
| 不给具体实践，从组织和管理层面讲开发为什么要**适应** | **自适应开发 ASD** |
| **每个不同的项目需要一套不同的策略、约定和方法论** | **水晶方法 Crystal** |
| 针对**中小型项目**、模型驱动的快速迭代，适合需求经常变动 | **特性驱动开发 FDD** |

**反查表 · Scrum 三角色**

| 题干里出现 | 答 |
|---|---|
| 定做什么、排优先级、管产品待办列表 | **产品负责人** |
| 管流程、清障碍、保证团队按 Scrum 走 | **Scrum Master** |
| 定怎么做、自己认领任务 | **开发团队** |
| 选项里出现"项目经理" | Scrum **没有这个角色** |

**易混对③ XP 的价值观 vs 实践**

- 判据｜**价值观只有四个、是封闭清单，其余一律是实践。**
- 例子｜结对编程、小型发布、持续集成、现场客户（用户坐在团队里随时问）都是实践。其中**结对编程**常单独考：一人写、一人在旁审查代码，共同对代码负责。
- 错法｜四个价值观里混进"效率""持续集成"。

#### 统一过程 RUP

**反查表 · RUP 四阶段**

| 干什么 | 阶段 | 里程碑 |
|---|---|---|
| 定范围、算值不值得做 | 初始 Inception | 生命周期目标 |
| 分几层、用什么框架、模块怎么通信——**建立体系结构基线**；另有分析问题域、编制项目计划、**淘汰最高风险的元素** | **细化 Elaboration** | 生命周期体系结构 |
| 往骨架上挂功能、集成、测试 | 构建 Construction | 初始运作能力 |
| 移交用户、beta 测试、培训 | 交付 Transition | 产品发布 |

RUP 三个显著特点：**用例驱动**（拿"员工提交报销单"这类用例来排任务、验收）、**以体系结构为中心**（先把骨架搭起来）、**迭代和增量**。每阶段结束有技术评审和一个里程碑，里程碑是阶段末的检查点。目标是在可预见的日程和预算内交付高质量产品。"体系结构基线在细化阶段建立"这一句最常考。

> 考试这样问：给一段描述认是敏捷家族里的哪一个；或在 XP 的四个价值观里混进"效率""持续集成"这类不是价值观的项；或问"建立体系结构基线、淘汰最高风险元素"在哪个阶段、里程碑叫什么。

其余认名即可：能力成熟度模型 CMM/CMMI 放在讲义 20。先记一句——CMM 五级是"初始、可重复、已定义、已管理、优化"，CMMI 阶段式五级是"初始、已管理、已定义、定量管理、优化"，**没有"可重复级"**，两套名字的差别是常考点。

#### 深入 · 原型化方法的五步流程

确定用户基本需求 → 设计系统初始原型 → 试用和评价原型 → 不满意就修改完善再试用 → 满意后整理原型并提供文档。卷面未见考过，认得即可。

## 速记

- 七阶段：可行性 → 需求 → 概要设计 → 详细设计 → 编码 → 测试 → 维护；分析定"做什么"（逻辑模型），设计定"怎么做"（物理模型）；维护最久最贵；消亡只在四大阶段里
- 选型看题干怕什么：说不清＝原型、要先用上＝增量、风险驱动＝螺旋、测试早准备＝V、需求已定＝瀑布、无缝迭代＝喷泉、买现成构件＝CBSD、数学证明＝形式化；瀑布与 V 二选一看题干提不提测试
- 螺旋四象限：制订计划 → 风险分析 → 实施工程 → 客户评估
- V 模型（教材口径）：**单元对详细设计、集成对概要设计、系统对需求分析、验收对用户需求**，编码在 V 的底点；问"依据哪份文档"是同一条链
- 增量每块可独立运行，原型只是演示；原型分抛弃式/演化式、水平/垂直
- 结构化：自顶向下逐步求精模块化；周期长、难适应变化、少考虑数据结构。面向对象：复用好、阶段无缝、更适合复杂系统；不能涉足分析之前
- 敏捷宣言四句；XP 沟通简单性反馈勇气、测试先行；Scrum 固定冲刺三角色；水晶每项目一套方法；FDD 中小型；ASD 适应性
- RUP：用例驱动、以体系结构为中心、迭代增量；初细构交；细化定架构基线
