## 定位

**这一课回答**：报销系统跑起来之后，对象之间怎么打交道——谁通知谁、请求交给谁处理、行为怎么随情况自动切换；行为型 11 个模式各自在收拾哪一种烂摊子。

## 开讲：报销系统跑起来了，麻烦才刚开始

还是讲义 15、16、23 那套内部报销系统。讲义 23 结束时，"审批"已经从一个大 if-else 拆成了对象和类，SOLID 那几条规矩也立好了。可规矩只说了"该往哪个方向拆"，没说"具体拆成什么形状"。**设计模式**就是把这个形状固定下来的名字——前人把"反复出现的同一类设计难题 + 已被验证过的解法"整理成 23 个条目，你遇到同样的难题，直接照着搭就行，不必自己现想。这一课讲其中的**行为型**11 个：它们管的都是**跑起来之后对象之间怎么打交道**，而不是对象怎么被造出来（创建型）、也不是对象怎么拼装成更大的结构（结构型），后两组共 12 个在讲义 28。

系统真的上线了，七件麻烦事一件件冒出来。**下面七节就是它们各自的解法，一一对应**：

- ① 财务隔三个月改一次审批规则：这个月按金额分级，下个月招待费一律二级，年底又改成按部门比例。每改一次都要撬开 `审批级别()` 这个方法。
- ② 有些行为压根不是"外面挑哪套规则"，而是"单子自己走到哪一步了"——同一个"提交"按钮，草稿状态下是送审，待审批状态下应该拒绝，已通过状态下更不该响应。
- ③ 一笔报销要顺着组长 → 经理 → 财务总监逐级往上审，谁批取决于金额，而且这条链的长短随公司组织架构变。写成 if-else 是一层套一层。
- ④ 主管批错了要能撤回；月底要批量审批，得先排队；审计要求每一次审批动作都留痕。可"调一次方法"这件事转瞬即逝，存不下来。
- ⑤ 单子状态一变，短信要发、台账要记、报表要刷、预算要扣。每接一个下游，就得回来改一次"审批通过"这段代码。
- ⑥ 提单模块、审批模块、预算模块、财务模块互相直接调用，四个模块两两认识，成了一张网。**耦合**（改 A 就得跟着改 B 的牵连程度）高到不敢动任何一个。
- ⑦ 月底财务要"按部门统计"，季度要"导出税务报表"，明年还要"算碳排放"。每加一种统计，就得往报销单类、明细类、附件类里各塞一个方法，这三个类越来越胖。

### 一、审批规则老是变：策略模式（治①）

最朴素的写法，是把三套规则写成 `if 规则名 == "按金额": ... elif 规则名 == "一律二级": ...`。问题是新增第四套规则必须改这个方法，而这个方法是全系统都在调的。

**策略模式**的做法：把每一套算法各做成一个类，让它们长着同一个方法名，用哪个由**外面**塞进来。转录本给的定义是"**定义一系列算法，把它们一个个封装起来，并且使它们之间可相互替换，从而让算法可以独立于使用它的用户而变化**"，记忆关键字是"**算法替换**"。

```python
class 按比例:
    def 级别(self, 金额): return "二级审批" if 金额 > 5000 else "一级审批"
class 一律二级:
    def 级别(self, 金额): return "二级审批"

class 报销单:
    def __init__(self, 金额, 规则):
        self.金额, self.规则 = 金额, 规则     # ← 规则由外部塞进来，这一行是策略的命根子
    def 审批级别(self): return self.规则.级别(self.金额)

报销单(6000, 按比例()).审批级别()     # → 二级审批
报销单(100,  按比例()).审批级别()     # → 一级审批
报销单(100,  一律二级()).审批级别()   # → 二级审批
```

两个细节考试会问。第一，`self.规则` 这个字段必须声明成**抽象类型**（Python 里靠约定，Java 里就是接口名）——写死成 `按比例` 就换不掉了，"可相互替换"这五个字就没了。第二，`报销单` 这个持有策略、把活委托出去的角色叫**上下文（Context）**，它不关心算法怎么算，只负责把请求转发给当前那个策略对象。

### 二、不是外面挑，是自己走到哪一步：状态模式（治②）

**先别往下看，猜一个**：报销单在"草稿 / 待审批 / 已通过"之间流转，同一个"提交"操作在三个状态下行为完全不同——你会用刚讲的策略模式吗？

多数人答"会"，因为看起来一模一样：都是把一坨 if-else 拆成几个类，都是让主对象持有其中一个、把活委托过去。**结构确实一样，但换的方式不一样，所以是两个模式。**判据只有一句：**谁来换那个对象。**

- 策略：**外面**挑一个塞进来。财务今年用"按比例"，明年换"一律二级"，报销单自己不会主动换规则；几个策略之间互不认识。
- 状态：**对象自己**在运行中换。草稿单被提交之后，它自己就变成了待审批单，没有任何外人来做这个决定；而且状态类之间**知道彼此**——"草稿"这个类里写着"下一站是待审批"。

```python
class 草稿:
    def 提交(self, 单): 单.状态 = 待审批(); return "已送审"   # ← 迁移：自己换掉自己
class 待审批:
    def 提交(self, 单): return "已在审批中，不能重复提交"
class 已通过:
    def 提交(self, 单): return "已通过，不能再提交"

class 单据:
    def __init__(self): self.状态 = 草稿()
    def 提交(self): return self.状态.提交(self)   # 行为委托给"当前状态"

d = 单据(); d.提交()   # → 已送审
d.提交()               # → 已在审批中，不能重复提交
```

转录本给的定义只有一句："**允许一个对象在其内部状态改变时改变它的行为**"，记忆关键字是"**状态变成类**"——三个字就把做法说完了：原来写在 `switch(状态)` 里的每一个分支，各升级成一个类。

**这里有个同名陷阱要点破**：讲义 27 讲的 **UML 状态图**是一张画圆角矩形和箭头的图，用来描述一个对象一生经历哪些状态；本课的**状态模式**是一种代码写法。两者不是一回事，但关系很近——状态图上的每一个圆角矩形，落到状态模式里正好是一个状态类。考题贴一张圆角矩形加迁移箭头的图、问"该 UML 图为（ ）"，那是 27 的地盘；问"该设计采用（ ）模式"才是这里。

### 三、逐级往上审：职责链模式（治③）

组长批 1000 以内，经理批 1 万以内，再往上找总监。朴素写法是提单人先判断该找谁，可提单人凭什么知道公司的审批权限表？而且这条链随组织架构变。

**职责链模式**（Chain of Responsibility，考卷上多印作**责任链**，两个译名指同一个模式）把每一级审批人做成一个对象，每个对象只认识自己的**下家**：能批就批，批不了往下传。转录本的定义是"**通过给多个对象处理请求的机会，减少请求的发送者与接收者之间的耦合。将接收对象链接起来，在链中传递请求，直到有一个对象处理这个请求**"，记忆关键字是"**传递请求、职责、链接**"。

```python
class 审批人:
    def __init__(self, 名, 上限): self.名, self.上限, self.下家 = 名, 上限, None
    def 接单(self, 金额):
        if 金额 <= self.上限: return f"{self.名}批"
        if self.下家: return self.下家.接单(金额)      # ← 处理不了就往下传
        return "无人可批"

组长, 经理, 总监 = 审批人("组长",1000), 审批人("经理",10000), 审批人("总监",100000)
组长.下家, 经理.下家 = 经理, 总监
[组长.接单(x) for x in (800, 6000, 50000, 200000)]
# → ['组长批', '经理批', '总监批', '无人可批']
```

两个考点常被忽略。第一，**最终只有一个对象真的处理了**请求，其余的只是"有机会处理"而已——这是它和下面观察者"人人都收到"的分水岭。第二，**链的组装是运行时决定的**：`组长.下家 = 经理` 这两行随时可以改，所以 2022 下半年那道真题的答案说它适用于"可处理一个请求的对象集合应被动态指定"。

### 四、批错了要能撤回：命令模式（治④）

撤销、排队、留痕，这三件事有一个共同前提：**"审批这一次"本身得是一样能拿在手里的东西**。而"调一次方法"是个动作，执行完就没了，塞不进历史栈，也塞不进队列。

**命令模式**的招数就是把请求本身变成对象：定义一个命令类，里面装着"要对谁做什么"，再给它配一个 `执行` 和一个 `撤销`。转录本的定义是"**将一个请求封装为一个对象，从而可用不同的请求对客户进行参数化，将请求排队或记录请求日志，支持可撤销的操作**"，记忆关键字是"**日志记录、可撤销**"。

这句定义里藏着**四个信号词**，题干沾上任何一个基本就是它：**参数化、排队、日志、撤销**。"参数化"是句里最绕的一个词，意思是：调用方（比如那个"批量审批"按钮）不需要知道自己按下去会发生什么，它只拿着一个命令对象，换个命令对象就换了行为——请求成了可以传来传去的参数。

角色有四个，2021 年那道真题第二空考的就是角色：抽象命令（声明 `执行` 接口）、具体命令、**调用者**（只认抽象命令，负责触发，还可以把命令压进历史栈或队列）、**接收者**（真正干活的那个对象，比如报销单本身）。

### 五、一变全都要动：观察者模式（治⑤）

"审批通过"这段代码里，每接一个下游就得加一行调用。反过来做就对了：**审批通过只管喊一嗓子"我变了"，谁关心谁自己来登记**。

转录本定义："**定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并自动更新**"，记忆关键字是"**通知、自动更新**"。

```python
class 单据:
    def __init__(self): self.订阅者 = []
    def 订阅(self, f): self.订阅者.append(f)
    def 通过(self):
        self.状态 = "已通过"
        return [f(self) for f in self.订阅者]     # ← 一变，全体收到

s = 单据()
s.订阅(lambda x: "发短信:"+x.状态); s.订阅(lambda x: "记台账:"+x.状态); s.订阅(lambda x: "刷报表:"+x.状态)
s.通过()   # → ['发短信:已通过', '记台账:已通过', '刷报表:已通过']
```

要害是"**一对多**"和"**全部**"：一个被观察的目标，多个观察者，目标一变，观察者**统统**收到同一条通知。这正好和职责链相反——职责链是"沿链找到第一个能办的就停"。

### 六、四个模块两两直接调：中介者模式（治⑥）

提单、审批、预算、财务四个模块互相持有对方的引用，改一个牵动三个。**中介者模式**让它们谁也不直接找谁，全都只跟一个中介对象说话，由中介决定这条消息该转给谁。转录本定义："**用一个中介对象来封装一系列的对象交互。它使各对象不需要显式地相互调用，从而达到低耦合，还可以独立的改变对象间的交互**"，记忆关键字是"**不直接引用**"。

**观察者 vs 中介者**是另一对高频辨析，判据是**方向和对称性**。观察者是**一对多的单向广播**：一个目标变了，一群订阅者被动收到同一条消息，订阅者之间毫无关系；中介者是**多对多交互的集中调停**：四个模块地位对等，中介看消息内容决定转给谁，可能转给一个，也可能谁都不转。一句话——**报销单变了要通知短信台账报表，是观察者；四个模块想互相说话都得过中介，是中介者。**

### 七、不改类却要不断加新统计：访问者模式（治⑦）

报销单类、明细类、附件类这三个类本身很稳定，几年都不变；变的是**要对它们做的操作**——今天按部门统计，明天导税务报表。往类里加方法，等于为了新操作去改稳定的老代码。

**访问者模式**把这件事翻了过来：数据结构不动，把每一套新操作打包成一个"访问者"对象，让元素接受访问者上门。转录本定义："**表示一个作用于某对象结构中的各元素的操作，使得在不改变各元素的类的前提下定义作用于这些元素的新操作**"，记忆关键字是"**数据和操作分离**"。

代价也要知道：**元素类必须先留一个 `accept(访问者)` 的口子**，2018 下半年那道真题第二空考的就是这个口子开在哪个类上——开在**元素**（被访问的那些对象）上，不是开在访问者上。它适合"结构稳定、操作频繁新增"的场合；如果元素类本身老是加新种类，反而是灾难，因为每加一种元素，所有访问者都要改。

### 八、剩下四个不在这条链上，认得关键字即可

报销系统这条链到第七条就走完了。剩下四个模式解决的不是上面任何一条，**不要硬往链上挂**，能凭关键字认出来就够了：

**迭代器**——"**提供一种方法来顺序访问一个聚合对象中的各个元素而不需要暴露该对象的内部表示**"，记忆关键字"**顺序访问，不暴露内部**"。"聚合对象"就是一个内部装着一堆别的对象的对象，比如那个装满明细的报销单。Python 的 `for x in 列表`、Java 的 `Iterator` 都是它，你天天在用，只是不知道它有名字。

**模板方法**——"**定义一个操作中的算法骨架，而将一些步骤延迟到子类中，使得子类可以不改变一个算法的结构即可重新定义算法的某些特定步骤**"。**培训资料这一栏的"记忆关键字"原件上就是空的**（十一个模式里只有它空着，不是转录漏抄），自己补一个：**骨架固定、步骤下放**。它和策略常被拿来对比：模板方法靠**继承**，父类把"校验 → 算级别 → 落库 → 通知"四步的顺序焊死，子类只能改其中某一步；策略靠**组合**，整个算法作为一个对象被整体替换。一句话——**改一步用模板方法，换整套用策略。**

**备忘录**——"**在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态，从而可以在以后将该对象恢复到原先保存的状态**"，记忆关键字"**保存，恢复**"。"不破坏封装性"是它最容易被问的一句：对象不用把自己的字段公开出去，而是自己生成一份快照交给外面的保管者存着，保管者只负责保管、看不懂也不改，要恢复时再把快照还给对象自己去还原。它和命令都能实现"撤销"，区别是——**命令记的是"做过什么"（把操作反着做一遍），备忘录存的是"当时的样子"（整个覆盖回去）。**

**解释器**——"**给定一种语言，定义它的文法表示，并定义一个解释器，该解释器用来根据文法表示来解释语言中的句子**"，记忆关键字"**解释器，虚拟机**"。报销系统里真要用上它，得是"允许财务自己写一行规则表达式 `金额>5000 && 类型=='招待'`，系统读懂并执行"这种场合。考试里认"文法""语言""句子"三个词就行。

### 九、11 个模式还有第二个坐标：类模式还是对象模式

**先别往下看，猜一个**：行为型这 11 个里，有几个是"类模式"？

多数人会答"全都是对象模式"，或者干脆答不上来——因为培训资料的表格里根本没有这一栏，它藏在分类总览那张图上：图里少数几个模式名带**下划线**，图右下角的说明写着"有下划线的表示既可以是类模式，也可以是对象模式；无下划线的表示只是对象模式"。放大逐条看下来，行为型 11 个里带下划线的只有 **2 个：解释器、模板方法**（迭代器那一行下面是拼写检查的红色波浪线，不是下划线，别数错），其余 9 个都只是对象模式。

这条区分背后的道理很简单：**类模式靠继承，在编译期就把关系定死；对象模式靠对象组合，运行时才装配。**解释器和模板方法都是"子类继承父类、覆盖某个方法"，所以是类模式；观察者、策略、状态这些都是"持有一个别的对象、把活委托过去"，只能是对象模式。

不记这一条，你就答不了考卷上那个反复出现的空："**该模式属于（ ）模式**"，四个选项长这样：创建型对象 / 结构型对象 / 行为型类 / 行为型对象。**已核到的、带这个空的五道真题（2017下、2018下、2019上、2021上、2022下）里，答案全是"行为型对象"**——因为被考到的状态、访问者、责任链、迭代器、命令，没有一个是那两个类模式。创建型和结构型那两列的下划线情况归讲义 28。

## 考试怎么考

**考点① 第 44–47 这四分有两种长相。** 一种是**一道四空大题**（2017下、2018下、2020下、2021上）：一段业务场景 + 一张类图 + 四个空——**认模式名 / 认角色（哪个类扮演哪个角色）/ 判分类（行为型对象模式）/ 选适用场景**；另一种是**拆成两三道小题**（2019上、2022下、2023上），不给类图，直接甩意图原句或场景让你认模式名，最多再追问分类和适用场景。四空大题里各空难度天差地别：第一空和第三空只要背了意图和分类就能拿，第二空要看类图，第四空要认得几个模式各自的适用场景描述。**保 45 分的打法是稳拿一三两空**，第二空按"角色名里带 State 的都是状态类、客户程序用的是上下文"这类常识排除，第四空对照下面考点②的意图句反推。

**考点② 给意图句选模式名。** 考卷上的意图句和培训资料"定义"栏那 11 句同出一源（都译自 GoF 原著），意思一样，但用词常差一两个虚词——同一句状态模式的意图，培训资料写"允许一个对象在其内部状态改变时改变它的行为"，2017 下的卷面写"一个对象在其内部状态改变时改变其行为"。所以要认的是**关键词组合**，不是背整句。最容易搞错的三句：看见"**一对多 + 自动更新**"选观察者，不要选中介者；看见"**顺序访问 + 不暴露内部表示**"选迭代器，不要选组合；看见"**排队 / 日志 / 撤销**"选命令，不要选备忘录。

**考点③ 分类判断。** 答案要把两个坐标叠起来写：只有正好考解释器或模板方法时才填"行为型类模式"，其余一律"行为型对象模式"。

**考点④ 五对易混，各有一句判据。**

| 容易混的一对 | 一句话判据 | 报销系统里的例子 |
|---|---|---|
| 策略 vs 状态 | **谁来换**：外面挑一个塞进来是策略；对象自己走到下一步是状态 | 财务换一套审批规则（策略）vs 单子从草稿变成待审批（状态） |
| 职责链 vs 命令 | **传下去** vs **存起来**：沿链找第一个能办的是职责链；把请求变成能排队能撤销的对象是命令 | 组长批不了转经理（职责链）vs 主管撤回自己刚才那次审批（命令） |
| 观察者 vs 中介者 | **一对多广播** vs **多对多调停**：全体收到同一条是观察者；谁跟谁说话都得过中间人是中介者 | 单子通过后短信台账报表全收到（观察者）vs 四个模块互相通信都走中介（中介者） |
| 模板方法 vs 策略 | **继承改一步** vs **组合换整套**：骨架焊死只让子类填某步是模板方法；整个算法作为对象被替换是策略 | 审批四步流程只换"算级别"那步（模板方法）vs 整套算级别的规则换掉（策略） |
| 迭代器 vs 访问者 | **遍历** vs **加操作**：只是把元素挨个取出来是迭代器；在不改元素类的前提下加新操作是访问者 | 挨个读报销单的明细（迭代器）vs 给明细加"按税种汇总"（访问者） |

**考点⑤ 错误选项的三种造法。** 一是**同类互换**——把中介者的"降低多个对象通信复杂性"安到观察者头上；二是**跨类混排**——四个候选里既摆行为型也摆结构型，2022 下那道"统一驱动接口"题就是三个行为型（中介者、访问者、观察者）陪着一个结构型的适配器，答案偏偏是那个结构型（该题归讲义 28）；三是**分类写错**——模式名对了，但"该模式属于"那一空给你"结构型对象""行为型类"。三种造法认出来，逐字比对的功夫能省一半。

### 参考答案

1. **A、D、C**。第一空"连成一条链、沿链传递、直到有一个对象处理为止"是职责链定义的原句；第二空"顺序访问聚合对象各元素、不暴露内部表示"是迭代器定义的原句。第三空最容易丢分：责任链和迭代器都靠对象组合（链上对象互相持有引用、迭代器持有被遍历的聚合对象），不是继承，所以是**行为型对象模式**，D 的"行为型类模式"只轮得到解释器和模板方法。
2. **D**。A 是迭代器的适用场景，B 是中介者的（"减少通信复杂性"＝多对多收成星形），C 是备忘录的。这道题正是"意图句反着认"的标准形态：四个选项各是一个行为型模式的适用场景，只有 D 出现了"一对多 + 自动得到通知"。
3. **A、D**。"根据季节、节假日推出不同定价包"＝有一族算法要按情况挑一个，是从**外面**挑，不是旅行包自己变，所以选策略不选状态。第二空 D 是策略定义的原句；A 是命令、B 是观察者、C 是状态——四个选项刚好是第一空四个候选的意图句，这是命题人最偏爱的配对方式。
4. **B、B、D、C**。第一空题干把"库存、货币量、找零能力"这些**内部状态**列出来，说不同状态下同一个"投币并选择"的行为不同——是状态模式；策略是干扰项，但售货机没有"外面挑一套算法"这回事。第二空不看图也能排除：另外三个选项都以 State 结尾，是三个状态类，而客户程序用的是**上下文**那个角色，四个里只有 Buy 不是状态类，选 B。第三空状态模式靠组合，是**行为型对象模式**，选 D（注意这里 D 才是"行为型对象"，选项顺序和第 1、5 题不同，别背位置）。第四空 C 是状态模式的意图原句，A 是观察者、B 是备忘录、D 是命令。
5. **B、A、D、C**。第一空："对购物车里每个物品做汇总"＝对一个对象结构中的各元素施加操作，且 Manual / Auto 是两种不同的汇总方式——访问者。第二空不看图也能定：`accept(Checkout)` 是**元素**交给访问者的那个口子，Checkout 是访问者，Item 才是元素，选 A；Manual 和 Auto 是具体访问者。第三空同样是**行为型对象模式**（本题 D）。第四空 C 是访问者的适用场景原句，A 是备忘录、B 是职责链、D 是命令。

7. **A、B、B**。"检查、能处理就处理、否则传给下一个"就是职责链的做法，题干里"多个前后连接的对象都有机会处理请求""避免请求的发送者和接收者之间的耦合关系"两句更是把定义摊开了摆在眼前。第二空：链上对象靠互相持有引用组装，是**行为型对象**。第三空日志链可以随配置增删几级，所以选"对象集合应被动态指定"；A 说的是过滤器（Filter），它压根不在 GoF 那 23 个模式里，是纯干扰项；C 是备忘录的适用场景，D 是策略的（"多种行为以多个条件语句的形式出现"正是策略要拆掉的那坨 if-else）。
8. **B、B**。稳定的元素结构 + 不断新增的操作，是访问者的教科书场景；代价是元素类必须各留一个 `accept` 口子。若答迭代器，那只解决了"怎么把明细一个个取出来"，没解决"新统计写在哪"。
9. 第一个是**模板方法**（父类把四步骨架焊死，子类只覆盖"算级别"那一步，靠**继承**）；第二个是**策略**（把整套算级别的算法做成对象，运行时整体替换，靠**组合**）。
10. **C**。享元是结构型（讲义 28），解释器、备忘录、中介者都在行为型 11 个里。
11. **解释器**和**模板方法**。判据是它们靠继承在编译期定死关系（子类覆盖父类方法），其余九个都靠持有别的对象、运行时委托，只能是对象模式。

## 速记

- 七条毛病对七个模式：规则常变→策略、自己走到下一步→状态、逐级往上审→职责链、要撤销要留痕→命令、一变全都动→观察者、模块互相直调→中介者、不改类加新统计→访问者
- 不在这条链上的四个，认关键字：迭代器「顺序访问，不暴露内部」、模板方法「骨架固定、步骤下放」（培训资料原件此栏为空）、备忘录「保存，恢复」、解释器「解释器，虚拟机」
- 另七句原文关键字：职责链「传递请求、职责、链接」、命令「日志记录、可撤销」、中介者「不直接引用」、观察者「通知、自动更新」、状态「状态变成类」、策略「算法替换」、访问者「数据和操作分离」
- 策略 vs 状态：**外面挑的是策略，自己变的是状态**；职责链只有一个人真办，观察者人人都收到
- 模板方法靠继承改一步，策略靠组合换整套；命令记"做过什么"，备忘录存"当时的样子"
- 类模式只有**解释器、模板方法**两个，其余九个是对象模式；"该模式属于（ ）"绝大多数填**行为型对象模式**
- 设计模式固定考第 44–47 题共 4 分，或一道四空大题（配类图），或拆成两三道小题（不配图）
- 状态模式 ≠ UML 状态图：图归讲义 27，模式在这里，状态图上一个圆角矩形＝一个状态类
