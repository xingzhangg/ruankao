# 16 · 软件工程：系统分析与设计基础（模块独立性 + 体系结构风格）

> 真题：耦合内聚排序 2021上/2022下/2023上、体系结构风格 2022下/2023上｜无计算｜未讲（自学讲义）

---

## 第 0 层 · 定位

**这一课回答**：概要设计切出来的模块好不好，凭什么判断（内聚 7 档、耦合 7 档），以及系统整体按什么骨架搭（体系结构风格）。

**前后关系**：15 生存周期表里「概要设计」那一格的放大；「高内聚低耦合」是下午题 1 DFD 分解和题 3 类职责划分共用的评判尺子。

**分值与去向**：板块 11–13 分，本课在 2021上/2022下/2023上 多场出现；下午不直接考。零计算，背两条 7 档排序。

## 第 1 层 · 理解

### 一句话

> 这一章给"设计得好不好"发了**两把尺子**（模块之间的耦合、模块内部的内聚），再往上给"整个系统按什么骨架搭"编了**一本套路目录**（体系结构风格）——尺子量模块，目录选骨架，本质是同一个问题在不同尺度上重复。

### 痛点：改一行代码要动八个文件

- **改一处要动八处**：给订单加个字段，结果支付、物流、报表、导出全要跟着改——模块之间缠得太紧（**耦合太强**）。
- **万能 Utils 类**：里面堆着"格式化日期 + 发邮件 + 算税率"，谁都往里塞，谁都不敢删——模块内部毫无共同理由（**内聚太低**）。
- **全局配置结构体谁都能改**：五个模块直接读写同一个 `g_config`，某天有人改了一个字段的含义，线上全炸。
- **新系统开工第一天不知道骨架怎么搭**：是流水线式处理？还是事件总线？还是中央数据库大家围着转？——这是**体系结构风格**要回答的。

前三条是"模块尺度"的麻烦，第四条是"系统尺度"的麻烦。本课把这两个尺度一起讲，不是拼盘——见下面的主线。

### 一条主线

```
概要设计要回答一件事：系统切成哪些模块、模块之间怎么摆
   ↓ 切法有好有坏。坏在哪？坏在【改一处要动八处】
   ↓ 于是要给"切得好不好"定个量 —— 术语叫【模块独立性】
   ↓
   独立性拆成两把尺子，因为麻烦的来源只有两个方向：
        麻烦来自模块【外面】：它和别人缠得太紧 → 尺子①【耦合】越松越好
        麻烦来自模块【里面】：它自己是个杂物箱 → 尺子②【内聚】越紧越好
   ↓
   两把尺子各分 7 档，档位怎么排？各有一条【单一判据】：
     耦合排序判据 = 两个模块【靠什么通信】，通信手段越"能绕过接口"越糟：
        不通信 < 传简单值 < 传数据结构 < 传控制开关 < 共享全局变量 < 共享数据区 < 直接改人内部
        （越往右，一个模块改动能波及另一个的路径就越隐蔽、越管不住）
     内聚排序判据 = 模块内的东西【凭什么待在一起】，理由越"功能一体"越好：
        凑巧 < 同类 < 同时 < 同次序 < 同数据 < 数据接力 < 同一个功能
        （越往右，把它们拆开就越没道理）
   ↓ 两把尺子合起来 = 设计目标八个字：【高内聚、低耦合】
   ↓
   但尺子只能量"模块切得对不对"，量不出"整个系统按什么骨架组织"
   ↓ 骨架不必每次原创 —— 前人反复用、被验证有效的组织套路已编成目录：
        【软件体系结构风格】= 系统级别的"设计模式"
        五大类的分类判据，仍然是那个老问题【构件之间靠什么协作】：
             靠数据顺着流过去 ─────→ 数据流风格（管道-过滤器）
             靠调用栈一层层调用 ───→ 调用/返回风格（主程序子程序、面向对象、分层）
             靠事件/消息互不认识 ──→ 独立构件风格（事件驱动/隐式调用）
             靠解释执行一段"程序"→ 虚拟机风格（解释器、规则系统）
             靠围着一份中央数据 ──→ 仓库风格（数据库、黑板、超文本）
   ↓
   最后再按"物理上部署在哪台机器"切一刀 → 【C/S、B/S、三层架构】
        这仍是同一个问题：把业务逻辑从胖客户端抽到中间层，
        就是在给客户端【解耦】——尺度从"模块"升到了"部署单元"而已。

━━━ 收口：本章从头到尾只在讲一件事 ━━━
   【把系统拆成块，让块与块之间的联系尽可能少而清晰】
   模块尺度叫"高内聚低耦合"，系统尺度叫"体系结构风格"，
   部署尺度叫"三层架构"。三个尺度，同一条原则。
```

**这条链就是本章的答题直觉**：任何一道题，先问自己"它在问哪个尺度"——模块尺度就上两把尺子，系统尺度就查五大类目录，部署尺度就看 C/S、B/S、三层。

## 第 2 层 · 考点：考试怎么问

### 考点① 耦合类型判断（模块之间，7 档由弱到强）

**题目长相**：
> "模块 A 把学生成绩记录（一个结构体）整体作为参数传给模块 B……A 与 B 之间的耦合类型是（ ）"
> "模块 P、Q 都直接读写同一个全局数组，这属于（ ）耦合"

**怎么解**：走一条固定的判断流程，**只看"信息是怎么过去的"**，不看模块干什么。

```
① 两模块有直接联系吗？ 没有（只被同一上层调度）→ 无直接耦合
② 信息走【参数表】吗？
     走参数 → 传的是什么？
         简单值（int/double/String）………→ 数据耦合
         数据结构 / 记录 / 对象 ……………→ 标记耦合
         控制开关，决定对方走哪条分支 …→ 控制耦合
     不走参数、靠【全局】 → 共享的是什么？
         全局简单变量 ……………………→ 外部耦合
         全局数据结构 / 公共数据区 ……→ 公共耦合
③ 直接伸手用/改对方内部数据，或跳进对方中段执行 → 内容耦合（最恶劣）
```

| 强弱 | 类型 | 判断标志 | 代码场景（一眼共鸣版） |
|---|---|---|---|
| 最弱（最好） | 无直接耦合 | 两模块毫无直接关系，只被同一上层模块调度 | `main()` 分别调 `parse()` 和 `report()`，两者互不认识 |
| ↓ | 数据耦合 | 通过参数传**简单数据值** | `send(userId, amount)`——只传两个基本类型 |
| ↓ | 标记耦合 | 通过参数传**数据结构（记录/对象）** | `send(Order order)`——把整个订单对象递过去，其实只用到其中两个字段 |
| ↓ | 控制耦合 | 传**控制标志**，对方据此选择走哪段逻辑 | `render(mode)`，被调方内部 `if (mode == 1) ... else ...`——调用方在遥控对方怎么干活 |
| ↓ | 外部耦合 | 多个模块访问**同一全局简单变量**（不经参数表传递） | 模块 A、B 都直接读写全局 `int g_debugLevel` |
| ↓ | 公共耦合 | 多个模块访问**同一公共数据环境**（全局数据结构、共享内存区、公共文件） | 五个模块都读写全局 `g_config` 结构体——谁改了字段含义，全体遭殃 |
| 最强（最差） | 内容耦合 | 一个模块**直接使用/修改另一模块内部**的数据，或跳到对方中间执行 | 用指针/反射直接改另一模块的私有变量；汇编 GOTO 跳进别的模块中段 |

**陷阱**——三组最爱考的辨析：

- **数据 vs 标记**：都走参数表。传 `int`、`double` 等**简单值**是数据耦合；传**结构体/对象**（哪怕对方只用其中一两个字段）是**标记耦合**。错误选项最爱写成"只用了其中两个字段，所以是数据耦合"——**只看传了什么，不看用了多少**。
- **控制 vs 数据**：同样走参数，看这个参数的**用途**——参与运算的是数据耦合；**用来决定对方内部走哪条分支**的"开关/标志"是控制耦合。
- **外部 vs 公共**：都不走参数、都靠全局。共享的是**简单变量**→**外部耦合**；共享的是**数据结构/公共数据区**→**公共耦合**。分界线只有一句："**共享的东西是不是数据结构**"。

### 考点② 内聚类型判断与排序（模块内部，7 档由低到高）

**题目长相**：
> "以下四组内聚类型中，按内聚程度**从低到高**排列正确的是（ ）"
> "某模块内先解析文件再统计报表，两步缺一不可，该模块的内聚类型是（ ）"

**怎么解**：判断方法只有一句——**问"这个模块里的东西，凭什么待在同一个模块里？"** 理由越"功能一体"，内聚越高。

| 强弱 | 类型 | 待在一起的理由 | 代码场景 |
|---|---|---|---|
| 最低（最差） | 偶然内聚（巧合内聚） | 没有任何有意义的关系，纯粹凑一起 | 万能 `Utils` 类里堆着"格式化日期 + 发邮件 + 算税率"，互不相干 |
| ↓ | 逻辑内聚 | 逻辑上同类的一组功能，**靠传入参数挑一个**执行 | `handle(type)` 内 `switch(type)`：case 1 打印、case 2 导出、case 3 发送 |
| ↓ | 时间内聚 | 只因需要在**同一时间**执行 | `init()` 里一口气初始化日志、连接池、缓存——彼此无关，只是都在启动时做 |
| ↓ | 过程内聚 | 相关，且必须按**特定次序**执行 | 一个模块内依次"读配置→校验配置→注册路由"，次序不能乱 |
| ↓ | 通信内聚 | 各部分都操作**同一份数据** | 一个模块对同一份订单列表既"打印清单"又"汇总金额"——输入数据相同 |
| ↓ | 顺序内聚 | 前一部分的**输出**正是后一部分的**输入**，像流水线 | 模块内先 `解析CSV得到记录` 再 `用这些记录做清洗`——数据接力 |
| 最高（最好） | 功能内聚 | 所有成分共同完成**一个单一功能**，缺一不可 | `calcCRC(data)`——整个模块就干"算校验码"这一件完整的事 |

**陷阱**：
- **过程 / 顺序 / 通信 三兄弟**（最常放一起考）：过程内聚是"**动作**按次序相关"（数据未必相接）；顺序内聚是"**数据**逐级接力，前者输出=后者输入"；通信内聚是"共用**同一份输入**但动作各自独立"。
- **排序题的错误选项** 90% 是把**逻辑排到偶然前面**，或把**偶然排到时间后面**——记死 7 字序即可一眼排除。
- **一个高频规律**：**控制耦合的另一头，往往就是一个逻辑内聚的模块**——因为"要靠标志挑功能"恰恰说明被调模块把多个功能捆在了一起。这条能一次答对"耦合+内聚"双问题。

### 考点③ 体系结构风格：给场景认风格

**题目长相**：
> "某语音识别系统由多个独立知识源共同监视并修改一个共享数据区……采用的体系结构风格是（ ）"
> "`cat log | grep ERROR | sort` 这类处理属于（ ）风格，它属于（ ）大类"

**怎么解**：先抓**特征词**定具体风格，再回下表定所属大类。**考法只有两种：给场景认风格，或问某风格属于哪一大类。**

#### 五大类（Garlan & Shaw 分类，《教程》采用）

| 大类 | 包含的具体风格 | 核心思想 |
|---|---|---|
| 数据流风格 | 批处理序列；**管道-过滤器** | 数据像水一样流过一串处理单元 |
| 调用/返回风格 | 主程序/子程序；面向对象；**层次结构（分层）** | 通过调用-返回组织控制流 |
| 独立构件风格 | 进程通信；**事件系统（隐式调用/事件驱动）** | 构件各自独立，靠消息/事件松散协作 |
| 虚拟机风格 | 解释器；基于规则的系统 | 构造一台"软件虚拟机"去执行输入的"程序/规则" |
| 仓库风格 | 数据库系统；超文本系统；**黑板系统** | 中央数据 + 独立处理单元围绕它工作 |

#### 重点风格逐个认

**管道-过滤器（数据流）**：每个构件（过滤器）独立工作——读输入流、做变换、写输出流；构件之间用管道连接，前一个的输出接后一个的输入。**过滤器彼此独立、不共享状态、不知道上下游是谁。**
- 典型应用：Unix 命令行 `cat log | grep ERROR | sort | uniq -c`；编译器的"词法分析→语法分析→语义分析→代码生成"流水线
- 优点：构件可复用可替换、易于并行；**缺点：不适合交互式应用**（数据单向流，没法频繁来回对话），且常有格式转换开销

**事件驱动 / 隐式调用（独立构件）**：构件不直接调用彼此，而是**发布事件**；对某事件感兴趣的构件事先注册回调，事件发生时由系统触发它们。核心特征：**发布者不知道（也不关心）谁会响应、响应顺序如何**。
- 典型应用：GUI 框架（点击按钮触发监听器）、消息队列/发布订阅系统、IDE 里"文件保存后自动触发编译检查"
- 优点：极低耦合、易于扩展新响应者；**缺点：控制流不直观、难以推断执行顺序与结果**

**仓库风格**：一个**中央数据结构（仓库）** + 一组**独立的处理单元**，处理单元都围绕中央数据工作。
- **数据库系统**：数据库是仓库，各事务/应用是处理单元
- **黑板系统**（仓库的动态版）：多个专家知识源盯着"黑板"（共享数据区），谁发现自己能推进一步就上去改写黑板，逐步逼近解；典型应用是**语音识别**、信号处理等**没有确定解法**的问题
- **超文本系统**：网状链接的文档库也归入仓库类

**层次结构 / 分层（调用/返回）**：系统组织成一摞层，**每层只为紧邻的上层提供服务、只使用紧邻下层的服务**。典型应用：OSI 七层网络协议、操作系统内核分层。优点：逐层抽象、可替换某一层；缺点：层层转发有性能开销，层次划分不总是清晰。

**陷阱与常考搭配链**：
- **「黑板 → 仓库风格 → 语音识别」这条链是教材钦点搭配**，题干只要同时出现"多个独立知识源 + 共享数据区 + 逐步改写中间结果"，闭眼选黑板/仓库。
- 干扰项区分：**管道-过滤器**是数据**单向流过**一串变换，**没有共享中央数据**；**事件驱动**靠事件触发而非共享数据区；**分层**是逐层服务的调用关系。
- **分层属于「调用/返回」大类**，不属于独立的一大类——问"分层属于哪一大类"时最容易错选。
- 管道-过滤器的标准弱点是"**不适合交互式应用**"，这句常被反写成优点当错误选项。

### 考点④ C/S、B/S 与三层架构（部署尺度）

**题目长相**："将企业内部 C/S 结构的客户端程序改造为浏览器访问，其主要好处是（ )"；"三层 C/S 结构中，业务逻辑位于（ ）"。

**怎么解**：抓"客户端胖不胖、业务逻辑放在哪、升级要不要挨台装"。

| 结构 | 组成 | 特点 | 弱点 |
|---|---|---|---|
| C/S（客户机/服务器，两层） | 胖客户端程序 + 数据库服务器 | 客户端承担界面 + 业务逻辑，交互能力强、响应快 | **客户端要逐台安装升级，维护成本高**；业务逻辑散在客户端，安全与复用差 |
| 三层架构（三层 C/S） | **表示层 / 业务逻辑层（功能层）/ 数据（访问）层** | 业务逻辑从客户端抽出来集中放中间层：各层独立演化、逻辑可复用、更安全、易扩展 | 层间通信有开销，结构更复杂 |
| B/S（浏览器/服务器） | **浏览器 / Web 服务器 / 数据库服务器** —— 《教程》原话：**"B/S 风格就是上述三层应用结构的一种实现方式"**（即上一行的三层 C/S） | **客户端零安装、升级只改服务器**，跨平台（直观理解：把胖客户端瘦成一个浏览器） | 服务器压力大；传统上交互体验不如胖客户端 |

程序员类比：三层架构就是日常的"前端页面（表示层）→ 后端服务（业务逻辑层）→ DAO/数据库（数据层）"；把公司内部老 ERP 的 exe 客户端改造成网页版，就是 C/S → B/S 的迁移，动机通常正是"**几百台电脑挨个升级客户端太痛苦**"。

**陷阱**：
- 教材口径是 **B/S 是"三层应用结构的一种实现方式"**（浏览器/Web服务器/数据库服务器），而不是"两层 C/S 的一个变种"——按"C/S 的特例"理解，容易在"B/S 属于几层结构"这类问法上失分。
- 《教程》另有一句常被拿来出题：实践中**应用系统常以 C/S 与 B/S 混合的形式出现**——所以"B/S 已全面取代 C/S"这类绝对化选项必错。
- **B/S 的最大卖点是"客户端零安装、升级只改服务器"**，不是"性能更好"——选项写"B/S 响应速度优于 C/S"必错。
- 三层架构里，**业务逻辑在中间的功能层**，不在客户端也不在数据库。

## 第 4 层 · 速记

> 设计目标八个字：**高内聚、低耦合**
> 耦合由弱到强：「**无 数 标 控 外 公 内**」（无直接、数据、标记、控制、外部、公共、内容）——**越靠后越差，内容耦合最恶劣**
> 一句话记判据：**传简单值=数据，传结构体=标记，传开关=控制；共享简单变量=外部，共享数据结构=公共，改人内部=内容**
> 内聚由低到高：「**偶 逻 时 过 通 顺 功**」（偶然、逻辑、时间、过程、通信、顺序、功能）——**功能内聚最好，偶然内聚最差**
> 三兄弟辨析：**过程=动作按次序，顺序=数据接力（前输出即后输入），通信=共用同一份输入**
> 附赠规律：**控制耦合的另一头常是逻辑内聚模块**
> 风格五大类：「**数据流、调用返回、独立构件、虚拟机、仓库**」（分层属于**调用/返回**）
> 三条常考搭配链：**管道-过滤器 → Unix 管道/编译器（不适合交互式）**；**事件驱动 → GUI，发布者不知道谁响应**；**黑板 → 仓库风格 → 语音识别**
> 三层架构：**表示层 / 业务逻辑层 / 数据层**；**B/S 是"三层应用结构的一种实现方式"**（浏览器/Web服务器/数据库服务器），最大卖点 = **客户端零安装、升级只改服务器**（不是"性能更好"）

## 考题回顾

**1.【模拟·重现2021上考点】** 模块 A 把学生成绩记录（一个结构体）整体作为参数传给模块 B，B 只使用其中的"学号"和"总分"两个字段。A 与 B 之间的耦合类型是（ ）。
A. 数据耦合　B. 标记耦合　C. 控制耦合　D. 公共耦合

**解答**：走考点①的判断流程。①信息通过**参数表**传递 → 排除靠全局数据的公共耦合（D）；②传的不是"开关/标志"、没有控制对方走哪条分支 → 排除控制耦合（C）；③传的是**整个数据结构（结构体）**而非简单值 → 不是数据耦合（A），正是标记耦合的定义。**"B 只用其中两个字段"是干扰信息——只看传了什么，不看用了多少。选 B**。

**2.【模拟·重现2022下考点】** 以下四组内聚类型中，按内聚程度**从低到高**排列正确的是（ ）。
A. 偶然内聚 → 时间内聚 → 顺序内聚 → 功能内聚
B. 逻辑内聚 → 偶然内聚 → 通信内聚 → 功能内聚
C. 功能内聚 → 顺序内聚 → 时间内聚 → 偶然内聚
D. 时间内聚 → 偶然内聚 → 过程内聚 → 顺序内聚

**解答**：给 7 档编号「偶然1 < 逻辑2 < 时间3 < 过程4 < 通信5 < 顺序6 < 功能7」，逐项代入。
A：1 → 3 → 6 → 7，严格递增 ✔
B：2 → 1，逻辑排在偶然前面 ✘
C：7 → 6 → 3 → 1，整个是从高到低 ✘
D：3 → 1，偶然排在时间后面 ✘
**选 A**。

**3.【模拟·重现2023上考点】** 某语音识别系统由多个独立的知识源构件组成，它们共同监视并修改一个共享数据区中的中间识别结果，逐步得到最终答案。该系统采用的体系结构风格是（ ）。
A. 管道-过滤器　B. 事件驱动　C. 黑板（仓库风格）　D. 分层结构

**解答**：抓特征词。"多个独立知识源 + **共享数据区** + 逐步修改中间结果 + 语音识别"四个特征全部命中**黑板系统**（仓库风格的典型代表，教材钦点的应用就是语音识别）。管道-过滤器是数据单向流过一串变换，没有共享中央数据；事件驱动靠事件触发而非共享数据区；分层是逐层服务关系。**选 C**。

**4.【模拟】** 模块 F 接收参数 `flag`，内部根据 `flag` 的取值决定执行"新增"还是"删除"逻辑。调用方与 F 之间的耦合类型，以及模块 F 自身的内聚类型分别是（ ）。
A. 数据耦合；功能内聚　B. 控制耦合；逻辑内聚　C. 标记耦合；通信内聚　D. 控制耦合；时间内聚

**解答**：两问分开判。①`flag` 是决定对方内部走哪条分支的**控制标志** → 控制耦合；②F 内部是"一组同类操作，靠参数挑一个执行" → **逻辑内聚**的标准定义。这题正好印证考点②那条规律：**控制耦合的另一头往往就是一个逻辑内聚的模块**——因为"要靠标志挑功能"恰说明模块把多个功能捆在了一起。**选 B**。

## 自测练习

1. 【模拟】模块 P 和 Q 都直接读写全局结构体 `g_sysConfig`（不通过参数传递）。二者的耦合类型是什么？若共享的改为全局整型变量 `g_retryCount`，又是什么类型？
2. 【模拟】某模块内先"从文件解析出用户列表"，再把该列表作为输入"生成统计报表"，两步缺一不可。该模块的内聚类型是什么？
3. 【模拟】把 `cat access.log | grep 500 | wc -l` 这类命令行处理归入哪种体系结构风格？该风格为什么不适合做交互式应用？

### 参考答案

1. 共享**全局数据结构** → **公共耦合**；改为共享**全局简单变量** → **外部耦合**。这对辨析的分界线就是"共享的东西是不是数据结构"。
2. **顺序内聚**——前一部分的输出（用户列表）正是后一部分的输入，数据逐级接力。若两步只是用同一份输入数据、彼此输出无关，才是通信内聚。
3. **管道-过滤器风格**（数据流大类）。因为数据只能沿管道单向流动、各过滤器独立且不保存交互状态，无法支持"用户频繁输入—系统即时响应—再输入"的往返式交互。
