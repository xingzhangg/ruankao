## 开讲：老板说"把报销的 Excel 搬到线上"，你第一步干什么

还是讲义 15 那套内部报销系统。老板扔下一句"把现在的 Excel 流程搬到线上"就走了。最朴素的做法只有四步：**找老板问一遍，记下来，把系统切成几块，开写**。

这四步会在九个地方翻车。本课全部名词，就是这九个坑各自的补丁——**前五个坑在"话"上（需求），后四个坑在"块"上（设计）**：

- ① 老板那一句话，程序员没法照着写代码；
- ② 该问的人没问全，有些话用户根本不会主动说；
- ③ 问回来是一地碎话，互相打架、还有窟窿；
- ④ 说过的话过两周就变味，谁也不认账；
- ⑤ 签完字照样要改，改完没人说得清到底实现了没有；
- ⑥ 照着线下流程原样搬上线，搬完还是那么慢；
- ⑦ 三个人各切各的模块，接口对不上；
- ⑧ 切完了，凭什么说这次比上次切得好；
- ⑨ 系统跑起来了，财务点了三层菜单找不到"导出"。

### 一、坑①：老板的话、员工的话、能写成代码的话，不是同一种话

**先猜一下**，下面三句话有什么本质区别，别急着往下看：

> 甲："上线后每月能省两个财务人力。"　乙："我要能一次把本月所有已审批的单子导成 Excel。"　丙："导出接口响应时间不超过 3 秒。"

三句都叫"需求"，但它们**是谁说的、回答什么、能不能直接开工**完全不同。培训资料把需求分成三个层次，正好一句一层：

| 层次 | 谁说的 | 回答什么 | 报销系统里 |
|---|---|---|---|
| **业务需求** | 项目投资人、客户、市场营销部门或产品策划部门 | 企业或客户对系统**高层次的目标要求**；由它确定项目视图和范围 | 甲："每月省两个财务人力" |
| **用户需求** | 具体使用的人，靠用户访谈、问卷调查等整理场景得到 | **用户的具体目标，或用户要求系统必须能完成的任务**——即用户**能使用系统来做什么** | 乙："一次导出本月已审批单子" |
| **系统需求** | 分析人员写给开发看 | 从**系统的角度**说明软件的需求 | 丙及以下三类 |

系统需求再分三类，这三类的名字考试直接考：

- **功能需求**（也称行为需求）：**规定了开发人员必须在系统中实现的软件功能**，用户利用这些功能完成任务。报销系统里是"金额超过 5000 元自动转二级审批"。
- **非功能需求**：**系统必须具备的属性或品质**，又细分为软件质量属性（可维护性、可靠性、效率等）和其他非功能需求。丙那句"响应不超过 3 秒"就是。
- **设计约束**（也称限制条件或补充规约）：**对系统的一些约束说明**，例如必须采用国有自主知识产权的数据库系统、必须运行在 UNIX 操作系统之下。报销系统里是"必须接公司现有的单点登录"。

**判题的口诀**：看这句话**站在谁的立场、颗粒度多粗**。"能有效地纠正拼写错误"这种说不出具体动作的目标是业务需求；"用户能做某件事"是用户需求；"系统必须实现某个具体功能"是功能需求。

还有一件事三个层次答不了：**用户说出来的需求，不等于用户满意的全部**。**质量功能部署（QFD）是一种将用户要求转化成软件需求的技术**，目的是最大限度提升软件工程过程中用户的满意度。它把需求按"实现了用户什么反应"分成三类：

- **常规需求**：用户认为**系统应该做到的功能或性能**，实现越多用户越满意——"能提单、能审批"。
- **期望需求**：用户**想当然认为系统应具备**，但**并不能正确描述**自己想要的——"当然能查我去年的单子吧"，没人会主动提，做不到就不满意。
- **意外需求**（也称兴奋需求）：**用户要求范围外的功能或性能**，实现了用户更高兴，不实现也不影响购买决策——"提单时自动 OCR 识别发票金额"。

把这一节和后面四节串起来的骨架，是需求这条线的总目录。**软件需求的定义**是：用户对系统在功能、行为、性能、设计约束等方面的期望；是**用户解决问题或达到目标所需的条件或能力**，是系统或系统部件要满足合同、标准、规范或其他正式规定文档所需具有的条件或能力，以及反映这些条件或能力的文档说明。它分**需求开发和需求管理**两大过程，中间用一条线隔开：

```
需求开发 ──→ 需求获取 → 需求分析 → 需求定义（需求规格说明书）→ 需求验证
                                  ↓
                              【需求基线】   ← 签字确认，这条线是分水岭
                                  ↓
需求管理 ──→ 变更控制 → 版本控制 → 需求跟踪 → 需求状态跟踪
```

**基线之前叫开发（把需求做出来），基线之后叫管理（守住它、追踪它）**。下面四节就是沿这张图往下走。

### 二、坑②：问谁、怎么问——需求获取

**需求获取是一个确定和理解不同的项目干系人的需求和约束的过程**。"项目干系人"就是跟这个系统有利害关系的所有人：报销系统里是提单的员工、审批的主管、对账的财务、管服务器的运维，只问老板必然漏。培训资料给了六种常见方法，考试常考"哪种方法适合什么场合"：

| 方法 | 什么时候用 | 它的软肋 |
|---|---|---|
| **用户访谈** | 1 对 1-3，找有代表性的用户；分**结构化和非结构化**两种 | **灵活性好、应用范围宽，但信息量大、记录困难、需要足够的领域知识** |
| **问卷调查** | 用户多、无法一一访谈时 | 问卷设计死，问不出没想到的东西 |
| **采样** | 从种群中**系统地选出有代表性的样本集** | 基于数理统计，能减少数据收集偏差，但样本选偏就全偏 |
| **情节串联板** | 一系列图片，**通过这些图片来讲故事** | 只能表达流程，说不清规则 |
| **联合需求计划 JRP** | 联合关键用户代表、系统分析师、开发团队代表，**通过有组织的会议**讨论需求 | 组织成本高，得高度组织的群体会议 |
| **需求记录技术** | 把问到的东西记下来：任务卡片、场景说明、用户故事、Volere 白卡 | 只是记录形式，不负责问 |

采样是唯一带公式的一个：**样本数量 = 0.25\*(可信度因子/错误率)²**。取常用的可信度因子 1.96、错误率 10%，样本量 = 0.25×(1.96/0.10)² = 0.25×384.16 = **96.04**；错误率收紧到 5%，样本量 = 0.25×(1.96/0.05)² = **384.16**——错误率减半，样本量涨四倍。这个公式软设很少直接算，认得公式形状即可。

### 三、坑③：一地碎话变成能开工的需求——需求分析

问回来一堆话："报销单要能改""金额不对要退回""财务说月底要能锁账"。它们彼此可能矛盾（谁能改？提单人还是审批人？），可能缺口（退回之后单子处于什么状态？）。**需求分析就是分析人员把杂乱无章的用户要求和期望转化为用户需求**这件事。

判断转化到位没有，有一把八项的尺子：一个好的需求应具有**无二义性、完整性、一致性、可测试性、确定性、可跟踪性、正确性、必要性**。"报销单要能改"就同时踩了无二义性（谁改）和可测试性（怎么验收）两条。

需求分析的任务共七项，按报销系统对照着看就不用背：

1. **绘制系统上下文范围关系图**——先画出"系统"这个圈，圈外是员工、主管、财务、银行，圈内是报销系统，先把边界钉死；
2. **创建用户界面原型**——搭几个能点的页面给财务看，这就是讲义 15 讲的原型化方法用在需求这一格；
3. **分析需求的可行性**；4. **确定需求的优先级**；5. **为需求建立模型**；6. **创建数据字典**；7. **使用 QFD**。

第 5、6 项要用工具，这就是**结构化的需求分析**。它的特点三句话：**自顶向下，逐步分解，面向数据**——先把"报销"当成一个大加工，再往下拆成提单、审批、打款，一层层拆细；盯的是数据怎么流，不是对象长什么样。它建**三大模型**加一本字典，各管一件事：

- **功能模型 = 数据流图 DFD**：**描述数据在系统中如何被传送或变换，以及如何对数据流进行变换的功能或子功能，用于对功能建模**。图上四种东西：**数据流**（箭头，一组固定成分的数据，表示流向）、**加工**（圆或圆角框，描述输入数据流到输出数据流之间的变换）、**数据存储**（双横线，暂存的数据，流向它表示写文件、流出表示读文件）、**外部实体**（方框，**存在于软件系统外的人员或组织**）。报销系统的外部实体是员工、主管、银行；报销单是数据流；报销单库是数据存储。DFD **可以分层**，从**顶层**（上下文数据流图）到 0 层、1 层等，**顶层数据流图只含有一个加工处理表示整个管理信息系统**，描述系统的输入输出和与外部实体的数据交互。**怎么画、父子图怎么配平、加工怎么补数据流，是讲义 21 和下午题 49 的正题，本课只要认得"问功能建模用哪张图"就够。**
- **行为模型 = 状态转换图 STD**：画的是"东西现在处于什么状态、什么事件让它跳到下一个状态"。报销单的状态是草稿→待审→已审→已打款，事件是"提交""驳回""打款成功"，图上还要标出**初态和终态**。转录本给的例子是学员：注册 --开通课程[已交费]--> 学习 --已学完指定教材--> 测试 --合格--> 终点，测试不合格就退回学习。
- **数据模型 = 实体联系图 E-R**：画**实体**和**联系**，回答"要存哪些东西、它们之间几对几"。报销系统里员工、报销单、审批记录是实体，"一个员工提多张单"是联系。E-R 图的画法在数据库板块细讲。
- **数据字典**：给图上出现的每个名字写定义。转录本原话是**为数据流图中的每个数据流、文件、加工，以及组成数据流或文件的数据项做出说明**——图只说"有一条数据流叫报销单"，字典才说清报销单由哪些字段组成。

### 四、坑④：说过的话要作数——需求定义与需求验证

**需求定义的产物就是软件需求规格说明书 SRS**，它是需求开发活动的产物，**编制该文档的目的是使项目干系人与开发团队对系统的初始规定有一个共同的理解，使之成为整个开发工作的基础**；它是软件开发过程中最重要的文档之一，**对于任何规模和性质的软件项目都不应该缺少**。

写 SRS 有两条路，考试爱考它们各自的前提假设：

- **严格定义**（也称预先定义）：建立在三条基本假设上——**所有需求都能够被预先定义**；开发人员与用户之间能够准确而清晰地交流；采用图形（或文字）可以充分体现最终系统。报销系统若照这条走，就是一次把需求谈死、签字、再不改。
- **原型方法**：**迭代的循环型开发方式**。它承认**并非所有的需求都能在系统开发前被准确地说明**，也承认项目干系人之间通常都存在交流上的困难，而**原型提供了克服该困难的一个手段**。它的特点是：需要实际的、可供用户参与的系统模型；有合适的系统开发环境；**反复是完全需要和值得提倡的，需求一旦确定，就应遵从严格的方法**。

写完了得有人认。**需求验证也称需求确认，目的是与用户一起确认需求无误**，对需求规格说明书进行评审和测试，两个步骤：**需求评审**（分正式评审和非正式评审）和**需求测试**（设计概念测试用例——不是跑代码，而是用假想的业务场景去"跑"文档，看文档答不答得上来）。

**验证通过后请用户签字确认，作为验收标准之一，此时这个需求规格说明书就是需求基线，不可以再随意更新，如果需要更改必须走需求变更流程。** 这一句是需求这条线的分水岭，前后判若两个世界。

（转录本此处把"需求规格说明书 SRS"写成了"需求规格说明书 SAS"，是 OCR 讹字，正确写法是 SRS，做题时按 SRS 认。）

### 五、坑⑤：签完还得改——需求管理

签字不等于不变。报销政策一改、公司一重组，需求就得动。需求管理管的就是"怎么改、改到哪一步了、改完能不能追回去"。

**需求状态**回答"改到哪一步了"。一条需求从提出到交付要过六种状态，转录本的状态图是：被建议 --通过评审--> 被批准 --设计完成/编码完成/通过单元测试--> 被实现 --通过集成测试--> 被验证 --通过用户验收--> 被交付；没通过评审的进**被拒绝**，被批准或被实现之后取消的进**被丢弃**。考试问"某需求已通过集成测试，此时状态是"，答**被验证**。

**变更控制**回答"怎么改"。**变更产生的原因**有四条：外部环境的变化、需求和设计做的不够完整、新技术的出现、公司机构重组造成业务流程的变化。改动要过一个组织：**变更控制委员会 CCB，也称配置控制委员会，其任务是对建议的配置项变更做出评价、审批，以及监督已经批准变更的实施**。流程固定七步：变更请求 → PM 和团队评估影响 → 将评估结果通知项目干系人（客户）→ CCB 审批 →（同意）执行变更 → 记录变更实施情况 → 分发新文档；不同意则取消变更。**注意"评估影响"排在"CCB 审批"前面**——先算清楚代价再送审，这个顺序是考点。

需求管理还要防七种**带有风险的做法**：**无足够用户参与、忽略了用户分类、用户需求的不断增加、模棱两可的需求、不必要的特性、过于精简的 SRS、不准确的估算**。报销系统里最常见的是第三条"用户需求的不断增加"，俗称需求蔓延。

**需求跟踪**回答"追得回去吗"。它是**双向跟踪、两个层次**：用户原始需求 ↔ 软件需求 ↔ 下游工作产品（设计、代码、测试用例）。

- **正向跟踪表示用户原始需求是否都实现了**；
- **反向跟踪表示软件实现的是否都是用户要求的**，不多不少。

落到纸上就是一张**需求跟踪矩阵**：行是原始需求，列是用例，对上了就打对号。**若某行都没有对号，表明原始需求未实现，正向跟踪发现问题；若某列都没有对号，表明有多余功能用例，软件实现了多余功能，反向跟踪发现问题。** 拿报销系统四条原始需求、五个用例排一张：

| | UC-1 提单 | UC-2 一级审批 | UC-3 二级审批 | UC-4 导出 | UC-5 短信通知 |
|---|---|---|---|---|---|
| FR-1 员工能提单 | ✓ | | | | |
| FR-2 超 5000 走二级 | | ✓ | ✓ | | |
| FR-3 能查历史单据 | | | | | |
| FR-4 财务能导出 | | | | ✓ | |

FR-3 整行空 → "能查历史单据"根本没做，**正向跟踪**抓到；UC-5 整列空 → 短信通知没有任何原始需求要求，**反向跟踪**抓到，是开发自己加的戏。**空行是漏做，空列是多做**，这一句就是这张表的全部考法。

---

到这里"话"这一半闭合了。**分析阶段交出去的是一份文档，不是一套技术方案**——培训资料把这一步的定位说得很清楚，它是一条四步的转化路径：

（1）认识、理解当前的现实环境，**获得当前系统的"物理模型"**——先看清财务现在到底怎么用 Excel、纸单子怎么在楼里传；
（2）从当前系统的"物理模型"**抽象出当前系统的"逻辑模型"**——扔掉"Excel""纸""跑腿"这些实现细节，只留"谁提、谁审、按什么规则"；
（3）对当前系统的"逻辑模型"进行分析和优化，**建立目标系统的"逻辑模型"**——在这里砍掉冗余环节、补上新规则；
（4）对目标系统的逻辑模型具体化（物理化），**建立目标系统的物理模型**——落到 MySQL 表、Java 服务、页面上。

**系统开发的目的是把现有系统的物理模型转化为目标系统的物理模型，而系统分析阶段的结果是得到目标系统的逻辑模型。逻辑模型反映了系统的功能和性质，而物理模型反映的是系统的某一种具体实现方案。** 第（4）步，就是下面"块"这一半要干的事。

### 六、坑⑥：照搬线下流程，搬完还是那么慢——处理流程设计

报销单在公司里要盖三个章、走两个楼层。你把它原样搬到线上，就成了"线上盖三个电子章、走两个电子楼层"，一天还是一天。**处理流程设计**要先把流程本身画出来、看明白，才知道该不该照搬。

**业务流程建模**是画流程的一批方法，认名字即可：**标杆瞄准**（以行业领先的标杆企业为目标，结合本企业情况分析建模）、**IDEF**（一系列建模、分析和仿真方法的统称）、**DEMO**（组织动态本质建模法）、**Petri 网**（一种用"库所—变迁—令牌"画并发流程的数学化图形模型，报销单在两个审批人手上并行流转这种情形就适合用它做仿真）、**业务流程建模语言 BPEL、BPML、BPMN、XPDL**（把流程写成机器能读的格式，好让流程引擎直接跑起来，其中 BPMN 是画给人看的图形标记法）、**基于服务的 BPM**（基于 Web 服务的思想对业务流程进行建模）。

IDEF 是一个从 0 编到 14 的系列（外加 IDEF1X），常考的只有几号：**IDEF0 业务流程（功能）建模、IDEF1X 数据建模（如 ER 模型）、IDEF2 仿真建模设计、IDEF4 面向对象设计、IDEF8 用户界面建模、IDEF12 组织结构建模**。记法是"0 功能、1X 数据、4 对象、8 界面"。

流程画出来还要能写进文档，这就是**流程表示工具**，四种各有明确的长短处，正好两两对照：

| 工具 | 它是什么 | 长处 | 短处／考点 |
|---|---|---|---|
| **程序流程图 PFD** | 用一些图框表示各种操作 | **独立于任何一种程序设计语言**，直观清晰、易于学习掌握 | **任何复杂的程序流程图都应该由顺序、选择和循环结构组合或嵌套而成**——这句常单独出成一道题 |
| **IPO 图** | 描述构成软件系统的**每个模块的输入、输出和数据加工** | 一眼看清一个模块吃什么、吐什么 | 只描述模块级，不画整体控制流 |
| **N-S 图** | 盒图，用嵌套的方框表示结构 | **容易表示嵌套和层次关系，并具有强烈的结构化特征** | **当问题很复杂时 N-S 图可能很大，因此不适合于复杂程序的设计**——错误选项最爱把这句反写成"特别适合复杂流程" |
| **问题分析图 PAD** | 支持**结构化程序设计**的图形工具 | 清晰的逻辑结构、标准化的图形，**引导设计人员使用结构化程序设计方法，从而提高程序的质量** | 干扰项常写成"支持原型化设计方法"，错 |

流程看明白了，才轮到"要不要改流程"。两个词一字之差，考的就是那个差：

- **业务流程管理 BPM**：**以规范化的构造端到端的卓越业务流程为中心，以持续的提高组织业务绩效为目的的系统化方法**。它包含三个层面：**规范流程、优化流程和再造流程**。
- **业务流程重组 BPR**：**对企业的业务流程进行根本性的再思考和彻底性的再设计**，从而获得可以用成本、质量、服务和速度等方面的业绩来衡量的显著性的成就。基本原则三条：以流程为中心的原则、团队管理原则（以人为本）、以客户为导向的原则。

**两者最根本的不同**，转录本写得很直白：**BPM 并不要求对所有的流程进行再造**，构造卓越的业务流程并不是流程再造，而是**根据现有流程的具体情况，对流程进行规范化的设计**。一句话记：**BPR 是"根本性、彻底性"地推倒重来，BPM 是"能规范就规范、该再造才再造"**。考题固定问 BPR 是什么式改造（答**根本性**，不是增量式/迭代式/保守式）、以什么为中心（答**流程**，不是需求/组织/资源）。

### 七、坑⑦：三个人切出三套模块——系统设计

**系统设计的主要目的是为系统制定蓝图，在各种技术和实施方法中权衡利弊，精心选择，合理地使用各种资源，最终勾画出新系统的详细设计方法**。方法有两种：**结构化设计方法、面向对象设计方法**（后者归面向对象板块）。内容分两段，这两段的分界线是最常考的一处：

- **概要设计，又称为系统总体结构设计**，基本任务是**将系统的功能需求分配给软件模块，确定每个模块的功能和调用关系，形成软件的模块结构图，即系统结构图**。报销系统里就是定下"分提单、审批、报表、打款四个模块，提单调审批、审批调打款"。
- **详细设计**的基本任务是**模块内详细算法设计、模块内数据结构设计、数据库的物理设计、其他设计（代码、输入/输出格式、用户界面）**，然后编写详细设计说明书、评审。报销系统里是"审批状态机具体怎么写、报销单表建几个索引"。

**分界线：模块之间的接口在概要设计定，模块内部的算法和数据结构在详细设计定。** 2021 上就直接考了这一刀——"软件详细设计阶段的主要任务不包括"，答案是"模块之间的接口设计"，因为那是概要设计的活。

切模块靠四条**系统设计基本原理**：**抽象化；自顶而下，逐步求精；信息隐蔽；模块独立（高内聚，低耦合）**。其中"信息隐蔽"是说模块内部的数据和实现不让外面看见、只留接口；"模块独立"就是第八节整节的内容。

再加六条**系统设计原则**，逐条落到报销系统上：

1. **保持模块的大小适中**——不是越小越好，切太碎接口数量暴涨（2020 下就考了"模块规模越小越好"是错的）；
2. **尽可能减少调用的深度**——A 调 B 调 C 调 D 调 E，出错时一层层剥太痛苦；
3. **多扇入，少扇出**——**扇出**是一个模块直接调用的下级模块个数，**扇入**是有多少个上级模块调用它。扇出太大说明这个模块什么都管；**扇入大说明这个模块被很多人复用，是好事**（考题固定问"模块的扇入大表示什么"，答**复用程度高**，不是"复杂度高"）；
4. **单入口，单出口**；
5. **模块的作用域应该在模块之内**；
6. **功能应该是可预测的**——同样的输入必须得到同样的输出，不许模块内部藏着随机或隐藏状态。

> ⚠️ 第 5 条培训资料写成"模块的作用域应该在模块之内"，这句自己跟自己绕。业界与考试的标准表述是"**模块的作用范围（作用域）应该在其控制范围（控制域）之内**"：**控制范围**指这个模块本身加上它所有的直接和间接下级模块；**作用范围**指模块里某个判定条件影响到的全部模块。报销系统里若"是否超 5000"这个判断写在提单模块，却要影响到不归提单管的打款模块，就是作用范围跑出了控制范围，改法是把判断上移到共同的上级模块。2021 上原题考的正是这一条，按标准表述记。

子系统怎么划、模块怎么算一个模块，培训资料还给了四组清单，考试以"下列哪项不属于"的形式出现，按"这一条在回答什么"归类即可记住：

- **子系统划分的原则**（六条，回答"横着切成几大块"）：子系统要具有相对独立性；子系统之间数据的依赖性尽量小；划分的结果应使数据冗余较小；设置应考虑今后管理发展的需要；划分应便于系统分阶段实现；划分应考虑到各类资源的充分利用。
- **子系统结构设计要考虑的问题**（四条，回答"块里再怎么切"）：每个子系统如何划分成多个模块；如何确定子系统之间、模块之间传送的数据及其调用关系；如何评价并改进模块结构的质量；如何从数据流图导出模块结构图。**它不管"采用何种数据结构和核心算法"——那是详细设计的事**，这正是本考点的标准错项。
- **系统结构设计原则**（八条）：分解-协调原则；自顶向下的原则；信息隐蔽、抽象的原则；一致性原则；明确性原则；**模块之间的耦合尽可能小，模块的内聚度尽可能高**；模块的扇入系数和扇出系数要合理；模块的规模适当。
- **模块的四个要素**：**输入和输出、处理功能**（把输入转换成输出所做的工作）是**外部特性**，反映模块的外貌；**内部数据**（仅供该模块本身引用的数据）、**程序代码**是**内部特性**。模块的特点是**可以组合、分解和更换**，**系统中的任何一个处理功能都可以看成是一个模块**，按功能具体化程度分为**逻辑模块和物理模块**——"审批"在概要设计阶段只是一个还没落到代码上的框，是逻辑模块；到详细设计写成 `ApprovalService` 这个具体的类或程序，就是物理模块。

画出来的图叫**模块结构图**，四条规矩：模块内部的凝聚性要强、模块之间的联系要少；**模块之间的连接只能存在上下级之间的调用关系，不能有同级之间的横向联系**；**整个系统呈树状结构，不允许网状结构或交叉调用关系出现**；所有模块都必须严格地分类编码并建立归档文件。**模块结构图主要关心的是模块的外部属性**，即上下级模块、同级模块之间的数据传递和调用关系，并不关心模块的内部。

### 八、坑⑧：凭什么说这次切得好——内聚与耦合（本课最重）

模块切完了，两个人各交一版，怎么判高下？**衡量模块独立程度的标准有两个：耦合性和内聚性。** 名字很唬人，其实就是"随手切"会犯的两类毛病，一类在模块外面，一类在模块里面：

- **黏得太紧**：给报销单加一个"附件"字段，结果审批、报表、打款、导出全要跟着改——这是**耦合**太强，毛病在模块**之间**；
- **各干各的**：`ReimbUtils` 里塞着"格式化日期""发邮件""算个税"，谁都往里加、谁都不敢删——这是**内聚**太低，毛病在模块**内部**。

**耦合谱是"两个模块靠什么通信"，通信手段越能绕过接口越糟；内聚谱是"模块里的东西凭什么待在一起"，理由越接近同一个功能越好。** 培训资料两条谱各分七档，都按**从低到高**列。

**先猜后讲。** 下面三段描述，各是哪一档？先自己给个答案，再看下面的表：

> 甲：提单模块把整张报销单结构体传给校验模块，校验模块只用其中的"金额"字段。
> 乙：导出模块收到一个 `mode` 参数，`mode=1` 导 Excel、`mode=2` 导 PDF。
> 丙：审批模块直接改了提单模块内部的私有变量 `_state`。

#### 耦合：七档，从"最松（最好）"到"最紧（最差）"

| 档 | 转录本定义（照录）｜记忆关键字 | 报销系统里的样子 | 改动会怎么波及 |
|---|---|---|---|
| 1 **无直接耦合** | **两个模块之间没有直接的关系，它们分别从属于不同模块的控制与调用，不传递任何信息**｜无直接关系 | `main` 分别调"提单模块"和"月度报表模块"，两者互不认识 | 完全不波及 |
| 2 **数据耦合** | **两个模块之间有调用关系，传递的是简单的数据值，相当于高级语言中的值传递**｜传递数据值调用 | `校验金额(amount, limit)`，只传两个数字 | 只有这两个数的含义变了才波及 |
| 3 **标记耦合** | **两个模块之间传递的是数据结构**｜传递数据结构 | `校验金额(报销单 r)`，对方其实只用 `r.金额`（甲） | 报销单加一个字段，校验模块也得跟着重新编译；看签名还看不出它用了哪几个字段 |
| 4 **控制耦合** | **一个模块调用另一个模块时，传递的是控制变量，被调用模块通过该控制变量的值有选择的执行模块内的某一功能**｜控制变量、选择执行某一功能 | `导出(报销单 r, int mode)`，mode 决定走 Excel 还是 PDF 分支（乙） | 调用方必须知道对方内部有哪几条分支；对方加一条分支，所有调用方都要改 |
| 5 **外部耦合** | **模块间通过软件之外的环境联合（如 I/O 将模块耦合到特定的设备、格式、通信协议上）时**｜软件外部环境 | 打印模块和归档模块都按财务局规定的固定报文格式往同一台票据打印机写 | 换打印机、报文格式改一位，两个模块一起改 |
| 6 **公共耦合** | **通过一个公共数据环境相互作用的那些模块的耦合**｜公共数据结构 | 五个模块直接读写全局的"报销政策"结构体（限额、审批级数、可报销科目） | 谁改了字段含义全体遭殃，而且出了事查不出是谁改的 |
| 7 **内容耦合** | **当一个模块直接使用另一个模块的内部数据，或通过非正常入口转入另一个模块内部时**｜模块内部关联 | 审批模块直接改提单模块的私有变量 `_state`（丙）；或用跳转直接跳进提单模块中段 | 对方内部随便改一行就可能崩，**最恶劣，任何情况下都要消灭** |

甲=标记耦合，乙=控制耦合，丙=内容耦合。**猜错最多的是甲**：常见错法是想"它只用了一个字段，那不就是传了个值吗"——**只看传过去的是什么，不看对方用了多少**，传结构体就是标记耦合。

> ⚠️ **外部耦合有两套口径**。培训资料用的是上表那句"通过软件之外的环境联合"；另一套在软考里同样常见的表述是"**一组模块都访问同一全局简单变量，而不是同一全局数据结构，且不通过参数表传递**"。两套口径在做题时不冲突，因为它们各自对应的题面不一样：题干出现**设备、格式、通信协议**，选外部耦合；题干出现**共享全局简单变量**，也选外部耦合；题干出现**公共数据环境、全局数据结构、共享内存区、公共文件**，选公共耦合。**分界线只有一句：共享的东西是不是一份数据结构。**

#### 内聚：七档，从"最差"到"最好"

| 档 | 转录本定义（照录）｜记忆关键字 | 报销系统里的样子 |
|---|---|---|
| 1 **偶然内聚** | **一个模块内的各处理元素之间没有任何联系**｜无直接关系 | `ReimbUtils` 里堆着"格式化日期 + 发邮件 + 算个税" |
| 2 **逻辑内聚** | **模块内执行若干个逻辑上相似的功能，通过参数确定该模块完成哪一个功能**｜逻辑相似、参数决定 | `处理单据(int 类型)`：1 新建、2 修改、3 作废，靠参数挑一个 |
| 3 **时间内聚** | **把需要同时执行的动作组合在一起形成的模块**｜同时执行 | `系统启动()` 一口气读配置、连数据库、预热汇率缓存、开日志——彼此无关，只因为都在启动那一刻做 |
| 4 **过程内聚** | **一个模块完成多个任务，这些任务必须按指定的过程执行**｜指定的过程顺序 | `月末结账()` 依次"锁定上月单据→生成凭证→通知财务"，次序不能乱，但前一步并不把结果直接喂给下一步 |
| 5 **通信内聚** | **模块内的所有处理元素都在同一个数据结构上操作，或者各处理使用相同的输入数据或者产生相同的输出数据**｜相同数据结构、相同输入输出 | 一个模块对同一张报销单表既"统计本月总额"又"导出明细清单"——两件事互不相干，只是操作同一份数据 |
| 6 **顺序内聚** | **一个模块中的各个处理元素都密切相关于同一功能且必须顺序执行，前一个功能元素的输出就是下一个功能元素的输入**｜顺序执行、输入为输出 | `生成月报()` 先"查出本月单据列表"，这个列表直接作为"汇总成报表"的输入——数据接力 |
| 7 **功能内聚** | **最强的内聚，模块内的所有元素共同作用完成一个功能，缺一不可**｜共同作用、缺一不可 | `计算个税(收入)`——整个模块就干这一件完整的事 |

**最容易混的是 4、5、6 三兄弟**，判据各只有一个词：**过程内聚看"动作"按次序（数据不接力）；顺序内聚看"数据"接力（前者的输出就是后者的输入）；通信内聚看"同一份数据"（动作之间互不相干）**。报销系统那三个例子换着读一遍就分得开：结账三步各自去库里读数（过程），生成月报第一步的返回值就是第二步的入参（顺序），统计和导出谁也不用谁的结果（通信）。

**一条附赠规律，能一次答对"耦合 + 内聚"的双问题**：**控制耦合的另一头，往往就是一个逻辑内聚的模块**——因为"要靠一个标志参数挑功能"这件事本身，就说明被调模块把若干个相似功能捆在了一起。上面的乙（`导出(r, mode)`）就是：调用方与它是控制耦合，它自己是逻辑内聚。

设计目标合起来八个字：**高内聚、低耦合**。注意"耦合低"不等于"模块之间不许说话"——报销系统里提单必须调审批，这是业务决定的；能改的是**用什么方式说话**，把传结构体改成传必要的值，把传开关改成拆成两个方法，就是在往谱系左边挪。

### 九、坑⑨：系统能跑，人却用不明白——人机界面设计

最后一公里。财务打开系统，点了三层菜单没找到"导出"，功能做了等于没做。培训资料给了**三大黄金原则**，每条下面的细则考试直接当选项用：

**1. 置于用户控制之下**——**以不强迫用户进入不必要的或不希望的动作的方式来定义交互方式**；提供灵活的交互；**允许用户交互可以被中断和撤销**；当技能级别增加时可以使交互流水化并允许定制交互；使用户隔离内部技术细节；设计应允许用户和出现在屏幕上的对象直接交互。（报销系统里：审批到一半能存草稿退出，不强迫一次填完。）

**2. 减少用户的记忆负担**——**减少对短期记忆的要求**；**建立有意义的缺省**；定义直觉性的捷径；**界面的视觉布局应该基于真实世界的隐喻**；以不断进展的方式揭示信息。（报销系统里：提单页默认填上申请人和当天日期，页面画成一张"报销单"的样子。）

**3. 保持界面的一致性**——允许用户将当前任务放入有意义的语境；**在应用系列内保持一致性**；**如过去的交互模型已建立起了用户期望，除非有迫不得已的理由，不要改变它**。（报销系统里：所有页面的"提交"都在右下角，别这一页在左上、那一页在右下。）

三条的立场分别是"谁做主"（用户）、"要记多少"（越少越好）、"变不变"（别乱变）。选项里凡是出现"强迫用户""不允许撤销""每个模块自成一套风格"，一定是反着写的。

---

**收口**：九个坑连起来是一条线——**用户嘴里的一句话，怎么一步步变成一堆切得干净、还能用的模块，并且随时能倒查回那句话**。①–⑤ 管"话"，把话分层、问全、理顺、写死、守住；⑥–⑨ 管"块"，先看清流程、再切模块、再量切得好不好、最后让人用得上。中间那条分水岭是**分析交出逻辑模型、设计交出物理模型**：分析回答"做什么"，设计回答"怎么做"，跨过它之前谈技术方案是越位，跨过它之后再改需求是返工。

## 考试怎么考

**考点① 内聚与耦合的档位判断（本课分值最高，2020下、2021上 连着考）。** 题目只给一句描述让你判档，判据是**固定的两个问题**：判耦合问"信息是**怎么**过去的"（不看模块干什么）；判内聚问"这些东西**凭什么**待在一起"（不看它们干得对不对）。错误选项的三种造法：把"只用了其中两个字段"当成数据耦合的理由（错，看传的是什么）；把控制耦合和数据耦合按"是不是走参数"分（都走参数，看参数的用途）；把过程/顺序/通信三兄弟互换（看动作、数据接力、同一份数据三个词）。排序题必错的选项一般把**逻辑排在偶然前面**，或把**内容排在公共前面**，记死两条七字序即可排除。

**考点② 概要设计 vs 详细设计。** 固定问法是"××阶段的主要任务不包括"。**模块之间的接口在概要设计定；模块内部的算法、数据结构、数据库物理设计在详细设计定。** 概要设计的产物是**模块结构图（系统结构图）**，不是用例图、类图或部署图。

**考点③ 模块结构的判断题。** 三句常考结论：**扇入大 = 复用程度高**（不是复杂度高）；**模块规模不是越小越好**；**作用范围应在控制范围之内**（不是反过来）。这三句在 2018上、2020下、2021上 都出现过。

**考点④ 需求的三个层次。** 一题三空，把三句话分别归到业务／用户／功能需求。判据是立场和颗粒度：说不出具体动作的组织级目标 → 业务需求；"用户能做某件事" → 用户需求；"系统必须实现某功能" → 功能需求；"响应时间、可靠性" → 非功能需求；"必须用某某数据库/操作系统" → 设计约束。

**考点⑤ 需求过程的阶段归属。** "需求开发分为获取情况、分析、（ ）和评审四个阶段"答**制订规格说明**——因为形成基线、跟踪变更、控制版本三个干扰项全属需求**管理**，不属开发。同类问法还有"需求验证通过后签字确认得到什么"（需求基线）、"某需求通过集成测试后处于什么状态"（被验证）。

**考点⑥ 需求获取方法配对。** 三空题固定搭配：**灵活性好、范围宽、但信息量大记录困难、需要领域知识 → 用户访谈**；**基于数理统计、能减少数据收集偏差 → 采样**；**通过高度组织的群体会议 → 联合需求计划 JRP**。

**考点⑦ 需求管理的判断题。** 正确项通常是"**变更控制委员会对项目中任何基线工作产品的变更都可以做出决定**"；常见错项是把变更流程的顺序写反（正确顺序是先评估影响、再送 CCB 审批、批准后才执行变更）。另外要记"需求的稳定性**属于**需求属性"，说它不属于的是错的。

**考点⑧ 流程表示工具与 BPR。** PFD 由**顺序、选择、循环**三种结构组合或嵌套而成；N-S 图**不适合**复杂程序设计；PAD 支持**结构化**程序设计（不是原型化）；IPO 图**可以**用于流程设计。BPR 是**根本性**改造、以**流程**为中心；BPM 与 BPR 的分界是"**BPM 不要求对所有流程进行再造**"。

**考点⑨ 人机界面三原则的归类。** 给一条细则问属于哪条原则：跟"能不能中断、撤销、定制"有关的归**置于用户控制之下**；跟"缺省值、捷径、真实世界隐喻"有关的归**减少用户的记忆负担**；跟"应用系列内统一、别改已建立的期望"有关的归**保持界面的一致性**。

### 参考答案

1. **D**。"非正常入口转入另一个模块内部"是**内容耦合**定义里的原句，也是七档中最恶劣的一档。A、B、C 三项都要求信息经由参数表或公共数据环境这类"正常途径"传递。

2. **C**。"所有处理元素都在同一个数据结构上操作"是**通信内聚**定义的前半句原话。别被"同一个数据结构"骗去选顺序内聚——顺序内聚要求前一步的**输出就是后一步的输入**，本题只说共用数据，没说接力。

3. **B**。**作用范围（判定影响到的模块）应该落在控制范围（本模块及其全部下级模块）之内**。反过来写的 A 是最常见错项。注意培训资料把这条原则写成"模块的作用域应该在模块之内"，表述不完整，按本题的标准表述记。

4. **C**。模块**之间**的接口在**概要设计**定，详细设计只管模块**内部**：算法、数据结构、数据库物理设计都在里面。

5. **B**。模块规模要**适中**，切得越碎接口越多、调用越深，反而更难维护。A、C、D 三条都是标准的启发式设计原则。

6. **D**。耦合衡量的是模块**之间**连接的紧密程度，取决于调用方式、接口复杂程度、通过接口的信息类型；"模块提供的功能数"说的是模块**自己**有多少功能，那是内聚的范畴，与耦合无关。

7. **C**。"前一处理元素的输出就是下一处理元素的输入"是**顺序内聚**的判别词。过程内聚同样讲次序，但各步之间不传数据。

8. **D**。题干特别说明传的是**数据结构**而不是数据值——传数据值是数据耦合，传数据结构就是**标记耦合**。

9. **B　C　A**。第一句"找出拼写错误并提供替换项列表来供选择"是站在用户角度说"我能用系统做什么"→ 用户需求；第二句"显示对话框、实现整个文档范围的替换"是明确规定开发人员要实现的软件功能 → 功能需求；第三句"用户能有效地纠正拼写错误"是说不出具体动作的高层目标 → 业务需求。三空的顺序恰好是"用户—功能—业务"，不是自然的从大到小，这正是本题的坑。

10. **A　D　C**。"灵活性好、范围宽、信息量大、记录困难、需要领域知识"是用户访谈的固定描述；"基于数理统计、减少数据收集偏差"是采样；"高度组织的群体会议"是联合需求计划 JRP。问卷调查在这三句里没有对应描述，是纯干扰项。

11. **A**。需求**开发**的四步是获取、分析、定义（制订规格说明）、验证（评审）。B、C、D 三项——形成需求基线、跟踪需求变更、控制需求版本——全部落在需求**管理**里，用"开发 vs 管理"这条分水岭一刀切掉。

12. **D**。CCB（变更控制委员会，也称配置控制委员会）的职责就是对建议的配置项变更做出评价、审批并监督实施，覆盖任何基线工作产品。B 错，需求的稳定性属于需求属性；C 错，正确顺序是先问题分析和变更描述、再变更分析和成本计算、最后变更实现，选项把前两步颠倒了；A 是 CMM 的内容，与需求管理不是一回事。

13. **A**。程序流程图由**顺序、选择、循环**三种基本结构组合或嵌套而成。B 错，IPO 图正是流程描述工具；C 错，PAD 支持的是**结构化**程序设计；D 错，N-S 图**不适合**复杂程序的设计——这一句被反写成"特别适合"是本题最爱的造错法。

14. **B　A**。BPR 的定义原话是"**根本性的再思考和彻底性的再设计**"，所以是根本性改造；核心是**以流程为中心**。增量式、迭代式是过程模型里的词，被借来当干扰项。

15. **A　B**。系统设计的主要内容就是**概要设计和详细设计**；系统总体结构设计（即概要设计）的产物是**模块结构图**。用例图、类图属于面向对象分析设计，部署图描述物理部署，都不是结构化概要设计的产物。

16. **D**。扇入是"有多少个上级模块调用它"，扇入大说明这个模块被反复复用，是**好事**，所以 C 错 D 对。A 错，扇出过大应该**增加中间层的控制模块**把下级分组，而不是继续分解下级；B 错，扇出过小才应该把下级模块**分解**，两项恰好互换了做法。

17. **B**。"采用何种数据结构和核心算法"是**详细设计**的任务，子系统结构设计只管划分模块、确定模块间传送的数据与调用关系、评价改进模块结构质量，以及如何从数据流图导出模块结构图。

18. **A**。给七档编号"偶然1 < 逻辑2 < 时间3 < 过程4 < 通信5 < 顺序6 < 功能7"，逐项代入：A 是 1→3→6→7，严格递增 ✔；B 是 2→1，逻辑排到了偶然前面 ✘；C 是 7→6→3→1，整个反着走 ✘；D 是 3→1，偶然排到了时间后面 ✘。

19. **A**。给七档编号"无直接1 < 数据2 < 标记3 < 控制4 < 外部5 < 公共6 < 内容7"：A 是 2→3→4→7 ✔；B 是 3→2 ✘；C 是 2→4→3 ✘；D 是 7→6→4→2，从高到低 ✘。

20. **B**。两问分开判。耦合看信息怎么过去：`mode` 是决定对方走哪条分支的**控制变量** → 控制耦合（`报销单 r` 这一半虽然是标记耦合，但判档取**最紧的那一档**）。内聚看凭什么待在一起：模块里是两个逻辑上相似的功能、靠参数挑一个执行 → **逻辑内聚**。这题正是"控制耦合的另一头常是逻辑内聚"那条规律。

21. ①业务需求（组织级目标，说不出具体动作）；②用户需求（用户能做什么）；③功能需求（规定开发人员必须实现的功能）；④设计约束（对系统的限制条件）。若再补一句"导出接口响应不超过 3 秒"，那是非功能需求。

22. 行全空 = FR-3 这条原始需求**根本没实现**，是**正向跟踪**（看用户原始需求是否都实现了）发现的问题；列全空 = UC-5 这个用例**没有任何原始需求要求**，属多做的功能，是**反向跟踪**（看软件实现的是否都是用户要求的）发现的问题。口诀：**空行漏做、空列多做**。

23. 原来是**过程内聚**——多个任务必须按指定的过程次序执行，但数据不接力。改成"第一步返回值作为第二步入参"后，前一功能元素的输出就是下一功能元素的输入，升为**顺序内聚**。

24. 违反"**模块的作用范围应该在其控制范围之内**"。"金额是否超 5000"这个判定写在提单模块里，控制范围只覆盖提单模块及其下级，却影响到了不归它调用的打款模块。改法是把这个判定上移到提单模块与打款模块共同的上级模块中，让作用范围重新落回控制范围之内。（培训资料把这条原则写作"模块的作用域应该在模块之内"，表述不完整，以本题的标准表述为准。）

## 速记

- 需求三层：业务（组织目标）→ 用户（我能做什么）→ 系统（功能／非功能／设计约束）；QFD 三类：常规、期望、意外
- 两大过程以**需求基线**为界：开发＝获取→分析→定义(SRS)→验证；管理＝变更控制、版本控制、需求跟踪、需求状态跟踪
- 获取六法：访谈（灵活但记录难）、问卷、采样（数理统计减偏差）、情节串联板、JRP（有组织的群体会议）、需求记录技术；采样量 = 0.25×(可信度因子/错误率)²
- 结构化分析三模型：DFD 功能、STD 行为、E-R 数据，外加数据字典；跟踪矩阵**空行漏做（正向）、空列多做（反向）**
- 分析出**逻辑模型**、设计出**物理模型**；概要设计定模块与接口、产出模块结构图，详细设计定算法、数据结构与数据库物理设计
- 模块口诀：扇入大＝复用高，扇出大要加中间控制模块；规模适中不是越小越好；作用范围 ⊆ 控制范围
- 耦合低→高：**无 数 标 控 外 公 内**；传值＝数据、传结构＝标记、传开关＝控制、绑设备格式协议或共享全局简单变量＝外部、共享公共数据环境＝公共、伸手改内部或非正常入口＝内容
- 内聚低→高：**偶 逻 时 过 通 顺 功**；过程＝动作按次序、顺序＝数据接力、通信＝同一份数据；BPR 根本性、以流程为中心，BPM 不要求全部再造
