## 定位

**这一课回答**：“这个对象该怎么造”“这两个类该怎么拼”这两类反复出现的麻烦，前人整理出的 12 个成套解法各治什么病、考试怎么从一句话把它认出来。

**前后关系**：23 的 SOLID 说的是该守什么规矩，这一课是守规矩的成套招式；行为型 11 个归 29；下午题 6 的 Java 代码填空归 53，本课只到上午题为止。

**分值与去向**：板块上午约 9–11 分，已核到的三个场次（2018下、2022下、2023上）设计模式都是整组出现、每次 4 分，本课的创建型＋结构型在其中占 0–2 分，另一半是 29 的行为型。零计算。

## 开讲：报销系统写到第三个月，两句话在代码里到处都是

还是讲义 15、16、23 那套内部报销系统：员工提单、主管审批、财务打款。代码写到第三个月，你会发现两句话出现的频率高得离谱——一句是 `new 一个对象`，一句是"把对象包一层再用"。这一课的 12 个模式，就是这两句话各自惹出来的麻烦的标准答案。开始之前先把"模式"这个词分层，不然后面全乱。

### 一、先分清层次：架构模式、设计模式、惯用法

周会上问一句"我们这套报销系统用了什么模式"，三个人给了三个答案：架构师说"B/S，浏览器直连服务端"；后端说"通知那块用了工厂"；一个写 C++ 的同事说"我那个模块用的是引用计数"。**先别往下看，你觉得这三个答案是同一个层次的东西吗？**

不是。三个人各答了一层，而资料把这三层分得很清楚，考试也就考这三层的归属。

**架构模式**，原文：「软件设计中的**高层决策**，例如 C/S 结构就属于架构模式，架构模式反映了开发软件系统过程中所作的基本设计决策。」C/S 就是 Client/Server（客户端—服务端），把系统劈成两半、一半装在用户机器上、一半跑在服务器上。这是整个系统的骨架级决定，定错了要推倒重来。报销系统选 B/S（拿浏览器当客户端）属于这一层。

**设计模式**，原文：「每一个设计模式描述了一个在我们周围**不断重复发生的问题，以及该问题的解决方案的核心**。这样，你就能一次又一次地使用该方案而不必做重复劳动。」原文还有一句：「设计模式的核心在于提供了相关问题的解决方案，使得人们可以更加简单方便的复用成功的设计和体系结构。」它管的是骨架里面某几个类怎么摆，跟用哪门语言写没关系。四个基本要素是封闭清单，考过原句：**模式名称、问题（应该在何时使用模式）、解决方案（设计的内容）、效果（模式应用的效果）**。

**惯用法**，原文：「是最低层的模式，关注**软件系统的设计与实现，实现时通过某种特定的程序设计语言**来描述构件与构件之间的关系。每种编程语言都有它自己特定的模式，即语言的惯用法。例如引用—计数就是 C++ 语言中的一种惯用法。」引用计数就是给对象记一个"现在有几个人在用我"的数，减到 0 就自动释放——这是 C++ 没有垃圾回收才要操心的事，换到 Java 根本用不上，所以它只能算"某一门语言里的"模式，层次最低。

三层一句话：**架构模式定骨架（系统级）→ 设计模式定几个类怎么摆（跨语言）→ 惯用法定一门语言里怎么写（语言相关）**。

**23 个模式是怎么分的。** GoF 是 Gang of Four（四人组，《设计模式》原书的四位作者），资料和考卷上说"23 种设计模式"都指这本书。它按**目的**把 23 个分三类：**创建型 5 个**管对象怎么造出来，**结构型 7 个**管类和对象怎么拼成更大的结构，**行为型 11 个**管对象之间怎么分工、怎么传消息（行为型整块在 29）。5＋7＋11＝23，这个拆分本身就是考点。

![设计模式分类总览：三类与 23 个模式名，带下划线者兼类模式与对象模式](../外部资源/转录md/images/fig_d14_s028.png)

图右下角那行小字是**第二个分类维度**，资料正文没写，但已核到的三组设计模式真题（2018下、2022下、下面练习 2）都拿它凑了一个空：「有下划线的表示既可以是类模式，也可以是对象模式；无下划线的表示只是对象模式」。**类模式**指这个模式靠继承搭起来，父子关系在编译时就定死；**对象模式**指靠一个对象持有另一个对象（组合）搭起来，运行时还能换人。

图上带下划线的只有四个：**工厂方法、适配器、解释器、模板方法**（前两个在本课，后两个在 29）；迭代器那一条下面是一道红色波浪线，那是排版软件的拼写检查痕迹，不是下划线，别数成第五个。所以考卷上出现"结构型类模式""行为型对象模式"这种"分类＋类／对象"的两段式答案时，后半个词就靠这条判——除这四个之外，一律是"对象模式"。

### 二、`new` 那条线：创建型五个

报销系统里第一句到处出现的代码是 `new`。一开始没人觉得这是问题，麻烦是一件件冒出来的，每冒一件就逼出一个创建型模式。资料给每个模式配了一句原文定义和一栏**「记忆关键字」**——后者是资料替你压缩好的题眼，也是上午题最直接的抓手，下面每个模式都照录。

**① 换个实现，要改遍全场 → 工厂方法（Factory Method）**

代码里到处 `new 钉钉通知()`。公司把办公软件换成企业微信，这一句要在几十个文件里改。第一反应是把 `new` 集中到一处：写个 `通知工厂.create("钉钉")`，里面一串 if 决定造哪个。

散落的 `new` 是收拢了，但新增一种通知方式仍要回来撬开这串 if，"对扩展开放、对修改关闭"（23 讲过的开闭原则）还是没做到。顺带一提：这种带 if 的集中工厂叫**简单工厂**，**它不在 GoF 的 23 个之内**，别把它当第 24 个模式。

GoF 的答案是把工厂本身也做成能继承的。原文定义：「定义一个创建对象的接口，但由子类决定需要实例化哪一个类。使得子类实例化过程推迟」，记忆关键字是**「子类决定实例化」**。落到报销系统：留一个抽象的 `通知工厂`，钉钉工厂、企业微信工厂各是它的一个子类，各自只负责造自己那种通知对象；换实现＝换传进来的工厂子类，已有代码一行不改；新增一种＝加两个新类。

**② 要换的不是一个类，是配套的一整套 → 抽象工厂（Abstract Factory）**

报销系统要支持两套税务口径。口径 A 有它自己的发票校验器、金额计算器、报表生成器；口径 B 另有三个，而且三个必须成套用——拿 A 的校验器配 B 的计算器会算错。这时要换的是"一族"东西，不是一个。

原文定义：「提供一个接口，可以创建一系列相关或相互依赖的对象，而无需指定它们具体工作的类」，记忆关键字是**「抽象接口」**。（这句里的"具体工作的类"是转录多出来的两个字，扫描原件与本章真题原文都作"而无需指定它们具体的类"，考场按后者认。）

"一系列相关或相互依赖"就是"一族"的意思：`口径A工厂` 一个人负责交出配套的三件，客户端拿到哪一族，全看给它的是哪个工厂。

**③ 构造步骤复杂，同样的步骤要拼出不同结果 → 生成器（Builder，资料作"构建器"）**

报销单的打印件：抬头、明细表、合计栏、签字栏，四步顺序固定，一步都不能少；但差旅报销单和招待费报销单每一步填的内容完全不同。

把"四步的顺序"和"每一步填什么"拆开——顺序写在一个指挥者（专门按固定步骤发号施令、自己不填内容的那个类）里，每一步填什么交给不同的生成器实现。原文定义：「将一个复杂类的表示与其构造相分离，使得相同的构建过程能够得出不同的表示」，记忆关键字是**「类和构造分离」**。

下午题 6 考过一整道生成器：快餐厅的儿童套餐包括主餐、饮料和玩具，餐品种类可能不同但制作过程相同，前台服务员调度厨师制作——"过程相同、结果不同"正是这句定义的场景版。代码怎么填在 53，上午题只要能从"相同的构建过程、不同的表示"这句话认出它。**归类要记牢：生成器是创建型**，最常见的错法是被"构建过程"里的"过程"两个字带偏、误记成行为型。

**④ 全系统只该有一份 → 单例（Singleton）**

汇率表、审批规则缓存、写日志的那个对象——报销系统里这几样多造一份就出乱子：两份汇率表各自刷新，同一张单前后能算出两个数。靠口头约定"别再 new 了"不管用，得把规则焊在类自己身上：构造方法私有（外面 new 不出来）、类里自己攥着那唯一一份、再开一个静态方法当全世界唯一的取用入口。

原文定义：「保证一个类只有一个实例，并提供一个访问它的全局访问点」，记忆关键字是**「唯一实例」**。定义里两个要件缺一不可，"只有一个实例"是结果，"全局访问点"是手段。

**⑤ 造起来太贵，而我只要"跟它差不多的一份" → 原型（Prototype）**

生成一张报销单模板要查三张表、跑一遍规则引擎，几百毫秒；而员工连着提十张差旅单，抬头、部门、审批链几乎一样，只有明细不同。与其造十次，不如造一次、拷贝九份、每份改改明细。原文定义：「用原型实例指定创建对象的类型，并且通过拷贝这个原型来创建新的对象」，记忆关键字是**「原型实例，拷贝」**。

2023 年上半年考过一道招聘系统自动生成简历的题，题干里就是"声明一个复制自身的接口""通过复制……的对象来创建新的对象"，答原型、创建型。题干只要出现"拷贝""复制自身""克隆"，就是它。

### 三、"包一层"那条线：结构型七个

第二句到处出现的代码是"包一层"：拿到一个对象不直接用，先给它套个壳。壳的用途不一样，就长成了七个不同的模式。麻烦接着上面的编号往下排。

**⑥ 第三方接口跟我方对不上，两边都改不了 → 适配器（Adapter）**

报销系统要接税务局的发票查验服务。我方内部约定的接口是"查验(发票号, 金额)"，对方 SDK（Software Development Kit，第三方发的一包现成代码，只能调、改不了）给的是 "verify(一串 XML 字符串)"。

两边都动不了，只能在中间加个转换头：它朝我方这一侧长成我方接口的样子，调用进来后翻译成对方的参数格式再转发出去。原文定义：「将一个类的接口转换成用户希望得到的另一种接口。它使原本不相容的接口得以协同工作」，记忆关键字是**「转换，兼容接口」**。生活里就是出国用的电源转换插头。

适配器是本课两个"兼类模式"的其中一个：转换头**继承**被适配的类，叫类适配器；转换头**持有**被适配的对象，叫对象适配器。

**⑦ 想加功能又不想改原类，还要能自由组合 → 装饰（Decorator）**

报销单提交后要加两件事：写一条审批日志、给审批人发条短信。两件事将来可能只开一件、也可能都开，而且不许动 `报销单` 这个类。用继承写：得有"带日志的""带短信的""两个都带的"三个子类；再加第三件事就要 7 个——功能一多子类个数按指数涨，行话叫**类爆炸**。

装饰的做法是每件事做成一层壳，壳对外仍然是一张报销单，壳里裹着上一层，可以无限往外套。原文定义：「动态的给对象添加一些额外的职责。它提供了用子类扩展功能的一个灵活的替代，比派生一个子类更加灵活」，记忆关键字是**「附加职责」**。加第三件事只多一个类，而且开哪几件是运行时决定的，不是编译期写死的。

**⑧ 功能不变，只想在访问前面加一道关卡 → 代理（Proxy）**

同样是包一层，但这一层不添新职责。报销单上的银行卡号只有财务能看，别人拿到的该是打码的——功能还是"读卡号"，只是前面加了一道"你是谁"的检查；或者单据上挂着十兆的发票附件，列表页先不去取，等真点开了才去加载（**延迟加载**：先给个空壳，用到时才真去拿数据）。原文定义：「为其他对象提供一种代理以控制这个对象的访问」，记忆关键字是**「代理控制」**。

**⑨ 子系统太乱，每个调用方都得懂全套流程 → 外观（Façade）**

提一张报销单，后台要按顺序调预算校验 → 发票查验 → 生成会计凭证 → 通知审批人。四个子系统各有各的接口，而 Web 端、App 端、批量导入三个调用方都得把这套顺序背下来，流程一改三处跟着改。外观的做法是在这四个子系统前面立一扇门：外面只调 `提单服务.提交(单据)`，顺序只在门后维护一处。

原文定义：「定义一个高层接口，为子系统中的一组接口提供一个一致的外观，从而简化了该子系统的使用」，记忆关键字是**「对外统一接口」**。注意"子系统"三个字，题干里出现"为一组接口提供统一入口／一致界面""简化子系统的使用"就是它。

**⑩ 单个和整体想一样对待 → 组合（Composite）**

一张报销单下面挂费用明细，明细下面还能再挂子明细：一次差旅拆成机票和住宿，住宿再拆成三晚。算总额时如果每次都要先判断"这是一条还是一组"，这种判断会写得到处都是。

组合的做法是让"单条明细"和"一组明细"实现同一个接口，都有一个 `金额()`；一组的 `金额()` 就是把下面每一项的 `金额()` 加起来。原文定义：「将对象组合成树型结构以表示"整体-部分"的层次结构，使得用户对单个对象和组合对象的使用具有一致性」，记忆关键字是**「整体-部分，树形结构」**。

**⑪ 小对象太多，内存吃不消 → 享元（Flyweight）**

年底导出全公司十万行报销明细，每行都带一个"费用类型"对象（类型名、报销比例、会计科目）。十万个对象里其实只有十几种不同的内容。享元的做法是这十几种各造一个、全场共用，每行都不一样的东西（这一行的金额）不塞进对象里，用的时候当参数传进去。

原文定义：「提供支持大量细粒度对象共享的有效方法」，记忆关键字是**「细粒度，共享」**。这里有一对配套的词，资料表里没写，出自 GoF 原书对享元的标准描述：可共享、不随场合变的部分（费用类型的名称和比例）叫**内部状态**，存在享元对象里；随场合变的部分（这一行的金额）叫**外部状态**，调用时传进去。

**⑫ 两个维度都在长，组合起来会炸 → 桥接（Bridge）**

报销单有差旅、招待、办公三种类型，审批通知有钉钉、邮件、纸质三种渠道。用继承写就是 3×3＝9 个类，再加一种类型就要 12 个。桥接的做法是把两个维度拆成两条各自独立的继承线——报销单这一侧只管类型，渠道那一侧只管怎么送——再让报销单持有一个渠道对象，谁长都不影响对方，9 个类变回 3＋3 个。

原文定义：「将类的抽象部分和它的实现部分分离开来，使它们可以独立地变化」，记忆关键字是**「抽象和实现分离」**。定义里的"抽象部分"指报销单这一侧（使用者直接打交道的那层），"实现部分"指渠道这一侧（真正干活的那层）。

### 四、四对最容易混的，各给一条可操作判据

**第一对：工厂方法 vs 抽象工厂。** **先别往下看**：上面 ① 的"把钉钉通知换成企业微信通知"和 ② 的"整体切换税务口径、三件配套一起换"，各该用哪个？

判据一句话：**一个工厂交出几种产品**。交出一种，是工厂方法（造哪一种由工厂子类决定）；交出一族配套的，是抽象工厂。所以 ① 是工厂方法、② 是抽象工厂。题干里出现"一系列""一族""相关或相互依赖""整套"就往抽象工厂上靠；只说"由子类决定实例化哪一个类"就是工厂方法。

**第二对：适配器 vs 桥接。** 两个都在摆弄"抽象一侧和实现一侧"，判据是**事后补救还是事前设计**。税务局的 SDK 已经在那儿摆着、接口对不上、两边都改不了，只能事后加一个转换头——适配器；报销单类型和审批渠道两个维度都还会继续长，一开始就拆成两条线用组合连起来、谁变都不牵连谁——桥接。再补一条：适配器改的是**接口长相**（类还是那些类），桥接改的是**类的搭法**（一条继承线拆成两条，中间用组合连）。

**第三对：装饰 vs 代理。** **先别往下看**：⑦ 里"给报销单加审批日志、加短信通知，但不想改原类"，你会说这是装饰还是代理？

多数人第一反应是代理，因为"包一层拦一下"听起来就很代理。正确答案是装饰。这两个模式的类结构几乎一模一样——都实现使用者看到的那个接口、内部都握着一个被包住的对象——**只能靠意图分**：判据是**你在给它加新职责，还是在管谁能用它**。

日志和短信是新加的职责，而且要能自由组合，所以是装饰；打码、鉴权、延迟加载并没有添新功能，只是控制访问，所以是代理。附带两个旁证：装饰常常一层套一层，代理通常只有一层；装饰的使用者知道自己在加料，代理的使用者往往根本不知道背后还有个真身。

**第四对：组合 vs 享元。** 两个都跟"一大堆小对象"沾边，但问的不是一件事。判据看题干在问什么：问"能不能把单个和整体一样对待"→ 组合（报销单挂明细、明细挂子明细，算总额时对一条和对一组用同一个方法）；问"对象太多、内存吃不消、能不能共用"→ 享元（十万行共用十几个费用类型对象）。一个关心**结构长成什么样**，一个关心**实例有几个**。

再补两句对照。**外观 vs 适配器**：外观是**简化**（子系统本来就能用，只是调起来麻烦），适配器是**转换**（接口本来就对不上，不转就没法用）。**外观 vs 中介者**：外观是**单向**的，外面通过它进子系统，子系统不反过来找它；中介者是**双向**的，一组对象互相通信全走它——中介者属行为型，在 29。

**收口**：`new` 那条线上五件麻烦——换实现、换整套、构造步骤复杂、只能有一个、造起来太贵——对上创建型五个；"包一层"那条线上七件麻烦——接口对不上、加职责、控访问、子系统太乱、树形结构、对象太多、两个维度都在变——对上结构型七个。12 件麻烦对 12 个模式，不多不少。剩下 11 个行为型不在这两条线上，它们管的是对象之间怎么分工、怎么传消息，那是 29 的事。

## 考试怎么考

**考点① 分类归属。** 直接问"XX 属于哪一类"，或者在多空题的最后一空问。三处最容易记反：**享元是结构型**（它有个"享元工厂"，最容易被当成创建型）；**生成器是创建型**（"构建过程"四个字像行为型）；**简单工厂不在 23 个之内**。第二个维度按图上的下划线判：只有**工厂方法、适配器、解释器、模板方法**四个能当类模式，其余一律是对象模式——23 个里只有这 4 个沾"类"，所以两段式答案的后半个词绝大多数是"对象"，见到"结构型类"先怀疑。

**考点② 给一句意图，选模式名。** 这是本课最主要的题型，题干往往就是定义原句的改写，考的是"记忆关键字"这一栏。下表左列一字照录资料原文，右列是它在题干里通常的说法：

| 模式 | 资料原文的「记忆关键字」 | 题干里通常长这样 |
|---|---|---|
| 抽象工厂 Abstract Factory | 抽象接口 | 一系列／一族相关或相互依赖的对象、整套配套 |
| 构建器 Builder（生成器） | 类和构造分离 | 表示与构造分离、相同的构建过程得出不同的表示 |
| 工厂方法 Factory Method | 子类决定实例化 | 由子类决定实例化哪一个类、实例化推迟到子类 |
| 原型 Prototype | 原型实例，拷贝 | 复制自身、通过拷贝已有对象来创建新对象、克隆 |
| 单例 Singleton | 唯一实例 | 只有一个实例、全局访问点 |
| 适配器 Adapter | 转换，兼容接口 | 接口不相容／不符合要求、转换成希望的接口 |
| 桥接 Bridge | 抽象和实现分离 | 抽象部分与实现部分分离、都可以独立变化 |
| 组合 Composite | 整体-部分，树形结构 | 树型结构、部分-整体层次、单个与组合使用一致 |
| 装饰 Decorator | 附加职责 | 动态添加额外职责、比派生子类更灵活 |
| 外观 Façade | 对外统一接口 | 为子系统的一组接口提供一致的外观、高层接口 |
| 享元 Flyweight | 细粒度，共享 | 支持大量细粒度对象的共享 |
| 代理 Proxy | 代理控制 | 为其他对象提供代理以控制对该对象的访问 |

**考点③ "该模式适用于（ ）的情况"和"以下叙述不正确的是"。** 这两种题的四个选项里，错项常见的造法有三种：**把另一个模式的适用场景搬来当选项**（"想表示对象的部分-整体层次结构"是组合的、"想使用一个已经存在的类，而它的接口不符合要求"是适配器的、"以动态透明的方式给单个对象添加职责"是装饰的——这三条就是练习 2 里三个错项的真实出处）；**把分类写错**（问的是结构型，给你一个行为型的名字）；**把方向写反**（"由父类决定实例化哪一个子类"，工厂方法是反过来的）。对付它的办法是先认出正确那条对应哪个模式，再回头看题干问的是不是同一个。

## 速记

- 三层：架构模式定骨架（C/S）＞设计模式定几个类怎么摆＞惯用法定一门语言怎么写（C++ 引用—计数）；设计模式四要素＝模式名称、问题、解决方案、效果
- 23＝创建 5＋结构 7＋行为 11；**享元属结构型、生成器属创建型、简单工厂不在 23 内**
- 兼类模式与对象模式的只有**工厂方法、适配器、解释器、模板方法**，其余都是对象模式
- 创建型关键字：抽象工厂＝抽象接口、构建器＝类和构造分离、工厂方法＝子类决定实例化、原型＝原型实例拷贝、单例＝唯一实例
- 结构型关键字：适配器＝转换兼容接口、桥接＝抽象和实现分离、组合＝整体-部分树形结构、装饰＝附加职责、外观＝对外统一接口、享元＝细粒度共享、代理＝代理控制
- 一种产品用工厂方法、一族配套用抽象工厂；事后转接口用适配器、事前拆维度用桥接（m×n 变 m＋n）
- 加职责是装饰、控访问是代理；简化子系统是外观、转换接口是适配器；外观单向、中介者双向
- 享元：可共享不随场合变的是内部状态（存对象里），随场合变的是外部状态（调用时传）
