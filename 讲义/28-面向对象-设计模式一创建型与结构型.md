# 28 · 面向对象：设计模式(一)——创建型与结构型

> 真题：高频设计模式 2021上/2022下/2024上/2025上（未逐题对应模式）｜无计算｜未讲（自学讲义）

## 第 0 层 · 定位

**这一课回答**：常见设计问题有没有成套解法：创建型 5 个（对象怎么造）、结构型 7 个（类/对象怎么装），每个的意图和识别关键词。

**前后关系**：设计模式是 23 SOLID 原则的落地招式；行为型 11 个在 29；53 是下午题实战（按 Java 练一门）。

**分值与去向**：上午稳定 1–2 题（给意图选模式、判分类归属）；下午题 5/6 二选一 15 分考代码填空。零计算。

## 第 1 层 · 理解

### 一句话

> 写业务代码久了会反复撞上同几类结构性麻烦。GoF 把 23 个经工程验证的解法整理成册——**设计模式不是语法，是"面向接口编程、组合优于继承、封装变化点"这些原则的成套用法**。

### 痛点：你一定撞过的三堵墙

- **新增一种类型，要改一堆调用方** —— 代码里到处 `new PdfExport()`，加个 CSV 就得满仓库改
- **功能想自由组合，子类却爆炸** —— 奶茶要能加珍珠、椰果、布丁任意组合，用继承得建 2ⁿ 个子类
- **两个模块焊得太死，改不动** —— 接口对不上、调用顺序散落各处

### 一条主线（分类本身就是考点）

```
反复出现的结构性问题
   ↓
GoF 23 个模式，按【目的】分三类 —— 分类归属本身年年考：

  创建型 (5)  ── 对象怎么【造】     把 new 的细节封装起来
                 工厂方法、抽象工厂、生成器、原型、单例
  结构型 (7)  ── 类/对象怎么【装】   怎么拼成更大的结构
                 适配器、桥接、组合、装饰器、外观、享元、代理
  行为型 (11) ── 对象间怎么【协作】  职责怎么分、消息怎么传（第27课）
                 观察者、策略、责任链、命令、状态、模板方法、
                 迭代器、中介者、备忘录、访问者、解释器
   ↓
上午题的考法主要两种：① 给一句 GoF 意图原句 → 选模式名；② 判断分类归属
   ↓ 所以真正要背的不是代码，是每个模式的
        【一句话意图 + 识别关键词】
   ↓
下午题 5/6 才考代码填空，且只考高频那 8–10 个
```

**结论：上午靠"识别关键词"，下午靠"高频子集的代码结构"。两者投入方式不一样，别搞混。**

## 第 2 层 · 考点：考试怎么问

### 考点① 分类归属（"XX 属于哪一类"，送分）

**创建型 5 个**：工厂方法、抽象工厂、**生成器**、原型、单例
**结构型 7 个**：适配器、桥接、组合、装饰器、外观、享元、代理
**行为型 11 个**：见第 27 课

> ⚠️ 最常见的陷阱：**享元是结构型**，不是创建型（虽然它有个"享元工厂"）；**生成器是创建型**（本讲义因排课把它放在 27 课讲，但归类要记牢）。
> ⚠️ **简单工厂不属于 GoF 23 模式**，但考试里出现过这个名字。

### 考点② 创建型五模式——意图与识别关键词

#### 简单工厂（非 GoF，理解工厂方法的台阶）

**痛点**：到处 `new PdfExport()`、`new ExcelExport()`，调用方和具体类焊死。第一步改进：把 new 集中到一个工厂类按参数分发。
```java
class ExportFactory {
    public static Export create(String type) {
        if ("pdf".equals(type))   return new PdfExport();
        if ("excel".equals(type)) return new ExcelExport();
        throw new IllegalArgumentException(type);
    }
}
```
**遗留问题**：新增产品仍要改这个 if/switch，**违反开闭原则**——这正是工厂方法要解决的。

#### 工厂方法 Factory Method【下午题高频】

**意图（GoF 原句）**：定义一个用于创建对象的接口，**让子类决定实例化哪一个类**；使一个类的实例化**延迟到其子类**。

**思路**：把"工厂"本身抽象成接口，**每种产品配一个具体工厂子类**。

**角色**：Product（抽象产品）、ConcreteProduct、Creator（抽象创建者，声明工厂方法）、ConcreteCreator。

```java
interface Export { void export(String data); }               // 抽象产品
class PdfExport implements Export { public void export(String d) {} }

abstract class ExportFactory {                               // 抽象创建者
    public abstract Export create();                         // 工厂方法：造什么由子类决定
}
class PdfExportFactory extends ExportFactory {               // 具体创建者
    public Export create() { return new PdfExport(); }
}
// 新增 CSV：加 CsvExport + CsvExportFactory 两个新类，已有代码一行不改（开闭原则）
```
**识别关键词**：**"让子类决定实例化哪一个类"、"实例化延迟到子类"**

#### 抽象工厂 Abstract Factory

**意图**：提供一个创建**一系列相关或相互依赖对象**的接口，而无需指定它们具体的类。
**识别关键词**：**"产品族"、"一系列/一组相关产品"**
**场景**：换皮肤时按钮 + 文本框 + 滚动条要**整套一起换**风格。
> **与工厂方法的分界线**：工厂方法一个工厂只造**一种**产品；抽象工厂一个工厂造**一族**产品。

#### 单例 Singleton【下午题高频】

**痛点**：全局配置、连接池、日志对象——整个进程只该有一份。靠口头约定"别 new 第二个"不可靠，要把规则**焊死在类自己身上**。

**意图**：保证一个类**仅有一个实例**，并提供一个访问它的**全局访问点**。

**三件套**：**构造私有 + 类内持有唯一实例 + 静态方法作全局访问点**

```java
// 饿汉式：类加载时就创建 —— JVM 类加载机制保证线程安全；缺点：不用也占内存
class Config {
    private static final Config INSTANCE = new Config();
    private Config() {}                                   // 构造私有
    public static Config getInstance() { return INSTANCE; }
}
// 懒汉式：第一次调用才创建（延迟加载）—— 多线程下两个线程可能同时通过 null 判断，
// 各建一份，所以【必须加锁】；进阶写法 DCL + volatile，软考知道名字即可
class LazyConfig {
    private static LazyConfig instance;
    private LazyConfig() {}
    public static synchronized LazyConfig getInstance() {
        if (instance == null) instance = new LazyConfig();
        return instance;
    }
}
```
**识别关键词**：**"仅有一个实例"、"全局访问点"**
**高频错误选项**：**"懒汉式天然线程安全"→ 错**，必须加同步。

#### 原型 Prototype

**意图**：用原型实例指定创建对象的种类，并通过**拷贝**这些原型创建新对象。
**识别关键词**：**"拷贝 / 克隆已有对象来创建"**（Java 的 `clone()`）
**场景**：对象初始化成本高（要读库、大量计算），复制现成的比从头造快。

> 创建型第 5 个成员 **生成器 Builder** 在第 27 课补讲（排课原因），但**归类记住是创建型**。识别关键词：**"复杂对象的构建与表示分离"、"同样的构建过程可创建不同表示"**。

### 考点③ 结构型七模式——意图与识别关键词

#### 适配器 Adapter【下午题高频】

**痛点**：接入第三方支付 SDK。我方接口是 `pay(int cents)`，SDK 给的是 `sendPayment(String json)`——两边对不上，且**都改不了**。生活类比：**电源转换插头**。

**意图**：将一个类的接口**转换**成客户希望的另一个接口，使原本由于**接口不兼容**而不能一起工作的类可以一起工作。

**角色**：Target（客户期望的接口）、Adaptee（被适配的现有类）、Adapter。
> 继承 Adaptee 的叫**类适配器**，组合持有的叫**对象适配器**——Java 单继承，实际多用**对象适配器**。

```java
interface Payment { void pay(int cents); }                  // Target
class AliSdk { public void sendPayment(String json) {} }     // Adaptee（改不了）

class AliAdapter implements Payment {                       // Adapter：转换头
    private AliSdk sdk = new AliSdk();                      // 对象适配器：组合持有
    public void pay(int cents) {
        sdk.sendPayment("{\"amount\":" + cents + "}");      // 翻译成对方接口
    }
}
```
**识别关键词**：**"接口不兼容"、"转换接口"**

#### 装饰器 Decorator【下午题高频】

**痛点**：奶茶可加珍珠、椰果、布丁，任意组合任意份数。用继承建"珍珠奶茶、珍珠椰果奶茶……"→ **2ⁿ 种，类爆炸**。
**思路**：把每种加料做成一层**包装**——每层包着一杯奶茶，它**自己也是**奶茶，可无限叠加。
**现成例子**：`new BufferedInputStream(new FileInputStream(f))`，缓冲就是包上去的一层。

**意图**：**动态**地给一个对象**添加额外的职责**；就增加功能来说，**比生成子类更为灵活**。

**角色**：Component（抽象构件）、ConcreteComponent（原始对象）、Decorator（**实现 Component 的同时持有一个 Component**）、ConcreteDecorator。

```java
interface MilkTea { int cost(); }                                     // Component
class BaseTea implements MilkTea { public int cost() { return 10; } }

abstract class Topping implements MilkTea {           // 既"是"奶茶
    protected MilkTea inner;                          // 又"包着"一杯奶茶  ← 关键结构
    Topping(MilkTea inner) { this.inner = inner; }
}
class Pearl extends Topping {
    Pearl(MilkTea t) { super(t); }
    public int cost() { return inner.cost() + 2; }    // 在原功能之上叠加
}
// new Pearl(new Pearl(new BaseTea())) —— 双份珍珠，任意组合
```
**识别关键词**：**"动态添加职责/功能"、"比生成子类更灵活"**

#### 代理 Proxy

**痛点**：高清图加载慢、远程服务调用、敏感操作要鉴权——不让客户端直接碰真实对象，中间放个**替身**。
**意图**：为其他对象提供一种代理以**控制对这个对象的访问**。
**角色**：Subject（抽象接口）、RealSubject、Proxy（实现 Subject、持有 RealSubject，在转发前后加控制逻辑）。

> ⚠️ **装饰器 vs 代理（最高频辨析）**：两者**结构几乎相同**（都实现同一接口 + 持有同类型引用），**只能看意图区分**：
> **增强功能 → 装饰器**（常多层叠加）；**控制访问 → 代理**（通常一层，客户端往往不感知真实对象）。

**识别关键词**：**"控制对对象的访问"、"替身"**

#### 外观 Facade【下午题高频】

**痛点**：下单要按顺序调 库存→支付→物流。每个调用方都得懂这套流程，流程一变全体跟着改。
**意图**：为**子系统**中的一组接口提供一个**一致的界面**；定义一个**高层接口**使子系统更容易使用。

```java
class OrderFacade {                                   // 外观：唯一入口
    private StockService stock = new StockService();
    private PayService   pay   = new PayService();
    private ShipService  ship  = new ShipService();
    public void placeOrder(String sku, int amt, String addr) {
        stock.lock(sku); pay.charge(amt); ship.ship(addr);   // 顺序只在这一处维护
    }
}
```
**识别关键词**：**"为子系统提供一致（统一）的界面/入口"、"简化子系统的使用"**
> 与适配器的区别：外观是**简化**（子系统本来能用，只是麻烦）；适配器是**转换**（接口本来对不上）。

#### 享元 Flyweight【下午题高频】

**痛点**：围棋一盘几百颗子，每颗建一个对象（颜色+坐标）太多。但棋子只有黑白两种"长相"，逐颗不同的只有坐标。
**思路**：黑白各建**一个共享对象**存颜色，坐标不存对象里、绘制时传入。

**意图**：运用**共享**技术有效地支持**大量细粒度的对象**。

> **内部状态 vs 外部状态（软考爱考的辨析）**：
> **内部状态** = 可共享、不随场景变（**颜色**），存在享元对象里
> **外部状态** = 随场景变、**调用时传入**（**坐标**），不存在对象里

```java
class ChessPiece {
    private final String color;                       // 内部状态：可共享
    ChessPiece(String color) { this.color = color; }
    void draw(int x, int y) {}                        // 外部状态：调用时传入
}
class PieceFactory {                                  // 享元工厂：对象池
    private static Map<String, ChessPiece> pool = new HashMap<>();
    static ChessPiece get(String color) {
        return pool.computeIfAbsent(color, ChessPiece::new);   // 有则复用，无则新建
    }
}
// 满盘几百颗棋子，实际只有 2 个 ChessPiece 对象
```
**识别关键词**：**"共享"、"大量细粒度对象"、"内部状态/外部状态"**

#### 桥接 Bridge

**意图**：将**抽象部分与它的实现部分分离**，使它们都可以**独立地变化**。
**识别关键词**：**"两个维度独立变化"、"抽象与实现分离"**
**场景**：消息有 普通/加急 两种类型 × 短信/邮件 两种渠道。继承要建 2×2 个类；桥接把两个维度拆成两条独立继承线用组合连起来，**m×n 变 m+n**。

#### 组合 Composite

**意图**：将对象组合成**树形结构**以表示"**部分-整体**"层次；使用户对**单个对象和组合对象的使用具有一致性**。
**识别关键词**：**"树形结构"、"部分-整体"、"单个与组合一致对待"**
**场景**：文件夹里可装文件、也可装文件夹，对外都支持"算大小"同一个操作。

### 考点④ 识别关键词速查表（上午题就靠这张）

| 模式 | 分类 | **题干信号（看到就选它）** |
|---|---|---|
| 工厂方法 | 创建型 | 让**子类决定实例化哪一个类**、实例化延迟到子类 |

## 第 4 层 · 速记

> 三大分类：**创建管"造"、结构管"装"、行为管"协作"**
> 创建型5：**工厂方法、抽象工厂、生成器、原型、单例**
> 结构型7：**适配器、桥接、组合、装饰器、外观、享元、代理**
> 创建型串记：**只要一个找单例，子类决定找工厂方法，一族产品找抽象工厂，克隆创建找原型，分步构建找生成器**
> 结构型串记：**不兼容找适配器，加功能找装饰器，统一入口找外观，控制访问找代理，共享省内存找享元，两维变化找桥接，树形整体找组合**
> 单例三件套：**构造私有、静态实例、全局访问点**；饿汉天生安全，**懒汉必须加锁**
> **装饰器 vs 代理：结构一样看意图——增强功能是装饰，控制访问是代理**
> 陷阱：**享元是结构型**；**简单工厂不属于 GoF 23**

## 考题回顾

> 说明：核实考点为"高频设计模式"，见于 2021上/2022下/2024上/2025上 多场次，未逐题对应年份。以下按已核实考点自编重现，**非原题原文**。

**1.【模拟·考点重现】** 欲使原本由于接口不兼容而不能一起工作的两个类可以协同工作，应采用（ ）模式。
A. 单例　B. 适配器　C. 外观　D. 桥接
**解**：**B**。"接口不兼容 → 转换接口使其协同工作"是适配器的标志性意图原句。外观是"给子系统统一入口"（简化，非转换）；桥接是"抽象与实现分离"；单例管实例个数。

**2.【模拟·考点重现】** 希望在不改变原有类代码、也不通过生成子类的情况下动态给对象增加职责，应采用（1）；若目的是控制对某对象的访问（延迟加载、权限检查），应采用（2）。
A. 装饰器/代理　B. 代理/装饰器　C. 适配器/外观　D. 装饰器/享元
**解**：**A**。两者结构几乎相同，只看意图：**增强功能→装饰器；控制访问→代理**。

**3.【模拟】** 关于单例模式的实现，**错误**的是（ ）。
A. 构造函数必须私有化，防止外部 new 出第二个实例
B. 饿汉式在类加载时创建实例，由 JVM 类加载机制保证线程安全
C. 懒汉式实现了延迟加载，无需任何同步措施天然线程安全
D. 需提供一个静态方法作为全局访问点
**解**：**C**。懒汉式多线程下两个线程可能同时通过 `instance == null` 判断各建一份，必须 synchronized（或 DCL+volatile）。

**4.【模拟】** 围棋软件中棋盘有数百颗棋子，系统仅创建黑子、白子两个对象供全盘共享，坐标在绘制时由外部传入。这采用了（1）模式，其中"颜色"属于（2）状态。
A. 原型/外部　B. 享元/内部　C. 享元/外部　D. 组合/内部
**解**：**B**。"大量细粒度对象 + 共享少量对象"= 享元；可共享、不随场景变的信息（颜色）是**内部状态**，随场景变、调用时传入的（坐标）是**外部状态**。

3. 【模拟】下列哪个模式**不属于**创建型？A. 原型　B. 生成器　C. 享元　D. 单例

### 参考答案

1. **抽象工厂**。核心区别：工厂方法的一个工厂只造**一种**产品（造什么由子类决定）；抽象工厂的一个工厂造**一族**相关产品（同一主题的按钮+文本框+滚动条整套）。
2. **装饰器模式**——缓冲是"包"在文件流外面的一层装饰。不用继承的原因：要加的功能（缓冲、解压、加密…）可**任意组合**，继承会导致**子类组合爆炸**；且继承在编译期固定，装饰器可在**运行时动态叠加**。
3. **C**。享元属于**结构型**；创建型 5 成员是原型、生成器、单例、工厂方法、抽象工厂。
