## 开讲：报销系统上线第一天，财务和主管同时点了"审批"

还是讲义 15、30 那套内部报销系统：员工提单、主管审批、超 5000 元走二级审批、审完打款。前四课默认的场景是**你一个人对着数据库敲命令**。上线第一天这个假设就没了——财务小王在改一张单的金额，主管老李同时在给同一张单盖审批章，两个人手速差了半秒。

**最朴素的做法：什么都不管，谁的语句先到数据库就先执行谁的。** 这是每个 DBMS 出厂时的出发点，也是这一课全部名词的起点。它在四个地方不够用，后面每一节补一条：

- ① 两个人同时改同一行，两边的代码都没有 bug，结果却错了；
- ② 有人读到了别人还没定下来的中间值，对方转头一撤销，读到的那个值从来没真正存在过；
- ③ 同一个人前后读了两次同一份数据，中间被别人改掉，自己算的账对不上；
- ④ 就算上面三种毛病一次都不犯，也**不等于**这一批操作的最终结果，跟"一个一个排队做"是一样的。

补 ① 靠 **X 锁与一级封锁协议**，补 ② 靠 **S 锁与二级封锁协议**，补 ③ 靠**三级封锁协议**，补 ④ 靠**可串行性与两段锁协议**。加锁本身还会带来一种新麻烦（活锁与死锁），单开一节。

### 一、先把"一件事"框起来：事务与 ACID

要谈"两个人同时操作"，得先说清"一次操作"到底指多大一块。审批一张报销单在库里至少是两条语句：把单据状态改成"已通过"，再把这笔钱记进本月应付表。只做完第一条就断电，单子显示通过、钱却没记账。

**事务（Transaction）**就是把这样一组语句打包成一个不可分割的执行单位——培训资料的原话是"由一系列操作组成，这些操作，要么全做，要么全不做"。写法上以 `BEGIN TRANSACTION` 开头，以 `COMMIT`（提交，全部生效）或 `ROLLBACK`（回滚，全部撤销）结尾。至于**并发控制**，培训资料给的定义只有一句——"控制不同的事务并发执行"，为的是"提高系统效率"：让小王和老李的操作真的同时跑（而不是排队一个做完再做下一个），同时又不许跑出错。**事务是并发控制的前提条件**：不先划出这个单位，"两个人同时干"里的"一件事"就没有边界。

事务对外给出四条承诺，取四个英文首字母合称 **ACID**。培训资料在每条前面加了一个提示词，正好点出它管的是哪个侧面，照录并各配一个报销场景：

| 承诺 | 培训资料原文 | 它防的是什么事 | 报销系统里 |
|---|---|---|---|
| **（操作）原子性** Atomicity | 要么全做，要么全不做 | 半截状态留在库里 | 状态改成"已通过"、应付表还没写就失败 → 整笔撤销，单子退回"待审批" |
| **（数据）一致性** Consistency | 事务发生后数据是一致的，例如银行转账，不会存在 A 账户转出，但是 B 账户没收到的情况 | 做完之后账目本身讲不通 | 报销单里"已审批金额合计"必须等于应付表里这张单的金额，做完一笔审批两边还得对得上 |
| **（执行）隔离性** Isolation | 任一事务的更新操作直到其成功提交的整个过程对其他事务都是不可见的，不同事务之间是隔离的，互不干涉 | 别人看见你干到一半的样子 | 老李盖章盖到一半，小王查这张单只能看到"待审批"，看不到"半通过" |
| **（改变）持续性** Durability | 事务操作的结果是持续性的 | 说成功了又丢了 | 页面提示"审批成功"之后机房断电，重启这张单仍然是已通过 |

两点要交代清楚。其一，**D 这条承诺有两种叫法：培训资料正文写"持续性"，而它自己配的那道真题（下面练习 2）选项里印的是"持久性"，指的是同一条**，选项里看到哪个都别犹豫。其二，**D 靠什么兑现（日志、转储、断电后怎么把没落盘的补回来）不在本课**，那是讲义 35 的内容；本课只负责"承诺是什么"，以及承诺被并发破坏的那一半。

**A 和 C 是本课最容易混的一对**，因为它们的例子长得几乎一样。分界线只有一句：**A 说的是机制，C 说的是结果。** "失败了就把已经做的那部分撤销掉"——这是在描述数据库的动作，属 **A**；"审批前后，报销单合计与应付表合计始终相等"——这是在描述一条业务约束在事务前后都成立，属 **C**。做题的抓手：题干里出现"撤销、回滚、要么全做要么全不做"选 A；出现"总额不变、约束仍然满足、数据仍然是对的"选 C。

至于 I，就是下面整节的正题：并发到底怎么把它破坏掉。

### 二、不管的话会出三种事（补 ①②③ 的病因）

培训资料把这三件事直接列成"并发控制中存在下面三个问题"。下面三张时间线取自它的原始配图 `images/fig_d04_s033.png`。

**（1）丢失更新。** 表里字段 A 的当前值是 10。T1 想减 5，T2 想减 8，两人几乎同时动手：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=10 | |
| ② | | 读 A=10 |
| ③ | A=A−5 写回 | |
| ④ | | A=A−8 写回 |

**先别往下看：跑完这四步，库里的 A 是多少？两笔都算上本该是多少？丢的是谁那一笔？**

多数人第一反应会去凑一个"减了 5 又减了 8"的数。实际结果是 **A=2**。原因在第 ② 步：T2 读到的是 10，不是 T1 改过之后的 5——它手里那份 10 一直算到第 ④ 步，写回 10−8=2，把 T1 写下的 5 整个盖掉了。两笔都生效应当是 10−5−8=**−3**，差的正好是 T1 那 5。培训资料的定性照录：**"此时事务 2 写回的数据会覆盖事务 1 写回的数据，就丢失了事务 1 对 A 的更新。即对数据的更新会被覆盖。"**

这就是短板 ①。注意 T1 和 T2 的代码各自都没有一行是错的，错在"读"和"写"之间被别人插了队。

**（2）读脏数据。** "脏"指的是**还没被提交、随后又被撤销掉的值**——它在库里出现过一瞬间，但从结果看它从来不该存在。A 初值 20：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=20，A←A+50，写回 70 | |
| ② | | 读 A=70 |
| ③ | ROLLBACK，A 恢复为 20 | |

T2 在第 ② 步读到 70，可第 ③ 步 T1 一回滚，A 又变回 20。T2 手里那个 70 是一个从没算数过的值，它后面所有基于 70 的计算全部作废。培训资料原文：**"那么事务 2 对数据 A 做的事是无效的，读到了脏数据。"** 这是短板 ②。

**（3）不可重复读。** 同一个事务前后读两次同一份数据，中间被别人改了。A=20、B=30：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 读 A=20，读 B=30，求和=50 | |
| ② | | 读 A=20，A←A+50，写 A=70 |
| ③ | 读 A=70，读 B=30，求和=100（验算不对） | |

T1 从头到尾一个字节都没写，它只是想把刚才那笔和验算一遍，两次却得出 50 和 100。这是短板 ③。

**三者的分界线只有两个问题，按顺序问就不会错**：第一问，**有几个事务在写同一份数据**？两个都写，且**后写的那个是拿"还没算上前一个修改"的旧值去算的** → 丢失更新，判完收工。（这个附加条件不能省：若后写的那个是等前一个写完之后才读的，两笔就都算上了，虽然两个事务都写了，也不叫丢失更新——第四节一级封锁协议那张表正是这种情形。）只有一个在写、另一个在读，才问第二问：**读方读到的那个值，写方最后认不认账**？写方回滚了（读的是未提交值）→ 读脏数据；写方提交了、而读方前后读了两次值不一样 → 不可重复读。

> 培训资料的文字描述里，"不可重复读"那一条写的是"事务 2 读 A，而后事务 1 对数据 A 进行了修改并写回"，与配图 `fig_d04_s033` 中间那张表的 T1/T2 角色正好对调（图上是 T1 读两次、T2 改）。**现象是同一个，谁叫 T1 谁叫 T2 不影响判断**，对着资料看的时候别被绕住——判类型只看"谁在写、提没提交"，不看事务编号。

### 三、两把锁：S 锁与 X 锁（补 ① 的第一步）

三个问题的病因是同一个：**读和写在时间上交叉了**。既然交叉是病因，最直接的药就是**不许交叉**——谁要动这份数据，先申请一个"使用权"，别人拿不到就得等。这个使用权就叫**封锁（Locking）**，简称加锁。

数据库只准备了两种锁，规则照录培训资料原文：

- **X 锁是排它锁（写锁）**。"若事务 T 对数据对象 A 加上 X 锁，则只允许 T 读取和修改 A，**其他事务都不能再对 A 加任何类型的锁**，直到 T 释放 A 上的锁。"
- **S 锁是共享锁（读锁）**。"若事务 T 对数据对象 A 加上 S 锁，则只允许 T 读取，但不能修改，**其他事务只能再对 A 加 S 锁（也即能读不能修改）**，直到 T 释放 A 上的 S 锁。"

考试真正要用的是一张 2×2 的**相容表**——"相容"就是"两把锁能同时挂在同一份数据上"。**先别往下看：四个格子里，有几个是相容的？** 这张表不用背，从上面两条原文两步就推出来：X 那条说"其他事务不能再加任何类型的锁"，于是**凡是 X 出现的格子一律不相容**，一下划掉三个；S 那条说"其他事务只能再加 S 锁"，剩下的那个格子相容。答案是**只有一个格子相容**：

| T2 请求 ＼ T1 已持有 | S 锁 | X 锁 |
|---|---|---|
| **请求 S 锁** | 相容，可以同时读 | 不相容，等 |
| **请求 X 锁** | 不相容，等 | 不相容，等 |

一句话口径：**只有"读+读"能共存，沾上写就得等。**

### 四、光有锁不够，还得规定什么时候放：三级封锁协议（补 ①②③）

锁只是工具，真正决定治得了哪种病的是**规矩**：读要不要加锁、锁在哪一步加、加完什么时候放。培训资料"共分为三级封锁协议"，三级的差别就在这两个旋钮上。下面三张时间线同样取自培训资料的原始配图。

**一级封锁协议**，原文：**"事务在修改数据 R 之前必须先对其加 X 锁，直到事务结束才释放。可解决丢失更新问题。"** 拿第二节丢失更新那组数字（A=10、T1 减 5、T2 减 8）重跑一遍，就是扫描图 `fig_d04_s034.png`：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 加写锁 | |
| ② | | 对 A 加写锁 → 拿不到 |
| ③ | 读 A=10 | 等待 |
| ④ | A=A−5 写回 | 等待 |
| ⑤ | 释放对 A 的写锁 | 等待 |
| ⑥ | | 读 A=**5** |
| ⑦ | | A=A−8 写回 |
| ⑧ | | 释放对 A 的写锁 |

关键在第 ⑥ 步：T2 是等 T1 完全结束之后才开始读的，读到的是 T1 写下的新值 5，最后写回 5−8=**−3**——正是两笔都生效应有的结果。**要点：X 锁保护的不是"写"这一个动作，而是"读—改—写"整段**；把读也圈进锁里，才不会出现"拿着过期的值去算"。

但一级封锁协议**对纯粹的读不加任何锁**。所以只想读一下的 T2，照样能在 T1 改到一半时读进那个中间值——**它防不住读脏数据**，短板 ② 还在。

**二级封锁协议**，原文：**"一级封锁协议的基础上加上事务 T 在读数据 R 之前必须先对其加 S 锁，读完后即可释放 S 锁。可解决丢失更新、读脏数据问题。"** 拿第二节读脏那组数字重跑，就是扫描图 `fig_d04_s035.png`：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 加写锁 | |
| ② | 读 A=20 | |
| ③ | A←A+50 | |
| ④ | 写回 70 | |
| ⑤ | | 对 A 加读锁 → 拿不到（X 与 S 不相容） |
| ⑥ | ROLLBACK | 等待 |
| ⑦ | A 恢复为 20 | 等待 |
| ⑧ | | 读 A=**20**，释放对 A 的读锁 |

T2 被挡在第 ⑤ 步，一直等到 T1 回滚完，读到的是回滚后的真值 20，那个昙花一现的 70 它根本没机会看见。**读之前先申请 S 锁，就意味着必须等写方把话说完**——这就是二级比一级多出来的全部本事。

代价也在这里：S 锁**读完就放**。T1 第一次读完 A 就把 S 锁交出去了，别人立刻可以拿 X 锁去改，等 T1 第二次读，值已经变了。**二级防不住不可重复读**，短板 ③ 还在。

**三级封锁协议**，原文：**"一级封锁协议加上事务 T 在读取数据 R 之前先对其加 S 锁，直到事务结束才释放。可解决丢失更新、读脏数据、数据重复读问题。"**（原文这里写的是"数据重复读"，标准术语是**不可重复读**，指的是同一件事。）拿第二节不可重复读那组数字重跑，就是扫描图 `fig_d04_s036.png`：

| 步 | 事务 T1 | 事务 T2 |
|---|---|---|
| ① | 对 A 与 B 加 S 锁（读锁），读 A=20，读 B=30，求和=50 | |
| ② | | 对 A 加 X 锁（写锁）→ 由于 A 已加了读锁，所以等待 |
| ③ | 读 A=20，读 B=30，求和=**50**，释放对 A 和 B 的读锁 | 等待 |
| ④ | | 读 A=20，A←A+50，写 A=70，释放对 A 的写锁 |

T1 两次求和都是 50，验算对得上。差别只有六个字：S 锁从"读完即放"改成"**事务结束才放**"，T2 在 T1 整个事务期间都拿不到 X 锁。

三级的关系是**层层累加**，级别越高管得越严、并发度越低：

| 协议 | 写之前 | 读之前 | 累计解决 |
|---|---|---|---|
| **一级** | 加 X 锁，事务结束才放 | 不加锁 | 丢失更新 |
| **二级** | 同上 | 加 S 锁，**读完即放** | ＋读脏数据 |
| **三级** | 同上 | 加 S 锁，**事务结束才放** | ＋不可重复读 |

### 五、加了锁，冒出两种新麻烦：活锁与死锁

> 本节与第六节（活锁、死锁、可串行性、两段锁协议）**15 份转录本均未覆盖，按《软件设计师教程》（第 5 版）补**。

锁把"抢同一份数据"变成了"排队等同一份数据"，队排不好就出两种事。

**活锁**：T1 正锁着数据 R，T2 来申请，只能等；这期间 T3 也来申请；T1 一放锁，系统批准了后到的 T3，T2 接着等；T4 又来……**T2 一直没轮上，可它并没有被卡死，只是永远排在后面**。解法很土也很有效：**先来先服务**——按请求到达的先后排一个队列，谁先来谁先拿。

**死锁**：T1 锁住了 A，接着要 B；T2 锁住了 B，接着要 A。**两边都在等对方手里的东西，谁也不肯先放**，就这么僵住。处理分两路：**预防**（一次封锁法：把要用的数据一次全锁上，缺一个就一个都不锁；顺序封锁法：所有事务按同一个约定顺序申请锁，比如永远先 A 后 B）；**诊断与解除**（超时法：等超过时限就判定死锁；等待图法：画一张"谁在等谁"的有向图，图里出现环就是死锁——然后挑一个代价最小的事务回滚掉，把锁让出来）。

**活锁与死锁的分界线**：死锁是**互相等**，等待图上成环，不动手就永远解不开；活锁是**单向等**，没有环，理论上随时可能轮到它，只是运气一直不好。

操作系统里进程抢打印机、抢缓冲区遇到的是同一类问题，那边的工具是**信号量与 P/V 操作**（讲义 36），死锁的定义、资源分配图与判定在讲义 37；数据库这一侧换成了锁和事务，思路完全一样，本课只讲数据库这一边。

### 六、真正的验收标准：可串行性与两段锁协议（补 ④）

到这里三种病都治了，但短板 ④ 还没动：**"三种病都不犯"和"结果是对的"不是一回事。** 怎么才算对？只有一把尺子。

先说清**调度**这个词：它指的就是几个事务的那些读写操作实际交错成的那张执行次序表——第二节那三张 T1/T2 时间线，每一张就是一个调度。**并发调度的可串行性**：多个事务的并发执行是正确的，**当且仅当其结果与按某一次序串行执行这些事务的结果相同**。满足这个条件的并发调度，叫**可串行化的调度**。"串行执行"就是一个事务从头做到尾再做下一个，那样绝不会出错，只是慢；并发的目标是**跑得像并发一样快、错得像串行一样少**。回头看第二节那张丢失更新的表：串行做（不论谁先）都是 −3，交错做出来是 2，两个串行次序都对不上，所以那个调度不可串行化——它错了。

尺子有了，还得有一条**照着做就一定合格**的操作规程，这就是**两段锁协议（Two-Phase Locking，2PL）**：每个事务的加锁和放锁分成截然分开的两段——

- **扩展阶段（增长阶段）**：只能申请锁，**一把也不许放**；
- **收缩阶段**：只能释放锁，**一把也不许再申请**。

一句话记法：**一旦开始放锁，就再也不许加锁。**

它给出的保证是一条定理：**若所有事务都遵守两段锁协议，则对这些事务的任何并发调度策略都是可串行化的。** 但方向只有一个——

**这是充分条件，不是必要条件。** 遵守 2PL ⇒ 一定可串行化；可串行化的调度**不一定**遵守 2PL。举个反例就明白：T1 先写 A，放掉 A 的锁，T2 接着读 A、写 A，之后 T1 才去锁 B、写 B。T1 放锁之后又加锁，明摆着违反 2PL；可这个调度里两个事务只在 A 上有冲突，冲突方向只有 T1→T2 一条，等价于"先 T1 后 T2"串行执行，**结果完全正确**。所以"可串行化的调度一定遵守两段锁协议"是反着说的，是本考点最常见的错项。

**先别往下看：如果 T1 和 T2 都一丝不苟地遵守两段锁协议，还会不会死锁？**

会。**两段锁协议不能防止死锁。** 反例就是上一节那个：T1 锁 A 再申请 B，T2 锁 B 再申请 A——两边都在扩展阶段，一把锁都没放过，**完全遵守协议**，却互相等成了环。**2PL 管的是"结果对不对"，不管"会不会卡住"**，这是两个不同的问题，混起来就丢分。

最后把两节接上：**三级封锁协议要求所有的锁（X 锁和 S 锁）都持有到事务结束才释放，放锁全部挤在最后一刻，加锁段和放锁段天然分得干干净净——它是两段锁协议的一个特例**，所以三级封锁协议保证可串行化。（别把它说成"最严格的两段锁"：上一节那个一次封锁法要求开工前把所有要用的数据一次锁齐，在加锁这一头比三级更严，还顺带把死锁也防住了。）二级不行——它的 S 锁读完就放，放完之后事务还会去申请别的锁，放锁跑到了加锁前面，形式上就不是两段的；一级也不行——它只对写加锁、对读完全不加锁，读到的值不在任何锁的保护之下，两段锁那条定理的前提（每一次访问都受锁保护）根本不成立。

**收口**：四条短板对四个补丁。**两人对改互相覆盖 → X 锁 + 一级；读到别人的半成品 → S 锁 + 二级；两次读不一样 → 三级把 S 锁持到底；整体结果对不对 → 可串行性，照着两段锁协议做就一定合格。** 锁本身带来的活锁与死锁不在这条链上，是加锁这个手段的副作用，认得即可。

## 考试怎么考

**考点① 给一段时序，判是哪一类并发问题。** 拿到表先数"有几个事务在写同一个数据"，两个都写、且后写的那个在前写之前就把值读走了，直接选丢失更新；只有一个写就去找 `ROLLBACK` 和 `COMMIT`：看见回滚往读脏上想，看见提交且读方读了两次往不可重复读上想。三个错项的造法固定：把丢失更新说成脏读（其实两边都在写）、把已提交的修改说成脏读（脏的定义要求"未提交且随后撤销"）、把只读一次的场景说成不可重复读（不重复读两次就谈不上"不可重复"）。

**考点② 锁相容判定。** 题干给若干事务分别持有 S 锁/X 锁，问某个事务还能不能加锁。做法机械：把每份数据当前被谁锁着、锁的是哪种，列成一行，再逐个选项拿"只有 S+S 相容"去核。两个必踩的坑：**别人持 S 锁时，你还能加 S 锁**（"任何锁都加不上"是错的）；**"先加 S 锁再升级成 X 锁"绕不过相容表**，升 X 一样要求没有别人持锁，别人的 S 锁还在就升不上去。

**考点③ 封锁协议的级别归属。** 题干只会改一句话，盯住两处：读加不加锁（不加＝一级），以及 S 锁读完就放（二级）还是持到事务结束（三级）。问"**至少**要哪一级"就答能覆盖该问题的最低那级：丢失更新→一级、读脏→二级、不可重复读→三级。最高频的错项是"一级封锁协议可以防止读脏数据"——一级对读不加锁，防不住。

**考点④ 两段锁协议挑错。** 四个选项里三个抄定义、一个反着写，错项只有两种造法：**把充分条件说成必要条件**（"可串行化的调度一定遵守两段锁协议"），**把可串行化说成不死锁**（"遵守两段锁协议的事务不会发生死锁"）。另一种低级造法是把两段的顺序说反（"先集中放锁再集中加锁"）。

**考点⑤ ACID 对号入座。** 给一句场景描述选特性。抓手：出现"撤销、回滚、要么全做要么全不做"选原子性；出现"总额不变、约束仍成立"选一致性；出现"别的事务看不见、互不干扰"选隔离性；出现"提交之后断电也不丢"选持久性（＝持续性）。A 与 C 的分界线是**机制 vs 结果**，题干描述动作选 A、描述约束选 C。

### 参考答案

1. **D**。把当前锁状态列出来：D1 被 T1 加了 S 锁，D2 被 T2 加了 X 锁，D3 被 T3 加了 X 锁。逐项核：A 要 T1 对 D2、D3 加 X 锁成功，但那两份数据上都挂着别人的 X 锁，X 与任何锁都不相容，失败；B 前半句对（加 X 锁确实都失败），后半句要 T2、T3 对 D1 加 X 锁成功，D1 上有 S 锁，S 与 X 不相容，失败；C 要 T1 对 D2、D3 加 S 锁成功，同样被别人的 X 锁挡住，失败。只剩 D：前半句"加共享锁都失败"成立，后半句"对 D1 加共享锁成功"也成立，因为四格里唯一相容的就是 S+S。
2. **C**。"对其他事务都是不可见的"——关键词是"其他事务"，管的是并发时互不干扰，正是隔离性。原子性管的是自己有没有留下半截，持久性管的是提交之后丢不丢，一致性管的是做完之后账对不对，都不涉及"别人看不看得见"。
3. **D、C**。第一空：D2、D3 上分别有 T2、T3 的 X 锁，T1 无论申请 X 还是 S 都不相容，全部失败 → D。第二空：D1 上是 T1 的 S 锁，T2 申请 S 锁与之相容，成功；D3 上是 T3 的 X 锁，T2 申请 X 锁不相容，失败 → C。两空都只用同一张相容表。
4. **B、A、A**。沿时间线走：T1 和 T2 都在第一步读到 100；T1 写回 100−30=70；T2 手里还是那份 100，写回 100−50=**50**，把 70 盖掉了。两笔都生效应为 100−30−50=20，实际 50，丢的正是 T1 那 30 → 两个事务都写同一数据、后写覆盖先写，是**丢失更新**。一级封锁协议就够：要改数据先拿 X 锁并持到事务结束，T2 的"读—改—写"整段被推到 T1 之后，读到的是 70，写回 20，覆盖不再发生。
5. **C、B**。T1 没写任何东西，只是前后读了两次，中间被已提交的 T2 改掉，值本身完全合法，只是"变了"——是不可重复读，不是脏读（脏读要求对方未提交且随后回滚）。第二空：能挡住它的唯一办法是让 T1 的 S 锁一直持到事务结束（三级封锁协议），二级恰恰是"读完即放"，两次读之间没有任何锁保护。A 不对，T1 只读不写，本来就不该加 X 锁；C 说反了，T2 提交了才叫不可重复读；D 不对，题干没有给出 T1 的加锁放锁次序，判不了它守没守 2PL。
6. **C**。A 是 2PL 的定义，对；B 是 2PL 那条定理，对；D 是"充分不必要"的另一半，对。C 错：T1 锁 A 再申请 B、T2 锁 B 再申请 A，两个事务都还在扩展阶段、一把锁没放过，完全遵守协议，却互相等成环。**2PL 保证结果可串行化，不保证不卡住。**
7. **B**。查相容表：S 与 S 相容，T2 可以再加一把 S 锁一起读。A 不行，X 与 S 不相容。C 是最诱人的错项——"升级为 X 锁"同样要通过相容表这一关，T1 的 S 锁还挂着就升不上去，仍要等。D 与 S+S 相容矛盾。
8. ①**原子性**（失败后把已做的部分撤销，是"要么全做要么全不做"的机制）；②**一致性**（描述的是一条业务约束在事务前后都成立，是结果不是机制）；③**隔离性**（"别人看到的"）；④**持久性/持续性**（"提交之后断电也不丢"）。①②这一对就是 A 与 C 最常互换的地方，判据是机制 vs 结果。
9. 因为二级封锁协议的 S 锁**读完就释放**。T1 第一次读完立刻放锁，T2 马上就能拿到 X 锁把数据改掉并提交，等 T1 第二次读，值已经变了——**两次读之间那段时间是没有锁保护的**。三级把 S 锁持到事务结束，这段空档才被堵上。
10. **没有违反**。两个事务都只在"申请"，一把锁都还没释放，全都处在扩展阶段，严格遵守两段锁协议。结果是**死锁**：T1 等 T2 手里的 B，T2 等 T1 手里的 A，等待图上出现环，不外力介入永远解不开（实际系统靠超时法或等待图检测，挑一个事务回滚掉）。这说明**两段锁协议保证的是调度可串行化，它对死锁无能为力**——可串行化和无死锁是两个独立的问题。

## 速记

- **ACID**：原子＝要么全做要么全不做（管半截）；一致＝做完账仍对得上（管结果）；隔离＝提交前对别人不可见、互不干涉（管别人）；持久（＝持续）＝提交后断电也不丢。**A 说机制、C 说结果**
- **三类并发问题**：**两个都写、后写拿旧值盖掉先写＝丢失更新；读了未提交且随后被回滚的值＝读脏；同一事务两次读不一样＝不可重复读**
- **相容表只有一个 ✓**：S+S 相容，**别人一沾 X 就得等**
- **三级封锁协议**：一级写前加 X 持到底、读不加锁 → 防丢失更新；二级读前加 S、**读完即放** → ＋防脏读；三级读前加 S、**持到事务结束** → ＋防不可重复读。口诀**一丢二脏三重复**
- **可串行化**：并发结果与某一串行次序的结果相同才算对
- **两段锁 2PL**：扩展阶段只加、收缩阶段只放，**一旦放锁不再加锁**；守 2PL ⇒ 可串行化（**充分不必要**），但**防不了死锁**。三级封锁协议的锁全持到事务结束，是 2PL 的一个特例，故保证可串行化；一二级不是
- **活锁**＝单向久等、先来先服务可解；**死锁**＝互相等、等待图成环，靠一次封锁法/顺序封锁法预防，靠超时法/等待图法检测后回滚一个事务解除
